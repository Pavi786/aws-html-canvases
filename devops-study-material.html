name: CI/CD Pipeline on: push: { branches: [main] } pull_request: { branches: [main] } env: REGISTRY: ghcr.io IMAGE_NAME: ${{ github.repository }} jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Run tests run: | pip install -r requirements.txt pytest tests/ -v security-scan: needs: test runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Trivy scan uses: aquasecurity/trivy-action@master with: image-ref: ${{ env.IMAGE_NAME }} severity: CRITICAL,HIGH exit-code: '1' build-push: needs: security-scan runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Build & push image run: | docker build -t $REGISTRY/$IMAGE_NAME:${{ github.sha }} . docker push $REGISTRY/$IMAGE_NAME:${{ github.sha }} deploy: needs: build-push if: github.ref == 'refs/heads/main' steps: - name: Deploy canary (10%) run: kubectl set image deploy/app app=$IMAGE:${{ github.sha }}
🚀
Deployment Strategies
RollingReplace pods gradually. Default in K8s. Zero downtime if configured right.
Blue/GreenTwo identical envs. Switch traffic instantly. Easy rollback.
CanarySend 5-10% traffic to new version. Monitor errors. Graduate or rollback.
GitOpsGit is source of truth. ArgoCD syncs cluster state to git state continuously.

Prometheus — PromQL Essentials
PROMQL
# HTTP error rate (5xx) rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) # 99th percentile latency histogram_quantile(0.99, sum(rate(http_duration_seconds_bucket[5m])) by (le, service) ) # CPU usage per pod sum(rate(container_cpu_usage_seconds_total{ container!=""}[5m])) by (pod) # Memory usage % container_memory_working_set_bytes{container!=""} / container_spec_memory_limit_bytes * 100 # Alert rule: high error rate # - alert: HighErrorRate # expr: error_rate > 0.05 # for: 5m # labels: { severity: critical }
🔭
OpenTelemetry — The 3 Pillars
Metrics — numeric measurements over time (Prometheus format). CPU, memory, request counts, latency.
Traces — request journey across services. Each span = one operation. Parent-child relationship shows flow.
Logs — structured events. Use trace_id in logs to correlate with traces (game changer for debugging).
Collector — OTEL Collector receives, processes, exports to any backend (Jaeger, Prometheus, Loki, Datadog).
Auto-instrument — for Python/Java/Go, one import instruments HTTP, DB, gRPC calls automatically. No code changes.
💡
Correlation is the skill: When a trace shows a slow span, click to the logs with the same trace_id, then check the metric spike at the same timestamp. That's senior-level debugging.

System Design
SENIOR LEVEL
"Design Zomato / Swiggy backend infra"
⚡
Caching — Redis
Cache-aside — app reads cache first, on miss reads DB + populates cache
Write-through — write to cache + DB simultaneously. Always consistent.
TTL — always set expiry. Stale cache is worse than no cache.
Eviction — LRU policy: evict least recently used when memory full
📨
Queues — Kafka vs RabbitMQ
KafkaHigh throughput, log-based, replay events, microservices events, streaming
RabbitMQTask queues, complex routing (topics, fanout), acknowledgements, RPC
TopicKafka: logical stream category. Partitioned for parallelism.
Consumer GroupMultiple consumers reading the same topic at different offsets

Practice: Design Zomato Infra
DESIGN CHALLENGE
Design infra for a food delivery app: 10L daily orders, real-time tracking, restaurant catalog, payment processing. What does your K8s + AWS architecture look like?
Show approach ▾ API Gateway → ALB → Microservices (order-svc, restaurant-svc, tracking-svc, payment-svc). Order events via Kafka. Restaurant data cached in Redis. Tracking uses WebSocket + Redis pub/sub. Payments in separate VPC.
SCALING CHALLENGE
Your API handles 500 req/sec normally. During a sale event it spikes to 50,000 req/sec in 30 seconds. How do you handle it?
Show approach ▾ Pre-scale with scheduled HPA. Rate limit at API Gateway. Cache heavy reads. Queue writes (Kafka). DB read replicas. CDN for static assets. Circuit breakers for downstream services.
