💡 EXAM TIPS & WINNING STRATEGIES
Test Strategy

Day-Of Exam Tactics

🎯 Read Questions Carefully (CRITICAL)
Most mistakes = misreading the question. Look for:
• "Which BEST..."
• "What is the MOST cost-effective..."
• "Which approach allows the LOWEST latency..."
Read the whole question + all options before answering.
⏰ Time Management
• 2 min per question = 130 min total
• Skip hard questions, come back later
• Budget 10 min for final review
• Mark questions for review (most exams allow this)
🧠 Elimination Strategy
If unsure: Eliminate obviously wrong answers first. Often 2 answers are clearly bad. Choose best of remaining 2.
🚩 Keyword Watch (Red Flags)
• "Cheapest" = Spot instances, S3 Standard
• "Fastest" = RDS Aurora, ElastiCache
• "Most reliable" = Multi-AZ, Multi-region
• "Lowest latency" = Local/same-region
• "Compliant" = Encryption, IAM, CloudTrail
Common Tricks

Exam Traps & How to Avoid Them

❌ Trap 1: Multi-AZ ≠ Multi-Region
Multi-AZ = High availability (same region, different AZ)
Multi-Region = Disaster recovery (different regions)
Question: "What provides disaster recovery?" → Answer: Multi-Region
❌ Trap 2: RDS Read Replica Wrong
Read replicas can be in DIFFERENT regions (async)
Multi-AZ is ONLY same region (sync)
Question: "Replicate data to another region?" → Answer: Read Replica
❌ Trap 3: CloudFront vs S3
• S3 = object storage
• CloudFront = CDN (caching)
Question: "Serve content faster worldwide?" → Answer: CloudFront
❌ Trap 4: Cheapest = Spot (Usually)
But Spot can be interrupted. If need reliability → Reserved/On-Demand
❌ Trap 5: IAM Role vs User
• User = Person (access key, password)
• Role = Service (assume, temporary credentials)
Question: "EC2 needs S3 access?" → Answer: IAM Role

Core Service

EC2 Instance Types & Selection

💡 Simple Explanation
Different EC2 types for different jobs. t3 = burstable (occasional peaks), m5 = general purpose, c5 = compute-heavy, r5 = memory-heavy, i3 = high I/O.
🔴 Instance Family Quick Reference
t3/t3a (Burstable): Low cost, variable performance. Good for dev/test, low traffic. Earn/burn CPU credits.
m5/m6i (General): Balanced CPU/RAM. Good for web servers, small databases. Most common.
c5/c6i (Compute): High CPU, low RAM. Good for batch jobs, analytics.
r5/r6i (Memory): High RAM, low CPU. Good for databases, caches, in-memory databases.
i3/i3en (Storage): High I/O. Good for NoSQL (DynamoDB), data warehouses.
g4/p3 (GPU): GPU accelerated. Good for ML training, rendering.

Core Concept

Auto Scaling Groups (ASG)

💡 Simple Explanation
Automatically add/remove servers based on demand. Set min/desired/max capacity. CloudWatch triggers scaling policies.
🔴 ASG Core Concepts
Launch Template: Blueprint (AMI, instance type, security group, key pair)
Min/Desired/Max: Min=2, Desired=3, Max=10
Scaling Policy: How to scale (target tracking, step, simple)
Health Check: ELB or EC2 status
Cooldown Period: Wait before next scale action (avoids rapid scaling)
// ASG Scaling Policy Examples // 1. Target Tracking (RECOMMENDED - simplest) TargetValue: 70% CPU → Scale up if CPU > 70% → Scale down if CPU < 70% // 2. Step Scaling (Advanced) If CPU 70-80% → Add 2 instances If CPU 80-90% → Add 5 instances If CPU > 90% → Add 10 instances // 3. Simple Scaling (OLD - don't use) If CPU > 80% → Add 2 instances (wait 300s) If CPU < 20% → Remove 1 instance (wait 600s)
