MODULE 01 • CONTROL PLANE

Control Plane Components: The Brain of Kubernetes

Deep dive into API Server, etcd, Scheduler, and Controller Manager

API Server (kube-apiserver)

The front-end of the Kubernetes control plane. Exposes the Kubernetes API and handles all REST requests.

Key Functions:

  • • Authentication & Authorization
  • • Validation & Admission Control
  • • etcd interaction only through API

etcd: Distributed Key-Value Store

Stores all cluster data: configuration, state, and metadata. The single source of truth.

Critical Aspects:

  • • Consistent and highly-available
  • • Watch API for real-time updates
  • • Backup essential for DR

Scheduler (kube-scheduler)

Watches for newly created Pods and assigns them to nodes based on resource availability and constraints.

Scheduling Algorithm:

  • • Filtering (node suitability)
  • • Scoring (ranking nodes)
  • • Binding (assigning pod)

Controller Manager

Runs controller processes that regulate the state of the cluster, ensuring desired state matches actual state.

Key Controllers:

  • • Node Controller
  • • Replication Controller
  • • Endpoints Controller

Failure Impact: If the API Server fails, no cluster operations can occur. If etcd fails, cluster state is lost. Always run multiple control plane nodes for HA.

  • • CNI plugin errors
  • • Disk pressure
  • • Memory pressure

Maintains network rules on nodes, enabling communication to Pods from inside or outside the cluster.

MODULE 01 • ETCD

etcd: The Distributed Brain

Understanding etcd's role, backup strategies, and troubleshooting

What etcd Stores

etcd is the consistent and highly-available key-value store used as Kubernetes' backing store for all cluster data.

Cluster State

Nodes, namespaces

Workloads

Pods, deployments

Config

ConfigMaps, Secrets

Network

Services, endpoints

etcd Architecture

Raft Consensus

Leader election, log replication

Quorum (n/2+1)

Minimum nodes for consistency

Watch API

Real-time change notifications

Backup & Recovery

Backup Command

ETCDCTL_API=3 etcdctl snapshot save \
  backup.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/etcd/ca.crt \
  --cert=/etc/etcd/etcd.crt \
  --key=/etc/etcd/etcd.key

Restore Command

ETCDCTL_API=3 etcdctl snapshot restore \
  backup.db \
  --data-dir=/var/lib/etcd-new

Common etcd Issues

No Quorum

Cluster becomes read-only

Disk Latency

High fsync = leader election

DB Size

Defragment regularly

Critical: Always run etcd on dedicated nodes with SSD storage. Network latency between members must be < 10ms.

MODULE 02 • DEPLOYMENTS

Deployment Strategies: Beyond Rolling Updates

Rolling updates, Recreate, Blue-Green, and Canary deployments

Rolling Update (Default)

Gradually replaces old pods with new ones. Zero downtime deployment strategy.

Key Parameters:

  • • maxSurge: Pods above desired count (default 25%)
  • • maxUnavailable: Pods below desired count (default 25%)
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0

Recreate Strategy

Terminates all existing pods before creating new ones. Causes downtime.

Use Cases:

  • • Incompatible DB schema changes
  • • Development environments
  • • When downtime is acceptable
strategy:
  type: Recreate

Blue-Green Deployment

Two identical environments. Switch traffic instantly by updating service selector.

Implementation:

  1. 1. Deploy "green" version alongside "blue"
  2. 2. Test green deployment
  3. 3. Update service selector to green
  4. 4. Keep blue for instant rollback

Canary Deployment

Gradually shift traffic to new version. Minimizes risk by testing with small user subset.

Tools:

  • • Flagger: Automated canary with metrics
  • • Istio: Traffic splitting by percentage
  • • NGINX Ingress: Canary annotations

Rollback: Use kubectl rollout undo deployment/<name> to revert to previous revision. View history with kubectl rollout history.

MODULE 02 • SERVICES

Services: ClusterIP, NodePort, LoadBalancer, ExternalName

When to use each service type and troubleshooting service issues

ClusterIP (Default)

Exposes service on a cluster-internal IP. Only reachable from within the cluster. 

spec:
  type: ClusterIP
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 8080

DNS: my-service.my-namespace.svc.cluster.local

NodePort

Exposes service on each node's IP at a static port. Accessible from outside cluster. 

spec:
  type: NodePort
  ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080

Range: 30000-32767 (default)

LoadBalancer

Exposes service externally using cloud provider's load balancer. Auto-creates NodePort + ClusterIP. 

spec:
  type: LoadBalancer
  ports:
  - port: 80
  sessionAffinity: ClientIP

Annotations: Cloud-specific configs for LB behavior

ExternalName

Maps service to external DNS name. No proxying, just CNAME record. 

spec:
  type: ExternalName
  externalName: \
    api.external-service.com

Use: External DBs, third-party APIs

Endpoints: Service creates EndpointSlice objects tracking pod IPs. Check with kubectl get endpoints

Headless: Set clusterIP: None for direct pod-to-pod communication (StatefulSets)

MODULE 02 • INGRESS

Ingress Controllers: Traffic Management at Scale

NGINX vs Traefik vs HAProxy - path routing, TLS, and troubleshooting

Popular Ingress Controllers

NGINX Ingress Most Popular

Mature, feature-rich, community NGINX. Two flavors: Kubernetes community vs NGINX Inc.

Traefik Cloud-Native

Auto-discovery, dynamic config, native Let's Encrypt support. Great for microservices.

HAProxy High Performance

Known for performance and reliability. Good for high-throughput scenarios.

Ingress Resource Example

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rate-limit: "100"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        backend:
          service:
            name: api-service
            port: 80

Ingress Features

Path-Based Routing

/api → backend, /web → frontend

Host-Based Routing

api.example.com, web.example.com

TLS Termination

HTTPS at ingress, HTTP inside

Rate Limiting

Prevent DDoS and abuse

Rewrite/Redirect

URL manipulation rules

MODULE 02 • STATEFULSETS

StatefulSets: Managing Stateful Applications

Pod identity, stable network IDs, and volume claim templates

StatefulSet Characteristics

Unlike Deployments, StatefulSets maintain sticky identity for each pod. Critical for stateful apps.

Stable Network ID

Pod name: <name>-<ordinal> (web-0, web-1)

DNS: web-0.nginx.default.svc.cluster.local

Ordered Deployment

Pods created sequentially: 0, 1, 2...

Scaled in reverse order

Stable Storage

PVCs created from template, retained on deletion

StatefulSet Example

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: "nginx"
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi

Use Cases

Databases

MySQL, PostgreSQL

Message Queues

Kafka, RabbitMQ

Search

Elasticsearch

Distributed

ZooKeeper, etcd

Headless Service: StatefulSets require a headless service (clusterIP: None) for stable network identities. Each pod gets its own DNS entry.

MODULE 02 • DAEMONSETS

DaemonSets: Running Pods on Every Node

Use cases, node selectors, and update strategies

What is a DaemonSet?

Ensures that a copy of a pod runs on all (or some) nodes in the cluster. When nodes are added, pods are added. When nodes are removed, pods are garbage collected.

Key Characteristics:

  • • One pod per node (by default)
  • • Pods are not scheduled by default scheduler
  • • Pod name includes node name
  • • Supports rolling updates

Common Use Cases

Log Collection

Fluent Bit, Fluentd, Filebeat - collect logs from each node

Monitoring Agents

Prometheus Node Exporter, Datadog Agent, New Relic

Network Proxies

CNI plugins, service mesh sidecar injectors

DaemonSet Example

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluent-bit
spec:
  selector:
    matchLabels:
      name: fluent-bit
  template:
    metadata:
      labels:
        name: fluent-bit
    spec:
      tolerations:
      - key: node-role.kubernetes.io/master
        effect: NoSchedule
      containers:
      - name: fluent-bit
        image: fluent/fluent-bit
        volumeMounts:
        - name: varlog
          mountPath: /var/log
      volumes:
      - name: varlog
        hostPath:
          path: /var/log

Node Selection

Run on Specific Nodes

nodeSelector:
  disktype: ssd

Tolerations for Taints

tolerations:
- key: "dedicated"
  operator: "Equal"
  value: "monitoring"
  effect: "NoSchedule"

Update Strategy: Use RollingUpdate (default) for zero-downtime updates. Set maxUnavailable to control update speed. Use OnDelete for manual control.

MODULE 02 • BATCH WORKLOADS

Jobs and CronJobs: Batch Workload Management

Parallelism, completions, cron scheduling, and failure handling

Jobs

Creates one or more pods and ensures a specified number complete successfully. Perfect for batch processing. 

apiVersion: batch/v1
kind: Job
metadata:
  name: pi
spec:
  completions: 5
  parallelism: 2
  template:
    spec:
      containers:
      - name: pi
        image: perl
        command: ["perl"]
        args: ["-Mbignum=bpi", "-wle", "print bpi(2000)"]
      restartPolicy: Never
  backoffLimit: 4

completions

Total pods to complete

parallelism

Pods at same time

Job Patterns

One Shot

Single pod runs to completion

Parallel with Work Queue

Multiple pods process queue

Indexed Job

Each pod gets unique index

CronJobs

Creates Jobs on a repeating schedule. Similar to Linux cron but runs within the cluster. 

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: backup-tool
          restartPolicy: OnFailure

Cron Schedule Format

# ┌───────────── minute (0 - 59)

# │ ┌───────────── hour (0 - 23)

# │ │ ┌───────────── day of month (1 - 31)

# │ │ │ ┌───────────── month (1 - 12)

# │ │ │ │ ┌───────────── day of week (0 - 6)

0 2 * * * # Daily at 2 AM

Concurrency Policies: Allow (default), Forbid (skip if running), Replace (cancel running)

MODULE 03 • ISSUE #2

Issue: CrashLoopBackOff - The Dreaded Loop

Common causes, log analysis, and debugging techniques

Common Causes

Application Crashes

Unhandled exceptions, nil pointer dereference

Misconfigurations

Wrong env vars, missing config files

Missing Dependencies

Resource Limits

Crash Backoff Pattern

Kubernetes uses exponential backoff between restart attempts:

Crash 1 Immediate restart
Crash 2 10 second delay
Crash 3 20 second delay
Crash N Max 5 minutes

Debugging Steps

1. Check Current Logs

kubectl logs <pod-name> --previous

  --image=busybox --target=<container>

4. Check Resource Usage

kubectl top pod <pod-name>

Pro Tips

Add readiness probes to prevent premature traffic

Use init containers for dependency checks

Set appropriate resource requests/limits

MODULE 03 • ISSUE #4

Issue: OOMKilled - Memory Management Problems

Memory limits vs requests, identifying leaks, and HPA strategies

Understanding OOMKilled

When a container exceeds its memory limit, the Linux OOM killer terminates it. Kubernetes shows this as OOMKilled.

Exit Code 137

128 + 9 (SIGKILL) = Container was forcefully killed

Memory Limit vs Request

Limit = hard ceiling (triggers OOM). Request = scheduling guarantee.

Diagnostic Commands

kubectl describe pod <pod> | grep -A 5 "State"
kubectl top pod <pod> --containers
kubectl logs <pod> --previous

Solutions

1. Increase Memory Limit

resources:
  limits:
    memory: "2Gi"  # Increase
  requests:
    memory: "1Gi"

2. Set Appropriate Requests

resources:
  requests:
    memory: "512Mi"  # Base usage
  limits:
    memory: "1Gi"    # Burst allowance

3. Enable HPA

kubectl autoscale deployment <name> \
  --cpu-percent=70 --min=2 --max=10

Memory Leak Detection

1. Monitor memory growth over time

2. Use profiling tools (pprof, JProfiler)

3. Check for unclosed connections

4. Review cache implementations

Best Practice: Always set memory requests close to actual usage. Limits should provide headroom for bursts, not be 10x requests (encourages overcommit).

MODULE 03 • ISSUE #7

Issue: Pod Eviction Due to Resource Pressure

Eviction signals, QoS classes, and prevention strategies

Eviction Signals

Kubelet monitors node resources and evicts pods when thresholds are exceeded.

memory.available

< 100Mi

Available memory drops below threshold

nodefs.available

< 10%

Root filesystem available space

imagefs.available

< 15%

Container runtime filesystem

pid.available

< 1000

Available PIDs on node

Eviction Order

1 BestEffort pods (no requests/limits)
2 Burstable pods (requests < limits)
3 Guaranteed pods (requests = limits)

QoS Classes Explained

Guaranteed (Highest)

resources:
  requests:
    memory: "1Gi"
    cpu: "1"
  limits:
    memory: "1Gi"  # Must equal request
    cpu: "1"       # Must equal request

Burstable (Middle)

resources:
  requests:
    memory: "512Mi"
    cpu: "500m"
  limits:
    memory: "1Gi"  # Greater than request
    cpu: "1"

BestEffort (Lowest)

# No resources specified
# First to be evicted

Prevention Strategies

Set resource quotas per namespace

Use LimitRanges for defaults

Enable cluster autoscaling

Set pod priority classes

MODULE 05 • POD SECURITY

Pod Security Standards and Admission

Implementing PSA: restricted, baseline, and privileged policies

Pod Security Standards (PSS)

Three policy levels that enforce security best practices for pods.

Privileged

Unrestricted

No restrictions, full access. Use sparingly.

Baseline

Minimal

Prevents known privilege escalations. Allows defaults.

Restricted

Maximum

Best practices enforced. Non-root, no escalation.

Pod Security Admission (PSA)

Built-in admission controller (replaces PSP in 1.25+).

enforce: Reject violating pods

audit: Log violations

warn: Warn users (dry-run)

Namespace Configuration

apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted

Restricted Policy Requirements

Run as non-root (runAsUser > 0)

No privilege escalation

Read-only root filesystem

Drop all capabilities

No hostPath, hostNetwork, hostPID

Compliant Pod Example

spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]

MODULE 07 • AUTOSCALING

Autoscaling: HPA, VPA, and Cluster Autoscaler

Horizontal, vertical, and cluster scaling strategies

HPA

Scales pod replicas based on CPU, memory, or custom metrics. 

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

Custom Metrics: Requests/sec, queue depth

VPA

Adjusts CPU/memory requests/limits based on actual usage. 

apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: my-app
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  updatePolicy:
    updateMode: "Auto"

Modes: Off, Initial, Recreate, Auto

Cluster Autoscaler

Adds/removes nodes based on pending pods.

How It Works

1. Detects unschedulable pods

2. Calculates node group needed

3. Provisions new nodes

4. Scales down underutilized nodes

Karpenter (AWS)

Faster provisioning, right-sizing, consolidation

Best Practice: Use HPA for variable load, VPA for right-sizing (not together on same workload), Cluster Autoscaler for node scaling.
