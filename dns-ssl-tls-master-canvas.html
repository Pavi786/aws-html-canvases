What is DNS?
DNS
Imagine the internet is a giant city. Every house (website) has a number address — like 93.184.216.34. But who can remember that? So there's a giant phone book called DNS that says: "Google.com? That lives at 142.250.80.46". When you type google.com, your computer secretly looks it up in this phone book before connecting. That phone book is DNS — the Domain Name System.
DNS is a globally distributed, hierarchical naming system that translates human-readable domain names into IP addresses. It operates as a UDP/TCP service on port 53. The system is hierarchical: root servers → TLD servers → authoritative nameservers. Without DNS, every application would need to hardcode IPs, making the internet unmanageable. Modern DevOps relies heavily on DNS for service discovery, load balancing, geo-routing, and health checks.
DNS is a distributed, fault-tolerant database with ~1,500+ root servers globally (anycast) and billions of queries per second. It supports DNSSEC (signed zones), split-horizon DNS (different answers for internal vs external clients), DNS-over-HTTPS (DoH), and DNS-over-TLS (DoT) for privacy. In cloud architectures, Route53 supports weighted routing, latency-based routing, failover, and geolocation policies — all implemented via DNS. DNS cache poisoning (BGP hijacking) remains a critical attack surface; DNSSEC and RPZ (Response Policy Zones) are mitigations.
Real World Analogy
When you type whatsapp.com, your browser doesn't know the IP. It asks DNS. DNS says "157.240.16.60". Your browser then connects to that IP. Without DNS, you'd have to type 157.240.16.60 every time you want to open WhatsApp.

How DNS Works — Step by Step
DNS

When you type www.example.com in your browser, here's exactly what happens under the hood — a journey that takes milliseconds but involves 5 different servers.

You type: www.example.com │ ▼ ┌─────────────────┐ Checks local cache first │ Your Browser │ ──► (already resolved? done in 0ms) └────────┬────────┘ │ Cache miss → ask OS ▼ ┌─────────────────┐ Checks /etc/hosts + local DNS cache │ OS Resolver │ ──► Linux: /etc/resolv.conf → 8.8.8.8 └────────┬────────┘ │ ▼ ┌─────────────────────────────┐ │ Recursive Resolver │ (ISP / 8.8.8.8 / 1.1.1.1) │ "I'll find the answer │ │ for you" │ └────────┬────────────────────┘ │ "Who handles .com?" ▼ ┌─────────────────────────────┐ │ Root Name Server │ 13 sets (a.root-servers.net etc) │ "I don't know example.com │ Anycast — hundreds of nodes │ but .com is handled by │ worldwide │ Verisign → a.gtld-servers"│ └────────┬────────────────────┘ │ "Who handles example.com?" ▼ ┌─────────────────────────────┐ │ TLD Name Server (.com) │ Managed by registries │ "example.com NS records │ (Verisign for .com) │ point to ns1.example.com" │ └────────┬────────────────────┘ │ "What is www.example.com IP?" ▼ ┌─────────────────────────────┐ │ Authoritative Name Server │ Your DNS (Route53 / Cloudflare) │ "www.example.com → │ This is where YOU configure │ 93.184.216.34" │ your DNS records └────────┬────────────────────┘ │ ▼ ┌─────────────────┐ │ Recursive │ Caches response (TTL: 300s) │ Resolver │ Returns IP to browser └────────┬────────┘ │ ▼ Browser connects to 93.184.216.34 on port 80/443
  1. 1
    Browser Cache Check
    Browser checks its own DNS cache. Chrome: visit chrome://net-internals/#dns. If found and TTL not expired → done instantly.
  2. 2
    OS Cache + /etc/hosts
    OS checks /etc/hosts (Linux/Mac) or C:\Windows\System32\drivers\etc\hosts. Then checks OS DNS cache. Override any DNS by adding entries here.
  3. 3
    Recursive Resolver
    Configured in /etc/resolv.conf. Your ISP's resolver, or public ones (8.8.8.8 Google, 1.1.1.1 Cloudflare). Does the hard work of finding the answer.
  4. 4
    Root Servers → TLD → Authoritative
    Full recursive lookup happens. Root servers point to TLD, TLD points to your authoritative NS, which has the actual A/AAAA record.
  5. 5
    Response Cached & Returned
    Answer cached at resolver for TTL duration. Browser connects to IP. Subsequent lookups within TTL are instant.

Cloudflare DNS Patterns

Proxy Mode (Orange Cloud)
Traffic goes through Cloudflare CDN/WAF. Real server IP hidden. DDoS protection. IP shown is Cloudflare's. Use for public HTTP/S.
DNS-Only (Grey Cloud)
Direct DNS resolution — returns your real IP. No Cloudflare proxy. Use for non-HTTP services (MX, FTP, SSH, game servers).
Cloudflare Tunnels
No inbound ports needed. Cloudflared daemon creates outbound tunnel. Zero-trust access. Best for internal services exposed publicly.

TTL, Propagation & Caching
DNS

TTL (Time To Live) is the number of seconds a resolver is allowed to cache a DNS answer before re-querying. Getting TTL wrong is one of the most common DevOps migration mistakes.

ScenarioRecommended TTLReason
Stable production record3600–86400s (1–24h)Fewer queries, better performance
Planned migration in 24h60sSet low 24h before cutover
Active cutover/failover30–60sFast TTL means fast failover
Health-check based routing10–30sRoute53 health checks need low TTL
After migration completeIncrease back to 3600+Reduce resolver load
⚠
DNS Propagation Myth: "Propagation takes 24–48 hours" is outdated. Modern DNS with low TTL propagates in minutes. The delay is just old caches respecting high TTL. Always set TTL to 60s 24 hours before any migration!

What is SSL/TLS — HTTP vs HTTPS
SSL/TLS
Imagine sending a letter. HTTP is like sending it on a postcard — everyone who handles it (mailman, post office) can read everything. HTTPS is like putting that letter in a locked box — only the receiver has the key. The lock is called TLS. When you see 🔒 in your browser, it means your data is in a locked box and nobody can read it on the way.
SSL (Secure Sockets Layer) is deprecated — don't use SSL 3.0 or TLS 1.0/1.1. TLS (Transport Layer Security) is the current standard. TLS 1.2 is still widely used; TLS 1.3 is the modern standard (faster handshake, better cipher suites). HTTPS = HTTP running over TLS. It provides: Confidentiality (encryption), Integrity (tampering detection via MAC), Authentication (certificate verifies server identity).
TLS 1.3 reduced handshake from 2-RTT to 1-RTT (and supports 0-RTT resumption for returning clients). Cipher suite negotiation in TLS 1.3 is simplified — only 5 suites, no RC4/DES/3DES. Forward Secrecy is mandatory (ECDHE key exchange means session keys aren't derivable even if server private key is compromised later). In production, enforce TLS 1.2+ with ssl_protocols TLSv1.2 TLSv1.3;, disable weak ciphers, and enable HSTS. OCSP stapling reduces latency by bundling cert revocation status in the TLS handshake.
🔓 HTTP (Port 80)
All data in plain text. Anyone on the network can read passwords, cookies, messages. No server identity verification. Never use for any sensitive data. Attackers can inject content (malvertising).
🔒 HTTPS (Port 443)
Encrypted with TLS. Server identity verified by certificate. Data integrity guaranteed. Mandatory in 2024 for any production workload. Google penalizes non-HTTPS in rankings.

TLS Handshake — Step by Step
SSL/TLS

The TLS handshake establishes an encrypted channel before any HTTP data is exchanged. Here's exactly what happens every time you open a banking website:

CLIENT (Browser) SERVER (Nginx/Apache) 1. ClientHello ──────────────────────────────────────────► • TLS version: 1.3 • Supported cipher suites (list) • Client random (32 bytes) • Supported extensions (SNI, ALPN) • SNI: "api.example.com" ← tells server which cert to use! 2. ServerHello ◄──── • Chosen cipher suite • Server random (32 bytes) • Session ID 3. Certificate ◄──────── • Server's TLS certificate • Full chain (intermediate + root) 4. ServerKeyExchange ◄── • ECDHE public key (for forward secrecy) 5. ServerHelloDone ◄─── 6. ClientKeyExchange ─────────────────────────────────────► • Client ECDHE public key Both sides compute: Pre-Master Secret → Master Secret → Session Keys 7. ChangeCipherSpec ──────────────────────────────────────► "I'm switching to encrypted now" 8. Finished (encrypted) ──────────────────────────────────► 9. ChangeCipherSpec ◄── 10. Finished (encrypted) ◄ ══ HANDSHAKE COMPLETE ══ All subsequent HTTP traffic is encrypted ══ TLS 1.3 improvement: This whole dance takes only 1 RTT (vs 2 RTT in TLS 1.2) 0-RTT: Resuming sessions can send data immediately (but no replay protection)

Certificate Verification During Handshake

  1. 1
    Cert Chain Validation
    Browser checks: Server Cert → signed by → Intermediate CA → signed by → Root CA. Root CA must be in browser's trusted store (OS truststore).
  2. 2
    Domain Validation
    Browser checks: does the cert's CN or SAN field match the domain I'm connecting to? api.example.com must match CN=api.example.com or SAN: DNS:api.example.com.
  3. 3
    Expiry Check
    Browser checks notBefore and notAfter fields. Certificate expired → hard browser error. No workaround for users.
  4. 4
    Revocation Check (OCSP/CRL)
    Has this cert been revoked? Browser queries OCSP responder or checks CRL (Certificate Revocation List). OCSP stapling: server pre-fetches and includes revocation status.

Encryption — Symmetric vs Asymmetric
SSL/TLS
SYMMETRIC ENCRYPTION ───────────────────────────────────────────── Same key used to encrypt AND decrypt 🔑 Alice: encrypt("Hello") with key123 → "Xk9pQ..." 🔑 Bob: decrypt("Xk9pQ...") with key123 → "Hello" Problem: How do you share key123 securely? → If you email it, attacker intercepts it! Used in TLS for: bulk data encryption (AES-256-GCM) FAST — gigabits per second ───────────────────────────────────────────── ASYMMETRIC ENCRYPTION ───────────────────────────────────────────── Two keys: Public Key + Private Key (mathematically paired) Anyone can encrypt with PUBLIC key → 🔓 (share freely) Only YOU can decrypt with PRIVATE key → 🔑 (NEVER share!) Also works in reverse for SIGNING: You SIGN with private key → anyone VERIFIES with public key Example (Bank website): 1. Bank has private key (secret, on server) 2. Bank shares public key (in certificate) 3. Browser uses public key to encrypt session key 4. Bank uses private key to decrypt session key 5. Both now have session key → switch to AES (fast!) Used in TLS for: handshake key exchange + certificate signing SLOW — much more computation ───────────────────────────────────────────── TLS USES BOTH: Asymmetric to securely exchange a symmetric key Symmetric (AES) for all actual data transfer

Private Key, Public Key — The Foundation
KEYS
Think of a mailbox. The public key is like the slot on the mailbox — anyone can drop a letter in (encrypt data to you). The private key is like the key to the mailbox door — only you can open it and read letters. You give everyone the public key. You NEVER share the private key. If you lose the private key, you can't read mail. If someone steals it, they can read all your mail.
Keys are generated together as a keypair. They're mathematically linked — data encrypted with the public key can only be decrypted with the corresponding private key. Common algorithms: RSA-2048 (legacy, still common), RSA-4096 (more secure, slower), ECDSA P-256/P-384 (smaller, faster, modern). Private key = key.pem on your server. Public key is embedded in the certificate (cert.pem). Private key never leaves your server — not even the CA sees it.
RSA security relies on integer factorization hardness. EC (Elliptic Curve) relies on ECDLP — provides equivalent security with shorter keys (P-256 ≈ RSA-3072). For post-quantum readiness, NIST standardized CRYSTALS-Dilithium and CRYSTALS-Kyber in 2024. Private key should be stored: encrypted at rest (passphrase or HSM), permissions 0600, owned by service user, ideally in Vault/KMS. Key rotation should be annual minimum. If key is compromised: immediately revoke cert (CA OCSP/CRL), generate new keypair, issue new cert, redeploy — within hours, not days.
BASHGenerate keys with OpenSSL
## ── RSA Key Generation ─────────────────────────────────── # Generate 2048-bit RSA private key openssl genrsa -out private.key 2048 # Generate 4096-bit with passphrase protection openssl genrsa -aes256 -out private-encrypted.key 4096 # Extract public key from private key openssl rsa -in private.key -pubout -out public.key ## ── EC Key Generation (modern, preferred) ───────────────── # Generate EC private key (P-256 = prime256v1) openssl ecparam -name prime256v1 -genkey -noout -out ec-private.key # P-384 (stronger, FIPS compliant) openssl ecparam -name secp384r1 -genkey -noout -out ec-private.key ## ── Inspect a private key ──────────────────────────────── openssl rsa -in private.key -text -noout # Shows: modulus, public exponent, private exponent, primes ## ── File permissions (CRITICAL!) ──────────────────────── chmod 600 private.key # Only owner can read/write chown nginx:nginx private.key # Service user owns it ls -la private.key # Should show: -rw------- 1 nginx nginx private.key
⚠
NEVER commit private.key to Git. Use git-secrets, trufflehog, or GitHub secret scanning. One leaked key = full cert compromise. Add *.key and *.pem to .gitignore immediately.

CSR — Certificate Signing Request Deep Dive
CSR
A CSR is like a passport application form. When you want a passport, you fill out a form with your name, birthdate, etc., and submit it to the passport office. The CSR is that form — it contains info about your website (name, company, location) and your public key. You send it to the Certificate Authority (the "passport office"). They verify your info and issue you a certificate (your "passport").
A CSR is a PKCS#10 formatted file containing: your public key + metadata about the domain/organization. It's digitally signed with your private key (proving you own the corresponding private key). The CA signs your CSR to produce a certificate. Critical: the private key NEVER leaves your server — only the CSR (with embedded public key) is sent to the CA. Regenerating a certificate? Generate a new keypair + new CSR. Reusing old keys with new CSR is a security risk.

BASHGenerate CSR with OpenSSL
## ── Method 1: Interactive ──────────────────────────────── openssl req -new -newkey rsa:2048 -nodes \ -keyout private.key \ -out request.csr # Will prompt for CN, O, OU, L, ST, C ## ── Method 2: One-liner with all fields ───────────────── openssl req -new -newkey rsa:2048 -nodes \ -keyout private.key \ -out request.csr \ -subj "/C=US/ST=California/L=San Francisco/O=Example Corp/CN=api.example.com" ## ── Method 3: Config file (recommended for SANs) ───────── # Create csr.conf cat > csr.conf <<EOF [req] default_bits = 2048 prompt = no default_md = sha256 req_extensions = req_ext distinguished_name = dn [dn] C = US ST = California L = San Francisco O = Example Corp CN = api.example.com [req_ext] subjectAltName = @alt_names [alt_names] DNS.1 = api.example.com DNS.2 = www.api.example.com DNS.3 = *.api.example.com # wildcard IP.1 = 192.168.1.100 # IP SAN (internal) EOF openssl req -new -config csr.conf \ -keyout private.key \ -out request.csr ## ── Verify your CSR ────────────────────────────────────── openssl req -text -noout -verify -in request.csr # Check: Subject, Public Key Info, Requested Extensions (SANs)
⚠
SAN is mandatory since 2017. Browsers deprecated CN-only matching. Every cert MUST have SANs. If you generate a CSR without SAN, browsers will show NET::ERR_CERT_COMMON_NAME_INVALID — even if CN matches perfectly.

CA — Certificate Authority
CA
A CA is like the government passport office. When you get a passport, the government vouches: "This person is who they say they are." Your browser comes with a list of trusted "government offices" (DigiCert, Let's Encrypt etc). If a website has a certificate signed by one of these trusted offices, the browser trusts it. If it's signed by someone unknown (self-signed), the browser shows a scary warning — like showing a passport you made yourself at home.
A CA is an organization trusted to verify domain ownership and sign certificates. DV (Domain Validated): only verifies domain control (HTTP challenge or DNS TXT). OV (Organization Validated): verifies company identity too. EV (Extended Validation): full legal identity — shows company name in old browser address bars. Let's Encrypt provides free DV certs. AWS ACM provides free DV certs for AWS services. DigiCert, Sectigo, GlobalSign for paid OV/EV.
CA hierarchy: Root CA (offline, air-gapped) signs Intermediate CAs. Intermediate CAs sign end-entity certs. If a Root CA is compromised, every cert it's ever issued must be revoked — catastrophic. Keeping Root CA offline and using Intermediates limits blast radius. CAA DNS records let you specify which CAs can issue for your domain — prevents rogue issuance. HPKP (cert pinning) was deprecated — too risky. Certificate Transparency (CT) logs are mandatory — all CAs must submit certs to public logs, enabling detection of misissued certs.

CA Verification Methods

HTTP-01 Challenge
CA sends a token. You serve it at /.well-known/acme-challenge/TOKEN on port 80. CA fetches it. Domain control proven. ❌ No wildcards. Needs port 80 open.
DNS-01 Challenge
CA sends a token. You create _acme-challenge.yourdomain TXT token. CA queries DNS. ✅ Supports wildcards. Works for private clusters. Needs DNS API access.
OV/EV — Manual
CA sends email to domain registrant. May call company phone number. Checks legal business registration. Takes 1–7 days. ✅ Highest trust level.

Public CA vs Private CA

Public CA
Private / Internal CA
Trusted by all browsers/OSes out of the box. Required for public-facing websites. Examples: Let's Encrypt (free), DigiCert, Sectigo, AWS ACM.
You run your own CA. Must manually install root cert on all machines that need to trust it. Perfect for internal services, K8s clusters, mTLS. Tools: cfssl, step-ca, HashiCorp Vault PKI, cert-manager with self-signed.
Cannot issue wildcard DV for non-public domains. Must prove domain control to internet.
Full control. Can issue certs for internal hostnames (api.internal, 10.0.0.5). No public internet required. No domain control proof needed.
BASHCreate your own Private CA with OpenSSL
## ── Step 1: Create Root CA ──────────────────────────────── # Generate Root CA private key (keep this VERY safe) openssl genrsa -aes256 -out root-ca.key 4096 # Self-sign the Root CA certificate (10 year validity) openssl req -new -x509 -days 3650 \ -key root-ca.key \ -out root-ca.crt \ -subj "/C=US/O=My Corp/CN=My Corp Root CA" ## ── Step 2: Create Intermediate CA ────────────────────── openssl genrsa -out intermediate.key 4096 openssl req -new -key intermediate.key \ -out intermediate.csr \ -subj "/C=US/O=My Corp/CN=My Corp Intermediate CA" # Root CA signs the Intermediate CA cert (5 year) openssl x509 -req -days 1825 \ -in intermediate.csr \ -CA root-ca.crt -CAkey root-ca.key \ -CAcreateserial -out intermediate.crt \ -extensions v3_ca ## ── Step 3: Sign a server cert with Intermediate CA ───── openssl x509 -req -days 365 \ -in server.csr \ -CA intermediate.crt -CAkey intermediate.key \ -CAcreateserial -out server.crt

CRT — The Certificate File
CRT

A certificate (.crt, .pem, .cer) is the signed document that proves your identity. It contains your public key, domain info, validity period, and the CA's digital signature.

BASHInspect a certificate completely
# View full certificate details openssl x509 -in certificate.crt -text -noout # Key fields to check: # Subject: CN=api.example.com (who the cert is for) # Issuer: CN=R3, O=Let's Encrypt (who signed it) # Validity: # Not Before: Jan 1 00:00:00 2024 GMT # Not After : Apr 1 00:00:00 2024 GMT # Subject Alt Names: DNS:api.example.com, DNS:*.example.com # Public Key: RSA 2048-bit # Signature Algorithm: sha256WithRSAEncryption # Quick: just check expiry date openssl x509 -in certificate.crt -noout -dates # Check cert of a live website echo | openssl s_client -connect api.example.com:443 -servername api.example.com 2>/dev/null \ | openssl x509 -text -noout # Get cert expiry of live server echo | openssl s_client -connect api.example.com:443 2>/dev/null \ | openssl x509 -noout -dates # Verify cert matches private key (fingerprints must match!) openssl rsa -noout -modulus -in private.key | openssl md5 openssl x509 -noout -modulus -in certificate.crt | openssl md5 # Both must produce identical MD5 hash

Chain of Trust — Root → Intermediate → Server
CRT

TROUBLESHOOT

Error: NET::ERR_CERT_COMMON_NAME_INVALID

Cause
SAN (Subject Alternative Names) missing or doesn't match the domain. Since 2017, browsers ignore CN and only check SAN. You might have a cert for example.com but accessing api.example.com.
BASHDebug + Fix
# Check what SANs are in the cert openssl x509 -in cert.pem -text -noout | grep -A5 "Subject Alternative" # OR for live site: echo | openssl s_client -connect api.example.com:443 2>/dev/null | \ openssl x509 -text -noout | grep -A5 "Subject Alternative" # FIX: Regenerate CSR with SANs in config file (see Section 11) # Then reissue cert with CA

Error: Certificate Has Expired

Cause
notAfter date has passed. Even by 1 second = hard failure for all clients. No browser bypass exists for this. Automated renewal with cert-manager or certbot prevents this.
BASHDebug + Fix
# Check expiry echo | openssl s_client -connect api.example.com:443 2>/dev/null | \ openssl x509 -noout -dates # EMERGENCY: certbot renew now certbot renew --force-renewal nginx -s reload # K8s: force cert-manager renewal kubectl annotate certificate api-cert -n production \ cert-manager.io/issuer-kind- --overwrite # OR delete the cert object to trigger re-issuance kubectl delete certificate api-cert -n production

Error: SSL Handshake Failed

Common Causes
TLS version mismatch (client wants 1.3, server only supports 1.1), cipher suite mismatch, no SNI support, firewall blocking 443, wrong port.
BASHDebug SSL handshake
# Verbose handshake debug openssl s_client -connect api.example.com:443 -debug -tls1_2 openssl s_client -connect api.example.com:443 -debug -tls1_3 # With SNI (needed for virtual hosting) openssl s_client -connect api.example.com:443 -servername api.example.com # Check supported protocols/ciphers on server nmap --script ssl-enum-ciphers -p 443 api.example.com # Test with curl and see cert chain curl -vI https://api.example.com 2>&1 | grep -E "SSL|TLS|certificate|expire"

Error: Mixed Content

Cause
HTTPS page loading HTTP resources (images, scripts, CSS). Browser blocks HTTP resources on HTTPS pages. Common after migrating to HTTPS.
BASH + NGINXFix mixed content

BASHVerify and fix certificate chain
# Verify chain is complete openssl s_client -connect api.example.com:443 -showcerts # Should show 2 certs: server cert + intermediate # "Verify return code: 0 (ok)" = chain is valid # "Verify return code: 21 (unable to verify)" = broken chain # Verify chain locally openssl verify -CAfile intermediate.pem server.crt # Build correct fullchain.pem cat server.crt intermediate.crt > fullchain.pem # Order matters! server cert FIRST, then intermediates # Do NOT include root CA in fullchain.pem # Check what's in fullchain openssl crl2pkcs7 -nocrl -certfile fullchain.pem | \ openssl pkcs7 -print_certs -noout

Interview Questions & Answers
Q&A
What is the difference between a Certificate and a Private Key?
A private key is the secret mathematical key you generate and never share. A certificate contains your public key (paired with private key) + domain info + CA signature. The certificate is PUBLIC — shared with every browser. The private key is SECRET — never leaves your server. Together they enable TLS: cert proves who you are, private key proves you actually own that cert.
What is a CSR and why is it needed?
A CSR (Certificate Signing Request) is a formatted file containing your public key and domain metadata, signed with your private key. It's needed because: (1) you can't just say "I own example.com" — you need to submit a verifiable request, (2) the CA needs your public key to embed in the certificate, (3) your signature on the CSR proves you have the corresponding private key. The CA never sees your private key — only the public key embedded in the CSR.
Why do you need to include the intermediate certificate?
Browsers trust Root CAs that ship in the OS. CAs don't sign your cert directly with the Root (it's kept offline). An Intermediate CA (signed by Root) signs your cert. So the chain is: Your cert → Intermediate → Root. If you omit the intermediate, the browser can't complete the chain to a trusted root → SSL error. Browsers may cache intermediates, but APIs and mobile apps won't.
What is the difference between HTTP-01 and DNS-01 ACME challenges?
HTTP-01: Let's Encrypt gives a token. You serve it at /.well-known/acme-challenge/TOKEN on port 80. Simple but requires public internet access and port 80. No wildcard support. DNS-01: Let's Encrypt gives a token. You create a TXT record _acme-challenge.yourdomain. Supports wildcards (*.example.com). Works for private clusters. Needs DNS API credentials.
What happens during TLS handshake and how are session keys generated?
Both client and server exchange random numbers and a key exchange algorithm (ECDHE). Using Diffie-Hellman math, they independently compute the same pre-master secret. From this, they derive symmetric session keys (one for each direction). The private key is NOT used to encrypt session data — it's used only to authenticate (sign) during handshake. This is Forward Secrecy: even if you later steal the private key, you can't decrypt past sessions because session keys were ephemeral.
What is SNI and why is it important?
SNI (Server Name Indication) is a TLS extension where the client sends the hostname it's connecting to during the handshake — before the server presents a certificate. Without SNI, a server can only have one TLS cert per IP. With SNI, a single IP can serve hundreds of different certs for different domains (virtual hosting). NGINX uses SNI to pick which ssl_certificate to present. K8s Ingress uses SNI to route TLS traffic to the right certificate. SNI hostname is visible to network observers (not encrypted in TLS 1.2; encrypted in TLS 1.3 with ESNI).
What is Perfect Forward Secrecy and why does it matter?
PFS means each session uses a fresh, ephemeral key pair (ECDHE). Even if the server's long-term private key is compromised years later, past encrypted sessions cannot be decrypted — there's no mathematical relationship between the long-term key and session keys. Without PFS (RSA key exchange): steal private key today → decrypt all past traffic. With PFS (ECDHE): steal private key today → can only impersonate future connections, NOT decrypt past traffic. Enable with: ssl_ciphers ECDHE-RSA-AES256-GCM-SHA384.
How would you set up SSL for a private Kubernetes cluster with no public internet access?
Options: (1) Private CA: Use cert-manager with a self-signed ClusterIssuer. Install root cert on all clients. (2) DNS-01 challenge: Even without inbound access, you can use DNS-01 (Route53/Azure DNS) — cert-manager creates TXT records, Let's Encrypt validates them. No inbound port 80/443 needed. (3) Internal CA via Vault: HashiCorp Vault PKI Engine acts as intermediate CA. cert-manager uses Vault issuer. Best for large orgs with many internal services needing mTLS.
