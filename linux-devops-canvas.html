Chapter 01 · OS Fundamentals

What Is an Operating System?

Before you can master Linux, you need to understand what an OS actually does — and why Linux is the backbone of all modern infrastructure.

The Big Picture
An Operating System is software that sits between your hardware (CPU, RAM, disk) and the programs that run on it. It manages resources so multiple programs can run simultaneously without chaos.

Linux is an OS kernel — the core engine. When we say "Linux" in DevOps, we usually mean a Linux distribution (distro) like Ubuntu, CentOS, or Amazon Linux — which bundles the kernel with tools, package managers, and utilities.
Think of the OS as the manager of an office building. Programs are workers, the CPU is the staff, RAM is the desks. The OS decides who gets a desk, for how long, and ensures nobody steals someone else's stuff.
The 4 Core Jobs of an OS
🧠
Process Management
Creates, schedules, and kills processes. Ensures the CPU is shared fairly. Handles multitasking via time-slicing.
💾
Memory Management
Allocates RAM to processes, manages virtual memory, uses swap space when RAM is full, prevents one process from reading another's memory.
📁
Filesystem Management
Organizes data on disk via file systems (ext4, xfs, btrfs). Controls who can read/write/execute what via permissions.
🌐
Device Management
Talks to hardware via drivers. Manages I/O devices like NICs, disks, and GPUs through a unified API.
Why Linux in DevOps?

✅ Why Linux Wins

  • Free and open source — no licensing costs for thousands of servers
  • Highly stable — servers run for years without reboots
  • Extremely customizable — strip it down to bare essentials
  • Dominant in cloud — AWS, GCP, Azure all run Linux VMs
  • Massive ecosystem — Kubernetes, Docker, Ansible — all Linux-native
  • Excellent security model — fine-grained permissions, SELinux, AppArmor

⚠️ Challenges

  • Steep learning curve for beginners — CLI-first approach
  • No single vendor — distro differences can be confusing (Debian vs RHEL)
  • Some enterprise software still Windows-only
  • GUI tools are less polished (but you rarely use GUIs on servers)

Chapter 02 · Kernel & User Space

Kernel vs User Space

Understanding this boundary is the foundation for debugging, performance tuning, and understanding why programs crash or behave unexpectedly.

The Two Realms
Linux runs in two protected rings. Kernel space is where the kernel operates — with unrestricted hardware access. User space is where every app you run lives — isolated from the hardware.

When your app needs something from the hardware (read a file, send a network packet), it makes a system call (syscall) — a formal request to the kernel. The kernel does the work, returns the result.
Kernel space is the bank vault. User space is the customer lobby. You (user app) give instructions to the teller (syscall). The teller goes into the vault (kernel) and comes back with your money (data). You never enter the vault directly.

System Calls (Syscalls) Explained
Every meaningful action in Linux is a syscall under the hood. When you open a file in Python with open('file.txt'), Python internally calls the open() syscall. You can spy on syscalls with strace.
BASH · Common Syscall Tracing
# Watch every syscall a command makes strace ls # Watch only file-related syscalls strace -e trace=file ls # Attach to a running process (PID 1234) strace -p 1234 # Common syscalls you'll see: open() → open a file read() → read data write() → write data fork() → create a child process exec() → run a program socket() → create a network socket
init Systems — systemd
When Linux boots, the kernel starts exactly one process: PID 1. This is the init system. In modern Linux, that's systemd. It starts everything else — your network, SSH daemon, web server, database — in the right order.
systemd is the opening manager of a restaurant. They arrive first, turn on the lights, start the fryers, unlock the doors, and then call in the rest of the staff in the correct order.
BASH · systemd Init
# Check PID 1 ps -p 1 PID TTY TIME CMD 1 ? 00:00:03 systemd # See systemd boot time analysis systemd-analyze Startup finished in 1.2s (kernel) + 3.8s (userspace) = 5.0s # What started at boot and in what order systemd-analyze blame

✅ Kernel Space Benefits

  • Direct hardware access — maximum performance
  • Isolation from user app bugs — a crashed app can't corrupt the kernel
  • Central resource arbitration — fair CPU/memory allocation

⚠️ The Tradeoffs

  • Syscall overhead — every crossing has a small cost (context switch)
  • Kernel bugs are catastrophic — a kernel panic = system crash
  • Kernel modules (drivers) run in kernel space — buggy drivers = panics

Chapter 03 · Core Concepts

Processes & Threads

Everything running on your Linux server is a process. Understanding how they're born, run, and die is fundamental to production debugging.

What Is a Process?
A process is a running instance of a program. Every process gets its own: PID (unique ID), memory space, file descriptors, and CPU time. Processes are isolated from each other by design.

A thread is a lightweight unit of execution inside a process. Multiple threads share the same memory space, making communication easy — but also risky (race conditions).
A process is a factory. Threads are workers inside that factory. All workers share the factory floor (memory). If one worker knocks over the chemicals (corrupts memory), it affects everyone. But they can collaborate faster than workers in separate buildings (processes).
Process Lifecycle
fork() Parent Process ──────────► Child Process │ │ │ exec() [loads new program] │ │ │ Running State │ │ └─── wait() ◄─────── exit() [zombie until parent collects] Process States: R = Running (on CPU right now) S = Sleeping (waiting for I/O or event) D = Uninterruptible Sleep (waiting for disk I/O — cannot be killed!) Z = Zombie (finished but parent hasn't collected exit code) T = Stopped (paused with Ctrl+Z) I = Idle (kernel threads only)
Process Commands
BASH · Process Management
# List ALL processes with details ps aux USER PID %CPU %MEM VSZ RSS STAT COMMAND root 1 0.0 0.1 22440 5216 Ss /sbin/init www-data 1234 2.1 1.4 123456 56789 S nginx: worker mysql 5678 5.3 8.2 890123 330000 Sl mysqld # Process tree — see parent-child relationships pstree -p # Find process by name pgrep -l nginx 1234 nginx # Show process file descriptors (what files it has open) lsof -p 1234 # See process environment variables cat /proc/1234/environ | tr '\0' '\n' # See process memory map cat /proc/1234/maps # Kill signals — the most important ones: kill -15 1234 # SIGTERM — polite shutdown, process can clean up kill -9 1234 # SIGKILL — brutal kill, kernel does it, no cleanup kill -1 1234 # SIGHUP — reload config (many daemons respect this) kill -19 1234 # SIGSTOP — pause process kill -18 1234 # SIGCONT — resume paused process # Kill all by name killall nginx pkill -f "python app.py"
⚠️
kill -9 is a last resort! SIGKILL prevents the process from flushing buffers, closing files, or rolling back transactions. Always try SIGTERM first and wait 5–10 seconds before escalating to SIGKILL.

✅ Processes (vs threads)

  • Complete memory isolation — one crash can't corrupt another
  • Easier to kill and restart individually
  • Better for microservices architecture
  • OS-level resource accounting per process

⚠️ Threads (vs processes)

  • Shared memory = faster communication but race conditions risk
  • Lower overhead than spawning new processes
  • One thread crashing can kill the whole process
  • Harder to debug concurrency bugs

Chapter 04 · Filesystem

Linux Filesystem Hierarchy

Linux follows the Filesystem Hierarchy Standard (FHS). Every directory has a purpose. Knowing this saves hours of searching.

The Directory Map
/ ├── bin/ → Essential user binaries (ls, cp, mv, bash) — always available even if /usr unmounted ├── sbin/ → System binaries for root (iptables, fdisk, mount) ├── boot/ → Bootloader files, kernel images (vmlinuz), initrd ├── dev/ → Device files (virtual files representing hardware) │ /dev/sda = first disk | /dev/null = black hole | /dev/random = random data ├── etc/ → ⭐ System-wide config files (nginx.conf, /etc/hosts, /etc/passwd) ├── home/ → User home directories (/home/alice, /home/bob) ├── lib/ → Shared libraries (.so files) needed by bin and sbin ├── media/ → Mount points for removable media (USB drives, DVDs) ├── mnt/ → Temporary mount point for sysadmins ├── opt/ → Optional/third-party software (rarely used now, mostly legacy) ├── proc/ → ⭐ Virtual filesystem — kernel exposes process info here │ /proc/meminfo | /proc/cpuinfo | /proc/{PID}/status ├── root/ → Home directory of the root user (not /home/root!) ├── run/ → Runtime data (PIDs, sockets) — cleared on reboot ├── srv/ → Data for services served (web files, FTP data) ├── sys/ → ⭐ Virtual filesystem — hardware and driver info from kernel ├── tmp/ → Temporary files — cleared on reboot, world-writable ├── usr/ → ⭐ User programs and libraries │ ├── bin/ → Most user commands (python3, git, curl, wget) │ ├── lib/ → Libraries for /usr/bin programs │ ├── local/ → Manually compiled software goes here │ └── share/ → Architecture-independent data (man pages, icons) └── var/ → ⭐ Variable data that changes at runtime ├── log/ → System and app log files ├── cache/ → App cache data ├── lib/ → Persistent app data (DB files, package state) ├── spool/ → Print/mail queues └── tmp/ → Temp files preserved between reboots
The DevOps Critical Directories
⚙️
/etc — The Config Home
Every service stores its config here. /etc/nginx/nginx.conf, /etc/ssh/sshd_config, /etc/hosts, /etc/crontab. First place to look when something breaks.
📋
/var/log — Log Central
All system and app logs live here. /var/log/syslog, /var/log/auth.log, /var/log/nginx/access.log. Daily home for DevOps debugging.
🔬
/proc — The Live Kernel Window
Not a real disk — it's RAM. The kernel writes live data here. cat /proc/meminfo shows real-time memory. cat /proc/cpuinfo shows your CPU. cat /proc/1/status shows PID 1's state.
🔧
/sys — Hardware Interface
Kernel exposes hardware settings here. You can tune kernel parameters, view hardware state, and control devices via simple file writes.
BASH · Useful /proc Commands
# CPU info — model, cores, speed cat /proc/cpuinfo # Memory info — total, free, cached cat /proc/meminfo # All kernel boot parameters cat /proc/cmdline # System uptime in seconds cat /proc/uptime # Open file descriptors for a process ls -la /proc/1234/fd # Kernel tunable parameters (sysctl) sysctl -a | grep "net.ipv4" sysctl vm.swappiness # How aggressively to use swap

Chapter 06 · File Viewing

File Viewing & Editing

You live in log files and config files as a DevOps engineer. Learn to navigate them at speed — especially real-time log monitoring.

Viewing Commands — When to Use Which
🐱
cat — Print Whole File
Best for small files. Dumps entire content to terminal. Bad for large logs — use less instead. Also used to chain files: cat file1 file2 > combined.
📄
less — Page Through Files
Best for large files. Opens in a pager: scroll with arrows, search with /, quit with q. Doesn't load entire file into memory — perfect for huge logs.
🔝
head — First N Lines
head -n 50 file.log shows first 50 lines. Useful to check file format, headers, or recent log entries in rotated files.
🔚
tail — Last N Lines + LIVE Follow
tail -f app.log is your real-time window into a running application. The -f flag follows the file as it grows. Essential for production debugging.
Real-Time Log Monitoring
BASH · Log Monitoring Arsenal
# Follow a log in real-time tail -f /var/log/nginx/access.log # Follow AND filter for errors only tail -f /var/log/app/app.log | grep --color "ERROR\|WARN" # Follow multiple log files at once tail -f /var/log/nginx/access.log /var/log/nginx/error.log # Show last 100 lines then follow tail -n 100 -f app.log # Search inside less (once opened) less /var/log/syslog Press / then type search term → highlights matches Press n → next match Press N → previous match Press G → go to end of file Press g → go to start Press q → quit
vim — The Essential Editor
vim is the standard terminal editor on every Linux server. You might not have nano. You might not have a GUI. But vim will always be there. Learn the basics — it will save you in emergencies.
vim is like learning to drive manual — harder at first, but once you know it, you can drive any car anywhere. Every server, Docker container, emergency console will have vi or vim.

Chapter 07 · Power Tools

Search & Text Processing

grep, awk, sed — the holy trinity of Linux text processing. Master these and you can extract any insight from any log or config file in seconds.

grep — The Search King
grep (Global Regular Expression Print) searches files for lines matching a pattern. It's the most-used command in log analysis. Pair it with pipes for incredible power.
grep is the "Ctrl+F" of the terminal — but turbocharged. It can search thousands of files at once, use complex patterns, and filter the output of any command.
BASH · grep Mastery
# Basic search grep "error" app.log # Case-insensitive search grep -i "error" app.log # Show line numbers grep -n "error" app.log # Show 3 lines BEFORE and AFTER match (context) grep -B 3 -A 3 "OutOfMemoryError" app.log # Recursive search all files in directory grep -r "PORT=8080" /etc/ # Invert match — show lines WITHOUT the pattern grep -v "DEBUG" app.log # Count matching lines grep -c "ERROR" app.log # Extended regex — multiple patterns grep -E "ERROR|FATAL|CRITICAL" app.log # Pipe grep output to another grep (AND logic) grep "ERROR" app.log | grep "database" # Count errors per minute from timestamps grep "ERROR" app.log | grep "2024-01-15 10:3" | wc -l
awk — The Data Extractor
awk processes text line by line and splits each line into fields. It's perfect for extracting specific columns from structured text like logs, CSVs, or command output.
awk is like Excel for the terminal — it sees text as rows and columns. $1 is column 1, $2 is column 2, etc., separated by spaces (or any delimiter you set).
BASH · awk Essentials
# Print first column of each line ps aux | awk '{print $1}' # Print process name and memory usage ps aux | awk '{print $11, $4"%"}' # Extract usernames from /etc/passwd (: delimited) awk -F: '{print $1}' /etc/passwd # Filter lines where field 3 (UID) >= 1000 (real users) awk -F: '$3 >= 1000 {print $1, $3}' /etc/passwd # Sum a column (total memory used) ps aux | awk '{sum += $6} END {print sum/1024 "MB total RSS"}' # Extract IPs from nginx access log awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20 # ↑ This shows top 20 IPs by request count — great for finding DDoS sources
sed — The Stream Editor
BASH · sed Mastery
# Find and replace in output (doesn't change file) sed 's/old_value/new_value/g' config.yml # Find and replace IN-PLACE (modifies file!) — always backup first sed -i.bak 's/localhost/db.prod.internal/g' app.conf # -i.bak creates app.conf.bak before changing # Delete blank lines sed '/^$/d' file.txt # Delete lines matching pattern sed '/^#/d' config.conf # remove comment lines # Print only lines 10-20 sed -n '10,20p' file.txt # Change port in config sed -i 's/listen 80/listen 8080/' /etc/nginx/nginx.conf

✅ Power of Pipes

  • Chain grep | awk | sed | sort | uniq for complex analysis
  • Process millions of log lines without loading into memory
  • No need for Python scripts for simple data extraction
  • Works on any Linux system — no installs needed

⚠️ Gotchas

  • awk and sed syntax is cryptic — easy to make mistakes
  • sed -i modifies files in-place — always use -i.bak for safety
  • Regex syntax differs between tools (basic vs extended)
  • For complex processing, Python or jq might be more readable

Chapter 08 · Security

Permissions & Ownership

Linux permissions are a security fortress. Misconfigured permissions are one of the top causes of security breaches. Understand them deeply.

Reading Permission Strings
drwxr-xr-- root root 4096 nginx/ │└──owner──┘└──group──┘└──other──┘ │ └─ d = directory | - = regular file | l = symlink | c = char device | b = block device r = read (4) w = write (2) x = execute (1) - = no permission (0) Example: rwx = 4+2+1 = 7 | rw- = 4+2+0 = 6 | r-- = 4+0+0 = 4
chmod — Change Permissions
BASH · chmod Patterns
# NUMERIC MODE — most precise chmod 755 script.sh # rwxr-xr-x owner:rwx group:rx others:rx chmod 644 config.yml # rw-r--r-- owner:rw group:r others:r chmod 600 secrets.env # rw------- owner:rw group:none others:none chmod 700 private/ # rwx------ only owner can enter directory chmod 777 shared/ # ⚠️ NEVER in production — everyone can write! # SYMBOLIC MODE — readable chmod +x deploy.sh # add execute for all chmod u+x script.sh # add execute for owner only chmod g-w config.yml # remove write from group chmod o-r secrets.env # remove read from others chmod -R 755 /app/ # recursive — apply to all files in dir # COMMON PRODUCTION PATTERNS: # SSH key files MUST be 600 or SSH refuses them chmod 600 ~/.ssh/id_rsa chmod 700 ~/.ssh/ # Web server files chmod 644 /var/www/html/*.html # nginx reads, others can read chmod 755 /var/www/html/ # nginx can list directory
chown — Change Ownership
BASH · chown
# Change owner chown alice file.txt # Change owner AND group chown alice:developers project/ # Recursive — change all files in directory chown -R www-data:www-data /var/www/html/ # ↑ nginx runs as www-data, needs to own web files # Change group only chgrp developers shared-project/ # Check effective permissions (who can access what) ls -la /etc/nginx/
Permission Quick Reference
ModeOctalMeaningTypical Use
rw-------600Only owner can read/writeSSH keys, secret files, .env files
rw-r--r--644Owner writes, others readWeb files, config files, logs
rwxr-xr-x755Owner full, others read/executeScripts, directories, executables

🔥
Never chmod 777 in production! World-writable files/directories let any process or user modify them — this includes compromised processes. Use 755 for dirs and 644 for files as your safe defaults.

Chapter 09 · Access Control

User & Group Management

Production access control is a security-critical skill. Creating the right users, assigning the right groups, and applying least-privilege principles keeps servers safe.

User & Group Architecture
Every Linux user has a UID (User ID — a number). Root is UID 0. System users (nginx, mysql, www-data) have UIDs 1–999. Real humans have UIDs ≥ 1000.

Every user belongs to a primary group and can be in many supplementary groups. Groups enable shared access — all members of the "docker" group can run Docker without sudo.
Users are employees. Groups are departments. An employee can be in multiple departments. If a file is owned by the "ops" group with group-write permission, any ops department member can edit it.
User Management Commands
BASH · User Management
# Create a new user useradd -m -s /bin/bash devops # -m creates home dir, -s sets shell # Set password passwd devops # Add user to sudo group (admin privileges) usermod -aG sudo devops # Debian/Ubuntu usermod -aG wheel devops # RHEL/CentOS # -a = append (don't remove from other groups!) # -G = supplementary groups # Add to multiple groups at once usermod -aG sudo,docker,adm devops # Check user's groups groups devops devops : devops sudo docker # Detailed user info (UID, GID, groups) id devops uid=1001(devops) gid=1001(devops) groups=1001(devops),27(sudo),999(docker) # Delete user (keep their files) userdel olduser # Delete user AND their home directory userdel -r olduser # Lock a user account (no login allowed) usermod -L devops # Unlock account usermod -U devops # Switch to another user su - devops # full login shell with their environment # Run a single command as root sudo systemctl restart nginx
Key Files
BASH · User Database Files
# /etc/passwd — one line per user cat /etc/passwd root:x:0:0:root:/root:/bin/bash devops:x:1001:1001::/home/devops:/bin/bash │ │ │ │ │ └── login shell │ │ │ │ └────────────── home directory │ │ │ └───────────────────── GID (primary group) │ │ └───────────────────────── UID │ └──────────────────────────── x = password in /etc/shadow └───────────────────────────────── username # /etc/shadow — encrypted passwords (root only) sudo cat /etc/shadow # /etc/group — group definitions cat /etc/group docker:x:999:devops,alice,bob sudo:x:27:devops
⚠️
Principle of Least Privilege: Only give users the permissions they absolutely need. Don't add everyone to the sudo group. Use specific group permissions instead. Create service accounts for applications — never run services as root.

Chapter 10 · Performance

Process & CPU Monitoring

High CPU is one of the most common production incidents. Know how to spot it, trace it to the culprit process, and act decisively.

Monitoring Tools Overview
📊
top — The Classic
Built-in on every Linux. Shows live CPU/memory per process. Press 1 for per-CPU view, M to sort by memory, P to sort by CPU, k to kill a process. Limited but always available.
🎨
htop — The Modern View
Color-coded, scrollable, mouse-support, tree view. Shows CPU bars per core. Filter processes, kill with F9, nice with F7/F8. Install with: apt install htop
🔥
atop — The Deep Diver
Records historical data. Shows disk I/O, network, per-process CPU steal. Stores metrics every 10min by default — you can review what happened during an incident AFTER it occurred.
⚡
uptime — Quick Health Check
Shows load average for 1, 5, 15 minutes. A load average above your CPU core count means CPUs are overloaded. Fastest way to assess system stress.

Chapter 11 · Memory

Memory Monitoring

Out of Memory (OOM) kills are a common production incident. Learn to read memory metrics correctly and prevent surprise process deaths.

Memory Concepts First
Linux memory is more complex than it looks. Total is your physical RAM. Used includes buff/cache — but that's actually GOOD! The kernel uses spare RAM for disk caching to speed up file reads.

Available is what actually matters — it's what processes can claim right now, including memory the kernel will free from cache if needed.
Think of RAM like a warehouse. "Used" includes shelves set aside for quick-access items (cache). "Available" is the actual empty floor space you can put new stock on. The warehouse manager (kernel) will clear cached shelves if you need the space.

Swap — The Overflow Tank
Swap is disk space used as overflow when RAM is full. It's MUCH slower than RAM (disk vs memory speed). High swap usage means you need more RAM or have a memory leak.

Swappiness (0-100) controls how aggressively the kernel moves data to swap. Default is 60. For database servers, set it to 1–10 to prefer RAM.
Swap is your office's storage room. Your desk (RAM) is where you work fast. When your desk is full, you move documents to the storage room (swap). Getting things from storage is 100x slower — you want to avoid it.

Understanding I/O Wait
iowait in CPU stats (the "wa" column in top) shows percentage of time CPUs are idle waiting for disk I/O. High iowait (>20%) means your application is bottlenecked by disk speed, not CPU.
iowait is like a chef (CPU) standing idle because they're waiting for ingredients to arrive (disk data). The chef isn't lazy — they're blocked. More chefs (CPUs) won't help. You need faster ingredient delivery (faster disk or read optimization).

✅ Fixes for High I/O

  • Upgrade to NVMe SSD if still on HDD or SATA SSD
  • Add more RAM to increase OS page cache (fewer disk reads)
  • Use RAID or striping for parallel I/O
  • Move database WAL to separate faster disk
  • Add query caching or application-level cache (Redis)

⚠️ Common I/O Causes

  • Database without proper indexing (full table scans)
  • Applications logging excessively to disk
  • Antivirus scanning every file write
  • Backup jobs running during peak hours
  • Memory pressure forcing constant swap usage

Chapter 25 · Firewalls

Firewalls: ufw & iptables

A firewall is your server's front door lock. Only open the ports you need. Everything else stays closed. This is non-negotiable in production.

ufw — The Simple Firewall
ufw (Uncomplicated Firewall) is a user-friendly frontend for iptables. Use it on Ubuntu/Debian servers. Simple rules, easy to read, hard to mess up.
BASH · ufw Complete Guide
# Check status ufw status verbose # Enable (CAREFUL — make sure SSH is allowed first!) ufw allow 22/tcp # allow SSH FIRST! ufw enable # now enable # Common rules ufw allow 22/tcp # SSH ufw allow 80/tcp # HTTP ufw allow 443/tcp # HTTPS ufw allow 5432/tcp # PostgreSQL (from anywhere — BAD!) # Better — allow only from specific IP ufw allow from 10.0.0.0/8 to any port 5432 # DB only from internal network ufw allow from 192.168.1.100 to any port 22 # SSH only from admin IP # Allow by service name ufw allow 'Nginx Full' # opens both 80 and 443 # Deny (explicitly block) ufw deny 3306 # MySQL — never expose to internet! # Delete a rule ufw status numbered ufw delete 3 # delete rule #3 # Block an attacking IP ufw deny from 45.123.67.89 # Rate limiting (prevent brute force) ufw limit 22/tcp # blocks IPs that connect >6 times per 30s # Reset to defaults ufw reset
iptables — The Power Tool
BASH · iptables Basics
# View current rules iptables -L -n -v # Allow SSH iptables -A INPUT -p tcp --dport 22 -j ACCEPT # Allow HTTP/HTTPS iptables -A INPUT -p tcp --dport 80 -j ACCEPT iptables -A INPUT -p tcp --dport 443 -j ACCEPT # Allow established connections (for outbound traffic replies) iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT # Allow loopback iptables -A INPUT -i lo -j ACCEPT # Drop everything else (default deny) iptables -P INPUT DROP # Save rules (persist across reboots) iptables-save > /etc/iptables/rules.v4
🔥
Lock-out Warning! When enabling ufw or iptables, always allow SSH FIRST before setting default deny. If you block yourself out, you'll need console access (physical or cloud console) to recover. Test with: ufw allow 22 before ufw enable.

  • Pull-based model — servers don't need to know about monitoring
  • Powerful query language (PromQL) for complex aggregations

  • Not for long-term storage — data compresses but grows; use Thanos for federation
  • Setup complexity — many moving parts
