✓ VM Do's
  • Always use Availability Zones for production (spread across ≥2 zones)
  • Use Premium SSD v2 for latency-sensitive IOPS workloads
  • Enable Azure Backup with a Recovery Services Vault on day one
  • Use Managed Identities — never store credentials in VMs
  • Enable Accelerated Networking for all D/E/F series VMs (massive perf boost)
  • Patch with Azure Update Manager — schedule maintenance windows
  • Use Spot VMs for stateless, fault-tolerant batch workloads (up to 90% cheaper)
  • Use VMSS Flexible orchestration for new deployments
✗ VM Don'ts
  • Don't expose port 22/3389 to the internet — use Azure Bastion
  • Don't use Standard HDD in production — latency spikes will hurt SLAs
  • Don't skip VM extensions — use for monitoring, security agents, config mgmt
  • Don't leave VMs running 24/7 in dev/test — use auto-shutdown schedules
  • Don't ignore proximity placement groups for latency-sensitive clusters
  • Don't overlook ephemeral OS disks — faster boot, no extra storage cost
  • Don't mix generations (v3 vs v5) in the same VMSS — inconsistent performance
Pro Tip — Ephemeral OS Disks: For stateless VMSS nodes, use ephemeral OS disks (--ephemeral-os-disk true). They live in VM cache/temp storage, boot 2-3× faster, and are free. Pair with a shared image for golden AMI-style deployments.

Durable Function — Fan-out/Fan-in Pattern
// Orchestrator: parallel execution of N activities [FunctionName("ParallelPipeline")] public static async Task<string[]> RunOrchestrator( [OrchestrationTrigger] IDurableOrchestrationContext ctx) { var tasks = new List<Task<string>>(); var items = ctx.GetInput<List<string>>(); foreach (var item in items) tasks.Add(ctx.CallActivityAsync<string>( "ProcessItem", item)); // Fan-out return await Task.WhenAll(tasks); // Fan-in } [FunctionName("ProcessItem")] public static async Task<string> ProcessItem( [ActivityTrigger] string item, ILogger log) { // Idempotent processing logic here return await DoWork(item); }
host.json — Production Tuning
{ "version": "2.0", "functionTimeout": "00:10:00", "concurrency": { "dynamicConcurrencyEnabled": true, "snapshotPersistenceEnabled": true }, "extensions": { "serviceBus": { "prefetchCount": 20, "maxConcurrentCalls": 16, "autoCompleteMessages": false }, "durableTask": { "storageProvider": { "type": "mssql" // Use MSSQL for scale }, "maxConcurrentActivityFunctions": 10, "maxConcurrentOrchestratorFunctions": 5 } }, "logging": { "applicationInsights": { "samplingSettings": { "isEnabled": true, "maxTelemetryItemsPerSecond": 20 } } } }
✓ Functions Do's
  • Use Premium Plan for VNet-integrated, production APIs — eliminates cold starts
  • Design activities to be idempotent — retries are guaranteed in Durable
  • Use App Configuration + Key Vault references for settings — never hardcode
  • Instrument with Application Insights — use structured logging (ILogger)
  • Set WEBSITE_RUN_FROM_PACKAGE=1 for faster, atomic deployments
  • Use Durable Functions for workflows > 10 min — HTTP is not enough
  • Implement dead-letter queue handling for all message-triggered functions
✗ Functions Don'ts
  • Don't use Consumption Plan for latency-sensitive, customer-facing APIs
  • Don't store state in static variables — Functions can scale to many instances
  • Don't ignore function chaining anti-pattern — use Durable instead
  • Don't call functions directly from other functions via HTTP — use queues/Durable
  • Don't neglect max scale-out limits — check downstream service limits first
  • Don't let Durable orchestrators call external services directly — use activities

NSG Rule — Zero-Trust Micro-segmentation
# Allow only app-tier to data-tier on 5432 (PostgreSQL) az network nsg rule create \ --nsg-name data-tier-nsg \ --resource-group prod-rg \ --name Allow-AppTier-DB \ --priority 200 \ --source-address-prefixes 10.1.10.0/24 \ --destination-address-prefixes 10.1.20.0/24 \ --destination-port-ranges 5432 \ --access Allow \ --protocol Tcp # Deny all other inbound to data tier (explicit deny-all) az network nsg rule create \ --nsg-name data-tier-nsg \ --name DenyAllInbound \ --priority 4000 \ --access Deny \ --direction Inbound \ --source-address-prefixes '*'
✓ VNet Do's
  • Design Hub-Spoke topology — centralize firewall, DNS, gateways in Hub
  • Use Private Endpoints for all PaaS services (Storage, SQL, Cosmos, Key Vault)
  • Enable Azure DDoS Protection Standard on public VNets
  • Use Azure DNS Private Zones linked to hub for private name resolution
  • Log all NSG flow logs to a Storage Account + enable Traffic Analytics
  • Use Service Endpoints only when Private Endpoints are not viable
  • Plan CIDR blocks carefully — leave room to grow without re-IPing
✗ VNet Don'ts
  • Don't use overlapping CIDR ranges — peering and VPN will silently fail
  • Don't allow PaaS services on public endpoints in production — always use Private Endpoints
  • Don't skip UDRs (User Defined Routes) — traffic won't traverse the hub firewall
  • Don't peer spokes directly — all traffic must route through hub (NVA/Firewall)
  • Don't forget Azure Firewall DNAT rules for inbound app traffic
  • Don't neglect subnet delegation for App Service, Functions, and AKS

Secure SAS Token (scoped, expiring)
# User delegation SAS — uses AAD, not account key # Get delegation key first (max 7 days) az storage blob generate-sas \ --account-name prodstorageacc \ --container-name uploads \ --name report-2025.pdf \ --permissions r \ --expiry 2025-12-31T00:00:00Z \ --auth-mode login \ --as-user \ --https-only # Enable soft delete + versioning (protect from accidents) az storage account blob-service-properties update \ --account-name prodstorageacc \ --enable-delete-retention true \ --delete-retention-days 30 \ --enable-versioning true \ --enable-change-feed true
✓ Blob Storage Do's
  • Enable Soft Delete + Versioning + Change Feed for all production accounts
  • Use User Delegation SAS instead of account-key SAS — revocable via AAD
  • Use GRS or RA-GZRS for disaster recovery — know your RTO/RPO
  • Enable Lifecycle Policies to automatically tier data down — huge cost savings
  • Use Hierarchical Namespace (ADLS Gen2) for big data / analytics workloads
  • Set immutability policies for compliance data (WORM)
  • Use Azure CDN / Front Door to serve static assets globally with cache
✗ Blob Storage Don'ts
  • Don't use account keys in application code — use Managed Identity + RBAC
  • Don't enable public container access — use SAS or Private Endpoints
  • Don't store sensitive data in Hot tier without lifecycle rules — costs balloon
  • Don't ignore storage firewall rules — restrict to known VNet subnets/IPs
  • Don't use LRS in production if data loss is unacceptable — at minimum ZRS
  • Don't mix Block/Page/Append blobs in the same container — plan access patterns first

Blue-Green Deployment with Slots
# Deploy to staging slot (zero downtime) az webapp deployment source config-zip \ --resource-group prod-rg \ --name myapp \ --slot staging \ --src app.zip # Warm up staging — run smoke tests here curl -f https://myapp-staging.azurewebsites.net/health # Atomic swap: staging → production az webapp deployment slot swap \ --resource-group prod-rg \ --name myapp \ --slot staging \ --target-slot production # Instant rollback if needed az webapp deployment slot swap \ --slot production \ --target-slot staging
App Service Environment (ASEv3) — Key Settings
# Slot settings — NEVER swapped (env-specific) az webapp config appsettings set \ --name myapp \ --resource-group prod-rg \ --slot-settings \ DATABASE_URL=@Microsoft.KeyVault(SecretUri=...) \ APPLICATIONINSIGHTS_CONNECTION_STRING=... \ ENVIRONMENT=production # Enable VNet integration (P-series+) az webapp vnet-integration add \ --name myapp \ --resource-group prod-rg \ --vnet spoke-vnet-prod \ --subnet app-service-subnet # Force all outbound through VNet (route table required) az webapp config appsettings set \ --settings WEBSITE_VNET_ROUTE_ALL=1
✓ App Service Do's
  • Use Deployment Slots for every production deployment — zero-downtime swaps
  • Mark connection strings and secrets as Slot Settings so they don't swap
  • Enable Always On (Standard+) — prevents cold start on long-idle apps
  • Use Health check path to automatically remove unhealthy instances
  • Use Key Vault references in app settings — never store secrets in portal
  • Configure Auto-scale rules on multiple metrics (CPU + HTTP queue)
  • Enable App Service Authentication (EasyAuth) for B2C/AAD protected APIs
✗ App Service Don'ts
  • Don't use Free/Shared plans for anything beyond experimenting — no SLA
  • Don't deploy directly to production slot — always use staging → swap
  • Don't share App Service Plans across wildly different apps — noisy neighbor effect
  • Don't skip HTTPS-only enforcement and TLS 1.2 minimum in config
  • Don't disable Application Insights — you're flying blind in production
  • Don't use SCM (Kudu) in production — disable remote debugging

Azure Cosmos DB
Partition Keys · Consistency Levels · RU Modeling · Multi-Region
The Cardinal Rule of Cosmos DB: Everything — performance, cost, scalability, and hotspot avoidance — flows from your Partition Key choice. Get this wrong and no amount of RU provisioning will save you. Choose a key with high cardinality and even distribution.
Consistency LevelStalenessPerf ImpactUse Case
StrongNone (linearizable)Highest latencyFinancial transactions, inventory
Bounded StalenessK ops or T secondsHighLeaderboards, IoT aggregation
Session ★Monotonic per sessionMediumUser profiles, shopping carts (default)
Consistent PrefixOrdered, not latestLowSocial feeds, event logs
EventualPossible divergenceLowestCounters, non-critical analytics
Optimal Partition Key Design Pattern
// ❌ BAD: Low cardinality, hot partition { "id": "order-123", "partitionKey": "orders" // ALL data on one partition! } // ❌ BAD: Too many small partitions { "partitionKey": "2025-01-15T14:32:00Z" } // ✅ GOOD: Synthetic partition key // High cardinality + even distribution { "id": "order-123", "partitionKey": "user:u-4829", // tenantId:userId "userId": "u-4829", "tenantId": "acme-corp", "status": "pending", "_ts": 1736025600 } // Hierarchical partition key (up to 3 levels) // /tenantId → /userId → /orderId // Enables efficient cross-partition queries within tenant
RU Estimation & Autopilot Configuration
# RU Cheat Sheet: # 1 RU = 1KB point read # 5 RU = 1KB write # 2.5 RU = 1KB upsert # Queries: base 2.3 RU + per-doc scanned # Enable Autoscale (recommended for variable workloads) # Scales 10%→100% of max RU, pay for max reached/hr az cosmosdb sql container create \ --account-name prod-cosmos \ --database-name AppDB \ --name Orders \ --partition-key-path "/partitionKey" \ --max-throughput 4000 # Multi-region write (Multi-master) az cosmosdb update \ --name prod-cosmos \ --enable-multiple-write-locations true \ --locations eastus=0 westeurope=1 southeastasia=2
✓ Cosmos DB Do's
  • Model data as single-document aggregates — denormalize to avoid cross-partition reads
  • Use Autoscale throughput for unpredictable traffic patterns (10%→100% RU/s)
  • Use Integrated Cache for repeated reads — 0 RU cost, sub-ms latency
  • Enable Analytical Store for reporting/analytics — no RU cost for OLAP queries
  • Use Change Feed to drive downstream event processing and materialized views
  • Set a TTL on transient documents — automatic cleanup, free operation
  • Use Transactional batch for multi-document ACID operations within a partition
✗ Cosmos DB Don'ts
  • Don't use cross-partition queries for hot paths — they fan out to every partition
  • Don't use SELECT * — project only fields needed; unused fields still cost RUs
  • Don't ignore the RU charge header (x-ms-request-charge) — log it every request
  • Don't enable Strong consistency globally — Session is almost always sufficient
  • Don't store binary large objects in documents — use Blob Storage with a reference URI
  • Don't design unbounded arrays in documents — they grow forever and explode document size

Bicep — Modular IaC Pattern
// main.bicep — orchestrates modules targetScope = 'subscription' param env string param location string = 'eastus' resource rg 'Microsoft.Resources/resourceGroups@2023-07-01' = { name: '${env}-rg' location: location } module network './modules/networking.bicep' = { name: 'networkDeploy' scope: rg params: { env: env, location: location } } module app './modules/app-service.bicep' = { name: 'appDeploy' scope: rg dependsOn: [network] params: { env: env subnetId: network.outputs.appSubnetId kvUri: keyvault.outputs.kvUri } } // Use What-If before every deployment // az deployment group what-if ...
🔍 Observability Stack
  • Application Insights — distributed tracing, dependency maps, live metrics
  • Log Analytics Workspace — centralized KQL-queryable log sink
  • Azure Monitor Alerts — metric + log-based alerting with Action Groups
  • Azure Monitor Workbooks — custom dashboards without Grafana license
  • OpenTelemetry SDK — vendor-neutral instrumentation that exports to App Insights
🔐 Secrets Management
  • All secrets in Azure Key Vault — apps reference via Managed Identity
  • Rotate secrets on a schedule using KV automatic rotation
  • Never store secrets in source code, environment files, or pipeline variables in plain text
  • Use OIDC / Workload Identity Federation for CI/CD — no service principal secrets needed
  • Audit KV access with Diagnostic Logs to Log Analytics
🛡️ Security Posture
  • Enable Microsoft Defender for Cloud — free tier for basic posture assessment
  • Apply Azure Policy to enforce guardrails (e.g., require Private Endpoints)
  • Use PIM (Privileged Identity Management) for JIT admin access
  • Run Microsoft Defender for Containers on every AKS cluster
  • Enable Entra ID Conditional Access — require MFA + compliant device
⚠ GitOps Warning: When using GitOps (Flux/ArgoCD) with Azure, ensure your repo is the single source of truth. Never make out-of-band changes in the portal — they will be reconciled away. Use What-If and Deployment Stacks (GA in Bicep) to prevent drift in non-GitOps environments.

✓ Cost Do's
  • Tag everything: CostCenter, Env, Team, Project from day one
  • Set up Budgets + Anomaly Alerts at subscription AND resource group level
  • Use Dev/Test subscription pricing for non-prod environments
  • Right-size VMs monthly using Azure Advisor recommendations
  • Auto-shutdown dev VMs at 7pm with Azure DevTest Labs schedules
  • Use Shared Image Gallery to reduce redundant OS disk costs across VMSS
✗ Cost Don'ts
  • Don't leave unattached disks, NICs, Public IPs — they silently bill
  • Don't run dev/staging environments 24/7 — use start/stop automation
  • Don't overlook data egress costs — the #1 surprise bill for growing teams
  • Don't use Premium storage for non-IOPS-sensitive workloads (logs, archives)
  • Don't buy RIs without analyzing baseline utilization for ≥30 days first
  • Don't skip Cost Management exports to Storage — your FinOps team needs raw data
⚡ Hidden Cost Traps
  • Egress charges: data leaving Azure region (~$0.08/GB)
  • Snapshot sprawl: old VM snapshots accumulate silently
  • Log Analytics retention: default 90 days; every GB counts
  • Premium Functions plan: minimum 1 pre-warmed instance always running
  • Cosmos DB provisioned RU/s: billed whether used or not — use Autoscale
  • Public IP (Standard SKU): billed even when unassigned
🏆 FinOps Pro Move — Stack Discounts: Combine Azure Hybrid Benefit (bring your Windows Server license) + 3-year Reserved Instance on D-series VMs + Savings Plan for compute overage. You can realistically hit 75–80% off pay-as-you-go pricing while retaining flexibility for burst capacity.
