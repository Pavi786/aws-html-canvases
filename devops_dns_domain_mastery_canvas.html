Root Domain "."

The invisible dot at the very top of the DNS hierarchy. All DNS queries ultimately terminate here. DNS resolvers know about 13 root server clusters (a–m.root-servers.net) that answer for the root zone.

TLD — Top Level Domain

The rightmost label: .com, .org, .net. Country codes (ccTLDs) like .uk, .in, .de. New gTLDs like .dev, .app, .cloud. Managed by IANA-assigned registries.

.com.dev.in.io.org
SLD — Second Level Domain

The name you register: example in example.com. This is what you purchase from a registrar (GoDaddy, Namecheap, Route53). Once registered, you control its entire DNS namespace below it.

Apex / Naked Domain

SLD + TLD with no prefix: example.com. Also called the zone apex. Special rules apply — you can't use CNAME here; use A/AAAA or ALIAS/ANAME records instead.

Subdomain

Any label to the left of the registered domain. You control them completely without extra cost. Unlimited nesting is technically allowed (max 253 chars total per FQDN, each label max 63 chars).

wwwapiappmailcdn
FQDN — Fully Qualified

The absolute, complete DNS name ending with a dot: www.example.com. (note trailing dot). In config files (nginx, bind, Route53) you'll often see this. Without it, the name is relative and may be completed by the search domain.

All domain categories a DevOps engineer encounters
gTLD Generic TLD

.com, .net, .org, .info, .biz. Open to registration globally. ICANN manages the list. .com is the default assumption in most browsers (type "example" → tries example.com).

ccTLD Country Code

.in, .uk, .de, .jp, .au. Managed by national registries. Some are repurposed globally: .io (British Indian Ocean Territory → popular with dev startups), .ai (Anguilla → AI companies), .tv (Tuvalu → streaming).

New gTLD Modern extensions

Post-2012 ICANN expansion: .dev, .app, .cloud, .tech, .store, .shop, .online. Many are HTTPS-only preloaded in HSTS lists (.dev, .app force HTTPS in Chrome).

sTLD Sponsored TLD

.gov (US government only), .edu (accredited US universities), .mil (US military), .aero (aviation), .museum. Require sponsoring organizations for eligibility verification.

IDN Internationalized

Non-ASCII domains using Punycode encoding. "München.de" becomes "xn--mnchen-3ya.de" internally. Browsers display the Unicode form; DNS and servers always see Punycode.

Internal Private / RFC2606

.local (mDNS/Bonjour), .internal, .corp, .home.arpa. Reserved for internal use. Never route externally. Used in K8s: svc.cluster.local. Split-horizon DNS serves different answers for internal vs external queries.

Wildcard vs explicit domain configuration

Wildcard Domain *.example.com

  • Matches ANY single-label prefix
  • One DNS record, infinite subdomains
  • Wildcard TLS cert covers all subdomains
  • Used for SaaS tenant routing
  • Preview/feature branch deployments
  • DNS: one A/CNAME record with *
  • Cert: requires DNS-01 ACME challenge

Explicit Domain api.example.com

  • Matches only exact label
  • Each subdomain needs own record
  • Per-subdomain cert or SAN cert
  • More controlled / auditable
  • Easier to route differently per service
  • Clear separation of concerns
  • Best for stable, known subdomains
Wildcard *.example.com does NOT match the apex domain example.com itself, nor does it match deeper labels like a.b.example.com — wildcards cover exactly one label level.
Wildcard DNS record
# In your DNS zone file (BIND / Route53 format) *.example.com. 300 IN A 203.0.113.10 *.example.com. 300 IN CNAME lb.example.com. # Nested wildcard — matches *.tenant.example.com *.tenant.example.com. 300 IN A 203.0.113.20
Wildcard TLS — cert must use DNS-01 challenge
# certbot with Cloudflare DNS plugin certbot certonly \ --dns-cloudflare \ --dns-cloudflare-credentials ~/.secrets/cf.ini \ -d example.com \ -d *.example.com # cert-manager in Kubernetes (ClusterIssuer) apiVersion: cert-manager.io/v1 kind: Certificate spec: dnsNames: - example.com - "*.example.com" issuerRef: name: letsencrypt-prod kind: ClusterIssuer
Nginx wildcard routing — SaaS tenant pattern
server { listen 443 ssl; server_name ~^(?<tenant>[^.]+)\.example\.com$; ssl_certificate /etc/ssl/wildcard.example.com.crt; ssl_certificate_key /etc/ssl/wildcard.example.com.key; location / { proxy_pass http://backend; proxy_set_header X-Tenant $tenant; # pass tenant name upstream } }
Wildcard certs are issued per-level. *.example.com covers foo.example.com but NOT bar.foo.example.com. For deeper nesting you need *.foo.example.com as a separate cert or SAN entry.

What is www, and why does it sometimes break?
www is just a subdomain — a convention from 1991 when servers had specific roles: www, ftp, gopher, mail. Today it carries no special meaning to DNS or HTTP, but billions of users still type it by habit.
The www vs naked domain problem
Why you need BOTH to work

Users type both example.com and www.example.com. They must resolve and ideally redirect to one canonical form. The apex domain (example.com) cannot have a CNAME — this is a DNS spec restriction (RFC 1912). This is the root of most www-related breakage.

2

3

4

www redirect config — nginx

Why www subdomain sometimes doesn't resolve
No DNS record at all

www.example.com was never added to the DNS zone. The apex exists but www is missing. Fix: add an A or CNAME record for www explicitly.

Low TTL / propagation lag

After adding a new record, old TTL value means recursive resolvers cache the negative (NXDOMAIN) response. Wait for old TTL to expire (can be hours). Use dig +trace www.example.com to verify.

Misconfigured NS delegation

Registrar NS still points to old nameservers after migrating to Route53/Cloudflare. The new zone has the record, but resolvers never reach it.

CDN/proxy not configured for www

Cloudflare/Vercel proxy has example.com added but not www.example.com as a hostname. The DNS resolves but the upstream rejects the Host header.

Common issues and fixes
NXDOMAIN

Record doesn't exist. Check: Is the subdomain in the DNS zone? Is the zone active at the authoritative NS? Use dig +trace to pinpoint where it fails.

No such domain
SERVFAIL

Authoritative server error. Common causes: DNSSEC misconfiguration, broken delegation, zone not loaded. Check NS records and zone file syntax on the authoritative server.

Server failure
SSL_ERROR_RX_RECORD_TOO_LONG

Browser connected on port 443 but got HTTP (not HTTPS). Usually means nginx/Apache not listening on 443, or cert not configured. Fix: add SSL config or check port 443 listener.

TLS mismatch
ERR_TOO_MANY_REDIRECTS

Redirect loop between www and apex, or between HTTP and HTTPS. Often caused by CloudFlare "Flexible SSL" + nginx redirect combo. Use "Full (strict)" SSL mode in Cloudflare.

Redirect loop
www works, apex doesn't

www has a DNS record (likely CNAME → CDN), but apex has no record or CNAME (invalid at apex). Solution: Add A record or ALIAS/Route53 Alias for the apex domain.

Missing apex
Cert invalid for domain

TLS cert was issued only for www but request is to apex, or wildcard cert doesn't cover the apex. Fix: Issue SAN cert for both example.com AND www.example.com.

Cert mismatch
DNS propagation reality check
DNS changes don't propagate "instantly" — they depend on the TTL of the old record. If you had a 24h TTL (86400s), resolvers that cached the old value will keep using it for up to 24 hours. Best practice: lower TTL to 300s 24–48 hours BEFORE making the change, then restore after the change propagates.
