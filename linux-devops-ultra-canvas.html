Chapter 01 · OS & Boot Process

OS Fundamentals & Linux Boot

What IS an OS? How does Linux boot from power-on to your shell prompt? Understanding this gives you superpowers in debugging failed boots and slow startups.

What Is an Operating System?
An Operating System is the master manager between hardware and software. It handles 4 core jobs: process scheduling (who gets CPU time), memory management (who gets RAM), filesystem management (organizing data on disk), and device management (talking to hardware via drivers).

Linux is technically just the kernel — the core engine. What we call "Linux" in DevOps is a distribution: kernel + GNU tools + package manager + init system bundled together.
Think of the OS as an airport control tower. Planes (programs) can't just land whenever they want. The tower (OS) allocates runways (CPU), gates (memory), and coordinates all traffic (I/O) safely.
The Complete Linux Boot Process
POWER ON → BIOS/UEFI (POST, finds boot device) → GRUB2 (/boot/grub/grub.cfg, choose kernel) → KERNEL LOADING (decompresses, mounts initramfs) → initramfs (minimal tools, mounts real root FS) → PID 1: systemd (reads unit files, resolves deps) → multi-user.target (network, SSH, databases) → graphical.target (display manager, login screen) → YOUR SHELL

Chapter 02 · Kernel Deep Dive

Kernel Space, User Space & Syscalls

The kernel is the most privileged code on your machine. Understanding the kernel/userspace boundary explains performance, crashes, and why containers work the way they do.

The Two Rings of Execution
Modern CPUs implement privilege rings. Ring 0 (kernel mode) has unrestricted hardware access. Ring 3 (user mode) is where your apps run — isolated and restricted.

The boundary between them is the system call interface. Every meaningful thing a program does — reading a file, opening a socket, creating a process — crosses this boundary.
Ring 0 is the pilot in the cockpit — full control of the plane. Ring 3 is the passenger. To get food (read a file), you press the call button (syscall). The attendant (kernel) fetches it from the galley (disk/network).
Tracing Syscalls with strace
BASH · strace & Syscall Investigation
# Watch ALL syscalls a command makes strace ls /tmp # Count syscalls — find the most frequent strace -c python3 app.py # Only trace file-related syscalls strace -e trace=file nginx # Attach to running process (non-invasive) strace -p 1234 -f # Time spent in each syscall strace -T -e trace=read,write -p 5678
Kernel Modules & sysctl Tuning
BASH · Kernel Modules & sysctl
lsmod # list loaded modules modprobe br_netfilter # load module (needed for k8s) modprobe -r br_netfilter # unload sysctl -a | grep net.ipv4 # view all network params sysctl -w vm.swappiness=10 # set temporarily # Production tuning: net.core.somaxconn = 65535 net.ipv4.tcp_max_syn_backlog = 65535 vm.swappiness = 10 fs.file-max = 2097152 sysctl -p /etc/sysctl.d/99-production.conf
Namespaces & cgroups — Container Foundation
Namespaces isolate what a process can SEE. cgroups limit what a process can USE (CPU, memory, I/O). Together they are the foundation of Docker and Kubernetes.
Namespaces give each department their own isolated office. cgroups are the budget limits — each department can only spend X amount of CPU/memory.
BASH · Namespaces & cgroups
ls -la /proc/1234/ns/ # view namespaces of process ip netns add myns # create network namespace ip netns exec myns bash # run in namespace # Check container's CPU limit cat /sys/fs/cgroup/cpu/docker/CONTAINER_ID/cpu.cfs_quota_us
"What is the difference between a process and a container?" — A container is just a process (or group of processes) with namespaces and cgroups applied. No hypervisor, no separate kernel. `docker run ubuntu bash` just starts bash in isolated namespaces with cgroup limits.

Chapter 03 · Process Management

Processes, Threads & Signals

Everything running on Linux is a process. Every DevOps incident involves processes — either too many, using too much resource, or dying unexpectedly.

Process States
R Running → Currently executing on CPU or runnable S Sleeping → Waiting for event (interruptible — can be killed) D Disk Sleep → Waiting for I/O (UNINTERRUPTIBLE — cannot be killed!) Z Zombie → Finished but parent hasn't collected exit status T Stopped → Paused (Ctrl+Z or SIGSTOP) WHY D-STATE MATTERS: → Cannot be killed with kill -9 → Usually caused by: NFS hang, broken disk, kernel bug → Only reboot or fixing the I/O issue resolves it → High D-state count = I/O bottleneck
Process Investigation Arsenal
BASH · Process Investigation
ps aux # full listing (RSS = actual RAM) pstree -p -n # process tree with PIDs pgrep -a python # find by name, full command lsof -p 1234 # open files for PID lsof -i :80 # who is using port 80 ss -tulnp | grep :8080 # find process by port strings /proc/1234/environ # environment at launch pmap -x 1234 # process memory map
Signals You Must Know

SIGHUP1Yes ✓Reload config (nginx, sshd)

Priority & Nice Values
BASH · Process Priority
# Nice: -20 (highest priority) to +19 (lowest). Default=0 nice -n 15 tar -czvf backup.tar.gz /data/ renice -n 10 -p 1234 # lower priority renice +19 -u nobody # all processes of a user # Low-priority I/O — perfect for backups ionice -c 3 nice -n 19 rsync -av /data /backup/
When a server is under load from a runaway process, use renice +19 PID BEFORE killing it. This immediately drops CPU priority so other services recover, buying you time to investigate.

Chapter 04 · Filesystem

Linux Filesystem Hierarchy Standard

Every directory has a purpose. Know where everything lives and you'll find anything on any Linux server in seconds.

The Complete FHS Map
/ (root) ├── bin/ Essential binaries (ls, cp, mv, cat, bash) ├── sbin/ System binaries for root (iptables, fdisk, mount) ├── boot/ Kernel, initrd, GRUB config ├── dev/ Device files (null, zero, urandom, sda, tty) ├── etc/ ⭐ ALL system config (nginx/, ssh/, systemd/, fstab, passwd) ├── home/ User home dirs ├── lib/ Shared libraries (.so files) ├── opt/ Optional third-party software ├── proc/ ⭐ Virtual FS — live kernel & process data (NOT on disk) ├── root/ Root user's home ├── run/ Runtime data cleared on reboot (PID files, sockets) ├── sys/ ⭐ Virtual FS — hardware/driver interface ├── tmp/ World-writable temp, cleared on reboot ├── usr/ ⭐ User programs │ ├── bin/ Most user commands (python3, git, curl, vim) │ ├── local/ Manually compiled software │ └── share/ Man pages, icons, docs └── var/ ⭐ Variable data that changes constantly ├── log/ ⭐ ALL system and app logs ├── cache/ Application cache └── lib/ Persistent app state (DB data)
Hard Links vs Symbolic Links
Every file is an inode. A hard link is another directory entry pointing to the SAME inode. A symlink is a special file containing a path — like a shortcut that breaks if target is deleted.
Inode is a box in a warehouse. Hard links are multiple labels on the same box. Symlinks are sticky notes saying "go look in aisle B7" — if the box moves, the note is useless.
BASH · Inodes, Hard Links, Symlinks
ls -i /etc/nginx/nginx.conf # view inode number ln original.txt hardlink.txt # hard link (same inode) ln -s /usr/bin/python3 /usr/local/bin/python # symlink readlink -f /usr/bin/python3 # follow to real path find / -xtype l 2>/dev/null # find broken symlinks # Check inode usage — can run out before disk space! df -i Filesystem Inodes IUsed IFree IUse% /dev/sda1 3276800 3270000 6800 99% ← DANGER!
Inode exhaustion causes "No space left on device" even when df -h shows free space. Always monitor BOTH disk space (df -h) AND inodes (df -i).

Chapter 11 · Memory

Memory Monitoring, OOM & Swap

Memory issues cause mysterious process deaths and cascading failures. Learn every memory metric and prevent OOM kills.

Key Memory Concepts
💾
RSS (Resident Set Size)
Actual physical RAM in use RIGHT NOW. This is what you care about for capacity planning.
🗺️
VSZ (Virtual Size)
Total virtual address space including shared libs. Much larger than RSS. Don't alarm on this alone.
📦
Page Cache (buff/cache)
OS uses spare RAM to cache disk data. Shows as "used" but IS available — kernel evicts it when needed.
🔄
Swap
Disk space as RAM overflow. 100x slower. High swap I/O = performance crisis.
Memory Analysis
BASH · Memory Deep Dive
free -h total used free shared buff/cache available Mem: 15Gi 10Gi 512Mi 234Mi 4.5Gi 4.8Gi # Watch 'available' not 'free'! If available drops below 500MB → investigate ps aux --sort=-%mem | head -15 # top memory consumers vmstat 1 5 # si/so=swap in/out (si/so high = problem) # OOM Killer investigation dmesg | grep -i "oom\|killed process" journalctl -k | grep -i "oom" # Protect critical process from OOM echo -1000 > /proc/1234/oom_score_adj # never kill echo 1000 > /proc/1234/oom_score_adj # kill first # Create swapfile on cloud VMs with no swap partition fallocate -l 4G /swapfile chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
Quick biggest memory consumers: ps -eo pid,user,comm,rss --sort=-rss | head -10 | awk '{printf "%-8s %-12s %-20s %s MB\n",$1,$2,$3,$4/1024}'

Disk I/O Monitoring & Performance Tuning

Slow disk I/O is invisible until it causes timeouts. Learn to measure, diagnose, and fix I/O bottlenecks.

I/O Monitoring Tools
BASH · I/O Analysis
iostat -xz 1 Device r/s w/s await util sda 450.2 890.5 0.3 45% ← healthy sdb 120.0 890.0 120.5 98% ← SATURATED! # await >20ms = slow, >100ms = very slow # util >80% = bottleneck iotop -ao # accumulated I/O, only active processes dstat -cdngy # combined CPU/disk/network/system # Raw speed test dd if=/dev/zero of=/tmp/test bs=1G count=5 oflag=sync # I/O scheduler tuning cat /sys/block/sda/queue/scheduler echo "kyber" > /sys/block/nvme0n1/queue/scheduler # best for NVMe echo "mq-deadline" > /sys/block/sda/queue/scheduler # best for SSD

Fix High I/O Wait

  • Upgrade to NVMe SSD — 10-100x better IOPS than HDD
  • Add RAM — bigger page cache = fewer disk reads
  • Fix slow DB queries (indexes! avoid full scans)
  • Use application-level caching (Redis, Memcached)
  • Move DB WAL to separate dedicated disk

Common I/O Culprits

  • Database without proper indexes (full table scans)
  • App logging at DEBUG level to disk
  • Backup jobs running during business hours
  • Memory pressure forcing swap I/O
  • NFS mount with high latency

Chapter 22 · Scheduling

Cron & Job Scheduling

Scheduled jobs keep production systems healthy — backups, cleanups, report generation. Master cron syntax and know when to use systemd timers instead.

Cron Syntax & Management
BASH · Cron Mastery
# Cron format: MIN HOUR DAY MON DOW command # * = any, */n = every n, n,m = specific, n-m = range 0 2 * * * /opt/backup.sh # 2 AM daily */5 * * * * /opt/healthcheck.sh # every 5 minutes 0 9-17 * * 1-5 /opt/report.sh # 9-5 weekdays 0 0 1 * * /opt/monthly.sh # 1st of every month @reboot /opt/startup.sh # at boot @daily /opt/cleanup.sh # shorthand for midnight crontab -e # edit current user's crontab crontab -l # list current crontab crontab -u alice -l # another user's crontab crontab -r # ⚠️ remove ALL cron jobs (dangerous!) grep -r "" /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/ # Cron output goes to user's mail by default # Redirect to log file instead: 0 2 * * * /opt/backup.sh >> /var/log/backup.log 2>&1 # Prevent overlapping cron jobs (run one at a time) * * * * * flock -n /tmp/myjob.lock /opt/long-script.sh # Check if a cron job ran grep "CRON" /var/log/syslog grep "backup.sh" /var/log/syslog # Test cron expression online: crontab.guru

Cron Strengths

  • Simple, universally available on all Linux
  • No daemon to manage (part of system)
  • User-level crontabs for non-root jobs
  • Easy to read and debug

Use systemd Timers When...

  • Need logging integrated with journalctl
  • Need to track if job ran while system was off
  • Need resource limits (CPU/memory) on the job
  • Job has service dependencies (after database is up)
Use flock -n /tmp/myjob.lock command to prevent cron job overlap — if previous run is still going, the new one exits immediately instead of running in parallel.

Chapter 28 · Incident Response

Troubleshooting Playbook — Production Incidents

When production is down, you need a systematic approach. Panic and random commands waste precious minutes. Follow this playbook.

The First 5 Minutes of an Incident
BASH · First 5 Minutes Runbook
# 1. What's the server doing right now? uptime # load average free -h # memory df -h # disk systemctl --failed # failed services # 2. Recent errors journalctl -p err --since "10 minutes ago" dmesg -T --level=err,warn | tail -30 # 3. What changed recently? rpm -qa --last | head # RHEL: recent package changes dpkg -l | head # Ubuntu: package changes journalctl --since "1 hour ago" -u sshd last | head # who logged in recently? # 4. Top resource consumers ps aux --sort=-%cpu | head -8 ps aux --sort=-%mem | head -8 iotop -ao -n 3 # I/O hogs # 5. Network issues? ss -s # socket summary ss -tnp state TIME-WAIT | wc -l # TIME_WAIT count netstat -i # interface errors
Common Incident Scenarios
🔴 Service Not Responding
Check: systemctl status → failed? → journalctl -u service. Is it running but not responding? → lsof -i :PORT, check if port is listening with ss -tulnp.
🔴 Disk Full
du -sh /* | sort -hr → find biggest dirs. docker system prune, journalctl --vacuum-time=3d, truncate log files with > file.log. Check inodes: df -i.
🔴 High CPU
ps aux --sort=-%cpu → find PID → renice +19 PID → strace -p PID -c → determine if runaway loop → kill -15 then -9 if needed.
🔴 Out of Memory / OOM Kill
dmesg | grep -i oom → what was killed → free -h → check swap → ps aux --sort=-%mem → increase memory or fix memory leak.
🔴 Can't SSH
Is server reachable? ping → port 22 open? nc -zv server 22 → use cloud console/IPMI → check sshd status → auth.log for clues → wrong key, fail2ban ban, sshd config error.
🔴 Database Connection Refused
Is DB running? systemctl status postgresql → listening on correct port? ss -tulnp | grep 5432 → check pg_hba.conf for IP allow rules → check max_connections limit.
