Apex / Root / Naked domain
SLD + TLD with NO prefix. Also called the zone apex. Has special DNS restrictions (no CNAME!).

Wildcard domain *.example.com
The * matches any single label — one level deep only.
# DNS zone file *.example.com. IN A 203.0.113.10 # Matches all of these: foo.example.com ✓ bar.example.com ✓ anything.example.com ✓ # Does NOT match: a.b.example.com ✗ example.com ✗
Wildcard does NOT cover the apex or multi-level subdomains.
Non-wildcard (specific) domain
Explicit DNS record for each subdomain. Only that exact label resolves.
# DNS zone file — must add each api.example.com. IN A 203.0.113.10 app.example.com. IN A 203.0.113.11 cdn.example.com. IN A 203.0.113.12 # Unlisted subdomains: xyz.example.com → NXDOMAIN ✗ # Apex can be set separately: example.com. IN A 203.0.113.10
Full control. Only declared subdomains resolve.
Wildcard + SSL/TLS certs
A wildcard TLS cert covers *.example.com — any single-level subdomain gets HTTPS for free. But same rule applies — it does NOT cover the apex or deep subdomains.
# Covers *.example.com → api, app, blog … # Doesn't cover example.com ✗ (use SAN) a.b.example.com ✗ (too deep) # Solution: SAN cert with both CN=*.example.com SAN: example.com, *.example.com
When to use wildcard
1
Multi-tenant SaaS: each customer gets tenant.app.com
2
Dynamic subdomains from code (e.g. GitHub Pages user sites)
3
Reducing DNS management overhead across many services
When NOT to use wildcard
!
When subdomains must route to different IPs — wildcard sends all to the same destination
!
Security-sensitive environments — wildcard is a wide blast radius
Nginx wildcard vhost config
# Catch all *.example.com subdomains server { listen 443 ssl; server_name ~^(?<tenant>[^.]+)\.example\.com$; # $tenant captures the subdomain label root /var/www/$tenant/public; ssl_certificate /etc/ssl/wildcard.example.com.crt; ssl_certificate_key /etc/ssl/wildcard.example.com.key; }
Core DNS record types
RecordMapsExampleDevOps notes
A Hostname → IPv4 example.com → 93.184.216.34 Use at apex and subdomains. Most common.
AAAA Hostname → IPv6 example.com → 2606:2800::1 Dual-stack. Always add alongside A records.
CNAME Alias → another hostname www → example.com Cannot be used at the apex. Common for CDN/load balancer aliases.
MX Domain → mail server example.com → mail.example.com (pri 10) Only on apex. Has priority values.
TXT Domain → text string v=spf1 include:… / site-verify=… SPF, DKIM, domain ownership proofs, DMARC.
NS Zone → authoritative nameserver example.com → ns1.nameserver.com Set at registrar. Delegates DNS authority.
SOA Zone metadata serial, refresh, retry, expire, TTL Auto-managed by DNS providers. Defines zone authority.
SRV Service → host + port _http._tcp → 10 5 80 api.example.com Service discovery. Used by SIP, XMPP, K8s headless services.
ALIAS/ANAME Apex → another hostname example.com ALIAS → lb.provider.com Not standard but supported by Cloudflare (CNAME Flattening), Route 53 (ALIAS). Solves apex CNAME problem.
PTR IP → hostname (reverse) 34.216.184.93.in-addr.arpa → example.com Reverse DNS. Required for mail servers to avoid spam flags.
CAA Domain → allowed CA example.com CAA 0 issue "letsencrypt.org" Restricts which CAs can issue certs for your domain.
TTL — Time To Live
How long resolvers cache a record (in seconds). Lower TTL = faster DNS changes propagate but more queries hit your nameserver.
# Before a migration → lower TTL 24h in advance api.example.com. 300 IN A 203.0.113.10 # 5 min cache # Stable records → higher TTL example.com. 86400 IN A 203.0.113.10 # 24h cache
What is www exactly?
www is just a subdomain — historically it meant "this host serves the World Wide Web." It is not special in DNS. You must configure it explicitly.
# www is NOT automatic # These are TWO separate DNS entries: example.com. IN A 93.184.216.34 www.example.com. IN CNAME example.com. # If only A record exists: example.com ✓ resolves www.example.com ✗ NXDOMAIN
www subdomain DNS options
A

www → 203.0.113.10
B
CNAME to apex
www CNAME example.com.
C

Subdomain delegation — giving a team/service control of a sub-zone
# Delegate staging.example.com to its own nameservers staging.example.com. IN NS ns1.staging-provider.com. staging.example.com. IN NS ns2.staging-provider.com. # Now the staging team manages ALL of *.staging.example.com # independently without touching parent zone
Redirect www ↔ non-www (canonical URL strategy)
Choose one canonical form. Redirect the other. Mixing both hurts SEO and cookie scoping.
# Nginx: redirect bare domain → www server { listen 80; server_name example.com; return 301 https://www.example.com$request_uri; } # OR redirect www → bare domain server { listen 80; server_name www.example.com; return 301 https://example.com$request_uri; }
The most common reasons www.example.com resolves but fails, or never resolves at all.
❶ www DNS record simply doesn't exist
The most common cause. An A record for example.com does NOT automatically create www.example.com.
# Diagnose: $ dig www.example.com ; ANSWER SECTION: (empty) → NXDOMAIN # Fix: add record in your DNS provider www.example.com. IN A 203.0.113.10 # OR www.example.com. IN CNAME example.com.
❷ CNAME chain resolves but SSL cert doesn't cover www
DNS works fine, but the TLS certificate only has example.com as SAN — browser shows a cert error for www.example.com.
# Check cert SANs: $ openssl s_client -connect www.example.com:443 \ | openssl x509 -noout -text | grep -A5 "Subject Alt" # Fix: reissue cert with both SANs certbot certonly --domains example.com,www.example.com
❸ Server / vhost not configured for www
DNS resolves, TLS is valid, but Nginx/Apache has no vhost matching www.example.com. Gets the default vhost or 404.
# Wrong — only handles bare domain: server_name example.com; # Fix — handle both: server_name example.com www.example.com; # OR separate redirect block: server { server_name www.example.com; return 301 https://example.com$request_uri; }
❹ CNAME at the apex (zone apex restriction)
You try to set example.com CNAME loadbalancer.provider.com — this is illegal per RFC 1034. You cannot have a CNAME at the apex because the apex must also hold NS and SOA records.
# ILLEGAL — breaks zone example.com. IN CNAME lb.provider.com. ✗ # Fix option 1: Use A record example.com. IN A 203.0.113.10 # Fix option 2: Cloudflare CNAME Flattening example.com CNAME (proxied) → lb.provider.com ✓ # Fix option 3: Route53 ALIAS example.com. ALIAS lb.us-east-1.elb.amazonaws.com.
❺ Cloudflare orange-cloud proxied — SSL mode mismatch
Cloudflare is proxying www.example.com. Your origin server has no SSL cert or a self-signed one, but Cloudflare SSL mode is set to Full (strict) — so Cloudflare rejects the connection to your origin.
# Symptoms: ERR_TOO_MANY_REDIRECTS or 525 SSL Handshake Failed # Fix options (in Cloudflare dashboard): SSL/TLS Mode → Flexible # origin has no cert (dev only) SSL/TLS Mode → Full # origin has self-signed cert SSL/TLS Mode → Full (strict) # origin has valid CA cert ← correct # Best practice: install cert on origin + use Full (strict)
