TOPIC 01

Containers & K8s Basics

Understanding what Kubernetes is, why it exists, and the foundation you need before diving deeper.

🐳

What is Kubernetes?

Kubernetes (K8s) is an open-source platform that automates deploying, scaling, and managing containerized applications. Originally built by Google, now maintained by CNCF.

Layman: Imagine you have 100 restaurant branches. Instead of hiring a manager for each, you hire ONE super-manager who watches all branches, fixes problems automatically, and scales staff during rush hours. That's Kubernetes for your apps.

✅ Pros

  • Self-healing — restarts crashed apps
  • Auto-scales on demand
  • Zero-downtime deployments
  • Works across cloud providers
  • Massive community support

❌ Cons

  • Steep learning curve
  • Over-engineered for small apps
  • Complex networking setup
  • Debugging is hard initially
  • Needs dedicated expertise

💰 Cost

  • EKS (AWS): ~$0.10/hr per cluster
  • GKE (Google): Free control plane
  • AKS (Azure): Free control plane
  • Node VMs: $50–500+/mo
  • DevOps engineer: $80k–150k/yr
📦

Containers

A container packages your app + all its dependencies (libraries, configs) into one portable unit. It runs the same everywhere.

Layman: A shipping container. Everything needed for your app is packed inside — wherever it lands (AWS, Azure, your laptop), it runs identically.
# Build a container image
docker build -t myapp:1.0 .

# Run a container
docker run -p 8080:80 myapp:1.0

🗂️

Container Registry

A registry stores container images — like GitHub but for Docker images. You push images here, Kubernetes pulls from here.

Docker Hub AWS ECR Google GCR Azure ACR Harbor (self-hosted)

✅ Pros

  • Centralized image storage
  • Version tagging
  • Access controls
  • Vulnerability scanning

❌ Cons

  • Docker Hub rate limits
  • Private repos cost money
  • Pull latency in some regions

💰 Cost

  • Docker Hub Free: 1 private repo
  • Docker Pro: $5/mo
  • ECR: $0.10/GB/month
  • Harbor: Free (self-host)
TOPIC 02

Kubernetes Architecture

How a K8s cluster is structured — the brain (Control Plane) and the workers (Nodes).

🏗️ Big Picture

A Kubernetes cluster has two main parts: Control Plane (the brain — decides what runs where) and Worker Nodes (the muscles — actually run your apps). You talk to K8s via kubectl which hits the API Server.

You / kubectl
→
API Server
→
etcd (stores state)
→
Scheduler
→
Worker Node
→
Kubelet → Pod

🧠 Control Plane (Master Node)

API Server
Entry point. All kubectl commands hit here. The "front desk" of K8s.
Scheduler
Decides WHICH node a new Pod runs on, based on resources & rules.
Controller Mgr
Watches cluster state. If 3 pods needed but only 2 running, it creates 1 more.
etcd
Distributed key-value database. Stores ALL cluster data. The single source of truth.
Layman: The Control Plane is like a hospital's admin office — it tracks every patient (pod), decides which ward (node) they go to, and keeps all records (etcd).

💪 Worker Node

Kubelet
Agent on each node. Talks to API Server. Ensures containers are running as expected.
Kube-proxy
Manages network rules on each node. Enables communication between Pods and Services.
Container Runtime
Actually runs containers. Can be containerd, CRI-O, or Docker (deprecated in newer K8s).
Pods
Your actual app containers running here. One or more per pod.
Layman: Worker nodes are like hospital wards — they actually house the patients (pods). Kubelet is the ward nurse who reports status back to admin.
💰

Architecture Cost & Trade-offs

✅ Pros

  • Highly available control plane (managed)
  • Nodes can scale independently
  • etcd ensures no data loss
  • Multi-zone fault tolerance

❌ Cons

  • etcd is a single point of failure if not HA
  • Control plane needs 3+ masters for HA
  • Complex networking between components

💰 Cost

  • Self-managed: 3 master VMs (~$100-300/mo)
  • EKS managed: $0.10/hr = ~$73/mo
  • GKE Autopilot: pay per pod only
  • Single node (dev): free with minikube
TOPIC 03

Core Kubernetes Objects

The fundamental building blocks — Pod, ReplicaSet, Deployment, StatefulSet, DaemonSet.

🟦

Pod — The Smallest Unit

A Pod is the smallest deployable unit in K8s. It wraps one or more containers that share the same network (IP) and storage. Containers in a pod talk to each other via localhost.

Layman: A Pod is like a hotel room. The containers are roommates — they share the same address (IP) and bathroom (storage volumes), but do their own thing.
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
  - name: app
    image: nginx:1.21
    ports:
    - containerPort: 80

✅ Pros

  • Simple unit of deployment
  • Shared network namespace
  • Co-location of related containers

❌ Cons

  • Ephemeral — dies and loses data
  • No auto-restart by itself
  • Not meant to be used alone

💰 Cost

  • Cost depends on node type
  • Idle pod: still uses memory
  • GKE Autopilot: pay per pod resource
🔁

ReplicaSet

Ensures a specified number of identical Pod replicas are always running. If a pod dies, it creates a new one.

Layman: You say "I always want 3 waiters on the floor." If one quits, ReplicaSet hires a new one automatically.

✅ Pros

  • High availability
  • Auto-healing

❌ Cons

  • No rolling updates
  • Use Deployment instead
🚀

Deployment

Manages ReplicaSets. Enables rolling updates (update pods one by one), rollbacks, and version tracking. Most common workload type.

Layman: The Deployment is the head chef. It manages the kitchen staff (ReplicaSet), trains new staff (rolling update), and can fire everyone and rehire from last week's roster (rollback).

✅ Pros

  • Rolling updates
  • Easy rollback
  • Self-healing

❌ Cons

  • Not for stateful apps
  • Pods have random names
🗄️

StatefulSet

Like a Deployment but for stateful applications (databases, Kafka, Zookeeper). Pods get stable, predictable names (pod-0, pod-1) and dedicated persistent storage.

Layman: Like hotel rooms with permanent numbers. Room 101 always belongs to the same guest. Even if they leave and come back, their stuff is still in Room 101.

✅ Pros

  • Stable pod names (pod-0, pod-1)
  • Ordered deployment/scaling
  • Each pod gets its own PVC

❌ Cons

  • Complex to manage
  • Slower rolling updates
  • Requires persistent storage setup
📡

DaemonSet

Ensures ONE pod runs on EVERY node (or selected nodes). Used for cluster-wide tools like log collectors, monitoring agents, network plugins.

Layman: Like a security guard required in every branch of a bank. No matter how many branches open, one guard is always assigned to each.

✅ Pros

  • Automatic on new nodes
  • Perfect for infrastructure tools
  • No manual scheduling needed

❌ Cons

  • Consumes resources on every node
  • Can't scale below 1-per-node
TOPIC 04

Services & Networking

How traffic flows in Kubernetes — from inside the cluster to the outside world.

🌐

Service — Stable Networking

Pods are temporary and get new IPs when restarted. A Service provides a stable IP and DNS name that always routes to the right Pods using label selectors.

Layman: Pods are like taxi drivers who change their car every day. A Service is like calling "Taxi" — you don't care which driver comes, you just need a ride. The Service finds the right pod for you.

🔒 ClusterIP

Default. Exposes service only INSIDE the cluster. Other pods can reach it via DNS name. Not accessible from outside.

Internal Only

✅

  • Secure
  • Simple

❌

  • No external access

🔌 NodePort

Exposes service on a static port on EACH node's IP (30000-32767). External traffic can hit any node IP + that port.

Dev/Testing

✅

  • Simple external access

❌

  • Exposes node IP
  • Port range limited

⚖️ LoadBalancer

Creates a cloud load balancer (AWS ALB/ELB, GCP LB). Gets a public IP. Best for production external services.

Production

✅

  • Production ready
  • Cloud-native

❌

  • 1 IP per service
  • $$$ expensive

🔗 ExternalName

Maps a Service to an external DNS name. Used to access services outside the cluster (like a database hosted on RDS).

External DNS

🚦 Ingress

HTTP/HTTPS routing rules. One entry point for multiple services. Routes by domain name or URL path. Needs an Ingress Controller (NGINX, Traefik).

HTTP Routing

✅

  • 1 LB for many services
  • TLS termination
  • Cost efficient

❌

  • HTTP only (L7)
  • Needs controller

🕸️ CNI Plugins

Container Network Interface — handles pod-to-pod networking. Popular options: Calico (security policies), Flannel (simple), Cilium (eBPF-based).

CalicoFlannelCilium

TOPIC 05

Storage in Kubernetes

How K8s handles data that needs to survive pod restarts — Volumes, PV, PVC, StorageClass.

🗄️ The Storage Problem

Pods are temporary. When a pod dies, its data is gone. To persist data (databases, file uploads, logs), you need Volumes. The K8s storage system separates "what storage exists" (PV) from "what storage is needed" (PVC).

📁 Volume

Temporary storage tied to a pod's lifetime. Types: emptyDir (temp), hostPath (node disk), configMap, secret, nfs, etc. Dies with the pod (emptyDir) or persists on node (hostPath).

Layman: Like a whiteboard in a meeting room — erased when the meeting ends (pod dies).

💾 PersistentVolume (PV)

A piece of actual storage provisioned in the cluster — an AWS EBS disk, NFS share, or cloud file system. Created by admins or dynamically. Independent of any pod.

Layman: Like a locker available at the gym. It exists whether anyone uses it or not.

📋 PersistentVolumeClaim (PVC)

A request for storage by a user/pod. "I need 10GB of SSD storage." K8s matches it to a suitable PV and binds them together.

Layman: Like submitting a form requesting locker #42. K8s assigns a matching available locker.

⚡ StorageClass

Defines how storage is dynamically provisioned. You say "I want gp2 (SSD) storage" and K8s creates a new PV automatically when a PVC is made.

Layman: Like selecting a hotel room category (Standard/Deluxe/Suite) — the hotel auto-assigns the right room.

PV ↔ PVC Lifecycle

Admin creates PV
→
Dev creates PVC
→
K8s binds PVC→PV
→
Pod mounts PVC
→
Data persists ✓
# PVC example
apiVersion: v1
kind: PersistentVolumeClaim
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 10Gi
  storageClassName: gp2

✅ Pros

  • Data survives pod restarts
  • Dynamic provisioning
  • Works with cloud storage (EBS, GCS)
  • Access modes: RWO, RWX, ROX

❌ Cons

  • Complex setup
  • PV/PVC binding can fail
  • Storage reclaim policies tricky
  • No built-in backup

💰 Cost

  • AWS EBS gp3: ~$0.08/GB/mo
  • AWS EFS: ~$0.30/GB/mo
  • GCP Persistent Disk: ~$0.04/GB/mo
  • Azure Disk: ~$0.10/GB/mo
TOPIC 06

ConfigMap & Secrets

Decoupling configuration and sensitive data from your container images.

⚙️

ConfigMap

Stores non-sensitive configuration data as key-value pairs — app settings, environment variables, config files. Injected into pods as env vars or files.

Layman: Like a notice board in an office — everyone reads the same settings (working hours, meeting room rules). Change the board once, everyone sees the update.
kind: ConfigMap
data:
  DB_HOST: mysql-service
  APP_ENV: production
  MAX_CONNECTIONS: "100"

✅ Pros

  • Decouple config from code
  • Easy to update
  • Human-readable

❌ Cons

  • Not for secrets
  • 1MB size limit
  • Changes need pod restart
🔐

Secret

Stores sensitive data — passwords, API keys, TLS certificates, tokens. Values are Base64 encoded (NOT encrypted by default — use encryption at rest!).

Layman: Like a sealed envelope given to each employee — they can open it to read the WiFi password, but it's not posted on the notice board for everyone to see.
kind: Secret
type: Opaque
data:
  # base64 encoded values
  DB_PASSWORD: cGFzc3dvcmQxMjM=
  API_KEY: c2VjcmV0a2V5MTIz

✅ Pros

  • Separate from code
  • RBAC controlled access
  • Multiple secret types

❌ Cons

  • Base64 ≠ encryption
  • Stored in etcd (encrypt it!)
  • Needs Vault for enterprise

⚠️ Secret Security Best Practices

Enable Encryption at Rest

By default, Secrets in etcd are NOT encrypted. Enable EncryptionConfiguration in kube-apiserver.

Use External Secret Managers

Use HashiCorp Vault, AWS Secrets Manager, or GCP Secret Manager for production secrets.

Restrict with RBAC

Only grant get/list on Secrets to service accounts that actually need them.

TOPIC 07

Scheduling & Resource Management

How K8s decides WHERE pods run and HOW MUCH compute they get.

🎯

Requests & Limits

Requests: What the pod is guaranteed. Used by scheduler to find a node with enough capacity.
Limits: Maximum the pod can use. If exceeded, CPU is throttled; if memory exceeds limit, pod is OOMKilled.

Layman: Requests = the seat you reserved at a restaurant (guaranteed). Limits = maximum number of dishes you're allowed to order. Exceed it and the waiter stops serving you.
resources:
  requests:
    memory: "128Mi" # guaranteed
    cpu: "250m" # 0.25 core
  limits:
    memory: "256Mi" # max allowed
    cpu: "500m" # 0.5 core max

🏷️ NodeSelector

Simplest way to constrain pods to nodes with specific labels. "Only run on nodes labeled gpu=true."

Layman: Only send heavy machinery workers to the factory floor, not the office floor.

🧲 Node Affinity

Advanced version of NodeSelector. Supports required (hard) and preferred (soft) rules. "Must be in us-east-1, prefer SSD nodes."

Layman: Must be a non-smoking room (hard rule), prefer high floor (soft preference).

🔗 Pod Affinity/Anti-Affinity

Schedule pods near (affinity) or away from (anti-affinity) other pods. Spread replicas across zones for HA.

Layman: Anti-affinity = don't put all your eggs in one basket. Spread DB replicas across racks.

🚫 Taints & Tolerations

Taints REPEL pods from nodes unless pods have matching Tolerations. Used to dedicate nodes for specific workloads (GPU, production-only).

Layman: Taint = "No Entry" sign on a VIP lounge. Toleration = your VIP pass to enter.

💰 Resource Management Cost Impact

✅ With Proper Limits

  • Predictable costs
  • No one pod starves others
  • Better bin-packing (use nodes fully)
  • Autoscaler works accurately

❌ Without Limits

  • One pod can hog entire node
  • OOMKilled crashes in production
  • Unpredictable cloud bills
  • Noisy neighbor problems

💰 Savings Tips

  • Right-size requests = fewer nodes
  • VPA auto-adjusts requests
  • LimitRange enforces defaults
  • ResourceQuota per namespace
TOPIC 08

Scaling & Auto-Scaling

From manual scaling to intelligent auto-scaling — handling traffic spikes without wasting money.

📊 Manual Scaling

Directly set the number of replicas. Simple, predictable, but requires human intervention.

kubectl scale deployment/app \
  --replicas=5

✅

  • Simple
  • Predictable

❌

  • Manual work
  • Wastes or lacks capacity

⚡ HPA — Horizontal Pod Autoscaler

Automatically scales the NUMBER of pods based on CPU, memory, or custom metrics. The most common autoscaler.

Layman: Like a call center — when call volume goes up, more agents are called in. When quiet, some go home.

✅

  • Handles traffic spikes
  • Cost efficient
  • Custom metrics support

❌

  • Cold start delay
  • Needs metrics-server
  • Not for stateful apps

📏 VPA — Vertical Pod Autoscaler

Automatically adjusts CPU/memory REQUESTS of pods. Makes pods bigger or smaller, not more or fewer. Requires pod restart.

Layman: Instead of hiring more workers, give each worker a bigger desk and better tools when workload increases.

✅

  • Right-sizes pods
  • Reduces over-provisioning

❌

  • Restarts pods
  • Conflicts with HPA

🖥️ Cluster Autoscaler

Adds or removes NODES from the cluster. When pods can't be scheduled (insufficient resources), it adds a node. When nodes are underutilized, it removes them.

Layman: If the office is full, rent another floor. If half the floors are empty, terminate the lease.

✅

  • Massive cost savings
  • Works with HPA

❌

  • Node spin-up takes 2–5 min
  • Cloud-provider specific

💰 Scaling Cost Strategy

✅ Best Practice

  • HPA + Cluster Autoscaler combo
  • Use Spot/Preemptible nodes (70% cheaper)
  • Set min replicas = 1 for non-critical
  • KEDA for event-driven scaling

❌ Avoid

  • Always-on large fleets
  • High min replicas when not needed
  • Not setting scale-down delays

💰 Savings

  • Cluster Autoscaler: 40–60% savings
  • Spot nodes: 60–70% off on-demand
  • HPA prevents over-provisioning
  • GKE Autopilot: pay per pod only
# HPA example — scale when CPU > 70%
kubectl autoscale deployment/app \
  --cpu-percent=70 \
  --min=2 --max=20
TOPIC 09

Health Checks & Probes

How Kubernetes knows your application is alive, ready to serve traffic, and started successfully.

❤️ Liveness Probe

Question it answers: "Is the app still alive? If not, restart it."

Detects deadlocks or frozen processes. If it fails, K8s kills and restarts the container.

Layman: Like a guard checking if the security monitor is still on. If the screen is frozen, he reboots it.
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

✅ Readiness Probe

Question it answers: "Is the app ready to receive traffic?"

If it fails, the pod is removed from the Service endpoints. Traffic stops routing to it — but it's NOT restarted.

Layman: Like a restaurant that opens the doors only when the kitchen is fully set up. K8s doesn't send customers (traffic) until "Ready" signal.
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  failureThreshold: 3
  periodSeconds: 5

🚀 Startup Probe

Question it answers: "Has the app finished starting up?"

Disables liveness/readiness checks until startup succeeds. For slow-starting apps (Java Spring Boot, etc.).

Layman: Like a slow old computer — don't keep checking if it crashed during boot. Give it time to fully start up, THEN begin monitoring.
startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  failureThreshold: 30
  periodSeconds: 10

🔍 Probe Types & When to Use

Probe TypeCheck MethodUse Case
HTTP GETCalls an HTTP endpoint — 2xx/3xx = healthyWeb servers, REST APIs
TCP SocketTries to open TCP connection to a portDatabases, non-HTTP services
Exec CommandRuns a command inside container — exit 0 = healthyCustom logic, scripts
gRPCCalls gRPC health check protocol (K8s 1.24+)gRPC microservices

✅ Pros

  • Zero-downtime deployments
  • Auto-recovery from crashes
  • No stale pods in load balancer
  • Graceful startup for slow apps

❌ Cons

  • Wrong config causes restart loops
  • Probe endpoint must be lightweight
  • initialDelaySeconds must be tuned

💰 Cost

  • Prevents costly cascading failures
  • Reduces mean time to recovery
  • Free feature — just YAML config
TOPIC 10

Security in Kubernetes

RBAC, Service Accounts, Network Policies, and Pod Security — protecting your cluster.

🔐

RBAC — Role-Based Access Control

Controls WHO can do WHAT in K8s. Defines Roles (set of permissions) and binds them to users or service accounts.

Layman: Like a hospital: Doctors can prescribe medicine (create/delete pods), Nurses can check charts (read pods), Janitors can only clean (no cluster access). Everyone has their lane.
User / ServiceAccount
→
RoleBinding
→
Role / ClusterRole
→
Permissions (verbs)
# Role: read-only pod access
kind: Role
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

👤 Service Accounts

Identity for pods/processes within the cluster. Pods use service accounts to call the K8s API. Default SA exists in every namespace.

Layman: Like a staff badge. Each pod wears a badge that determines what rooms (APIs) it can access.

🕸️ Network Policies

Firewall rules for pods. By default ALL pods can talk to ALL pods. Network Policies restrict this — "only frontend can talk to backend, not to database."

Layman: Office floor plan rules — the receptionist can talk to anyone, but the server room is only accessible to IT staff.

🛡️ Pod Security Standards

Three levels: Privileged (unrestricted), Baseline (minimal restrictions), Restricted (hardened, no root). Applied per namespace.

Layman: Like building security levels — lobby (privileged), employee areas (baseline), server room (restricted).

🔒 Security Checklist

✅ Must Do

  • Enable RBAC (on by default)
  • Encrypt etcd at rest
  • Use Network Policies
  • Run non-root containers
  • Scan images for CVEs
  • Rotate credentials regularly

❌ Common Mistakes

  • Too permissive RBAC
  • Secrets not encrypted
  • Privileged containers
  • No network isolation
  • Default service account overuse

💰 Security Tools

  • Falco: Free (runtime security)
  • OPA/Gatekeeper: Free
  • Aqua Security: $$$
  • Prisma Cloud: $$$
  • Trivy (image scan): Free

Observability — Monitoring & Logging

Seeing what's happening inside your cluster — metrics, logs, and traces.

📈

Prometheus — Metrics

Pull-based metrics collection system. Scrapes metrics from pods and K8s components at regular intervals. Stores time-series data.

Layman: Like a fitness tracker that every 15 seconds records your heart rate, steps, calories. Later you can query "what was my heart rate at 3pm yesterday?"

✅ Pros

  • CNCF standard
  • Powerful query (PromQL)
  • Huge ecosystem
  • Alertmanager built-in

❌ Cons

  • Short-term storage only
  • PromQL learning curve
  • Not for logs
📊

Grafana — Visualization

Beautiful dashboards for metrics from Prometheus, Loki, and other sources. Pre-built Kubernetes dashboards available.

Layman: If Prometheus is the raw data from the fitness tracker, Grafana is the beautiful app that shows graphs, trends, and alerts on your phone.

✅ Pros

  • Beautiful dashboards
  • Free & open source
  • Multi-datasource

❌ Cons

  • Just visualization
  • Alert fatigue risk
📜

EFK / ELK Stack — Logging

Centralized logging for all pods across all nodes. EFK: Elasticsearch + Fluentd + Kibana. ELK: Elasticsearch + Logstash + Kibana.

Pod writes logs
→
Fluentd/Logstash collects
→
Elasticsearch stores
→
Kibana visualizes
Layman: Like a hotel CCTV system — every room (pod) has a camera (log stream). All recordings go to a central archive (Elasticsearch). Security can search any incident (Kibana).

✅ Pros

  • Centralized search across all pods
  • Correlation of events
  • Long-term retention
  • Full-text log search

❌ Cons

  • Elasticsearch is resource-heavy
  • Complex to operate
  • Expensive at scale

💰 Cost

  • Self-hosted EFK: $200–2000+/mo
  • Elastic Cloud: from $95/mo
  • Datadog Logs: $0.10/GB/day
  • Loki (Grafana): much cheaper

TOPIC 13

Deployment Strategies

How to ship new versions of your app safely — zero downtime, instant rollback.

🔄 Rolling Update

Replace pods one by one. New pods start before old ones stop. Default K8s strategy. Zero downtime.

v1 v1 v1 v1 → v2 v1 v1 v1 → v2 v2 v1 v1 → v2 v2 v2 v2
Layman: Renovating a hotel one room at a time — guests always have somewhere to stay.

✅

  • Zero downtime
  • Built-in K8s

❌

  • Both versions live simultaneously
  • Rollback takes time

🔵🟢 Blue-Green

Run two identical environments (Blue=current, Green=new). Switch traffic all at once. Instant rollback by switching back.

Layman: Like having a spare fully-equipped kitchen. Cook the new menu there, then swap the sign from "Blue Kitchen" to "Green Kitchen" in one second.

✅

  • Instant rollback
  • Full testing before switch

❌

  • Double infrastructure cost
  • DB migrations complex

🐤 Canary

Send a small % of traffic (5-10%) to new version first. Monitor for errors. Gradually increase to 100% if healthy.

Layman: Like a restaurant testing a new dish — give it to 10% of tables first. If nobody complains, add it to the full menu.

✅

  • Minimal blast radius
  • Real user testing

❌

  • Complex traffic splitting
  • Needs monitoring

💥 Recreate

Kill ALL old pods first, then start new pods. Causes downtime. Use only for dev/staging or when you can't run two versions simultaneously.

Layman: Closing the restaurant completely for renovations. Customers have to wait until it reopens.

✅

  • Simple
  • No version conflicts

❌

  • Downtime guaranteed
  • Never for production

Kubernetes YAML Reference

The language of Kubernetes — every resource is defined in YAML. Master this and you master K8s.

📋 Every K8s YAML has 4 core fields

apiVersion: apps/v1 # Which API to use (v1, apps/v1, networking.k8s.io/v1...)
kind: Deployment # What resource type (Pod, Service, Ingress...)
metadata: # Name, namespace, labels
  name: my-app
  namespace: production
  labels:
    app: my-app
spec: # The actual desired state / configuration
  ...
Complete Examples

deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web
        image: nginx:1.21
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
