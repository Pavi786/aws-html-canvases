What is Azure? The 1-Minute Version
☁️
Microsoft Azure — The Big Picture
Cloud Computing Platform by Microsoft · Est. 2010
FoundationMust Read
What is it?

Azure is Microsoft's cloud computing platform. It's a massive network of data centers spread across the world, and they rent their computing power, storage, and software services to you — so you don't have to buy and maintain your own servers. You pay only for what you use, like an electricity bill.

Before cloud: You'd buy a physical server, rack it in a data center, manage power, cooling, hardware failures, OS patches — all your problem. With Azure: click, pay, use. Azure handles the physical stuff.

🏨 The Hotel Analogy: Buying a server is like buying a house — you own it, you fix broken pipes, you pay property tax. Using Azure is like staying at a hotel — you rent a room, they handle maintenance, security, cleaning. You just show up and live in it.
Azure's Hierarchy — How it's organized
Tenant — Your company's Azure account. Managed by Microsoft Entra ID. Think: the building you own.
Management Group — Groups subscriptions. Apply policies across all. Think: floors of the building.
Subscription — Billing container. Each department/project might have its own. Think: apartments on a floor.
Resource Group — A logical container for related resources. Like a project folder. Deploy together, delete together.
Resource — The actual thing (a VM, database, storage account). The furniture inside the apartment.
💡 Golden Rule: Put resources that share the same lifecycle into the same Resource Group. Delete the RG → everything in it gets deleted cleanly.

🖥️ Compute — Section 01
Azure Virtual Machines
The most fundamental cloud service. A Virtual Machine is a computer that runs inside Azure's data center. You get full control — OS, software, network — but you manage everything above the hardware.
🖥️
Virtual Machines (VMs)
Azure Virtual Machines · IaaS
IaaSCore Compute
What is it — plain English

A VM is a software-based computer running on Microsoft's hardware in their data center. You pick how powerful it is (CPU, RAM), what OS it runs (Windows Server 2022, Ubuntu 22.04, etc.), and it's yours to use over the internet. It behaves exactly like a real computer — you can SSH/RDP into it, install software, run your app.

💻 Real-world analogy: You want a powerful desktop PC but can't afford to buy one. You rent time on one remotely via the internet. You can remote-control it, install stuff, use it. When done, you stop paying. That's a VM.
Key VM Sizes (Families)
B-series (Burstable) — cheapest. Good for dev/test. CPU is weak but can burst to full power for short periods. Like a slow car that can temporarily go fast on the highway.
D-series (General Purpose) — balanced CPU/RAM. For most web apps and mid-tier workloads. The workhorse VM family.
E-series (Memory Optimized) — lots of RAM, less CPU. For databases, in-memory caches, SAP HANA.
F-series (Compute Optimized) — fast CPUs, less RAM. For batch processing, gaming servers, high-frequency trading.
N-series (GPU) — has NVIDIA GPUs. For AI training, video rendering, machine learning workloads.
How the billing works
Pay-as-you-go — charged per second while VM is running. Most expensive rate but no commitment.
Reserved Instances (1 or 3 yr) — commit upfront, save up to 72%. Best for production workloads that run 24/7.
Spot VMs — up to 90% discount but Azure can evict (shut down) with 30 seconds notice when capacity is needed. Only for batch jobs, fault-tolerant workloads.
Dev/Test pricing — if your subscription is flagged as Dev/Test, Windows VMs drop significantly in price (no Windows license charge).
When to use vs not
✅ Use VMs when
You need full OS control
Running legacy software
Custom OS configuration needed
Lift & shift from on-prem
❌ Avoid VMs when
You just need to run code — use App Service/Functions
Short-lived tasks — too expensive to keep a VM running
You don't want to patch/manage OS
⚠️ Most common mistake: Leaving VMs running when not needed. A VM costs money even when idle. Use Auto-shutdown schedules in dev environments — massive savings!
📈
VM Scale Sets (VMSS)
Azure Virtual Machine Scale Sets · Auto-scaling IaaS
Auto-ScaleDevOps Essential
What is it?

VMSS lets you run a group of identical VMs that automatically grows or shrinks based on demand. You define the template (which image, which size) and the scaling rules (when to add more, when to remove), and Azure handles spinning VMs up and down automatically.

🏭 Factory analogy: Imagine a factory that automatically hires temps when orders spike and lets them go when things quiet down. The manager (Azure) watches the order volume (CPU/traffic) and adjusts headcount (VMs) automatically. No manual work.
Scaling Modes
Scale Out — adds more VMs when load increases (e.g., CPU > 70% for 5 min → add 2 VMs)
Scale In — removes VMs when load drops (e.g., CPU < 30% for 10 min → remove 1 VM)
Schedule-based — "Add 5 VMs at 8am Monday, remove at 6pm" — for predictable traffic patterns
Manual — you control the count — good for planned events
How it fits in DevOps
VMSS is deployed behind a Load Balancer. Traffic is spread across all VMs evenly.
Use a custom VM image (with your app pre-installed) so new VMs come up ready to serve instantly.
Rolling upgrades — update VMs one-by-one so you never have downtime during deployments.
Works with Azure Monitor metrics — scale on custom metrics like queue depth, not just CPU.
💡 Pro tip: Set minimum instances to 2 spread across Availability Zones. If one AZ fails, other VMs still serve traffic. Cost of one extra VM = massive uptime improvement.
Real-world DevOps scenario

An e-commerce site gets normal traffic (3 VMs sufficient). On Black Friday, traffic spikes 10x. VMSS detects high CPU → scales to 15 VMs in minutes. Black Friday ends → VMSS scales back to 3 VMs. You pay extra only during the spike. No manual intervention needed.

🌐 Compute — Section 02
Azure App Service
The most popular way to run web apps in Azure. Push your code — Azure handles all the infrastructure, OS patching, SSL, and scaling. You never touch a server.
🌐
Azure App Service — Web Apps
Fully Managed Web App Hosting · PaaS
PaaSDevOps DailyMost Popular
What is it?

App Service is a fully managed platform for hosting web applications, REST APIs, and mobile backends. You write code in Node.js, Python, .NET, Java, PHP, or Ruby — push it to Azure — and it runs. You never configure a web server, install packages, manage OS patches, or set up SSL. Azure does all that for you.

🏠 Furnished apartment analogy: A VM is buying a house — you do everything. App Service is a fully furnished serviced apartment — kitchen stocked, AC set, bed made. You just walk in with your clothes (code) and live there. Someone else handles maintenance.
App Service Plans (Pricing tiers)
TierUse CaseKey Features
Free/SharedExperiments onlyNo custom domain, shared CPU
Basic (B1-B3)Dev/Test environmentsCustom domain, manual scale
Standard (S1-S3)Most production appsAuto-scale, deployment slots, backups
Premium (P1v3-P3v3)High perf productionVNet integration, zone redundancy
Isolated (I1-I3)Compliance, max isolationDedicated environment (ASE), VNet native
The Best Feature: Deployment Slots 🎯
Every App Service can have multiple slots (staging, QA, canary) — each is a separate instance of your app with its own URL and settings.
Deploy to staging → test there → when ready, swap staging with production in 1 click. Zero downtime, instant.
If the new version has a bug → swap back in seconds. Instant rollback.
During swap, Azure warms up the staging slot before routing traffic — no cold starts for users.
💡 This IS blue-green deployment — production and staging coexist. Swap = instant cutover. This is why most teams use App Service for web apps.
Other powerful features
Auto-scaling — scale horizontally (more instances) based on CPU, memory, or custom metrics
Built-in Auth — add Google/Microsoft/GitHub login with zero code changes (EasyAuth)
VNet Integration — securely call resources in your private VNet (databases, internal APIs)
App Settings — inject env variables that override config — no secrets in code
Key Vault references — App Settings can pull values directly from Key Vault automatically

⚡ Compute — Section 03
Azure Functions
Write code without thinking about servers. Functions run only when triggered — HTTP request, timer, message in queue — and you pay only for the execution time. Idle costs zero.
⚡
Azure Functions — Serverless Computing
Azure Functions · Event-driven, Serverless
ServerlessEvent-DrivenPay per Exec
What is serverless (layman version)

"Serverless" doesn't mean no server exists — it means you never see or manage a server. You write a function (a piece of code), upload it, and Azure runs it on-demand. The server is there but it's invisible to you. You just write logic.

Traditional server: Running 24/7, costing money even at 3am when nobody uses it. Function: Exists only when called. At 3am nobody calls it → zero cost.

⚡ Light switch analogy: A traditional server is a lightbulb hardwired ON 24/7 — you pay electricity constantly. A Function is a motion-sensor light — it only turns on when someone walks in, turns off when they leave. Zero waste.
Trigger types (what wakes up your function)
HTTP Trigger — A web request hits your function URL → function runs → returns response. Build APIs without a server.
Timer Trigger — Runs on a cron schedule. "Every day at 2am, run this cleanup job." Like a cron job, no VM needed.
Blob Trigger — "A file was uploaded to Blob Storage → run this function." Great for image resizing, file processing.
Service Bus Trigger — A message arrives in a queue → function processes it. Decoupled message processing.
Event Grid Trigger — Something happened in Azure (VM started, RG deleted) → react to it.
CosmosDB Trigger — A record changed in CosmosDB → function syncs data to another system.
Hosting Plans — critical differences

⚠️ Cold Start Problem: On Consumption plan, if your function hasn't been called in a while, the first call takes 1-5 seconds longer as Azure wakes it up. Use Premium plan for APIs where latency matters.
Best DevOps use cases
🖼️ Image ProcessingUser uploads photo → Function resizes + watermarks → saves to Blob
📧 NotificationsOrder placed (queue message) → Function sends confirmation email
🧹 Scheduled CleanupTimer: every night, delete temp files older than 7 days from storage
🔗 WebhooksGitHub pushes code → calls your Function webhook → triggers a pipeline
📊 ETL JobsCSV uploaded → Function parses it → inserts rows into database
🔒 Key RotationTimer: monthly → Function rotates API keys in Key Vault automatically
💡 Durable Functions: For long-running workflows (multi-step processes that take hours), use Durable Functions. They orchestrate chains of function calls with state management built in.
🌐 Network — Section 04
Azure Networking Deep Dive
Without networking, nothing in Azure can talk to anything else. This section covers how resources connect, how traffic flows, and how you control it all.
🏗️
Virtual Network (VNet)
Azure Virtual Network · Foundation of all Azure networking
Core NetworkMust Know
What is a VNet?

A VNet is your own private, isolated network inside Azure. Think of it as buying a plot of land in Azure's city. You define the address space (e.g., 10.0.0.0/16 — 65,536 private IP addresses). Resources inside your VNet communicate privately. Nothing from outside can get in unless you explicitly open a door.

🏘️ Gated neighborhood analogy: A VNet is a gated community. All houses inside can visit each other freely. Outsiders (internet) can't enter unless the guard at the gate (Load Balancer/App Gateway) lets them in to specific houses.
Subnets — dividing your VNet
Subnet = a section of your VNet with its own IP range. E.g., VNet = 10.0.0.0/16, Web Subnet = 10.0.1.0/24, DB Subnet = 10.0.2.0/24.
Public Subnet — has a route to an internet gateway. Resources here can talk to the internet.
Private Subnet — NO internet route. Only internal traffic. Your database should always be here.
Best practice: 3-tier architecture — Web subnet (public) → App subnet (private) → Data subnet (most private). Traffic can only flow down, never from Data back to Web directly.
VNet Peering — connecting VNets
By default, two VNets can NOT talk to each other — even in the same subscription. VNet Peering connects them.
Same-region peering — ultra-low latency, traffic stays on Microsoft's backbone (not internet)
Global peering — peer VNets in different regions. Used for cross-region architectures.
Hub-Spoke model — one central "Hub" VNet (with shared services like firewall, DNS) and many "Spoke" VNets for each app/team, all peered to the hub.
Connecting Azure to your office
VPN Gateway — Encrypted tunnel over the public internet. Cheaper (~$30-200/month), slightly slower, max ~1.25 Gbps. Good for most companies.
ExpressRoute — Private dedicated fiber circuit from your DC to Azure. NOT via internet. Expensive ($500+/month) but consistent latency, up to 100 Gbps. Required for banks, healthcare orgs with compliance needs.
Private Endpoints — Access Azure PaaS services (like Storage, SQL) via private IP inside your VNet, so traffic never leaves Azure's network at all.
💡 Private Endpoints are powerful: Without them, your App Service talks to your SQL Database via the public internet (even though both are Azure). With Private Endpoint, traffic stays inside Azure's private backbone. More secure, faster.
⚖️
Load Balancing — Azure's 4 Options Explained
Azure Load Balancer · App Gateway · Front Door · Traffic Manager
TrafficCritical
Why 4 different load balancers? Each does a different job.
ServiceLayerScopeWhen to Use
Azure Load BalancerL4 (TCP/UDP)RegionalDistribute traffic between VMs in same region. Simple, fast, raw.
Application GatewayL7 (HTTP/S)RegionalURL-based routing, SSL termination, WAF. Smart HTTP routing within a region.
Azure Front DoorL7 (HTTP/S)GlobalGlobal CDN + LB + WAF. Route users to nearest region worldwide.
Traffic ManagerDNS-basedGlobalDNS routing across regions. Failover, geographic routing. Works with any endpoint.
Azure Load Balancer — doesn't understand HTTP. Works at raw TCP level. Imagine a dumb switch that just forwards packets to VMs evenly. Use for: non-HTTP workloads, VM clusters, database clusters.
Application Gateway — understands HTTP. Can look at the URL and decide where to send traffic. "/api/*" → API servers. "/static/*" → storage. Also has WAF to block hackers. Use for: most web apps where you need smart routing or security.
Front Door — Same as App Gateway but global. Has 200+ edge nodes worldwide. User in India → served from India PoP. User in US → served from US PoP. Much faster global experience. Also has CDN to cache static content.
Traffic Manager — works at DNS level — redirects the DNS query itself to point to the best endpoint. Used for: active-active multi-region (weighted), failover (priority), geographic compliance. Works with non-Azure endpoints too.
🛡️ Network Security — Section 05
NSG, Firewall & DDoS
Controlling who can talk to what is the foundation of cloud security. NSGs, Azure Firewall, and DDoS protection are your three lines of defense.
🛡️
Network Security Groups (NSG)
Azure NSG · Stateful packet filtering for subnets and NICs
SecurityMust Know
What is an NSG?

An NSG is a list of firewall rules attached to a subnet or a VM's network interface. Each rule says: allow or deny traffic based on source IP, destination IP, port, and protocol. Rules are evaluated by priority (lower number = checked first). Last rule is always "deny everything else."

🚪 Bouncer analogy: NSG is a bouncer at a club with a very specific checklist. Rule 100: "Port 443 from anywhere — LET IN." Rule 200: "Port 3389 from my office IP only — LET IN." Rule 65000: "Everything else — DENY." The bouncer checks the list top to bottom and acts on the first matching rule.
Inbound vs Outbound rules
Inbound rules control traffic coming INTO your resource. By default: Azure denies all inbound from internet, allows inbound from within VNet.
Outbound rules control traffic going OUT from your resource. By default: allows all outbound (your VM can reach the internet).
Service Tags — instead of hard-coding IPs, use named groups like "Internet", "AzureCloud", "AzureLoadBalancer". Microsoft maintains these lists automatically.
Apply NSG at subnet level (not just VM NIC) — protects ALL VMs in subnet. Defence-in-depth = NSG on subnet AND NIC.
Azure Firewall vs NSG — what's the difference?
FeatureNSGAzure Firewall
TypeL3/L4 packet filterFull stateful firewall
FQDN filtering❌ IP only✅ domain names
Threat intelligence❌ None✅ Microsoft feed
Central managementPer-subnetOne FW for all VNets

Use NSG for: denying specific ports, allowing specific IPs — simple and free.
Use Azure Firewall for: enterprise hub-spoke, FQDN-based rules (allow *.microsoft.com), threat intel blocking, centralized logging of ALL network traffic.
DDoS Protection
Basic DDoS — free, always on. Protects Azure infrastructure from volumetric attacks.
Network DDoS (Standard) — ~$2,500/month. Adaptive tuning specific to YOUR traffic patterns. Attacks your VMs specifically get detected and mitigated. Cost reimbursement during attacks. Use for public-facing critical workloads.
⚠️ Don't mix up: NSG blocks malicious ports/IPs (firewall rules). DDoS protection handles volumetric attacks (100Gbps floods). You need both for full protection — they solve different problems.
💾 Storage — Section 06
Azure Storage — All Types Explained
Azure has 5 different storage types. Each solves a different problem. Understanding which to use when is a core DevOps skill. Pick the wrong one and you either overpay or get bad performance.
🗂️
Azure Blob Storage
Azure Blob Storage · Object/File Storage for Everything
Most UsedObject StoreDevOps Essential
What is Blob Storage?

Blob = "Binary Large Object." It's Azure's object store — store ANY file (images, videos, PDFs, backups, logs, pipeline artifacts, Terraform state files) at virtually unlimited scale. Each file gets a URL. Access from anywhere. Costs pennies per GB per month.

🪣 Bucket analogy: A Blob container is like a bucket. You throw files into it. Each file gets a URL like https://myaccount.blob.core.windows.net/my-bucket/my-file.jpg. Anyone with the right permission can access it via that URL from anywhere on earth.
The 3 Access Tiers (save money by choosing right)
Hot — data accessed frequently. Higher storage cost ($0.018/GB), lower access cost. For: website images, active app data, pipeline artifacts.
Cool — data accessed less than once/month. Lower storage cost ($0.01/GB), higher access cost. For: monthly reports, older logs. Minimum 30-day retention.
Archive — almost never accessed. Cheapest storage ($0.001/GB). BUT — retrieval takes hours (rehydrate first). For: compliance archives, disaster recovery backups, data you're legally required to keep but never look at.
💡 Lifecycle Management: Automatically move blobs between tiers based on age. "After 30 days → move to Cool. After 180 days → move to Archive. After 365 days → delete." Set it once, saves money automatically.
Security features
Access Levels: Private (only authenticated), Blob (public read), Container (fully public). ALWAYS start with Private.
Shared Access Signatures (SAS) — time-limited, permission-limited URL. "Here's a URL valid for 1 hour that lets you upload exactly one file to exactly this container." Great for giving temporary access without exposing your storage key.
Managed Identity — let your App Service/AKS access Blob without any keys. Zero credentials in code.
Encryption — ALL data encrypted at rest (AES-256) and in transit (HTTPS). Always on, no config needed.
Soft delete — deleted files kept for 7-30 days. Accidental deletion? Restore with one click.
Versioning — every change to a blob creates a new version. Roll back to any previous version.
DevOps use cases
🔧 Terraform StateStore tfstate remotely with state locking — never corrupt state again
📦 Build ArtifactsStore compiled binaries, Docker images (via ACR), release packages
📋 Pipeline LogsArchive CI/CD logs for debugging and compliance auditing
⚙️ App ConfigStore config files fetched at app startup (appsettings.json)
💿

Azure Files — need to mount as a drive (like Z:\)? Use Azure Files. Legacy apps expecting a file share path work out of the box. Multiple VMs can mount the same share simultaneously — great for shared config, certificates, or app content that multiple instances need to read.

🪪 Identity — Section 07
Identity, RBAC & Managed Identity
Security starts with identity. Who is this person? What are they allowed to do? These questions are answered by Azure Entra ID and RBAC. Get these wrong and either nothing works or everything is wide open.
🪪
Microsoft Entra ID (formerly Azure AD)
Entra ID · Cloud Identity Provider · The Gatekeeper
Core IAMMust Know
What is Entra ID (in simple terms)?

Entra ID is Azure's identity and access management (IAM) service. It's the system that knows: who are your users, what groups are they in, and which apps and resources are they allowed to use. Every login to Azure Portal, every API call, every "does this user have permission?" question goes through Entra ID.

Important difference from on-prem Active Directory: Azure AD/Entra ID is cloud-native, uses HTTPS, works with web protocols (OAuth2, OIDC, SAML). Old on-prem AD uses LDAP/Kerberos for PCs on a corporate network. They're related but different.

🏢 HR + Security desk analogy: Entra ID is your company's HR database + security reception combined. HR knows who you are and what team you're on. Security reception issues your badge and knows which doors your badge opens. When you swipe your badge → security calls HR → checks if your badge should work here → lets you in or not.
Key concepts in Entra ID
Tenant — your company's dedicated instance of Entra ID. Isolated from other companies. yourdomain.onmicrosoft.com
Users — individual people. Can be "Member" (internal employee) or "Guest" (external collaborator added via B2B)
Groups — collections of users. Assign permissions to groups, not individual users. "DevOps-Team" group gets Contributor on subscription.
Service Principals — identities for applications. Like a user but for a program. Your pipeline "logs in" to Azure using a service principal.
App Registrations — register an app so it can authenticate with Entra ID. Used for custom apps needing Azure access.
🌟 Managed Identity — The DevOps Game Changer

Managed Identity solves the question: "How does my App Service access Key Vault without storing credentials anywhere?" You assign a Managed Identity to your Azure resource (VM, App Service, Function, AKS pod). Azure generates and manages a secret credential automatically. The resource uses this identity to authenticate to other Azure services. You never see, store, or rotate the credential.

System-assigned — identity tied to the resource's lifecycle. Delete the resource → identity deleted too. 1:1 relationship.
User-assigned — standalone identity you create separately and can attach to MULTIPLE resources. Useful when 5 App Services all need the same DB access — assign one identity to all 5.
💡 Golden Rule: If code needs to access an Azure service (Storage, Key Vault, SQL), use Managed Identity. Zero credentials in code = zero credential leaks. This is the modern way. Any other approach (connection string in code) is bad practice.
RBAC — Role-Based Access Control
What it does: RBAC defines WHAT actions a user/group/service principal can perform on WHICH Azure resources.
Role = a named set of permissions. "Virtual Machine Contributor" = can create/delete VMs but NOT manage access.
Scope = where the role applies: Management Group, Subscription, Resource Group, or single Resource. Assign high = broad access. Assign low = narrow access. Always assign at the lowest scope needed.
Built-in RoleWhat they can doCan manage access?

⚠️ Principle of Least Privilege: Never give Owner when Contributor suffices. Never give Contributor when Reader works. Limit blast radius of compromised accounts.
🔐 Security — Section 08
Azure Key Vault
Secrets in code = security disaster waiting to happen. Key Vault is where ALL secrets, certificates, and encryption keys live. Apps fetch them at runtime. No hardcoding, no leaks.
🔐
Azure Key Vault — Complete Guide
Secrets · Certificates · Keys · Managed HSM
Secrets MgmtNon-negotiable
What are Secrets, Keys, and Certificates?
Secrets — any sensitive string value: database passwords, API keys, OAuth client secrets, connection strings. You name it "db-password" and store "P@ssw0rd123!". Your app calls Key Vault at startup and gets the value.
Keys — cryptographic keys for encryption/decryption and signing. Can be software-protected or HSM-protected (Hardware Security Module — a physical device that never exports the raw key). Used for "customer-managed keys" so YOU control encryption of your Azure storage/SQL.
Certificates — TLS/SSL certificates for HTTPS. Key Vault can auto-renew from Let's Encrypt or DigiCert before expiry. No more 3am "your cert expired" panic.
🏦 Bank vault with cameras: Your app shows its ID badge (Managed Identity), asks for "db-password", vault clerk verifies the badge is authorized, hands over the password. The transaction is logged (who accessed what, when). The actual password never travels insecurely — HTTPS only. The raw key material never leaves the vault.
How apps access Key Vault (the right way)
App starts
→

→

→

→

→

Key Vault Access Control
Key Vault RBAC (recommended) — Use Azure RBAC roles like "Key Vault Secrets User" (read secrets) or "Key Vault Secrets Officer" (manage secrets). Standard Azure RBAC model.
Access Policies (legacy) — older model where you explicitly grant each identity specific permissions (get, list, set, delete) per secret/key/cert. More complex, being deprecated in favor of RBAC.
Firewall/Private Endpoint — restrict Key Vault to only be accessible from your VNet IPs. No public internet access at all.
App Service Integration — Magic ✨
In App Service settings, set an App Setting value to: @Microsoft.KeyVault(SecretUri=https://myvault.vault.azure.net/secrets/db-password/)
App Service automatically fetches the secret at startup. Your app sees it as a normal environment variable. Zero code changes. Zero credentials stored anywhere visible.
If secret rotated in Key Vault → App Service picks up new value on next restart automatically.
Versioning & Soft Delete
Versioning — every update to a secret creates a new version. You can reference a specific version or always get "current". For certificates, old versions kept until you explicitly delete.
Soft delete — deleted secrets/keys recoverable for 90 days. Purge protection prevents even permanent deletion for 7-90 days. Protects against accidental or malicious deletion.
Full audit log — every access, every change, every failed attempt logged to Azure Monitor. Who accessed the database password at 3am? You can find out.
⚠️ Never do this: DB_PASSWORD=MySecret123 in a Dockerfile, .env file committed to Git, or hardcoded in source code. One public repo exposure = immediate breach. Use Key Vault. Always.

Containers, ACR & AKS

Docker & Containers — The Foundation
Container concepts every DevOps engineer must know
FoundationMust Master
What is a container (simple version)

A container is a lightweight, portable package that contains your app + its runtime + its libraries + its config — everything it needs to run. Unlike a VM, containers share the host OS kernel — they're much lighter (starts in seconds, uses MB not GB of RAM).

The "works on my machine" problem: Dev runs app on Python 3.9 with specific package versions. Production runs Python 3.7. App breaks. With Docker: same container image runs identically on dev laptop, CI server, staging, production. Guaranteed same environment everywhere.

📦 Shipping container analogy: Before shipping containers, loading a ship took weeks — every cargo item was different shape, needed different handling. Shipping containers standardized everything — same box, any ship, any port. Docker did the same for software — same image, any machine, any cloud.
Docker key concepts
Dockerfile — text file with instructions to build your image. FROM (base), RUN (install), COPY (add your code), EXPOSE (port), CMD (start command).
Image — built result of a Dockerfile. Read-only blueprint. Like a cookie cutter. Store in a registry.
Container — a running instance of an image. Like a cookie made from the cutter. Ephemeral — kill it, data gone (unless you use volumes).
Registry — where images are stored. Docker Hub (public), Azure Container Registry (private).
Layers — each Dockerfile instruction creates a layer. Layers are cached — unchanged layers not rebuilt. Always put things that change least (base image, apt installs) first for fastest builds.
Azure Container Registry (ACR)
Private Docker Hub — your company's own registry. Only people/services you authorize can push or pull images.
Geo-replication — replicate images to multiple Azure regions. AKS in East US pulls from nearby East US registry. AKS in Europe pulls from European copy. Faster pulls = faster pod startups.
Vulnerability scanning — Microsoft Defender scans every image for known CVEs. "This base image has 14 critical vulnerabilities" → fix before deploying.
ACR Tasks — build Docker images IN Azure (no local Docker needed). Trigger builds on git push. Rebuild automatically when base image is updated.
Retention policies — auto-delete old image tags. Keep only last 5 versions. Saves storage costs.
💡 AKS + ACR integration: Attach ACR to AKS cluster in one command. AKS nodes automatically get permission to pull from your ACR using Managed Identity. No registry credentials needed in Kubernetes secrets.

Kubernetes & AKS — Deep Dive
AKS · Managed Kubernetes · The Container Orchestrator
K8sCareer Critical
Why Kubernetes? What problem does it solve?

You have 50 containers to run across 10 VMs. Which container goes on which VM? What if a VM dies — how do you restart containers? How do you update them without downtime? How do containers discover each other? How do you scale from 2 to 20 copies of a container when traffic spikes? Kubernetes (K8s) solves all of this. It's the operating system for your container cluster.

🏙️ City management analogy: Kubernetes is a smart city manager. Your containers are citizens needing apartments (resources). K8s finds empty apartments (nodes with capacity), assigns citizens, monitors their health, and if an apartment building collapses (node fails), immediately moves citizens to other buildings. Citizens (containers) just say "I need 0.5 CPU and 256MB RAM" — K8s handles placement.
Kubernetes Objects — the vocabulary
Pod — smallest deployable unit. Usually 1 container (sometimes 2 with a sidecar). Pods are mortal — they can die and be replaced. Each gets a private IP.
Deployment — declares desired state: "I want 3 replicas of my-app:v2.1". K8s constantly reconciles actual state to match desired state. Pod dies → K8s starts a new one.
Service — stable virtual IP + DNS name that load balances across pod replicas. Pods change IPs when restarted, but the Service IP never changes. "How do I find my API pods?" → Use the Service, not pod IPs.
Ingress — HTTP/HTTPS routing for external traffic into the cluster. Route /api → API service, /web → frontend service. Often backed by NGINX or Azure App Gateway.
ConfigMap — non-secret configuration (feature flags, URLs). Mounted as env vars or files in pods.
Secret — sensitive config (passwords). Base64 encoded (NOT encrypted by default!). Better: use Azure Key Vault with CSI driver to sync secrets as K8s secrets automatically.
PersistentVolumeClaim (PVC) — request for storage. Azure creates a Managed Disk or Azure Files share and attaches it to your pod. Data survives pod restarts.
HorizontalPodAutoscaler (HPA) — automatically scales replica count based on CPU/memory/custom metrics. The Kubernetes equivalent of VMSS scaling rules.
AKS specifically — Azure extras on top of K8s
Managed Control Plane — FREE — the K8s master (API server, etcd, scheduler, controller manager) is managed and paid for by Microsoft. You pay ZERO for the control plane. You only pay for worker nodes.
Node Pools — groups of VMs with the same spec. Default pool (general). Add a GPU pool for ML workloads. Add a high-memory pool for cache services. Scale each pool independently.
Cluster Autoscaler — automatically adds/removes nodes based on pod scheduling pressure. "Pods can't fit on existing nodes → add a node. Nodes sitting idle → remove them." Cost optimization on autopilot.
Azure Key Vault Provider for Secrets Store CSI Driver — sync Key Vault secrets into pods as files/env vars. The K8s-native way to use Key Vault without code changes.
Azure CNI networking — pods get IPs from your VNet subnet. Pods are directly accessible within VNet. Required for integration with other Azure services.
Workload Identity — assign Managed Identities to Kubernetes pods. Pod authenticates to Azure services (like storage, Key Vault) without any credentials. K8s version of Managed Identity.
Helm — the package manager for K8s
Helm charts package K8s YAML configs into reusable, versioned templates. helm install my-app ./chart --set image.tag=v2.1
Like npm for Node.js or apt for Ubuntu, but for Kubernetes applications. Install NGINX ingress: helm install ingress-nginx ingress-nginx/ingress-nginx
helm upgrade --rollback — upgrade and if broken, rollback in one command. K8s deployment history preserved.
⚠️ K8s Secrets are NOT encrypted by default! Base64 is encoding, not encryption. Anyone with kubectl get secret can decode it. For real security: enable etcd encryption at rest (AKS supports this) AND use Key Vault CSI driver to avoid storing secrets in K8s at all.

IaC Tools Compared — Bicep vs Terraform vs ARM
Choose the right tool for your Azure IaC
IaCCareer Essential
ARM Templates — the native, the verbose
What it is: Azure's native IaC format. JSON files that describe Azure resources. The Azure portal generates ARM JSON under the hood for everything you click-deploy.
Idempotent: Run same template twice → same result. Azure compares desired state to actual state and only makes necessary changes.
Downside: 200 lines of JSON for a simple storage account. Hard to read. Hard to debug. Complex expressions using ARM functions look like: [concat(parameters('prefix'), uniqueString(resourceGroup().id))]
Use when: you find a pre-built ARM template that does exactly what you need (Azure quickstart templates gallery). Don't write ARM from scratch in 2024 — use Bicep.
Bicep — ARM but human-friendly
What it is: Microsoft's domain-specific language (DSL) that compiles to ARM JSON. Write cleaner code, Azure transpiles it to JSON behind the scenes.
Same 200-line ARM = ~40 lines of Bicep. Huge readability improvement. IntelliSense in VS Code tells you every valid property and its type.
Modules — split Bicep into reusable files. module storage './storage.bicep' = { name: 'myStorage', params: {...} }
Azure-only. All Azure features available day-1 (ARM feature parity). Microsoft's recommended choice for pure Azure environments.
Deploy: az deployment group create --template-file main.bicep --parameters @params.json
Terraform — the industry standard
What it is: Open-source, cloud-agnostic IaC tool. Write HCL (HashiCorp Configuration Language). Works with 3000+ providers: Azure, AWS, GCP, GitHub, Kubernetes, Datadog, PagerDuty, etc.
State file — Terraform maintains a state file tracking what exists. It compares state to code to determine changes. Store state in Azure Blob Storage with state locking (via blob leases) — never run terraform from two places simultaneously.
terraform init — download providers. terraform plan — dry run, shows changes WITHOUT applying. terraform apply — apply changes. terraform destroy — delete everything in state.
terraform plan is your safety net — always run plan in CI, have a human review it before apply in CD. "Will destroy 1 resource" in the plan → someone reviews before it's executed.
Modules — reusable Terraform packages. Community modules on Terraform Registry (like npm for Terraform). Module for Azure AKS, Azure SQL, etc — battle-tested configs.
Multi-cloud advantage — if your company uses Azure + AWS, one team, one tool. Skills transfer between jobs.
Ansible — configuring what Terraform built
Terraform provisions infra (VMs, networks, storage). Ansible configures it (installs Nginx, sets config files, deploys app). These are complementary, not competing.
Agentless — Ansible connects to VMs via SSH/WinRM. No agent installed on target. Just Python on the target.
Playbooks — YAML files describing tasks to run. Idempotent — run 10 times → same result. "Install Nginx" checks if already installed before installing.
Roles — reusable Ansible packages. "nginx role" sets up a production Nginx. Use community roles from Ansible Galaxy.
💡 Career advice: Learn Terraform first. It's the most in-demand IaC tool and Azure knowledge transfers directly. For Azure-only shops, add Bicep knowledge. For VM configuration management, add Ansible. This trio covers 95% of IaC interview questions.

🔄 Reliability — Section 15
HA & Disaster Recovery
High Availability (HA) = system keeps running despite individual component failures. Disaster Recovery (DR) = system recovers after a catastrophic event. Design for failure — in distributed systems, everything will eventually fail. The question is: does the user notice?
🔄
SLA, RTO, RPO — The Three Numbers That Matter
Understanding Azure's reliability guarantees
Critical Concepts
SLA (Service Level Agreement) — Microsoft's guarantee of uptime. 99.9% SLA = max 8.7 hours downtime/year. 99.99% = max 52 minutes/year. 99.999% = max 5 minutes/year. You get service credits if Azure violates the SLA. BUT — your SLA is the PRODUCT of all service SLAs in your chain. VM (99.9%) × SQL (99.99%) × Storage (99.9%) = 99.79% effective SLA. Use availability zones and redundancy to improve.
RTO (Recovery Time Objective) — how fast must we recover after a disaster? "Our business can tolerate maximum 2 hours of downtime." This drives architecture choices — cheaper recovery but slower vs. expensive but instant failover.
RPO (Recovery Point Objective) — how much data can we afford to lose? "Maximum 1 hour of data loss is acceptable." This drives backup frequency and replication choices. RPO=0 = zero data loss = requires synchronous replication = expensive. RPO=24h = daily backups = cheap.
Availability Zones — spread VMs/services across 3 physically separate data centers in one region. SLA jumps from 99.9% (single VM) to 99.99% (multi-zone). Cost: you pay for multiple VMs but get much stronger HA guarantee. Must-have for any production workload.
Region Pairs — Azure pairs every region with another (East US ↔ West US 2, North Europe ↔ West Europe). Paired regions are updated separately. If Microsoft rolls out an update that breaks things, it breaks one region before hitting the paired one. DR: replicate to your paired region. Azure restores paired regions first after major incidents.
Azure Site Recovery (ASR) — continuously replicates VMs from primary to secondary region (or Azure to Azure, on-prem to Azure). Failover = VMs start up in secondary region. RPO: typically 30 seconds for VM replication. RTO: 15-30 minutes for failover to complete. Use "test failover" regularly to ensure DR actually works — don't find out it's broken during a real disaster.
Azure Backup — simple backup service for VMs, SQL databases, file shares, Kubernetes (AKS) configurations. Stores in Recovery Services Vault. Immutable backup option: even admins can't delete backups during retention period — protection against ransomware.
🛡️ Three-layer defense: Availability Zones = protection against data center failure (power outage in one building). Region Pairs = protection against region failure (natural disaster, major outage). Global distribution (Traffic Manager/Front Door) = protection against full regional failure, serving users from multiple regions simultaneously.
💡 The chaos engineering mindset: Don't assume your HA setup works — test it. Run "game days" where you deliberately shut down services to see if failover works. Azure Chaos Studio lets you inject faults (kill a VM, add network latency, shut down a node) in a controlled way to validate your resilience.

Azure Cost Management — Full Guide
Visibility · Control · Optimization · Tagging · Reservations
FinOpsBusiness Impact
Step 1: Visibility — understand where money goes
Azure Cost Analysis — in the portal, break down costs by service, resource group, tag, location, or time. "Show me this month's spend grouped by ResourceGroup" — instantly see what's expensive.
Cost Forecast — ML predicts end-of-month spend based on current usage trend. "You're on track for $8,400 by month end, budget is $8,000." Warning before you exceed.

Step 2: Control — stop runaway costs
Budgets with alerts — set a monthly budget. Get email at 80% actual, 90% forecasted, 100% actual. For dev/test environments, trigger an Action Group at 100% that automatically shuts down VMs.
Auto-shutdown — for dev VMs, schedule auto-shutdown at 7pm, auto-start at 8am. A $200/month VM costs $67/month if it runs only work hours (8 of 24 hrs). 66% saving on dev infra.
Azure Policy — prevent expensive resources from being created without approval. Policy: "Deny creation of VMs larger than Standard_D8s_v3." Policy: "All resources must have an 'Owner' tag or creation is denied." Governance before the fact, not after.
Step 3: Optimize — cut the bill significantly
Reserved Instances (1 or 3 year) — commit to using a VM size in a region for 1-3 years. Up to 72% discount vs pay-as-you-go. Best for production workloads that run 24/7 365 days a year. Instance flexibility — some reservations apply to whole VM family (D-series), not just one specific size.
Savings Plans — newer, more flexible than reservations. Commit to $X/hour of compute spend for 1-3 years. Azure applies discount to whatever compute you use (any VM size, any region, App Service, ACI, Functions). Up to 65% saving. Good if your workload mix changes.
Spot VMs — up to 90% discount on unused Azure capacity. Tradeoff: Azure can evict with 30-second notice when capacity is needed. Only for: batch processing, CI/CD agents, stateless workers, fault-tolerant workloads. Never for databases or anything stateful.
Right-sizing — most companies over-provision. 80% CPU during peak but 10% rest of the time? Use VMSS to scale in. Azure Advisor specifically flags underutilized resources.
Dev/Test pricing — Azure offers 40-55% discounts on Windows VMs if the subscription is flagged as Dev/Test. No Windows license charge. Only for non-production workloads (licensing restriction).
Azure Hybrid Benefit — already have Windows Server or SQL Server licenses with Software Assurance? Apply them to Azure VMs — saves up to 85% on Windows VM cost. Huge saving for companies migrating from on-prem.
💡 FinOps culture: Cost optimization isn't just a platform team job. Developers make architectural decisions that hugely impact cost. "Should we use CosmosDB or SQL?" has major cost implications. Tag resources so teams see their OWN costs. Accountability drives optimization.
⚠️ Forgotten costs that add up: Unattached managed disks (VMs deleted but disk left behind), unattached public IPs, over-provisioned App Service plans with unused capacity, old snapshots never deleted, AKS nodes running at 5% — right-size or scale to zero.
