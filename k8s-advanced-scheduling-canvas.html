📌 FOUNDATIONS
The Kubernetes scheduler is the brain that decides which node each pod lives on. We'll explore how to control that brain using taints, tolerations, and affinity rules. Control placement = control cost, performance, and resilience.
Core Concept

K8s Scheduler Overview

🎯 What Is It?
The scheduler is a controller that watches for newly created pods and assigns them to nodes. It's like a hotel receptionist deciding which room to give each guest based on room features (amenities), guest preferences (allergies, view type), and room availability.
1. Pod Created: You submit pod manifest (kubectl apply)
2. Scheduler Watches: kube-scheduler watches for unscheduled pods (status.nodeName is empty)
3. Filtering: Remove nodes that DON'T match pod requirements (taints, affinity, node selectors)
4. Scoring: Rank remaining nodes (balance, resource usage, zone spread)
5. Binding: Assign pod to highest-scored node
6. Kubelet Takes Over: Node's kubelet pulls image and starts containers
✅ Requests/Limits: Resource requirements (CPU, memory)
✅ Taints/Tolerations: Node access restrictions
✅ Node Affinity: Which nodes to prefer/require
✅ Pod Affinity: Co-locate with other pods
✅ Pod Anti-Affinity: Spread pods across nodes/zones
✅ Node Selectors: Simple key=value matching
✅ Priority: PriorityClass (important pods get scheduled first)
Default plugins: PreFilter, Filter, PostFilter, Score, Reserve, Permit, PreBind, Bind, PostBind
Can be extended or replaced with custom schedulers
Multiple schedulers possible (scheduler-name in pod spec)

Pod Placement Lifecycle

🔄 The Journey
A pod goes through multiple states. Understanding the lifecycle helps debug "why isn't my pod running?" issues.
Pending: Scheduler hasn't assigned to node yet. Check: taints, affinity, resource availability
ContainerCreating: Node accepted, pulling image, starting container. Check: image size, pull errors
Running: Container is alive. Liveness/Readiness probes may still fail
CrashLoopBackOff: Container exits, kubelet restarts. Check: app logs, entry point
Evicted: Node ran out of resources. Pod killed to free resources. Check: node capacity
kubectl get pods -o wide # Shows: READY, STATUS, RESTARTS, NODE kubectl describe pod # Shows: Events (scheduling, errors), Conditions, Container states kubectl logs # App logs (requires container running) kubectl logs --previous # Logs from crashed container kubectl explain pod.spec.affinity # Affinity/tolerance format reference
🚫 Pending: Taints blocking, no nodes available, resource contention
🚫 ImagePullBackOff: Wrong image name, registry auth failed, image doesn't exist
🚫 CrashLoopBackOff: App exits immediately, wrong CMD, missing dependencies
🚫 NotReady: Liveness probe failing, readiness probe failing, network issues
🔐 TAINTS & TOLERATIONS
Taints are "don'ts" — node says "don't put pods on me unless they tolerate this." Tolerations are "can's" — pod says "I can tolerate that taint." Perfect for dedicated hardware, special workloads (GPUs, databases), node maintenance.
Node Feature

Taints Explained

🏷️ What Is It?
A taint is a marker on a node saying "only pods that tolerate this can live here." Think: "This room has dog hair everywhere — only dog-tolerant guests can stay."
Format: key=value:effect
Example: gpu=true:NoSchedule
Key: Any string (gpu, database, maintenance)
Value: Any string (true, dedicated, v1)
Effect: What happens to non-tolerating pods
NoSchedule: Don't schedule new pods (existing pods ok)
NoExecute: Don't schedule NEW + EVICT existing pods
PreferNoSchedule: Try not to, but ok if must
# Add taint to node kubectl taint nodes node1 gpu=true:NoSchedule # Add with value kubectl taint nodes node2 workload=database:NoExecute # Remove taint (dash at end) kubectl taint nodes node1 gpu=true:NoSchedule- # View taints kubectl describe node node1 | grep Taint
✅ Pros: Powerful resource isolation, simple syntax
❌ Cons: Requires explicit tolerations (not automatic), can trap pods if misconfigured
💰 Cost: Free, but helps prevent expensive misplacement
Pod Feature

Tolerations Explained

✅ What Is It?
Tolerations are on pods. "I can handle this taint" means the scheduler is allowed to place you on tainted nodes. Like saying "I'm ok with dog hair."
Structure: spec.tolerations[]
Key: Match taint key (or empty = all)
Operator: Equal (=) or Exists
Value: Match taint value (required if Equal)
Effect: Match taint effect (NoSchedule, NoExecute, PreferNoSchedule, or empty = all)
TolerationSeconds: Grace period before eviction (NoExecute only)
# Match exact taint: gpu=true:NoSchedule tolerations: - key: gpu operator: Equal value: "true" effect: NoSchedule # Tolerate ANY value of "gpu" key tolerations: - key: gpu operator: Exists effect: NoSchedule # Tolerate ANY taint tolerations: - operator: Exists # NoExecute with grace period tolerations: - key: workload operator: Equal value: maintenance effect: NoExecute tolerationSeconds: 3600 # 1 hour before eviction
TaintTolerationScheduled?
gpu=true:NoScheduleNo toleration❌ No
gpu=true:NoSchedulegpu=true, Equal✅ Yes
gpu=true:NoSchedulegpu (Exists)✅ Yes
gpu=true:NoScheduleworkload=db❌ No (different key)
workload=db:NoExecuteworkload (Exists), 300s✅ Yes (3min grace)
Real World

Common Taint Scenarios

🎭 When To Use
Taints shine in specific situations. Let's walk through them with examples and YAML.
🎮 Scenario: GPU Workloads
You have 3 nodes: 2x CPU, 1x GPU. Only ML apps should use GPU.
# Add taint to GPU node kubectl taint nodes gpu-node-1 gpu=nvidia:NoSchedule # Pod that needs GPU (add toleration) spec: containers: - name: ml-app resources: limits: nvidia.com/gpu: 1 tolerations: - key: gpu operator: Equal value: nvidia effect: NoSchedule # PLUS nodeAffinity to actually use GPU affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: accelerator operator: In values: - nvidia-tesla-v100
Pros: GPU won't be wasted on regular pods, cost-effective
Cons: Must add toleration + affinity to every ML pod
🗄️ Scenario: Dedicated Database Nodes
Database pods (stateful, high-performance) need dedicated hardware. Prevent noisy neighbors.
# Taint database node kubectl taint nodes db-node-1 workload=database:NoSchedule # Database Pod (Postgres) spec: containers: - name: postgres image: postgres:15 tolerations: - key: workload operator: Equal value: database effect: NoSchedule # Optional: ensure it stays there affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: node-type operator: In values: - database-dedicated # Regular app (NO toleration, won't schedule here) # Won't be placed on db-node-1
Pros: Database isolation, predictable performance
Cons: Wasted capacity if database pod is small
🔧 Scenario: Node Maintenance
Need to update node OS, but don't want to forcefully kill pods. Use NoExecute taint with grace period.
# Prepare for maintenance (graceful drain) kubectl taint nodes node-1 maintenance=true:NoExecute:3600 # Pods get 1 hour to gracefully shut down # Pod with toleration (can stay during maintenance) spec: containers: - name: controller tolerations: - key: maintenance operator: Equal value: "true" effect: NoExecute tolerationSeconds: 7200 # 2 hours # Regular pod: gets evicted after 1 hour, reschedules to other node # After maintenance, remove taint kubectl taint nodes node-1 maintenance=true:NoExecute-
Pros: Graceful shutdown, no service interruption
Cons: Requires monitoring, can block drain if pod doesn't shut down
📍 NODE AFFINITY
Node affinity is "I want to run on nodes that look like X." It's more powerful than node selectors. Required = must match. Preferred = try to match, but not required.
Pod Placement

Required Node Affinity

🎯 Hard Constraint
"I MUST run on a node matching these labels." If no node matches, pod stays Pending forever. Like saying "I only go to 4-star hotels."
# Required: pod won't schedule without matching node affinity: nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: zone operator: In values: - us-west-1a - us-west-1b - key: instance-type operator: In values: - t3.large - t3.xlarge
requiredDuringSchedulingIgnoredDuringExecution: Required during scheduling, ignored if node label changes later
nodeSelectorTerms: Array of OR conditions (pod matches ANY term)
matchExpressions: Array of AND conditions (must match ALL within a term)
OperatorMeaningExample
InValue in listzone In [us-east-1a, us-east-1b]
NotInValue not in listzone NotIn [eu-west-1a]
ExistsKey exists (any value)gpu-capable Exists (true or false ok)
DoesNotExistKey doesn't existmaintenance DoesNotExist
GtGreater thancpu-cores Gt [8]
LtLess thanprice-per-hour Lt [0.50]
Use Case 1: Zone-Specific App
# App must run in us-west zone (not us-east) nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: topology.kubernetes.io/zone operator: In values: - us-west-1a - us-west-1b
Use Case 2: Specific Hardware
# Only on large instances with SSD nodeAffinity: requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: node.kubernetes.io/instance-type operator: In values: - t3.large - t3.xlarge - i3.large # Has local NVMe SSD - key: storage operator: In values: - ssd
Soft Constraint

Preferred Node Affinity

🎪 Soft Preference
"I'd prefer to run on nodes matching these labels, but if no match, I'll take any node." Like saying "I prefer 4-star hotels, but 3-star is ok."
# Preferred: pod will schedule even if NO match affinity: nodeAffinity: preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - key: zone operator: In values: - us-west-1a - weight: 50 preference: matchExpressions: - key: instance-type operator: In values: - t3.large
weight: 1-100, higher = more preferred
preference: Label matching (same as required above)
Scheduler sums weights of matching preferences, picks highest-scoring node
Scoring Example
3 nodes available:
Node A: zone=us-west-1a, type=t3.large Match: zone (weight 100) + type (weight 50) = 150 points Node B: zone=us-west-1a, type=t3.small Match: zone (weight 100) = 100 points Node C: zone=us-east-1a, type=t3.xlarge Match: nothing = 0 points Scheduler picks: Node A (150 points)
Example: Try to Stay in Specific Zone
# Web app: prefer same zone as database affinity: nodeAffinity: preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - key: topology.kubernetes.io/zone operator: In values: - us-west-1a # Same zone as DB - weight: 10 preference: matchExpressions: - key: topology.kubernetes.io/region operator: In values: - us-west-1 # Same region fallback
Example: Prefer Cheaper Instances
# Use cheaper instances when possible affinity: nodeAffinity: preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - key: node.kubernetes.io/instance-type operator: In values: - t3.micro - t3.small - weight: 50 preference: matchExpressions: - key: capacity.spot operator: In values: - "true" # Spot instances (cheaper)

Node Affinity Patterns

⚡ Combination Strategies
Combine required + preferred, use negative constraints (NotIn), handle multiple zones/regions.
Pattern: Mandatory Zone + Preferred Type
# MUST be in us-west-1, PREFER large instance affinity: nodeAffinity: # Required (hard constraint) requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: topology.kubernetes.io/region operator: In values: - us-west-1 # Preferred (soft constraint) preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 preference: matchExpressions: - key: node.kubernetes.io/instance-type operator: In values: - t3.large - t3.xlarge
Pattern: Exclude Bad Nodes

Pattern: Multi-Region Failover
# Primary region required, but fallback to secondary if needed affinity: nodeAffinity: # Option 1: Primary region us-west # Option 2: Secondary region us-east (fallback) requiredDuringSchedulingIgnoredDuringExecution: nodeSelectorTerms: - matchExpressions: - key: topology.kubernetes.io/region operator: In values: - us-west-1 # Primary - matchExpressions: - key: topology.kubernetes.io/region operator: In values: - us-east-1 # Fallback (different term = OR)
👥 POD AFFINITY & ANTI-AFFINITY
Pod affinity says "run me near this other pod." Pod anti-affinity says "run me AWAY from this pod." Essential for HA, data locality, and resource sharing patterns.
Co-Location

Pod Affinity

🤝 Co-Location
"I want to run on the same node/zone as this other pod." Use case: web app near cache, app near database for low latency.
# MUST be on same node as app=cache pod affinity: podAffinity: requiredDuringSchedulingIgnoredDuringExecution: - labelSelector: matchExpressions: - key: app operator: In values: - cache topologyKey: kubernetes.io/hostname # Same node (hostname) # Pod will be Pending if no node has cache pod
labelSelector: Which pods to co-locate with (match labels)
topologyKey: Scope of "co-location" (node, zone, region)
namespaces: Optional, which namespace to look for matching pods
# TRY to be on same node as database affinity: podAffinity: preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 podAffinityTerm: labelSelector: matchExpressions: - key: app operator: In values: - postgres topologyKey: kubernetes.io/hostname # Same node - weight: 50 podAffinityTerm: labelSelector: matchExpressions: - key: app operator: In values: - postgres topologyKey: topology.kubernetes.io/zone # Same zone
Topology KeyScopeUse Case
kubernetes.io/hostnameSingle NodeUltra-low latency (same machine)
topology.kubernetes.io/zoneAvailability ZoneLow latency + some redundancy
topology.kubernetes.io/regionRegionSame geographic region
kubernetes.io/osOS TypeLinux-only pods, Windows-only pods
custom-labelCustomUse your own domain label
Separation

Pod Anti-Affinity

🌍 Spread Out
"Keep me AWAY from this other pod." Use case: spread replicas across nodes for HA, prevent both copies of cache from same node.
# MUST NOT be on same node as other replicas affinity: podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution: - labelSelector: matchExpressions: - key: app operator: In values: - web-app topologyKey: kubernetes.io/hostname # Result: If 3 nodes, 3 replicas each on different node # If only 2 nodes available, 3rd replica stays Pending
Same syntax as pod affinity, but keeps pods apart
Required = strict: Pod won't schedule if would violate rule
# TRY to be on different nodes (but not required) affinity: podAntiAffinity: preferredDuringSchedulingIgnoredDuringExecution: - weight: 100 podAffinityTerm: labelSelector: matchExpressions: - key: app operator: In values: - cache topologyKey: kubernetes.io/hostname
Pattern: HA Deployment (Spread Across Nodes)
apiVersion: apps/v1 kind: Deployment metadata: name: web-app spec: replicas: 3 selector: matchLabels: app: web-app template: metadata: labels: app: web-app spec: affinity: podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution: - labelSelector: matchLabels: app: web-app topologyKey: kubernetes.io/hostname containers: - name: app image: myapp:latest
Result: Each replica on different node (if enough nodes)
Pattern: Zone-Spread for Disaster Recovery
# Spread replicas across zones (survive AZ failure) affinity: podAntiAffinity: requiredDuringSchedulingIgnoredDuringExecution: - labelSelector: matchLabels: app: critical-service topologyKey: topology.kubernetes.io/zone # 3 replicas → 3 different zones # Zone failure → still have 2 zones running
Distribution

Topology Spread Constraints

📊 Even Distribution
"Distribute me evenly across zones/nodes." More flexible than anti-affinity. Guarantees balanced distribution.
# Spread evenly across zones topologySpreadConstraints: - maxSkew: 1 topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: DoNotSchedule labelSelector: matchLabels: app: web-app
maxSkew: Max difference in pod count between topology groups (1 = difference max 1)
topologyKey: What to spread across (zone, node, region)
whenUnsatisfiable: Action if can't satisfy (DoNotSchedule, ScheduleAnyway)
labelSelector: Which pods count toward spread
DoNotSchedule: Strict (Default)
# Don't schedule if would violate spread whenUnsatisfiable: DoNotSchedule # Example: 3 zones, maxSkew=1 # Zone A: 1 pod # Zone B: 1 pod # Zone C: 0 pods # New pod: CAN go to C (skew stays 1-0=1) # If all zones have 1: pod stays Pending
ScheduleAnyway: Best-Effort
# Try to spread, but schedule anyway if needed whenUnsatisfiable: ScheduleAnyway # Example: Only 2 zones available # Zone A: 5 pods # Zone B: 0 pods # New pod: Prefers B, but if B full, goes to A anyway
Example: Balanced Across Nodes
apiVersion: apps/v1 kind: Deployment metadata: name: cache spec: replicas: 9 template: metadata: labels: app: cache spec: topologySpreadConstraints: - maxSkew: 1 topologyKey: kubernetes.io/hostname whenUnsatisfiable: DoNotSchedule labelSelector: matchLabels: app: cache # Result: 3 pods per node (if 3 nodes) # No single node overloaded
Example: Multi-Level Spread
# Spread across zones, then nodes topologySpreadConstraints: # First: spread across zones - maxSkew: 1 topologyKey: topology.kubernetes.io/zone whenUnsatisfiable: DoNotSchedule labelSelector: matchLabels: app: app # Second: also spread across nodes - maxSkew: 2 topologyKey: kubernetes.io/hostname whenUnsatisfiable: ScheduleAnyway labelSelector: matchLabels: app: app

Graceful Handling

Azure Spot VM Eviction

⚠️ Prepare for Interruption
Azure spot VMs are terminated with 30-second notice. Use preemption handler + pod disruption budgets.
1. Azure Spot VM: Scheduled for eviction (cost saving, unpredictable)
2. 30-Second Notice: Azure sends eviction signal
3. Preemption Handler (daemon): Cordon node, drain pods gracefully
4. Pod Disruption Budget: Respects min-available/max-unavailable
5. Cluster Autoscaler: Spins up replacement node
6. Pod Rescheduled: To new node automatically

Graceful Shutdown Pattern

🛑 Elegant Exits
When a pod is killed (node draining, update, eviction), give it time to close connections gracefully.
apiVersion: v1 kind: Pod metadata: name: app spec: # Give 120 seconds to shutdown before force-kill terminationGracePeriodSeconds: 120 containers: - name: app image: myapp:latest ports: - containerPort: 8080 # Hook: runs before termination signal lifecycle: preStop: exec: # Custom shutdown script (app-specific) command: - /bin/sh - -c - | # Stop accepting new requests echo "Shutting down gracefully..." # Give app time to finish in-flight requests sleep 30 # Then exit exit 0 # Must implement /shutdown endpoint or handle SIGTERM
# Node.js example const http = require('http'); const server = http.createServer((req, res) => { res.writeHead(200); res.end('OK'); }); process.on('SIGTERM', () => { console.log('SIGTERM received, shutting down gracefully...'); // Stop accepting new connections server.close(() => { console.log('Server closed'); process.exit(0); }); // Force exit after 30 seconds (before k8s force-kills) setTimeout(() => { console.log('Forced shutdown'); process.exit(1); }, 30000); }); server.listen(8080);

Scheduling

Priority & Preemption Pattern

⚡ Critical First
Mark critical pods with high priority. If resources tight, scheduler kills low-priority pods to schedule high-priority ones.
apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: name: system-critical value: 2000 globalDefault: false description: "System critical services" --- apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: name: production value: 1000 globalDefault: false description: "Production workloads" --- apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: name: default value: 0 globalDefault: true description: "Default priority" --- apiVersion: scheduling.k8s.io/v1 kind: PriorityClass metadata: name: batch value: -100 globalDefault: false description: "Batch jobs (can be preempted)"
Preemption: If high-priority pod can't fit, scheduler kills low-priority pods
Grace Period: Low-priority pods get terminationGracePeriodSeconds to shutdown
No Preemption: Add priorityClass value: -1 to prevent preemption
Caveat: Preemption can hurt reliability. Use carefully!
