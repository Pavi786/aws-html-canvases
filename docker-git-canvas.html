What is Docker?

The tool that makes "it works on my machine" a problem of the past.

🐳
Foundation
Containerization at a Glance
Imagine you're shipping a pizza. Instead of just sending the recipe and hoping the other person has the same oven, ingredients, and kitchen — Docker lets you ship the entire kitchen, ingredients, and pizza already made, in a box. No surprises on the other end.

Docker packages your application together with everything it needs to run — libraries, config, runtime, OS layer — into a single, portable unit called a container. This container runs identically on any machine that has Docker installed: your laptop, a server, or the cloud.

Containers vs VMs
Why Not Just Use a VM?
A VM is like renting a whole apartment (full OS). A container is like renting just a room in an apartment — shared building, your own private space. Rooms spin up in seconds; finding a new apartment takes 10+ minutes.

Linux Internals
Namespaces & cgroups
Namespaces are like privacy screens — each container thinks it's the only one on the machine. cgroups are like a strict parent — they limit how much CPU, memory, and disk any single container can hog.
  • PID namespace — Container has its own process IDs
  • NET namespace — Container has its own network stack
  • MNT namespace — Container has its own filesystem view
  • cgroups — Limits CPU, memory, I/O per container
  • Union FS — Layered read-only + thin writable layer on top

Docker Architecture

Understanding the engine under the hood.

🖥️
Docker Client
This is you. When you type docker run, you're talking to the Docker Client — it takes your commands and sends them to the daemon.
The CLI tool that humans (and scripts) interact with. It communicates with the Docker Daemon via REST API calls over a Unix socket or TCP.
docker run -d -p 80:80 nginx
# You typed this ↑ (Client)
⚙️
Docker Daemon (dockerd)
The daemon is like a restaurant manager. You (client) place an order, and the manager handles the kitchen — pulling images, starting containers, managing networks, etc.
A background service that does all the heavy lifting: building images, running containers, managing networks and volumes. Listens for Docker API requests.
Strengths
  • Handles all container lifecycle
  • Background process
Watch Out
  • Runs as root by default
  • Single point of failure
🌐
Docker REST API
The language that the client and daemon use to talk to each other — like a waiter translating your order into kitchen language. You can even call it directly with curl!
The Docker API exposes endpoints for all Docker operations. Third-party tools, CI systems, and container orchestrators use this API to manage Docker programmatically.
# Direct API call example:
curl --unix-socket /var/run/docker.sock \
  http://localhost/containers/json
Docker — Page 3

Images & Containers

The blueprint vs the building. One produces, the other runs.

📦
Images = Blueprint. Containers = Running Instance.
An image is a read-only snapshot of your application. A container is a live, running process spawned from that image. You can run 10 containers from 1 image simultaneously. Kill a container — the image is untouched.
Images
Docker Images — Deep Dive
An image is like a frozen meal in a box — everything's prepared, sealed, and ready. You (the container) just open it and eat. The box doesn't change no matter how many meals you make from it.
Images are built in layers. Each Dockerfile instruction adds a layer. Layers are cached and reused — so changing one line doesn't rebuild everything from scratch.
docker pull nginx:latest
docker build -t myapp:v1 .
docker images
docker tag myapp:v1 myrepo/myapp:latest
docker push myrepo/myapp:latest
Pros
  • Immutable & versioned
  • Layer caching speeds builds
  • Shareable via registry
Cons
  • Large images waste bandwidth
  • Stale layers = security risks
  • No state — data is lost on delete
Containers
Running Containers — Commands
A container is a running instance of your image — like turning on your frozen meal in the microwave. It's alive, doing work, and can be stopped at any time. The meal stays frozen (the image); you just re-heat a new one.
Containers are ephemeral by default — when stopped, any data written inside is lost unless you use volumes. They are stateless, portable, and replaceable.
docker run -d -p 8080:80 nginx
docker ps # List running
docker exec -it <id> bash
docker logs <id>
docker stop <id>
docker rm <id>
Pros
  • Instant startup
  • Process-level isolation
  • Easy to replicate
Cons
  • Ephemeral — data lost on removal
  • Debugging can be tricky

Dockerfile

Your recipe card for building Docker images. Every line is a layer.

📄
Interview Hot
Complete Dockerfile Breakdown
A Dockerfile is a recipe. Just like baking — you start with base ingredients (FROM), prep things (RUN, COPY), set the oven (ENV, WORKDIR), then say what to serve (CMD/ENTRYPOINT). Docker reads this recipe and bakes your app into an image.
InstructionPurposeLayman Meaning
FROMSet base imageChoose your starting ingredient (e.g., Ubuntu, Node, Python)
RUNExecute a command during buildDo this while setting up the kitchen (install packages, compile)
COPYCopy files from host to imageBring your recipe/code into the kitchen
ADDLike COPY + extracts archives + URLsCOPY but with superpowers (use COPY unless you need extras)
CMDDefault command at runtimeWhat the container does when you start it (can be overridden)
ENTRYPOINTFixed main processThe main chef — always runs, CMD becomes its arguments
EXPOSEDocument which port to usePut a sign saying "knock here" (doesn't actually open the port)
ENVSet environment variablesWrite sticky notes for the app to read at runtime
WORKDIRSet working directoryGo to this folder before doing anything else
ARGBuild-time variableTemporary variable only available while building, not at runtime
# Multi-stage Dockerfile example (Best Practice)
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# --- Production stage (tiny!) ---
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
RUN adduser -D appuser && chown -R appuser /app
USER appuser
EXPOSE 3000
CMD ["node", "dist/server.js"]
Best Practice
Multi-Stage Builds
Build your app in one container (with all dev tools), then copy only the finished product into a tiny clean container. Like baking a cake in a big messy kitchen, but only serving the cake — not the flour bags and dirty bowls.
Pros
  • Massively smaller images
  • No dev tools in prod
  • Better security surface
Cons
  • Slightly more complex Dockerfile
  • Must explicitly copy needed artifacts
Best Practice
Layer Caching
Docker remembers previous steps. If step 3 didn't change, it skips re-doing it. So put slow things (installing packages) early, and fast-changing things (your code) last — this keeps builds lightning fast.
  • Copy package.json FIRST, then run npm install
  • Only then COPY your actual source code
  • Changing your code won't re-trigger npm install
  • Use .dockerignore to exclude node_modules, .git

Docker Networking

How containers talk to each other and the outside world.

🌉
Bridge Network (Default)
Containers are isolated islands. The bridge network is like a private town — all containers in the same bridge can talk to each other by name. The outside world can only get in through specific doors (port mapping).
Docker creates a virtual network. Containers on the same bridge discover each other via built-in DNS. Use -p host:container to expose ports.
docker network create mynet
docker run --network mynet --name db postgres
docker run --network mynet --name app myapp
# app can reach db via hostname "db"
Pros
  • Default & easy to use
  • Container DNS works out of box
Cons
  • Not suitable for multi-host
🏠
Host Network
No private town — the container uses your actual machine's network directly. No translation layer. Fast, but no isolation. Like removing a door from your house — great access, no privacy.
Container shares the host machine's network namespace. Port 80 in the container IS port 80 on your laptop. Useful for performance-sensitive apps.
Pros
  • Best network performance
  • No port mapping needed
Cons
  • No network isolation
  • Port conflicts possible
  • Linux-only feature
🌐
Overlay Network
For when you have multiple machines. Overlay networks create a virtual network spanning several physical machines — containers on Machine A can talk to containers on Machine B as if they were neighbors. Used in Swarm and Kubernetes.
Pros
  • Multi-host container communication
  • Encrypted traffic option
  • Essential for orchestration
Cons
  • Requires Swarm/K8s mode
  • More complex setup

Volumes & Storage

Containers are temporary. Your data shouldn't be.

💾
Why Do Volumes Exist?
Containers are ephemeral — when a container dies, all data written inside it dies too. Volumes solve this by storing data outside the container's lifecycle, on the host machine. Your PostgreSQL data, uploads, logs — all safe even when you restart or replace containers.
Recommended
Named Volumes
Docker manages a special folder on your computer. You just give it a name and point your container to it. Docker handles where on disk it actually lives. Best for databases and persistent app data.
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres
docker volume ls
docker volume inspect pgdata
Pros
  • Docker-managed, easy backup
  • Portable across hosts
  • Works on all platforms
Cons
  • Harder to browse directly
  • No specific host path
Bind Mounts
You tell Docker "use exactly this folder on my laptop." Changes you make on your laptop instantly appear in the container — great for development. But tied to your specific machine's folder structure.
docker run -v /home/user/app:/app myapp
# Host path : Container path
# Hot-reload dev: edit on host, runs in container
Pros
  • Perfect for local development
  • Direct file access from host
Cons
  • Not portable (absolute path)
  • Less secure — host exposed
tmpfs Mounts
Data lives only in RAM. Super fast, but disappears the moment the container stops. Use for sensitive temporary data like secrets or session tokens that you absolutely don't want written to disk.
Pros
  • Extremely fast
  • Data never hits disk
  • Perfect for secrets/tokens
Cons
  • Data lost on container stop
  • Linux-only
  • Limited by RAM

Docker Compose

Orchestrate multiple containers with one YAML file.

📋
Multi-Container Apps
One File to Rule Them All
Running a modern app usually needs multiple services: web server, database, cache, queue. Normally you'd run 10 docker commands. Docker Compose lets you write one YAML file describing everything, then one command to start it all: docker compose up. Shutdown? docker compose down.
# docker-compose.yml
version: '3.9'

services:
  web:
    build: .
    ports:
      - "8080:3000"
    environment:
      - DATABASE_URL=postgres://db:5432/mydb
    depends_on:
      - db
    volumes:
      - ./src:/app/src # hot reload

  db:
    image: postgres:15-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data
    environment:
      - POSTGRES_DB=mydb

  redis:
    image: redis:7-alpine

volumes:
  pgdata:
Pros
  • One command to start everything
  • Networks auto-created between services
  • Perfect for dev & testing
  • Readable, version-controllable config
Cons
  • Single-host only (no multi-node)
  • Not production-grade orchestration (use K8s)
  • Startup order is best-effort

Docker Security

Containers aren't secure by default. Here's what to know.

Critical
Non-Root User
By default, Docker containers run as root (superuser). If your container is hacked, the attacker has root inside it. Running as a non-root user is like locking your house — even if someone gets in, they can't touch the main systems.
# In Dockerfile:
RUN adduser -D appuser
USER appuser
Critical
Image Scanning
Your base image (like Ubuntu) might have known security holes. Image scanning tools scan your image like antivirus software — they check every layer against databases of known vulnerabilities.
docker scout cves myimage:latest
# or: trivy image myimage:latest
Critical
Secrets Management
Never bake passwords into your Dockerfile — they'll be visible to anyone with image access. Use environment variables for dev, Docker Secrets or Vault for production. Think: don't tattoo your PIN on your wrist.
  • Never use ARG for passwords (shows in build history)
  • Use Docker Secrets in Swarm mode
  • Use .env files (add to .dockerignore)
  • Consider HashiCorp Vault or AWS Secrets Manager

What is Git?

The time machine for your code. Distributed, fast, and industry-standard.

🌿
Foundation
Git in Plain English
Git is like Google Docs version history, but for code — and it works offline. You can save checkpoints (commits), create parallel universes of your code (branches), merge them, and travel back in time if you mess up. Every developer has the full history on their own machine.

Git is a distributed version control system. "Distributed" means every developer has a complete copy of the entire project history. No server needed to work offline. Every clone is a full backup.

Working Dir
→
git add (Stage)
→
git commit (Local)
→
git push (Remote)
Pros
  • Full offline capability
  • Complete history on every clone
  • Blazing fast branching
  • Industry standard everywhere
Cons
  • Steep learning curve (rebase, reflog...)
  • Merge conflicts can be messy
  • History rewriting can cause chaos in teams
The 4 Areas of Git
Git has 4 "places" where your files can live — each one a step closer to being saved permanently.
Working Directory
Where you edit files. Like your desk — messy, untracked changes live here.
Staging Area (Index)
Files you've git added. Like a shopping cart — chosen but not paid yet.
Local Repository
After git commit — saved to your machine's history. Like a receipt in your drawer.
Remote Repository
After git push — shared with the team on GitHub/GitLab. Like publishing your receipt to a shared drive.
Advanced Internals
Git Objects (Senior Level)
Under the hood, Git stores everything as objects in a database. Understanding this = senior-level Git knowledge that impresses interviewers.
  • Blob — Stores file content. Just the data, no filename.
  • Tree — Stores directory structure. Points to blobs and other trees.
  • Commit — Points to a tree + parent commit + author + message. The checkpoint.
  • Tag — A pointer to a specific commit with a label (e.g., v1.0.0).
git cat-file -t HEAD # Type of HEAD object
git cat-file -p HEAD # Content of HEAD
Git — Page 2 (Critical)

Branching & Merging

Git's killer feature. Create parallel universes of your code for free.

🌿
A Branch is Just a Pointer to a Commit
That's all it is. Not a copy of your entire codebase — just a lightweight pointer. Creating a branch in Git is essentially free and instant. This is why Git branching is so much more powerful than older VCS systems.
🔀
Merge
Merging is like combining two timelines back into one. Git weaves together changes from both branches and creates a "merge commit" as a record that two paths joined. History stays intact — you can always see that the feature branch existed.
git checkout main
git merge feature/login
# Creates a merge commit
# Preserves both branch histories
Pros
  • Preserves full history
  • Non-destructive
  • Safe for shared branches
Cons
  • Creates extra merge commits
  • History can look messy
🔁
Rebase
Rebase is like pretending your feature branch started today on the latest code, not 3 days ago when you branched off. It replays your commits on top of the latest main. Result: a clean, straight-line history. But: it rewrites history — dangerous on shared branches.
git checkout feature/login
git rebase main
# Replays your commits on top of main
# ⚠️ Never rebase shared/public branches
Pros
  • Clean linear history
  • No extra merge commits
  • Easier to read log
Cons
  • Rewrites commit history
  • Dangerous on shared branches
  • Can break teammates' work
🌲
Branch Commands
git branch # List branches
git branch feature/x # Create branch
git checkout feature/x # Switch to it
git switch feature/x # Modern way
git switch -c feature/y # Create + switch
git branch -d feature/x # Delete branch
git log --oneline --graph --all
Merge vs Rebase — The Ultimate Comparison
AspectMergeRebase
HistoryPreserves all history with merge commitsRewrites history — linear, clean
When to UseShared branches, feature → mainPrivate branches, keeping up with main
Safety100% safe on shared branches⚠️ Never on shared/public branches
AppearanceMessy graph with lots of linesClean straight line
RecoveryEasy — history intactHarder — commits have new hashes

Git Flow
Git Flow is like a formal company with many departments. You have permanent branches: main (production), develop (integration), and temporary branches: feature, release, hotfix. Very structured — great for versioned software releases.

Git Undo & Recovery

When things go wrong — and they will — here's how to fix it.

Know This
git reset
Reset moves your branch pointer backwards to a previous commit — like pressing Ctrl+Z on your commits. Three modes: soft (keep changes staged), mixed (keep changes unstaged), hard (throw everything away — dangerous!).
git reset --soft HEAD~1 # Undo commit, keep staged
git reset --mixed HEAD~1 # Undo commit, keep unstaged
git reset --hard HEAD~1 # ⚠️ Undo + delete changes
Use For
  • Undoing unpushed commits
  • Cleaning up local history
Warning
  • --hard deletes work permanently
  • Never reset pushed commits
Safe Option
git revert
Revert doesn't delete history — it creates a NEW commit that undoes the changes of a previous commit. Like officially acknowledging a mistake in a ledger rather than erasing it. Safe to use on shared branches.
git revert abc1234 # Creates undo-commit
# Safe for public/shared branches
# History preserved, audit trail intact
Pros
  • Safe on shared branches
  • Preserves history
  • Easily reversible
Cons
  • Adds an extra commit
  • Complex for multi-commit reverts
Superpower 🦸
git reflog
Reflog is Git's secret diary — it records every single thing that happened to your branches, even commits you "deleted" with reset. If you nuke your work by accident, reflog can bring it back. Every Git user should know this.
git reflog # Show all recent actions
# Find the commit hash you lost
git checkout abc1234 # Go back to it
# or:
git reset --hard abc1234 # Restore fully
git stash
Stash is a temporary drawer. You're in the middle of work, need to switch branches urgently, but don't want to commit messy code. Stash hides your changes, lets you switch, then you pop them back out.
git stash # Hide current changes
git stash list # See all stashes
git stash pop # Restore latest stash
git stash apply stash@{1} # Specific stash
git stash drop # Delete stash

Git Security & Best Practices

Protecting your code, secrets, and team workflows.

Critical
Never Commit Secrets
Once a secret (API key, password) is committed and pushed, it's in the public history forever — even if you delete the file in the next commit. Use .gitignore, environment variables, and tools like git-secrets to prevent this.
  • Add .env to .gitignore immediately
  • Use git-secrets or pre-commit hooks to scan
  • If leaked: rotate the key, don't just delete the file
  • Use git filter-repo to surgically remove history if needed
Best Practice
Branch Protection Rules
On GitHub/GitLab, you can lock your main branch so nobody (not even you) can push directly to it. All changes must go through a Pull Request with review. Like requiring 2 signatures to open a safe.
  • Require PR reviews before merging
  • Require passing CI checks
  • Disallow force-pushes to main
  • Require signed commits for verified authorship
Signed Commits
Git lets you fake a commit as anyone — "Bob from finance" could be anyone. GPG signing proves the commit actually came from you, verified by your personal cryptographic key. GitHub shows a "Verified" badge on signed commits.
git config --global user.signingkey <KEYID>
git commit -S -m "feat: verified commit"
# Shows "Verified" badge on GitHub

The Complete DevOps Flow
In a real team, you write code → push to Git → CI server detects the push → runs tests automatically → builds a Docker image → pushes it to a registry → Kubernetes/cloud pulls that image and deploys it. The whole pipeline can take minutes. You never manually deploy.

  • Tags create release artifacts
  • Branch strategies define deployment environments
Docker's Role
  • Builds consistent images in CI environment
  • Tagged images map to git tags/commits
  • Pushed to registry as the deployment artifact
  • Kubernetes pulls and runs these images
