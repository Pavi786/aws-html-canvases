Compute Services

The engines that run your code — from full VMs to serverless functions

🖥️

EC2 – Elastic Compute Cloud

VIRTUAL MACHINE • IaaS
👶 LAYMAN EXPLAIN Think of EC2 like renting a physical computer at Amazon's office. You get the computer's CPU, RAM, hard drive and network. You choose what OS to install, what software to run. You pay hourly rent. If you don't need it, you can turn it off and stop paying — just like returning a rental car.
🔬 Deep Explanation:
EC2 is AWS's core IaaS offering. Under the hood, it uses Xen/Nitro hypervisor technology to carve out virtual machines from physical servers. You choose an Instance Type (e.g., t3.medium = 2 vCPU, 4GB RAM), an AMI (Amazon Machine Image — the OS snapshot), and configure networking via VPC.

Key concepts: On-Demand (pay per hour), Reserved (1-3 year commitment, 60-70% cheaper), Spot (bid on unused capacity, up to 90% cheaper but can be interrupted), Dedicated Host (physical server for compliance). The Nitro System offloads hypervisor tasks to dedicated hardware, giving near-bare-metal performance.

✅ PROS

  • Full OS-level control
  • 100+ instance types
  • Spot saves up to 90%
  • Any workload compatible
  • Predictable performance

❌ CONS

  • You manage OS patches
  • Over-provisioning risk
  • Slow startup (mins)
  • Complex for beginners
  • Idle = wasted money
🏭 REAL WORLD EXAMPLE E-commerce site on EC2: 2× t3.large (web servers) + 1× r6i.xlarge (app server, memory-optimized) behind an ALB. Use Auto Scaling Group to add/remove instances based on CPU. Reserved instances for baseline traffic, Spot for peak sales events → 45% cost saving.
⚡ PRACTICAL CLI
# Launch EC2 instance aws ec2 run-instances \ --image-id ami-0c55b159cbfafe1f0 \ --instance-type t3.micro \ --key-name my-key \ --security-group-ids sg-12345678 \ --subnet-id subnet-12345678 \ --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=web-server}]' # Stop/Start instance aws ec2 stop-instances --instance-ids i-1234567890abcdef0 aws ec2 start-instances --instance-ids i-1234567890abcdef0 # Create AMI from running instance aws ec2 create-image --instance-id i-1234567890abcdef0 --name "my-app-ami-v1"
💰 PRICING NOTE t3.micro: ~$0.0104/hr (~$7.5/month). Reserved 1yr: ~$0.0060/hr. Spot: ~$0.003/hr. Always use Savings Plans or Reserved for production baseline.

AWS Lambda

SERVERLESS COMPUTE • FaaS
👶 LAYMAN EXPLAIN Lambda is like a vending machine for code. You put your code in the machine, someone presses a button (event happens), the machine runs your code, and returns the result. You only pay for the exact seconds it ran. No server to rent, no OS to manage. Zero cost when idle.
🔬 Deep Explanation:
Lambda runs code in ephemeral containers (microVMs using Firecracker). Each invocation gets a fresh or warm execution environment. Cold start occurs when no warm container is available (50-500ms penalty). Supports Node.js, Python, Java, Go, Ruby, .NET, custom runtimes.

Key concepts: Triggers (S3 events, API Gateway, SQS, EventBridge, etc.), Execution Role (IAM permissions), Layers (shared dependencies), Provisioned Concurrency (pre-warm containers to eliminate cold starts), SnapStart (for Java — faster init). Max 15 min execution, 10GB memory, 10GB /tmp.

✅ PROS

  • Zero server management
  • Auto-scales to millions
  • Pay per 1ms execution
  • 1M free requests/month
  • Event-driven by design

❌ CONS

  • Cold start latency
  • 15 min max timeout
  • No persistent state
  • Debugging harder
  • Vendor lock-in risk
🏭 REAL WORLD EXAMPLE Image processing pipeline: User uploads photo to S3 → S3 event triggers Lambda → Lambda calls Pillow to resize to 3 sizes → stores back to S3 → sends SQS message. Handles 50K uploads/day at $0.12 total cost. Same on EC2 would cost ~$30/month minimum.
⚡ PRACTICAL CLI
# Deploy Lambda from zip aws lambda create-function \ --function-name resize-image \ --runtime python3.11 \ --role arn:aws:iam::123456789:role/lambda-role \ --handler handler.main \ --zip-file fileb://function.zip \ --timeout 30 \ --memory-size 512 # Invoke Lambda manually aws lambda invoke \ --function-name resize-image \ --payload '{"key":"photo.jpg"}' \ response.json # Update function code aws lambda update-function-code \ --function-name resize-image \ --zip-file fileb://function.zip

AWS ECS

ELASTIC CONTAINER SERVICE • CaaS
👶 LAYMAN EXPLAIN ECS is like a shipping company manager. Your app is packed in a Docker container (shipping box). ECS decides which server to put the box on, tracks all boxes, restarts fallen ones, and scales from 1 box to 1000 boxes automatically. You just hand it the box.
🔬 Deep Explanation:
ECS is AWS's proprietary container orchestration. It uses Task Definitions (JSON config — image, CPU, memory, ports, env vars), Tasks (running instances of a definition), Services (maintain N running tasks, integrate with ALB), and Clusters (logical grouping).

Two launch modes: EC2 launch type (you manage the underlying EC2 fleet) and Fargate launch type (serverless — no EC2 management). Integrates tightly with IAM, CloudWatch, ELB. Simpler than EKS for AWS-native teams, but less portable than Kubernetes.

✅ PROS

  • Deep AWS integration
  • Simpler than Kubernetes
  • IAM per-task roles
  • No control plane fee
  • Works with Fargate

❌ CONS

  • AWS vendor lock-in
  • Less ecosystem than K8s
  • Limited scheduling
  • No native dashboards
  • Migration effort to K8s
⚡ PRACTICAL CLI
# Register Task Definition aws ecs register-task-definition \ --family my-web-app \ --network-mode awsvpc \ --requires-compatibilities FARGATE \ --cpu 512 --memory 1024 \ --container-definitions '[{"name":"web","image":"nginx:latest","portMappings":[{"containerPort":80}]}]' # Create ECS Service aws ecs create-service \ --cluster my-cluster \ --service-name web-service \ --task-definition my-web-app:1 \ --desired-count 3 \ --launch-type FARGATE

AWS EKS

MANAGED KUBERNETES • K8s
👶 LAYMAN EXPLAIN EKS is like AWS doing the hardest part of driving for you — managing the engine and transmission (Kubernetes control plane). You still need to know how to steer (deploy apps, write manifests). It's Kubernetes, but AWS handles the brain (etcd, API server, scheduler).
🔬 Deep Explanation:
EKS runs fully upstream Kubernetes. AWS manages the control plane (API server, etcd, scheduler, controller manager) across 3 AZs with automatic upgrades and patches. You manage the worker nodes (EC2 or Fargate).

Node Groups: managed (AWS-managed EC2 lifecycle) or self-managed. Fargate Profiles: serverless pods with no node management. Key add-ons: AWS Load Balancer Controller (ALB integration), EBS CSI driver (persistent volumes), VPC CNI (pods get VPC IPs). Supports Karpenter for intelligent node autoscaling. Great for portability and using the huge K8s ecosystem.

✅ PROS

  • Cloud-portable (K8s standard)
  • Massive ecosystem
  • Fine-grained scheduling
  • Karpenter autoscaling
  • Multi-cloud ready

❌ CONS

  • $0.10/hr control plane cost
  • Steep K8s learning curve
  • Complex networking
  • More ops overhead
  • Slower to set up
⚡ PRACTICAL CLI
# Create EKS cluster eksctl create cluster \ --name prod-cluster \ --region ap-south-1 \ --nodegroup-name workers \ --node-type t3.medium \ --nodes 3 --nodes-min 1 --nodes-max 10 \ --managed # Update kubeconfig aws eks update-kubeconfig \ --name prod-cluster --region ap-south-1 # Deploy app kubectl apply -f deployment.yaml kubectl get pods -n production

Storage Services

From object storage to block disks — every layer of the storage hierarchy

🪣

S3 – Simple Storage Service

OBJECT STORAGE • 11 NINES DURABILITY
👶 LAYMAN EXPLAIN S3 is like Google Drive or Dropbox but for developers, and virtually unlimited. You store files (called objects) in buckets (like folders). Each file gets a URL. You can make it public or private. Extremely cheap (~$0.023/GB/month). It never loses your files (99.999999999% durability — 11 nines).
🔬 Deep Explanation:
S3 stores objects (files + metadata) in buckets. Each object has a key (path), value (data), metadata, and version. Data is replicated across 3 AZs minimum. Storage classes optimize cost:
S3 Standard → frequent access. S3-IA → infrequent access (cheaper storage, retrieval fee). S3 One-Zone IA → single AZ, 20% cheaper. Glacier Instant → millisecond retrieval archive. Glacier Deep Archive → cheapest ($0.00099/GB), 12hr retrieval.

Advanced features: Versioning, Lifecycle policies (auto-transition storage classes), Replication (CRR/SRR), S3 Select (query CSV/JSON in-place), Event Notifications, Object Lock (WORM compliance), Intelligent Tiering (auto cost optimization).

✅ PROS

  • 11 nines durability
  • Virtually unlimited scale
  • Presigned URLs for temp access
  • Event-driven integrations
  • Static website hosting

❌ CONS

  • Not a filesystem (no append)
  • Eventual consistency (older)
  • Egress costs expensive
  • No native search/query
  • Object size limit 5TB
⚡ PRACTICAL CLI
# Create bucket aws s3 mb s3://my-app-bucket-2024 # Upload file / sync folder aws s3 cp ./app.zip s3://my-app-bucket-2024/ aws s3 sync ./dist s3://my-website-bucket/ --delete # Generate presigned URL (15 min expiry) aws s3 presign s3://my-app-bucket-2024/app.zip --expires-in 900 # Set lifecycle policy aws s3api put-bucket-lifecycle-configuration \ --bucket my-app-bucket-2024 \ --lifecycle-configuration file://lifecycle.json

EBS – Elastic Block Store

BLOCK STORAGE • ATTACHED TO EC2
👶 LAYMAN EXPLAIN EBS is the hard drive for EC2. Just like your laptop has an SSD/HDD inside it, EBS is the virtual hard disk attached to your cloud server. It stores the OS, app files, database files. When you stop EC2, data stays safe on EBS. Detach from one server, reattach to another.
🔬 Deep Explanation:
EBS volumes live in a single AZ and can be attached to one EC2 at a time (except io2 Multi-Attach). Types: gp3 (general purpose SSD — 3000 IOPS baseline, tunable up to 16K IOPS independently of size), io2 (provisioned IOPS SSD — 99.999% durability, up to 64K IOPS, for critical databases), st1 (throughput-optimized HDD — big data, log processing), sc1 (cold HDD — archive).

Snapshots are incremental backups stored in S3 (you don't see them in S3 console). Use Data Lifecycle Manager to automate snapshot schedules. EBS encryption uses KMS, is transparent to applications.

✅ PROS

  • Low latency block I/O
  • Snapshots to S3
  • Resizable without restart
  • KMS encryption built-in
  • Predictable performance

❌ CONS

  • Single AZ (not HA alone)
  • One instance at a time
  • Pay even when not used
  • Manual snapshot mgmt
  • Not for multi-instance share
⚡ PRACTICAL CLI
# Create gp3 volume aws ec2 create-volume \ --availability-zone ap-south-1a \ --volume-type gp3 \ --size 100 \ --iops 3000 --throughput 125 # Attach to EC2 aws ec2 attach-volume \ --volume-id vol-0abcdef1234567890 \ --instance-id i-0abcdef1234567890 \ --device /dev/sdf # Create snapshot aws ec2 create-snapshot \ --volume-id vol-0abcdef1234567890 \ --description "daily-backup-$(date +%Y-%m-%d)"

EFS – Elastic File System

MANAGED NFS • MULTI-EC2 SHARE
👶 LAYMAN EXPLAIN EFS is a shared folder that ALL your servers can access at the same time — like a network drive in an office where 50 computers all read/write the same folder simultaneously. You don't pick a size; it grows and shrinks automatically with your data.
🔬 Deep Explanation:
EFS is a fully managed NFS (Network File System) v4.1. It automatically scales to petabytes. Performance modes: General Purpose (low latency, most use cases) and Max I/O (higher latency but massive parallelism for big data). Throughput modes: Bursting (scales with storage) and Provisioned (fixed throughput).

Storage classes: EFS Standard and EFS-IA (Infrequent Access, 92% cheaper). Mount on EC2 via NFS mount or EFS mount helper (handles TLS encryption, retries). Also accessible from ECS tasks, Lambda, EKS pods.

✅ PROS

  • Concurrent multi-EC2 mount
  • Auto-scales, no provisioning
  • Multi-AZ by default
  • Works with ECS/Lambda/EKS
  • POSIX-compliant

❌ CONS

  • ~10× more expensive than EBS
  • Higher latency than EBS
  • Linux only (no Windows)
  • Not for transactional DBs
  • Complex burst credits

S3 Glacier

ARCHIVE STORAGE • COLD BACKUP
👶 LAYMAN EXPLAIN Glacier is like a storage unit at the edge of town — very cheap rent ($0.00099/GB/month), but getting your stuff back takes 12 hours minimum. Perfect for compliance archives, old backups, and data you rarely touch. 99.999999999% durable, just slow to retrieve.
🔬 Deep Explanation:
Three Glacier tiers: Glacier Instant Retrieval (milliseconds, quarterly access pattern), Glacier Flexible Retrieval (Expedited 1-5min, Standard 3-5hr, Bulk 5-12hr), Glacier Deep Archive (Standard 12hr, Bulk 48hr — cheapest in all of AWS).

Use S3 Lifecycle policies to auto-transition data: S3 Standard → Standard-IA (30d) → Glacier (90d) → Deep Archive (180d). Vault Lock enforces WORM compliance policies for regulatory requirements (HIPAA, SEC 17a-4).

✅ PROS

  • Cheapest storage in AWS
  • 11-nine durability
  • WORM compliance
  • Seamless S3 integration

❌ CONS

  • Slow retrieval (hours)
  • Retrieval fees add up
  • Minimum 90/180 day storage
  • Not for active data

Networking Services

Connecting, routing, protecting, and accelerating your traffic

🏠

VPC – Virtual Private Cloud

PRIVATE NETWORK • ISOLATION LAYER
👶 LAYMAN EXPLAIN VPC is your own private section of the AWS cloud, like having a dedicated office floor in a shared office building. You control who can enter (security groups, NACLs), which rooms connect (subnets), and who gets internet access (internet gateway, NAT gateway). Other AWS customers can't see inside your VPC.
🔬 Deep Explanation:
A VPC is a logically isolated network with a CIDR block (e.g., 10.0.0.0/16 = 65,536 IPs). Divided into Subnets (public = has route to Internet Gateway, private = routes to NAT Gateway for outbound only). Each subnet lives in one AZ.

Key components: Internet Gateway (public internet), NAT Gateway (private subnet outbound access, ~$0.045/hr), Route Tables (traffic routing rules), Security Groups (stateful firewall, instance level), NACLs (stateless firewall, subnet level), VPC Peering (connect VPCs), Transit Gateway (hub-and-spoke for many VPCs), VPC Endpoints (access AWS services without internet), PrivateLink.

✅ PROS

  • Complete network isolation
  • Multiple security layers
  • Flexible CIDR planning
  • VPC Endpoints (no IGW cost)
  • Flow Logs for audit

❌ CONS

  • Complex to design properly
  • NAT Gateway is expensive
  • CIDR mistakes hard to undo
  • VPC Peering non-transitive
🏭 BEST PRACTICE ARCHITECTURE 3-tier VPC: /16 CIDR split into Public subnets (ALB, NAT GW) across 3 AZs, Private App subnets (EC2/ECS) across 3 AZs, Private DB subnets (RDS) across 3 AZs. VPC Endpoint for S3 to avoid NAT Gateway charges. Security Groups: ALB SG allows 80/443 from 0.0.0.0/0; App SG allows only from ALB SG; DB SG allows only from App SG.

Route 53

MANAGED DNS • TRAFFIC ROUTING
👶 LAYMAN EXPLAIN Route 53 is the internet's phonebook inside AWS. When you type "myapp.com", Route 53 translates it to an IP address so your browser knows where to go. It also does health checks — if your server is down, it automatically redirects traffic to a healthy backup server in another region (failover).
🔬 Deep Explanation:
Route 53 is AWS's authoritative DNS service (100% SLA). Routing policies: Simple (single resource), Weighted (A/B testing — 20% v2, 80% v1), Latency-based (route to lowest-latency region), Failover (primary + standby with health checks), Geolocation (route by user country), Geoproximity (with Traffic Flow bias), Multivalue Answer (return multiple IPs, pseudo load balancing).

Health Checks monitor endpoints (HTTP/HTTPS/TCP) every 10-30 seconds from multiple global locations. Private Hosted Zones for internal DNS within VPC. Resolver for hybrid DNS (on-prem + AWS). DNSSEC for DNS spoofing protection.

✅ PROS

  • 100% uptime SLA
  • Rich routing policies
  • Health check integration
  • Global anycast network
  • Domain registration built-in

❌ CONS

  • $0.50/zone/month baseline
  • No GUI for bulk imports
  • Health checks cost extra
  • TTL propagation delays

CloudFront

CDN • GLOBAL EDGE NETWORK
👶 LAYMAN EXPLAIN Imagine your website is in Mumbai, but users from New York, Tokyo, and London are hitting it — all that distance causes slowness. CloudFront places copies of your content at 450+ edge locations worldwide. New York user? They get content from Virginia edge. Tokyo user? From Tokyo edge. Instant speed everywhere.
🔬 Deep Explanation:
CloudFront is a CDN with 450+ Points of Presence (PoPs) globally. Origins can be S3, ALB, EC2, API Gateway, or custom HTTP. Cache Behaviors define routing per URL pattern with TTL, headers, and cookies.

Key features: OAI/OAC (restrict S3 to CloudFront only), Lambda@Edge (run code at edge locations), CloudFront Functions (lightweight JS at edge — header rewrites, URL redirects, auth), Field-Level Encryption, Signed URLs & Cookies (for paid content), Origin Shield (extra caching tier, reduces origin load), Real-time Logs to Kinesis.

✅ PROS

  • 450+ edge locations
  • DDoS protection via Shield
  • Lambda@Edge for logic
  • Reduces origin load/cost
  • HTTPS with ACM (free certs)

❌ CONS

  • Cache invalidation costs
  • Complex cache debugging
  • Propagation can take 10-30min
  • Expensive for high egress
⚖️

ELB – Elastic Load Balancer

ALB / NLB / GLB • TRAFFIC DISTRIBUTION
👶 LAYMAN EXPLAIN ELB is like a traffic cop at a toll booth who directs cars to different lanes. If one lane (server) is busy, it redirects to a less busy lane. If a server dies, it stops sending traffic there. Three types: ALB (smart HTTP routing), NLB (ultra-fast TCP), GLB (for network firewalls).
🔬 Deep Explanation:
ALB (Application LB): Layer 7 (HTTP/HTTPS). Content-based routing (path /api/* → API servers, /images/* → image servers). Host-based routing (api.example.com vs web.example.com). Supports WebSocket, HTTP/2, gRPC. Target types: EC2, IP, Lambda, containers (ECS). Sticky sessions with cookies.

NLB (Network LB): Layer 4 (TCP/UDP/TLS). Ultra-low latency (~100µs). Handles millions of requests/sec. Static IP or Elastic IP per AZ. Good for gaming, IoT, financial trading.

GLB (Gateway LB): Layer 3 bump-in-the-wire. Routes traffic through third-party virtual appliances (firewalls, IDS/IPS).

✅ PROS

  • Seamless Auto Scaling integration
  • Health check automatic
  • SSL termination (ACM)
  • Access logs for analysis
  • Connection draining

❌ CONS

  • $0.008+/LCU/hour charge
  • Minimum ~$16/month even idle
  • ALB latency > NLB latency
  • WAF adds extra cost

Database Services

SQL, NoSQL, In-Memory, and Search — pick the right tool

🐬

RDS – Relational Database Service

MANAGED SQL • MULTI-ENGINE
👶 LAYMAN EXPLAIN RDS is like ordering a pre-built, fully serviced database instead of building your own from scratch. You choose your database engine (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Aurora). AWS handles installation, patching, backups, failover, and monitoring. You just write SQL queries and connect.
🔬 Deep Explanation:
RDS automates: automated backups (to S3, 0-35 day retention), manual DB snapshots, multi-AZ standby (synchronous replication, auto-failover in 60-120sec), read replicas (async, up to 15 for Aurora), patching with maintenance windows, storage auto-scaling.

Multi-AZ: primary and standby in different AZs, synchronous replication. Failover is automatic but causes 60-120 second downtime. Read Replicas: async copies for read scaling. Cross-region read replicas for DR. RDS Proxy: connection pooling (critical for Lambda + RDS — Lambda can spawn thousands of connections). Performance Insights: visual DB load monitoring.

✅ PROS

  • Automated patching/backup
  • Multi-AZ HA built-in
  • Familiar SQL engines
  • Performance Insights
  • IAM DB authentication

❌ CONS

  • No OS/DB config access
  • Expensive vs self-managed
  • Scale-up requires downtime
  • Storage scaling is one-way
⚡ PRACTICAL CLI
# Create RDS PostgreSQL instance aws rds create-db-instance \ --db-instance-identifier prod-db \ --db-instance-class db.t3.medium \ --engine postgres \ --engine-version 15.4 \ --master-username admin \ --master-user-password MySecurePass! \ --allocated-storage 100 \ --storage-type gp3 \ --multi-az \ --deletion-protection # Create read replica aws rds create-db-instance-read-replica \ --db-instance-identifier prod-db-replica \ --source-db-instance-identifier prod-db
⚡

DynamoDB

SERVERLESS NoSQL • SINGLE-DIGIT MS
👶 LAYMAN EXPLAIN DynamoDB is like a super-fast filing cabinet where you look things up by a unique number (primary key). No complex table joins. No schema. Just put data in, get data out by key — in under 10 milliseconds at any scale. Netflix, Airbnb, and Lyft use it for billions of requests per day.
🔬 Deep Explanation:
DynamoDB is a fully managed key-value and document database. Data model: items (rows) with a Partition Key (required, hash-based sharding) and optional Sort Key (range queries within partition). Items can have any attributes (schema-less).

Capacity modes: Provisioned (RCU/WCU, cheaper for predictable workloads) and On-Demand (pay per request, scales instantly). Advanced: DynamoDB Streams (change data capture → Lambda triggers), Global Tables (multi-region active-active), DAX (in-memory cache, microsecond reads), TTL (auto-expire items), Transactions (ACID across items), GSI/LSI (secondary indexes for alternate query patterns).

✅ PROS

  • Single-digit ms at any scale
  • Zero management overhead
  • Global Tables (multi-region)
  • Streams for event-driven
  • Great for serverless apps

❌ CONS

  • No SQL joins/complex queries
  • Access patterns must be pre-planned
  • GSI eventually consistent
  • Hot partition issues
  • Expensive for read-heavy + large items
🚀

Amazon Aurora

CLOUD-NATIVE SQL • 5× MYSQL SPEED
👶 LAYMAN EXPLAIN Aurora is MySQL/PostgreSQL but redesigned from scratch for the cloud — like upgrading from a regular car to a Tesla. It's 5× faster than MySQL, 3× faster than PostgreSQL, but uses the same SQL syntax your app already knows. Data is automatically replicated across 3 AZs, 6 copies. Even if 2 entire data centers fail, your data survives.
🔬 Deep Explanation:
Aurora separates compute from storage. The distributed storage layer spans 3 AZs with 6 copies (2 per AZ), tolerating 2 AZ failures for reads and 1 for writes. Only redo logs are shipped to storage, not data pages — drastically reducing I/O.

Aurora Serverless v2: scales in fractions of ACU (0.5 ACU = ~1GB RAM) within seconds, great for dev/variable workloads. Aurora Global Database: replication to 5 regions with sub-second lag. Aurora Multi-Master: write to multiple nodes. Parallel Query: pushes analytical queries to storage layer. Babelfish: run SQL Server workloads on Aurora PostgreSQL.

✅ PROS

  • 5×/3× faster than MySQL/PG
  • Auto storage scaling to 128TB
  • Serverless v2 for variable load
  • Global Database for low-latency DR
  • 99.99% availability

❌ CONS

  • ~2× cost of RDS MySQL
  • AWS-only (lock-in)
  • Failover still 30sec+
  • Serverless cold start

DevOps & Monitoring

Automate, observe, and deploy — the complete CI/CD and observability stack

📺

CloudWatch

MONITORING & OBSERVABILITY
👶 LAYMAN EXPLAIN CloudWatch is like CCTV cameras + vital monitors for your entire AWS infrastructure. It watches CPU usage, memory, errors, latency — everything. When something goes wrong (CPU > 90%), it sends you an alert (PagerDuty, email, SMS) and can even auto-trigger a fix (scale more servers).
🔬 Deep Explanation:
CloudWatch covers 4 observability pillars: Metrics (time-series numeric data, 1-min resolution for detailed monitoring), Logs (CloudWatch Logs — structured/unstructured, with Log Insights for SQL-like queries), Alarms (threshold-based + anomaly detection), Dashboards (visual ops boards).

CloudWatch Agent: collect custom metrics (memory, disk — not built-in), application metrics. Container Insights: ECS/EKS metrics. Lambda Insights: function-level performance. Synthetics: canary scripts to simulate user journeys. ServiceLens: distributed tracing + X-Ray integration. Contributor Insights: top-N analysis on log data.

✅ PROS

  • Native integration all AWS services
  • Anomaly detection (ML-based)
  • Log Insights SQL querying
  • 15 months metric retention
  • Cross-account dashboards

❌ CONS

  • Costly at high log volume
  • 5-min default metric frequency
  • UI not as polished as Datadog
  • Complex cross-account setup
⚡ PRACTICAL CLI
# Create CPU alarm → triggers Auto Scaling aws cloudwatch put-metric-alarm \ --alarm-name cpu-high \ --metric-name CPUUtilization \ --namespace AWS/EC2 \ --statistic Average \ --period 300 \ --threshold 80 \ --comparison-operator GreaterThanThreshold \ --dimensions Name=AutoScalingGroupName,Value=my-asg \ --evaluation-periods 2 \ --alarm-actions arn:aws:autoscaling:...:scalingPolicy/scale-out # Query logs with Insights aws logs start-query \ --log-group-name /aws/lambda/my-function \ --start-time 1699999200 \ --end-time 1700002800 \ --query-string 'filter @message like /ERROR/ | stats count(*) by bin(5m)'

CodePipeline + CodeBuild + CodeDeploy

CI/CD SUITE • FULL AUTOMATION
👶 LAYMAN EXPLAIN These 3 services together are your fully automated assembly line: CodePipeline = the conveyor belt (orchestrates everything), CodeBuild = the factory machine (runs tests, builds Docker images), CodeDeploy = the delivery truck (pushes the built app to your servers). Git push → everything happens automatically → app is live.
🔬 Deep Explanation:
CodePipeline: visual workflow with stages (Source → Build → Test → Deploy). Integrates GitHub, CodeCommit, ECR, S3 as sources. Can fan-out to multiple deployment targets. Free tier: 1 pipeline free, then $1/pipeline/month.

CodeBuild: fully managed build service. `buildspec.yml` defines commands. Runs in Docker containers. Auto-scales build workers. Caches npm/Maven/pip packages to S3. Outputs artifacts to S3 or ECR.

CodeDeploy: deployment strategies: In-Place (rolling, canary, all-at-once), Blue/Green (new ASG or ECS, swap traffic via ALB). Deployment Groups: tagged EC2, ASG, Lambda alias, ECS service. Hooks for pre/post validation (lifecycle hooks). Rollback on CloudWatch alarm.

✅ PROS

  • Native AWS integration
  • Blue/Green deployments built-in
  • Auto rollback on alarms
  • IAM-controlled per stage
  • No infrastructure to manage

❌ CONS

  • Less features vs Jenkins/GitLab CI
  • buildspec.yml can get complex
  • CodeDeploy agent needs installation
  • Debugging failures is hard

CloudTrail

AUDIT LOGGING • WHO DID WHAT
👶 LAYMAN EXPLAIN CloudTrail is like a CCTV recording of every action taken in your AWS account. Every API call — "John deleted the database at 3:47 AM", "CI bot launched 50 EC2 instances", "Someone changed the S3 bucket to public" — all recorded with timestamp, IP, and user identity. Essential for security audits and compliance.
🔬 Deep Explanation:
CloudTrail logs all AWS API calls as events: Management Events (control plane — create/modify/delete resources, free for first copy), Data Events (S3 object reads/writes, Lambda invocations — paid), Insights Events (anomaly detection — unusual API activity spikes).

Events stored in S3, optionally sent to CloudWatch Logs for real-time alerting. Log File Integrity Validation: hash chain proves logs weren't tampered. Organization Trail: single trail covers all accounts in AWS Organizations. Use with Athena to SQL-query CloudTrail logs for incident investigation.

✅ PROS

  • Enabled by default (last 90 days)
  • Log tamper-proof validation
  • Org-wide single trail
  • Athena integration

❌ CONS

  • Data events = extra cost
  • S3 storage costs accumulate
  • Not real-time (few min delay)

Security & IAM

Identity, encryption, secrets, and threat protection

👤

IAM – Identity & Access Management

ACCESS CONTROL • ZERO TRUST
👶 LAYMAN EXPLAIN IAM is like a security badge system for your AWS account. Each person or service gets a badge (identity). The badge determines which doors they can open (permissions). A developer's badge can open the S3 door but not the billing door. A Lambda function's badge can only write to DynamoDB. No badge = no access.
🔬 Deep Explanation:
IAM identities: Users (humans, programmatic), Groups (logical collection of users), Roles (assumed by services, humans, cross-account — no long-term credentials). Policies are JSON documents defining Allow/Deny actions on resources.

Policy evaluation: Explicit Deny > Explicit Allow > Implicit Deny. Permission boundaries: max permissions a role/user can have (delegation guardrail). Service Control Policies (SCPs): account-level max permissions in AWS Organizations. ABAC: tag-based access control. IAM Access Analyzer: detects overly-permissive policies. Least Privilege: only grant what's actually needed (use IAM Access Analyzer to generate policies from CloudTrail).

✅ PROS

  • Completely free service
  • Granular resource-level control
  • Roles = no hardcoded credentials
  • MFA enforcement
  • Cross-account access

❌ CONS

  • Policy complexity grows fast
  • Easy to over-provision
  • Global service (not regional)
  • Debugging permission denials hard
⚡ IAM BEST PRACTICES
# Create role for EC2 → S3 access (NO hardcoded keys!) aws iam create-role \ --role-name ec2-s3-read-role \ --assume-role-policy-document file://ec2-trust.json aws iam attach-role-policy \ --role-name ec2-s3-read-role \ --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess # Generate least-privilege policy from CloudTrail aws iam generate-service-last-accessed-details \ --arn arn:aws:iam::123456789:role/my-role # Enable MFA delete on S3 bucket aws s3api put-bucket-versioning \ --bucket critical-data \ --versioning-configuration Status=Enabled,MFADelete=Enabled \ --mfa "arn:aws:iam::123456789:mfa/root-account-mfa-device 123456"

KMS + Secrets Manager

ENCRYPTION KEYS • SECRET STORAGE
👶 LAYMAN EXPLAIN KMS is a bank vault for encryption keys — you never see the actual key, KMS uses it on your behalf to lock/unlock data. Secrets Manager is a password manager for your apps — stores DB passwords, API keys, OAuth tokens, and automatically rotates them every 30 days so you never have hardcoded passwords in your code.
🔬 Deep Explanation:
KMS: HSM-backed key management. CMKs (Customer Master Keys): symmetric (AES-256) or asymmetric (RSA/ECC). Key policies control who can use/manage each key. Envelope encryption: KMS generates a data key, encrypts data with data key, encrypts data key with CMK. CMK never leaves KMS HSM. Integrated with S3, EBS, RDS, DynamoDB, Lambda, etc. Audit via CloudTrail.

Secrets Manager: stores secrets as encrypted JSON. Automatic rotation: Lambda function rotates secrets on schedule (30/60/90 days) and updates the target service. Versioning: AWSCURRENT, AWSPENDING, AWSPREVIOUS. Cross-account access via resource policies. Compare: Parameter Store (free, simpler, for config + non-sensitive data) vs Secrets Manager ($0.40/secret/month, rotation, for actual secrets).

✅ PROS

  • FIPS 140-2 Level 3 HSM (KMS)
  • Auto rotation (Secrets Mgr)
  • Zero hardcoded credentials
  • Full audit via CloudTrail
  • Multi-region secrets

❌ CONS

  • Secrets Manager: $0.40/secret
  • KMS API calls: $0.03 per 10K
  • Rotation needs Lambda setup
  • Added latency for secrets fetch

WAF – Web Application Firewall

L7 FIREWALL • ATTACK PROTECTION
👶 LAYMAN EXPLAIN WAF is a bouncer at your website's door. It reads every incoming HTTP request and checks it against rules. SQL injection attempt? Block. Known bad IP? Block. Request from Russia when you only serve India? Block. Too many requests from one IP in 5 min? Rate limit. Legitimate user? Let through instantly.
🔬 Deep Explanation:
AWS WAF v2 uses Web ACLs with rules. Rule types: Managed Rule Groups (AWS-maintained — Core Rule Set, Known Bad Inputs, SQL Database, Linux/Windows OS, Bot Control), IP-based rules, Rate-based rules (throttle IPs), Geo match, Regex pattern matching, Custom rules.

Deploy in front of: CloudFront (global), ALB (regional), API Gateway, AppSync. WAF Logs to CloudWatch, S3, Kinesis. Bot Control managed group: detects and blocks scrapers, crawlers. Fraud Control: account takeover prevention, ATP (account creation fraud). Integrates with AWS Shield Advanced for DDoS response team.

✅ PROS

  • Managed rules (no config needed)
  • Rate limiting built-in
  • Bot Control
  • OWASP Top 10 covered
  • No latency impact (same PoP)

❌ CONS

  • $5/WebACL/month + per-rule cost
  • False positives need tuning
  • Managed rules: extra cost
  • Complex rule ordering

Interview Q&A

Most asked DevOps/Cloud Engineer interview questions with pro answers

EC2
Q: What's the difference between Stop and Terminate an EC2 instance?
Stop: instance shuts down, EBS data preserved, you stop paying for compute (but still pay for EBS). Can restart later with same instance ID. Terminate: instance deleted permanently, root EBS deleted (unless DeleteOnTermination=false). No going back. Use Stop for maintenance, Terminate when done forever.
EC2 SAVINGS
Q: When would you use Spot instances vs Reserved vs On-Demand?
On-Demand: dev/test, unpredictable workloads, anything that can't be interrupted. Reserved (1-3yr): production baseline with predictable load — 60-72% savings. Spot: fault-tolerant batch jobs, CI/CD workers, data processing, ML training — up to 90% savings but can be reclaimed with 2-min warning. Best strategy: Reserved baseline + Spot for burst.
LAMBDA
Q: How do you handle Lambda cold starts in production?
4 strategies: (1) Provisioned Concurrency — pre-warm N containers, eliminates cold start for critical functions. (2) Keep-warm pings via EventBridge every 5 minutes. (3) Reduce cold start time — use lighter runtimes (Node.js/Python), use Lambda SnapStart for Java, reduce package size, use Lambda Layers for dependencies. (4) Architect around it — use SQS as buffer so cold start latency doesn't affect user experience.
S3
Q: How would you secure an S3 bucket with sensitive data?
Multi-layer approach: (1) Block all public access at bucket + account level. (2) Enable versioning + MFA delete to prevent accidental/malicious deletion. (3) Enable server-side encryption (SSE-KMS with CMK). (4) Bucket policy: deny non-HTTPS, deny unencrypted uploads, limit to specific IAM roles only. (5) Enable S3 Access Logging + CloudTrail data events. (6) S3 Object Lock for WORM compliance if needed. (7) Use VPC Endpoint so traffic never leaves AWS network.
VPC
Q: What's the difference between Security Groups and NACLs?
Security Groups: stateful (return traffic auto-allowed), operates at ENI/instance level, allow rules only (no deny), evaluated as a whole. NACLs: stateless (must explicitly allow inbound AND outbound), operates at subnet level, allow AND deny rules, rules evaluated in order by number. Use SGs for instance-level firewall (primary defense). Use NACLs for subnet-level broad blocks (e.g., block entire IP range). Always add ephemeral ports (1024-65535) outbound on NACLs.
ECS vs EKS
Q: When would you choose ECS over EKS?
Choose ECS when: team is AWS-native and doesn't need K8s portability, simpler ops is priority, deploying 1-20 services, no need for K8s ecosystem (Helm, Istio, etc.), want zero control plane cost. Choose EKS when: multi-cloud strategy, team has K8s expertise, need advanced scheduling, using Helm charts, building platform teams, 20+ microservices, need K8s-native tooling (Argo CD, Prometheus Operator, etc.).
RDS
Q: RDS Multi-AZ vs Read Replica — what's the difference?
Multi-AZ: synchronous replication to standby in different AZ. Primary purpose = HIGH AVAILABILITY. Standby is hot (but NOT readable). Automatic failover on primary failure (60-120 sec). No performance boost. Read Replica: asynchronous replication to one or more replicas. Primary purpose = READ SCALING and OFFLOADING. Replicas ARE readable. No automatic failover. Can be promoted to standalone DB. You can combine both — Multi-AZ primary AND read replicas.
IAM
Q: How does IAM policy evaluation work when multiple policies apply?
AWS uses this priority order: (1) Explicit DENY in any policy = always denied, no exceptions. (2) SCPs (Service Control Policies) — must allow. (3) Resource-based policies. (4) Identity-based policies — must have explicit allow. (5) Permission boundaries — max allowed. (6) Session policies. Default is IMPLICIT DENY. All policies evaluated together — if ANY policy has explicit deny, request blocked regardless of allows elsewhere.
DEVOPS DESIGN
Q: Design a zero-downtime blue/green deployment on AWS.
Using ECS + ALB: (1) Deploy new "green" ECS service with new task definition. (2) ALB has 2 target groups — blue (100% traffic) and green (0%). (3) CodeDeploy gradually shifts traffic: 10% → green, monitor CloudWatch alarms for 5 min, 50% → 100%. (4) If any alarm fires → automatic rollback to blue. (5) After success → terminate blue tasks. Alternatively with Route 53 weighted routing or CloudFront origins. Key: always have health checks, alarms, and automated rollback.
COST OPTIMIZATION
Q: How would you reduce AWS costs in a production environment?
Systematic approach: (1) Right-size EC2 with Compute Optimizer recommendations. (2) Reserved Instances or Savings Plans for 60-70% savings on steady workloads. (3) Spot instances for non-critical workloads. (4) S3 Intelligent Tiering + lifecycle policies to Glacier. (5) Delete unattached EBS volumes, old snapshots, unused Elastic IPs. (6) NAT Gateway — use VPC Endpoints for S3/DynamoDB to avoid NAT charges. (7) CloudFront to reduce origin egress. (8) RDS: use Aurora Serverless for dev/staging. (9) Set budget alerts in AWS Budgets to catch surprises early.
MONITORING
Q: How do you monitor a microservices architecture on AWS?
Three pillars: (1) Metrics: CloudWatch Container Insights for ECS/EKS — CPU, memory, network per service. Custom metrics via CloudWatch Agent or EMF. (2) Logs: centralized to CloudWatch Logs Groups per service. Log Insights for querying. (3) Traces: AWS X-Ray for distributed tracing — see which service is slow in a request chain. ServiceLens correlates all three. Create CloudWatch dashboards with key SLIs (error rate, latency p99, saturation). Alert on SLO breaches via CloudWatch Alarms → SNS → PagerDuty.
SECURITY
Q: How do you securely pass credentials to an EC2 or ECS container?
Never hardcode! The correct way: (1) For EC2: attach IAM Role to the instance. App uses AWS SDK which auto-fetches temp credentials from instance metadata (169.254.169.254). (2) For ECS: IAM Task Role — each task gets its own role, credentials injected via metadata endpoint. (3) For DB passwords: store in Secrets Manager. App fetches at startup via SDK. Enable rotation. (4) For config: AWS Systems Manager Parameter Store for non-sensitive config. Zero credentials in code, env files, or Docker images.
