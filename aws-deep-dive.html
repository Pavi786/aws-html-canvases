Scaling Policies

Target Tracking — Best default. Set target (e.g., CPU 60%). ASG adjusts automatically. Use for most stateless web tiers.

Step Scaling — Triggered by CloudWatch alarms. Fine-grained control. Use when you need asymmetric scale-in/out.

Scheduled Scaling — Predictive ramp. Pre-warm for known traffic (marketing events, business hours).

Predictive Scaling — ML-based, learns weekly patterns. Enable alongside target tracking.

Warm Pools & Instance Refresh

Warm Pools — Pre-initialized instances in Stopped state. Eliminates bootstrap latency (~30-120s). Use for apps with slow startup.

Instance Refresh — Rolling AMI updates with min healthy %. Set checkpoints (25%, 50%, 75%) with manual approval. Never update AMI by terminating instances manually.

Health Checks — Use ELB health checks (not just EC2). Set grace period > your slowest startup time.

SnapStart Init

Cold Start Breakdown

Phase 1: Init (~100-500ms) — AWS allocates execution environment, downloads your code/layer, runs static initialization code. Most of your cold start time.

Phase 2: Invoke (~ms) — Handler runs. Warm invocations skip Phase 1.

Mitigation Options:
• SnapStart (Java 11+): Snapshots initialized env, 10x improvement
• Provisioned Concurrency: Pre-warmed instances, zero cold start
• Use ARM/Graviton2 runtimes: ~19% faster init
• Keep deployment packages small (<10MB unzipped ideal)
• Lazy-load heavy dependencies (only import when needed)

Provisioned Concurrency

Pre-initialize N execution environments. These never cold-start. Use Application Auto Scaling to scale PC up/down on schedule (business hours vs overnight).

Cost: You pay for PC idle time. Only provision for latency-sensitive functions.

Pattern: PC for critical APIs + Reserved Concurrency as cap + SQS queue in front for burst absorption. Never set PC = max concurrency — leave headroom for on-demand burst.

Account-Level Limit

1,000 Concurrent (default)

Shared across ALL functions in a region. Request increase via Service Quotas. Always set Reserved Concurrency on critical functions to guarantee their allocation — without it, one function can starve others.

Reserved Concurrency

Guaranteed Allocation

Sets hard cap AND reservation. Reserve = 0 throttles the function (useful for disabling without deleting). Leave 100 unreserved at account level for burst absorption. Monitor ConcurrentExecutions metric.

Throttle Behavior

Synchronous vs Async

Sync (API GW): returns 429 immediately. Async (SQS, S3, SNS): Lambda retries automatically with exponential backoff. SQS: unprocessed messages stay in queue. Use DLQ for all async invocations.

⚡ Pro Tip — Concurrency Math Concurrency = (invocations/sec) × (avg duration in sec). If your function takes 2s on average and processes 500 req/s, you need 1,000 concurrent executions. Plan this before going to prod and set Reserved Concurrency accordingly.
Pattern 1

Fan-Out (SNS → Lambda)

One SNS topic triggers N Lambda functions in parallel. Each function processes independently. Perfect for event notifications, audit logging, cache invalidation. Add SQS between SNS and Lambda for buffering and retry.

Pattern 2

Queue Worker (SQS → Lambda)

Lambda polls SQS. Batch size: 1-10,000 messages. Enable Report Batch Item Failures to only retry failed messages. Use FIFO queues for ordering guarantees. Set visibility timeout to 6× function timeout.

Pattern 3

Orchestration (Step Functions)

Use Express Workflows (<5min, 100k events/sec) for high-throughput. Standard Workflows for long-running, durable processes with exactly-once semantics. Never implement retry logic manually in Lambda — delegate to Step Functions.

Pattern 4

Event Filtering

SQS/DynamoDB/Kinesis sources support server-side filtering — Lambda only invoked for matching events. Reduces invocations and cost by up to 90%. Filtering happens before your code runs — no cost for filtered events.

Pattern 5

Lambda@Edge / CloudFront

Run code at 450+ PoPs. Use for: auth at edge, request/response manipulation, A/B testing, geo-routing. Max 128MB RAM, 30s timeout for origin-facing functions. Don't do heavy computation — keep it fast.

Pattern 6

Lambda Extensions

Run agents alongside your function code. Use cases: Datadog/ADOT telemetry, secrets caching (avoid Secrets Manager API calls per invocation), log shipping. External extensions run in separate process, don't share memory.

✓ Lambda Do's
  • Use AWS Lambda Powertools for structured logging, tracing, and custom metrics
  • Enable X-Ray tracing — understand latency breakdown across services
  • Set concurrency limits on all functions — prevent noisy neighbor throttling
  • Use ARM/Graviton2 runtime (arm64) — 20% cheaper, 19% faster
  • Keep Lambda functions single-purpose — one trigger, one action
  • Always configure DLQ or SQS for async invocations
  • Use Lambda Layers for shared dependencies — speeds up deployments
  • Enable function URLs for simple HTTP endpoints instead of API Gateway
✗ Lambda Don'ts
  • Never use Lambda for long-running jobs (>15min) — use ECS, Batch, or Step Functions
  • Don't ignore cold starts for user-facing APIs — implement Provisioned Concurrency
  • Never store state in /tmp across invocations — use S3, DynamoDB, or ElastiCache
  • Don't deploy Lambda inside VPC unless required — adds 100–400ms cold start overhead
  • Never hardcode credentials or connection strings — use Secrets Manager + caching
  • Don't use recursive invocation (Lambda calling itself) — can cause runaway costs
  • Avoid over-provisioning memory "just in case" — use Power Tuning to find optimum
  • Never set timeout to max (15min) by default — set it to 2× expected duration

Security Groups vs NACLs

Layer 4 Defense

  • SGs: stateful, instance-level, "allow" rules only
  • NACLs: stateless, subnet-level, allow + deny rules
  • Use SGs as primary control (always reference SG IDs not IPs)
  • NACLs: block known bad IPs/CIDRs at subnet level
  • Use SG chaining: ALB SG → App SG → DB SG
VPC Endpoints

PrivateLink & Gateway

  • Gateway Endpoints: S3 & DynamoDB — FREE, always use
  • Interface Endpoints (PrivateLink): ~$7/mo per AZ per service
  • Eliminate NAT Gateway data fees for AWS service calls
  • Use endpoints for: SSM, Secrets Manager, ECR, STS
  • Set VPC endpoint policies for least-privilege access
Transit Gateway

Hub-and-Spoke Networking

  • Replaces VPC peering mesh — centralized routing
  • Supports route table segmentation (prod/dev isolation)
  • TGW multicast for streaming architectures
  • Network Manager for global visibility
  • Attach VGW for hybrid connectivity (DX / VPN)
VPC Flow Logs

Network Visibility

  • Log accepted + rejected traffic at VPC/subnet/ENI level
  • Send to S3 (cheaper) or CloudWatch (real-time query)
  • Use custom format — include pkt-src, pkt-dst, traffic-path
  • Query with Athena for ad-hoc security investigation
  • Use for cost visibility: identify NAT heavy-hitters

✓ VPC Do's
  • Create one NAT Gateway per AZ — prevents cross-AZ NAT data transfer charges and single-AZ failure
  • Enable VPC Gateway Endpoints for S3 and DynamoDB — zero cost, eliminates NAT GW path
  • Use separate subnets per tier (public/app/data) with tight security group chaining
  • Plan CIDR ranges for all VPCs upfront to avoid peering/TGW overlap issues
  • Enable VPC Flow Logs to S3 with Athena for cost-effective security analysis
  • Use VPC Lattice for service-to-service communication across accounts
✗ VPC Don'ts
  • Don't use the default VPC for production — build purpose-built VPCs with proper isolation
  • Don't peer VPCs that need transitive routing — use Transit Gateway instead
  • Don't allow 0.0.0.0/0 in security group inbound — ever. Use ALB SG references
  • Don't put databases in public subnets — ever. Even with SG restrictions
  • Don't use single AZ NAT Gateway — it's a single point of failure for all egress
  • Avoid micro-subnets (/28, /29) — you'll run out of IPs fast with ENIs and Lambda

Performance

Request Rate & Partitioning

  • 3,500 PUT/COPY/POST/DELETE + 5,500 GET per prefix/sec
  • Use multiple prefixes (randomize key prefix) for high-throughput
  • Multipart Upload: required for >100MB, max throughput with parallelism
  • S3 Transfer Acceleration: CloudFront edge for global uploads
  • Byte-Range Fetches: parallel GET for large objects — 2–4x faster
Security

Access Control

  • Block all public access at account level — always
  • Use bucket policies, not ACLs (ACLs are legacy)
  • S3 Object Ownership: BucketOwnerEnforced — disables ACLs
  • VPC Endpoint policy + bucket policy for private buckets
  • Enable MFA Delete for critical versioned buckets
  • Use S3 Access Analyzer to find unexpected public access
Encryption

At Rest & In Transit

  • Default: SSE-S3 (AES-256, AWS manages keys)
  • SSE-KMS: audit trail via CloudTrail, per-key access control
  • SSE-C: customer provides keys (for strict compliance)
  • Enforce HTTPS: use bucket policy with aws:SecureTransport
  • DSSE-KMS: dual-layer encryption for regulated workloads
Events & Notifications

S3 Event Bridge

  • EventBridge (preferred): all API calls, 20+ event types
  • S3 Notifications: simpler, faster — Lambda/SQS/SNS
  • Object Lambda: transform data on-the-fly during GET
  • S3 Batch Operations: process billions of objects at scale
  • Inventory + Athena: analyze bucket metadata at PB scale
✓ S3 Do's
  • Enable S3 Intelligent-Tiering for objects >128KB with unpredictable access patterns
  • Use Lifecycle policies to transition cold data automatically — set on day one
  • Enable versioning for production buckets — pair with lifecycle to expire old versions
  • Always abort incomplete multipart uploads via lifecycle (major hidden cost)
  • Use VPC Gateway Endpoints — eliminates NAT data transfer cost for S3 traffic
  • Set S3 Requester Pays for public datasets shared externally
✗ S3 Don'ts
  • Never make a bucket public unless for intentional static site hosting
  • Don't use S3 as a database — it has no atomic transactions or locking
  • Don't use sequential key prefixes (date/time) at high throughput — creates hot partitions
  • Never ignore S3 Access Logs — they're critical for security forensics
  • Don't DELETE objects directly for compliance data — use S3 Object Lock (WORM)
  • Avoid downloading entire objects to filter — use S3 Select (SQL on S3)

Multi-AZ vs Read Replicas

Multi-AZ (HA): Synchronous replication to standby in different AZ. Automatic failover in ~35s. Standby cannot serve reads — it's purely for HA. Failover triggered by: hardware failure, AZ disruption, manual reboot with failover, storage failure.

Multi-AZ Cluster (RDS): 2 readable standbys. Commits acknowledged after 1 standby confirms. Writer failover in <35s. Readable replicas reduce read load on primary.

Read Replicas: Asynchronous replication. Can serve SELECT queries. Replicate across AZs and regions. Use for analytics offloading, reporting queries, cross-region DR. Up to 15 replicas.

Backup & Recovery Strategy

Automated Backups: Enable with 7–35 day retention. Stored in S3, supports PITR to any second within retention window. Zero performance impact (snapshots from standby).

Manual Snapshots: Point-in-time, retained indefinitely. Use before major migrations or schema changes.

Cross-Region Backups: Automate with AWS Backup — set RPO/RTO targets. Export to S3 Parquet for long-term analytics. Test restore monthly — untested backups are not backups.

Aurora Architecture

Distributed Storage

  • Storage auto-scales 10GB → 128TB in 10GB increments
  • 6 copies across 3 AZs — survives losing 1 AZ + 1 copy
  • Reads require 3/6 copies; writes require 4/6 quorum
  • Log-structured storage — no background disk I/O
  • Cluster endpoint (writer) + reader endpoint (load-balanced)
Aurora Serverless v2

Instant Auto-Scaling

  • Scale in 0.5 ACU increments in <1 second
  • Min: 0.5 ACU (~1GB RAM), Max: 256 ACU
  • Mixed config: 1 writer (Serverless) + read replicas
  • Ideal for dev/test, variable workloads, multi-tenant SaaS
  • Cannot scale to zero (v2) — use v1 for true zero-idle cost
Aurora Global Database

Cross-Region Active-Passive

  • Replication lag <1 second across up to 5 secondary regions
  • RPO <1s, RTO <1min for planned failover
  • Secondary clusters can serve local reads — reduce latency
  • Use for multi-region compliance and disaster recovery
  • Write forwarding: secondary can forward writes to primary
Aurora vs RDS MySQL

When to Choose

  • Aurora: 5× MySQL perf, 3× PostgreSQL perf. Choose at >10k IOPS
  • Aurora: higher cost per GB (but lower IOPS costs at scale)
  • RDS MySQL: simpler ops, lower cost for small workloads
  • Aurora is always Multi-AZ by default — no separate config
  • For <100 GB, low traffic: RDS may be cheaper
⚡ Pro Tip — Aurora IOPS Aurora's storage auto-scales but I/O cost can surprise you. Aurora I/O Optimized (new pricing tier) bundles I/O costs into storage price — better for I/O-heavy workloads (>25% I/O cost of total Aurora bill). Switch via Console/CLI with no downtime.

Connection Pooling

RDS Proxy

  • Pools and shares connections — critical for Lambda + RDS
  • Reduces DB connections by up to 66%
  • Automatic failover: <30s (vs <120s direct connection)
  • IAM authentication enforcement — no DB passwords in code
  • Always use with Lambda, ECS, or any ephemeral compute
Read Offloading

Cache Strategy

  • ElastiCache (Redis): lazy loading vs write-through caching
  • Read replicas for analytics/reporting — not OLTP reads
  • DAX for DynamoDB (built-in cache, microsecond reads)
  • Use pgBouncer for PostgreSQL connection pooling (self-managed)
  • Set replica lag alarm (>10s is a warning, >60s is critical)

✓ RDS Do's

  • Use RDS Proxy for Lambda/serverless to Lambda to prevent connection exhaustion
  • Enable Performance Insights (free for 7 days) — indispensable for query analysis
  • Set custom Parameter Groups from day one — never modify default groups
  • Enable deletion protection on production databases
  • Use IAM database authentication for EC2/Lambda — eliminate credential rotation
  • Monitor ReplicaLag, DatabaseConnections, FreeStorageSpace, and ReadIOPS
✗ RDS Don'ts

  • Don't use db.t3/t4g for production OLTP — burstable CPUs cause unpredictable latency
  • Never skip autovacuum tuning for PostgreSQL — table bloat kills performance
  • Don't allow unlimited max_connections — connection exhaustion crashes the DB
  • Never do major version upgrades without snapshot + testing in staging first
  • Don't use RDS for time-series or graph data — use Timestream or Neptune instead

Data Transfer Costs

Idle & Waste Elimination

  • Unused EBS volumes: snapshot + delete (use AWS Config rule)
  • Unattached EIPs: $0.005/hr each — release immediately

DevOps Patterns
IaC, CI/CD, observability, GitOps, blue/green deployments, and security posture

Terraform Best Practices

  • → Separate state per environment (dev/staging/prod)
  • → Remote state in S3 + DynamoDB lock table
  • → Use Terraform Workspaces or Terragrunt for DRY configs
  • → Always run terraform plan in CI, apply manually or with approval gate
  • → Module versioning via Git tags — pin versions in production
  • → Use moved blocks instead of destroy+recreate for refactoring
  • → tfsec + Checkov in CI for security misconfig scanning
  • → Atlantis or Spacelift for PR-based plan/apply workflow

CDK vs Terraform vs CloudFormation

Terraform: Best for multi-cloud, large teams, mature ecosystem. HCL learning curve. Best provider coverage.

AWS CDK: TypeScript/Python — type-safe, L2/L3 constructs reduce boilerplate. Compiles to CloudFormation. Ideal for AWS-only shops with strong dev teams.

CloudFormation: Native AWS, no state management issues. Verbose YAML. Use when integrating with AWS Service Catalog or Control Tower.

Recommendation: Terraform for infrastructure, CDK for application-centric resources (Lambda, ECS tasks).

Stage 1 — Source (CodeCommit / GitHub)

Branch protection rules, required PR reviews (min 2), signed commits enforced. Never push directly to main. Use feature flags (LaunchDarkly/AppConfig) over long-lived feature branches.

Stage 2 — Build (CodeBuild / GitHub Actions)

Run: unit tests, SAST (Semgrep/Snyk), dependency scanning, Dockerfile linting (Hadolint), IaC scanning (tfsec). Fail fast on any security finding. Build Docker image, push to ECR with immutable tags (never :latest in prod).

Stage 3 — Integration Tests (Staging)

Deploy to staging via CodeDeploy or Helm. Run integration tests, load tests (k6/Locust), smoke tests. Gate on: p99 latency <500ms, error rate <0.1%, all health checks green. Auto-rollback on failure.

Stage 4 — Deploy to Production (Blue/Green)

CodeDeploy Blue/Green or ECS Rolling with circuit breaker. Shift traffic: 10% → 30% → 100% with bake time and alarms at each step. Rollback trigger: CloudWatch alarm on error rate, latency, or custom business metric.

Stage 5 — Post-Deploy Validation

Synthetic canary (CloudWatch Synthetics) hits critical user journeys every minute. PagerDuty alert on failure. DORA metrics tracked: deployment frequency, lead time, MTTR, change failure rate.

Metrics

CloudWatch + EMF

  • Use Embedded Metric Format (EMF) for custom metrics — no PutMetricData API calls
  • Dashboards: USE method (Utilization, Saturation, Errors) per service
  • Composite Alarms: AND/OR multiple alarms — reduce alert noise
  • CloudWatch Contributor Insights: find top talkers in logs
  • Consider Managed Prometheus for Kubernetes workloads
Logging

Structured + Centralized

  • JSON structured logs — always include requestId, userId, traceId
  • CloudWatch Log Insights: SQL-like query across all log groups
  • Log retention policy: 90 days CloudWatch, then S3 Glacier
  • Cross-account log aggregation via Kinesis Data Firehose
  • Never log PII, credentials, or sensitive data
Tracing

X-Ray / ADOT

  • AWS X-Ray: distributed tracing across Lambda, API GW, ECS
  • OpenTelemetry (ADOT): vendor-neutral, exportable to Datadog/Grafana
  • Sampling rules: 5% default, 100% for errors or target paths
  • Service Map: visualize call graph and identify slow dependencies
  • Trace ID propagation: pass via HTTP headers X-Amzn-Trace-Id
Alerting

Actionable Alerts Only

  • Alert on symptoms (user impact), not causes (CPU high)
  • SLO-based alerting: burn rate alerts using error budget
  • PagerDuty / OpsGenie with escalation policies and runbooks
  • Every alert must have a runbook link in the alarm description
  • Review alert fatigue monthly — disable or tune noisy alerts
Identity

IAM Zero-Trust

  • Enable AWS IAM Identity Center (SSO) — no long-lived IAM users
  • Permission Boundaries on all IAM roles — prevent privilege escalation
  • SCPs at OU level: deny regions, deny root usage, deny public S3
  • IAM Access Analyzer: find external access + unused permissions
  • CloudTrail in all regions + Organization trail — never disable
Detection

GuardDuty + Security Hub

  • GuardDuty: ML-based threat detection — enable in ALL accounts, ALL regions
  • Security Hub: aggregates findings from GuardDuty, Inspector, Macie, Config
  • AWS Config: compliance rules for CIS Benchmarks, NIST, PCI DSS
  • Macie: scan S3 for PII and sensitive data patterns
  • EventBridge → Lambda for auto-remediation of critical findings
Secrets

Secrets Manager

  • Rotate DB credentials automatically (30-day default)
  • Never pass secrets via environment variables — use Secrets Manager + cache
  • SSM Parameter Store: free tier for config, SecureString for secrets
  • GitGuardian / truffleHog in CI: prevent secrets in code
  • Use OIDC for GitHub Actions → AWS — no long-lived access keys
Network Security

WAF + Shield

  • AWS WAF on ALB + CloudFront: OWASP Top 10 managed rule groups
  • Shield Advanced: $3k/mo but includes DDoS cost protection + 24/7 DRT
  • AWS Network Firewall for East-West VPC traffic inspection
  • GuardDuty VPC Flow Logs analysis — identifies port scans, crypto mining
  • AWS Firewall Manager: centralize WAF/SG rules across accounts
