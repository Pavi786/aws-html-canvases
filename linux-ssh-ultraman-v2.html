TOPIC 01 WHAT IS SSH? — THE LAYMAN EXPLANATION
👁 LAYMAN EXPLANATION SSH = Secure SHell. Imagine you want to control a computer that's physically sitting in a datacenter 1000km away from you. You can't walk up to it. SSH is like a super-secure invisible phone line between your laptop and that faraway server. You type commands on your laptop, SSH sends them over the internet — but fully encrypted so nobody can read what you're sending. The server executes them and sends results back.

Without SSH: Everyone between you and the server (hackers, ISPs) could read your password and commands like reading a postcard.
With SSH: Everything is locked in a safe that only you and the server can open. Even if someone intercepts the data, they just see scrambled garbage.
1
YOU TYPE
You run ssh user@server on your laptop. SSH client wakes up.
2
TCP HANDSHAKE
Your laptop connects to port 22 on the server. Like knocking on a door.
3
KEY EXCHANGE
Server and client negotiate a secret encryption key together — mathematically impossible to crack.
4
SERVER ID CHECK
Client checks server's fingerprint against known_hosts. Is this really the server we expect?
5
AUTH
You prove who you are — via SSH key (recommended) or password. Server checks authorized_keys.
6
SHELL OPENS
You now have a terminal on the remote server. Everything you type is encrypted end-to-end.
TOPIC 02 THE ~/.ssh/ DIRECTORY — YOUR SSH HOME BASE
👁 LAYMAN EXPLANATION ~/.ssh/ is a hidden folder in your home directory. The tilde (~) means "your home folder". The dot (.) before ssh makes it hidden — like a secret drawer in your desk. This folder holds ALL your SSH identity — your keys, the servers you trust, and your shortcuts. Every user on the system has their own ~/.ssh/ folder. On the SERVER side, the key files live in the same place but belong to the server user.
  YOUR LAPTOP — CLIENT MACHINE (~/.ssh/)

TOPIC 03 EVERY SSH FILE EXPLAINED — DEEP DIVE
id_ed25519  /  id_rsa
~/.ssh/id_ed25519  |  ~/.ssh/id_rsa
🔴 YOUR PRIVATE KEY — THE MASTER SECRET
🔑 Analogy: This is your actual house key. If someone steals this file, they can impersonate you to every server that knows your public key. Guard it like your life savings.
This is your cryptographic private key. It's generated in a pair with the public key. You NEVER send this to anyone. When you SSH into a server, your client uses this to solve a cryptographic challenge that proves you own the matching public key — without ever revealing the private key itself. Ed25519 is the modern, stronger algorithm. RSA 4096 is the older, still-OK alternative. ed25519 is shorter, faster, and more secure.
chmod 600 — REQUIRED Never store in cloud/email!

⚠ CRITICAL WARNINGIf this file has permissions 644 or 777, SSH will REFUSE to use it and show "Permissions too open" error. Always run: chmod 600 ~/.ssh/id_ed25519
id_ed25519.pub  /  id_rsa.pub
~/.ssh/id_ed25519.pub
🟢 YOUR PUBLIC KEY — THE LOCK YOU HAND OUT
🔒 Analogy: This is the lock that only your private key can open. You copy this to every server you want to access. Think of giving your padlock to someone — they put it on their door, only you have the key that opens it.
The public key is safe to share with anyone and any server. It's a long base64 string starting with ssh-ed25519 AAAA.... You add its contents to the server's ~/.ssh/authorized_keys file to grant yourself access. Never confuse pub with private! — The .pub file has no danger, the file WITHOUT .pub is the dangerous one.
chmod 644 — safe to share

✅ HOW TO COPY YOUR KEY TO A SERVERssh-copy-id -i ~/.ssh/id_ed25519.pub user@server
This command adds your public key to the server's authorized_keys automatically!
authorized_keys
~/.ssh/authorized_keys  (on the SERVER)
🟡 THE GUEST LIST — WHO CAN LOGIN
📋 Analogy: This file lives on the SERVER and is like the VIP guest list at a nightclub. Each line is one public key = one person allowed in. If your public key is in this file, you can login. If not — no entry!
Each line in this file is one person's public key. One line = one authorized person. You can have hundreds of lines for hundreds of users. To grant access to a new person, just append their public key to this file. To revoke access, delete their line. Comments after keys (like user@hostname) are purely informational. Format: algorithm base64key comment
chmod 600 — REQUIRED chown user:user — correct owner

✅ ADD A KEY MANUALLYecho "ssh-ed25519 AAAA...key..." >> ~/.ssh/authorized_keys
known_hosts
~/.ssh/known_hosts  (on CLIENT)
🔵 SERVER FINGERPRINTS — TRUST DATABASE
📸 Analogy: The first time you meet someone, you memorize their face. known_hosts is SSH's memory of server faces (fingerprints). Next time you connect, SSH checks: "Is this the same server I connected to before?" If the face changed (different fingerprint) — RED ALERT! Could be a hacker doing a man-in-the-middle attack!
Each line stores one server's fingerprint in format: hostname algorithm base64fingerprint. When you first connect to a server, SSH asks "Do you trust this fingerprint?" — type yes and it saves here. If a server's key changes (reinstall, migration), you get a scary warning. If legitimate change, remove the old entry with ssh-keygen -R hostname.
chmod 644 — standard

⚠ FINGERPRINT MISMATCH WARNINGIf you see "REMOTE HOST IDENTIFICATION HAS CHANGED" — STOP! Either the server was rebuilt (OK) or someone is intercepting your connection (BAD). Verify with your sysadmin before proceeding.
~/.ssh/config
~/.ssh/config  (personal client config)
🟦 YOUR SSH SHORTCUTS — PROFILES FILE
📒 Analogy: This is your phone contacts book for SSH. Instead of remembering "Call +91-9876543210 and use secret code 7543" — you just say "Call Ravi". Instead of typing the full SSH command with flags every time, you define a nickname and just type ssh myserver.
This file lets you define named SSH "profiles". Each block starts with Host nickname and lists settings below. When you type ssh nickname, SSH automatically uses those settings. Overrides /etc/ssh/ssh_config for your user only. Extremely powerful for DevOps with many servers.
chmod 600 — recommended

✅ EXAMPLE ~/.ssh/config 
Host prod-web
  HostName 203.0.113.10
  User ubuntu
  Port 2222
  IdentityFile ~/.ssh/prod_key
  ServerAliveInterval 60

Host staging
  HostName 192.168.1.50
  User deploy
  ProxyJump bastion

Host bastion
  HostName bastion.company.com
  User admin
  IdentityFile ~/.ssh/bastion_key
Now just type: ssh prod-web 🎉
ssh_host_*_key
/etc/ssh/ssh_host_ed25519_key  (on SERVER)
🔴 SERVER'S OWN IDENTITY — HOW CLIENTS RECOGNIZE IT
🪪 Analogy: Just like YOU have an SSH key to prove your identity to servers, the server also has its own key to prove ITS identity to you. These are generated when SSH is installed on the server. The server's public key is what gets saved in your known_hosts when you first connect.
These keys are auto-generated during OpenSSH installation. Multiple types exist: ed25519 (modern), rsa (legacy), ecdsa. Never manually create these. They are what allows your client to verify the server is genuine. The public versions (.pub) are the fingerprints clients save in known_hosts. If regenerated (e.g. after cloning a VM), clients will get fingerprint mismatch warnings.
chmod 600 — enforced by sshd owned by root:root
TOPIC 04 /etc/ssh/ssh_config — CLIENT CONFIG DEEP DIVE
👁 LAYMAN EXPLANATION /etc/ssh/ssh_config is the global SSH client settings file. It affects ALL users on the machine when they use the ssh command. Think of it as the default settings for the SSH app — like phone settings that apply to everyone who uses the device. Your personal ~/.ssh/config file always overrides this for just you. Admins usually edit this to set company-wide SSH defaults.
⚠ REMEMBEREditing /etc/ssh/ssh_config affects the SSH CLIENT behavior (when you run ssh FROM this machine). It does NOT control who can log INTO this machine — that's sshd_config.

TOPIC 05 /etc/ssh/sshd_config — SERVER DAEMON CONFIG DEEP DIVE
👁 LAYMAN EXPLANATION /etc/ssh/sshd_config is the config for the SSH SERVER (sshd = SSH Daemon). This controls who can connect to YOUR machine and HOW they can connect. Think of it as the rules for the bouncer at the door of your server. Everything in here determines: What port do we listen on? Do we allow passwords? Do we allow root login? Which users can enter? After every change you MUST restart sshd: systemctl restart sshd — otherwise changes don't take effect!
⚠ BEFORE EDITING sshd_configALWAYS keep an existing SSH session open while editing! If you make a mistake and lock yourself out, that open session is your rescue lifeline. NEVER blindly close all sessions after a sshd_config change.

Port 22⚠ CHANGE IT!The default port hackers scan first. Changing to e.g. 2222 or 22000 reduces automated attack noise by ~90%. Not foolproof, but reduces log spam. Layman: Like changing your front door from the standard door number — makes it harder for random burglars to find.
PermitRootLogin no🔒 MUST BE noNever allow direct root SSH login. If a key is compromised, attackers immediately get root — game over. Instead, login as a regular user then sudo su -. The single most important sshd_config setting.
PasswordAuthentication no🔒 MUST BE noDisable all password-based login. Force SSH key authentication ONLY. Completely eliminates brute-force password attacks. 2nd most important setting. Only set this AFTER confirming key auth works!
MaxAuthTries 3PROTECTIONAfter 3 failed login attempts in one connection, SSH disconnects. Makes brute-force attacks extremely slow. Each connection allows only 3 guesses — attacker would need thousands of connections to guess a key.
LoginGraceTime 30PROTECTIONIf someone connects but doesn't complete login within 30 seconds, disconnect them. Prevents connection hijacking and reduces resources held by unresponsive clients. Layman: If someone picks up the phone but says nothing for 30 seconds, hang up.
AllowUsers ubuntu deployWHITELISTONLY listed users can SSH into this server. Everyone else (including system users like www-data, postgres) cannot SSH in, even with valid keys. If omitted, all users who authenticate successfully can login. Always set this on production servers!
ClientAliveInterval 300SESSIONServer sends "are you alive?" ping to CLIENT every 300 seconds (5 min). Cleans up zombie sessions. Note: This is the SERVER pinging the CLIENT — opposite of ServerAliveInterval (client pinging server).
MaxStartups 10:30:100PROTECTIONRate-limit unauthenticated connections. Format: start:rate:full. Start dropping connections at 10 unauthenticated (30% drop rate), full drop at 100. Protects against connection flooding attacks.
AllowTcpForwarding yesTUNNELSAllows SSH port forwarding/tunneling. Set to no for restricted users who should only get a shell. Set to local to allow only local forwarding. Required for VPN-like tunneling use cases.
Match User ftpuserPOWERFULApply different settings to specific users/groups/IPs. Extremely powerful for creating different access tiers. Use ChrootDirectory to jail users, ForceCommand to restrict to SFTP only, AllowTcpForwarding no to block tunneling.
Ciphers / MACs / KexAlgorithmsCRYPTORestrict which encryption algorithms are allowed. Remove old weak ones (3des, md5, sha1). Stick to chacha20, aes256-gcm, curve25519, sha256+. Run ssh -Q cipher to see all supported ciphers.

TOPIC 06 SSH PORT FORWARDING & TUNNELING — LAYMAN DEEP DIVE
👁 LAYMAN EXPLANATION SSH tunneling is like creating a secret pipeline through the SSH connection. The pipeline carries OTHER network traffic (not just your terminal). Think of SSH as a secure armored truck — tunneling means you can also put other cargo inside that truck while it travels. Common uses: access internal databases from outside, bypass firewalls, secure unsecured protocols.
🔵 LOCAL PORT FORWARDING (-L)
What it does: Forward a port on YOUR machine to a port on the REMOTE server's network. You access localhost:localport and traffic goes through SSH to reach the remote target.
[YOUR LAPTOP :8080] ─────SSH TUNNEL────▶ [SERVER :3306] You browse localhost:8080 → arrives at MySQL 3306!
ssh -L 8080:localhost:3306 user@server
ssh -L 8080:db.internal:5432 user@jumpserver
💡 Layman: Like telling a courier to pick up your package from someone else's address. You give YOUR address for delivery, they pick from the other location.
🔴 REMOTE PORT FORWARDING (-R)
What it does: Forward a port on the REMOTE server back to a port on YOUR machine. The server exposes a port that proxies to your local machine. Useful for exposing local dev servers.
[SERVER :8080] ─────SSH TUNNEL────▶ [YOUR LAPTOP :3000] Someone visits server:8080 → reaches YOUR localhost:3000!
ssh -R 8080:localhost:3000 user@server
ssh -R 0.0.0.0:9090:localhost:8080 user@server
💡 Layman: Like giving a friend your home address so people who visit THEIR house can be redirected to yours.
🟢 DYNAMIC FORWARDING — SOCKS PROXY (-D)
What it does: Creates a SOCKS proxy on your local machine. Configure your browser to use it, and ALL browser traffic goes through the SSH server. Like a VPN but using SSH.
[YOUR BROWSER] → localhost:1080(SOCKS) → [SSH SERVER] → Internet All traffic appears to come FROM the SSH server!
ssh -D 1080 user@server
ssh -D 1080 -C -N user@server
💡 Layman: Like sending all your mail through a trusted friend in another city — it all looks like it came from their city.
🟡 JUMP HOST / PROXY JUMP (-J)
What it does: SSH through an intermediate "bastion" server to reach a private server that has no public IP. Standard enterprise security pattern.
[YOUR LAPTOP] → [BASTION :22] → [PRIVATE SERVER] Private server has no internet. Only bastion can reach it!
ssh -J bastion.company.com user@192.168.1.50
ssh -J admin@bastion:2222 deploy@10.0.0.5
💡 Layman: Like entering a secured building through a lobby guard (bastion), then being escorted to the inner office (private server).
