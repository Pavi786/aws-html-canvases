What is MLOps?
The Big Picture

MLOps = Machine Learning + Operations. Think of it like DevOps, but for AI models. Just as DevOps helps you ship software reliably, MLOps helps you build, deploy, and keep AI models running reliably in the real world — without them going stale, breaking, or costing a fortune.

"A model that only works in a Jupyter notebook is not a product. MLOps is the discipline of taking that notebook to production and keeping it alive."
🧠
The Problem MLOps Solves

Data scientists build great models in notebooks. But notebooks don't run in production. Models need to be packaged, served, monitored, and retrained — just like apps. Without MLOps, models rot silently.

⚙️
What MLOps Covers
  • Building repeatable training pipelines
  • Versioning data, code, and models
  • Deploying models as APIs or batch jobs
  • Monitoring predictions for quality issues
  • Retraining automatically when needed
👷
Why DevOps Engineers?

You already know CI/CD, containers, infra-as-code, and monitoring. MLOps is 70% those skills applied to a new domain. You just need to learn the ML-specific pieces on top: model formats, training pipelines, drift monitoring.

The Classic MLOps Pain Story

Without MLOps: Data scientist trains a fraud detection model in January. It gets 95% accuracy. Engineers copy-paste it into production. In March, fraudsters change tactics. The model's accuracy silently drops to 60%. Nobody notices. The business loses millions. Three months later, someone spots it manually.

This is called model drift — and it's the #1 reason MLOps exists.
With MLOps: The same model is deployed with a monitoring pipeline. When accuracy drops below 80%, an alert fires. An automated retraining job kicks off with new data. A new model is tested, validated, and deployed — all within hours, not months.

MLOps Core Pillars

📦 Reproducibility

Anyone can re-run the same experiment and get the same result. No "it works on my machine."

🔄 Automation

Data pipelines, training, testing, deployment — all automated. Minimal manual steps.

📊 Continuous Monitoring

Track model accuracy, data quality, and prediction distribution 24/7.

🚀 Scalability

Serve predictions to millions of users. Train on terabytes. Handle load spikes.

What's Different?

If you already know DevOps, you're 70% of the way to MLOps. But there are critical differences. In DevOps, code is deterministic — the same input always gives the same output. In ML, models are probabilistic — and they change behavior over time even if the code never changes.

🔴 Data Stage (Your Foundation)

Garbage in, garbage out. The data stage is where 80% of ML failures originate. You need pipelines that ingest raw data, validate it, version it, and transform it into features the model can learn from.

  • Raw data ingestion (batch or streaming)
  • Data validation (Great Expectations)
  • Data versioning (DVC, Delta Lake)

Data scientists run experiments to find the best model. Your job is to make these experiments reproducible, trackable, and scalable — not locked in someone's laptop.

  • Distributed training (Horovod, Ray)
  • Hyperparameter search (Optuna)

🟢 Serving Stage (Your Core Domain)

The model is live and answering real requests. This is pure DevOps territory — containers, APIs, load balancing, autoscaling. Plus ML-specific: latency budgets, model warming, prediction caching.

  • REST/gRPC API endpoint
  • Batch prediction jobs
  • Model versioning + rollback
  • Performance monitoring
⚠️ The Feedback Loop is Critical: The lifecycle is a circle, not a line. Monitoring data from production feeds back into the next training cycle. If you break this loop — by not logging predictions, not storing production inputs, or not triggering retraining — your model will degrade and nobody will catch it.

Data Collection
& Ingestion

Think of data ingestion as the equivalent of your source code repository in DevOps. Everything downstream depends on it. In ML, your training data is your "source of truth" — and if it's messy, missing, or biased, your model will be too.

Data Source Types

🗄️ Structured

SQL databases, CSV files, Excel spreadsheets. Rows and columns. Easiest to work with.

📄 Unstructured

Images, text, audio, video. Stored in object storage (S3, Blob). Needs preprocessing.

🌊 Streaming

Kafka, Kinesis. Real-time events. Complex pipelines. For fraud detection, recommendations.

🌐 APIs / Web

External data feeds, scraped websites, third-party enrichment services.

Data Ingestion Pipeline Example (Python)

# Data ingestion with validation import great_expectations as ge import pandas as pd def ingest_and_validate(source_path: str): # Load raw data df = pd.read_parquet(source_path) # Validate schema and quality gdf = ge.from_pandas(df) gdf.expect_column_to_exist("user_id") gdf.expect_column_values_to_not_be_null("label") gdf.expect_column_values_to_be_between( "age", min_value=0, max_value=120) result = gdf.validate() if not result["success"]: raise ValueError("Data validation FAILED") # Version the validated data with DVC df.to_parquet("data/processed/features.parquet") return df
✅ Pros of Good Data Pipelines
  • Catch data quality issues before they corrupt your model
  • Reproducible training — always know what data was used
  • Faster debugging when something goes wrong
  • Regulatory compliance — full audit trail of training data
  • Enables automated retraining with fresh data
❌ Common Data Ingestion Mistakes
  • No schema validation — corrupt data silently poisons the model
  • Training/serving skew — different transforms at training vs production
  • Data leakage — future data accidentally included in training
  • No versioning — can't reproduce an old training run
  • Ignoring class imbalance — 99% normal, 1% fraud = useless model

Data Versioning
with DVC

DVC (Data Version Control) is Git for data and models. Since data files are too large for Git, DVC tracks them using lightweight pointer files in Git while storing the actual data in S3, GCS, or Azure Blob. Think of DVC as a layer on top of Git that handles the big stuff.

Layman explanation: Git saves the history of your code. DVC saves the history of your datasets. When you ask "what data did we use to train model v2.3?", DVC can answer that instantly — even if that data was 500GB of images.

DVC Setup & Basic Workflow

# Initialize DVC in your repo git init && dvc init # Connect to remote storage (Azure Blob) dvc remote add -d azureblob azure://mldata-bucket/dvc dvc remote modify azureblob account_name mlacc # Track a dataset (creates data/train.csv.dvc) dvc add data/train.csv git add data/train.csv.dvc .gitignore git commit -m "Add training dataset v1" dvc push # uploads to Azure Blob # On another machine / in CI: git clone <repo> dvc pull # downloads the exact same data # Switch between data versions (like git checkout) git checkout v1.0 dvc checkout # restores the v1.0 dataset

DVC Pipeline (dvc.yaml)

# Define reproducible pipeline stages stages: preprocess: cmd: python src/preprocess.py deps: - data/raw/dataset.csv - src/preprocess.py outs: - data/processed/features.parquet train: cmd: python src/train.py deps: - data/processed/features.parquet - src/train.py params: - params.yaml: - model.learning_rate - model.max_depth outs: - models/model.pkl metrics: - metrics/eval.json: {cache: false} # Run the full pipeline # dvc repro — only reruns changed stages
✅ Why DVC is Essential
  • Reproduce any experiment from 6 months ago with exact data
  • Avoid re-running expensive stages if inputs haven't changed
  • Works with any cloud storage (S3, GCS, Azure, SSH)
  • CI/CD integration — pull data in pipeline, train, push model
  • Free and open source — no vendor lock-in
❌ DVC Limitations
  • Learning curve for teams used to pure Git workflows
  • Large file operations can be slow (10s of GBs take time to push)
  • Cache management gets complex on shared servers
  • Doesn't scale well to real-time streaming data
  • Team conflicts on .dvc files require care to resolve

Feature
Engineering

Raw data is almost never in the right format for an ML model. Feature engineering is the process of transforming raw data into the specific numbers and structures that models can understand. It's the most time-consuming and most impactful part of any ML project.

"In practice, feature engineering accounts for 80% of the work and 80% of the model's performance. Models are dumb — they just do math. The magic is in the features you give them."
Numerical Features

Numbers like age, price, distance. But raw numbers need treatment:

  • Normalization: scale 0→1 (e.g., house prices)
  • Standardization: mean=0, std=1
  • Log transform: squash huge outliers
  • Binning: age → age_group buckets
  • Polynomial features: age² for non-linear patterns
Categorical Features

Labels like "city", "product_type", "gender". Models can't do math on strings:

  • One-hot encoding: city → [is_NY, is_LA, is_Chicago]
  • Label encoding: low/med/high → 0/1/2
  • Target encoding: replace with mean target value
  • Embeddings: for high-cardinality (10k+ categories)
Temporal Features

Dates and timestamps hide rich patterns that models can't see by default:

  • Hour of day: midnight fraud spikes
  • Day of week: weekend vs weekday
  • Days since event: recency features
  • Rolling averages: last 7-day spend
  • Lag features: last month's sales

Feature Pipeline with scikit-learn (Production-Ready)

from sklearn.pipeline import Pipeline from sklearn.compose import ColumnTransformer from sklearn.preprocessing import StandardScaler, OneHotEncoder from sklearn.impute import SimpleImputer # Define which columns get which treatment numeric_features = ['age', 'income', 'days_active'] categorical_features = ['city', 'product_type'] numeric_transformer = Pipeline([ ('imputer', SimpleImputer(strategy='median')), ('scaler', StandardScaler()) ]) categorical_transformer = Pipeline([ ('imputer', SimpleImputer(strategy='constant', fill_value='unknown')), ('onehot', OneHotEncoder(handle_unknown='ignore')) ]) preprocessor = ColumnTransformer([ ('num', numeric_transformer, numeric_features), ('cat', categorical_transformer, categorical_features) ]) # Full pipeline: preprocess → model full_pipeline = Pipeline([ ('preprocessor', preprocessor), ('classifier', XGBClassifier()) ]) # This entire pipeline gets serialized as ONE artifact
🔑 Critical Rule — Training/Serving Parity: The EXACT same feature transformations must be applied at training time AND serving time. If training normalizes age with mean=35, std=12 — production must use the same numbers.

This is why scikit-learn Pipelines are so powerful — the scaler is fitted once during training and then applied consistently at serving. The pipeline object is the transform spec.
⚠️ Training-Serving Skew (Most Common MLOps Bug): Training uses the full history of a user's purchases as a feature. Production only has 7 days of history. The model was trained on something it never sees in production. This kills accuracy silently.

Feature Stores
Sharing Features Across Teams

A Feature Store is a centralized warehouse for pre-computed features. Imagine 10 different ML teams each computing "days since last login" in 10 slightly different ways. A feature store computes it once, stores it, and lets everyone use it — consistently, at training time AND serving time.

What Problem Does It Solve?

Without a feature store, every team recomputes the same features from raw data. They make slightly different assumptions. Training and production get out of sync.

  • Team A: "user_spend_7d" = last 7 calendar days
  • Team B: "user_spend_7d" = last 168 rolling hours
  • Result: two models trained on different things, named the same
  • Production disaster when they're swapped
How a Feature Store Works

It has an offline store (for training — historical data in a data warehouse) and an online store (for serving — fast key-value lookup like Redis).

  • Offline store: Parquet files, BigQuery, Redshift
  • Online store: Redis, DynamoDB, Cassandra
  • Both are synced from the same transform logic
  • Training and serving use the same feature definitions

Model Training
How It Actually Works

Training a model means running an algorithm over labeled data until it learns patterns well enough to make predictions on new data. As a DevOps engineer, you don't write the model code — but you provision the compute, orchestrate the runs, and manage the outputs.

Anatomy of a Training Script

import mlflow import xgboost as xgb from sklearn.metrics import accuracy_score, roc_auc_score def train(params: dict): mlflow.start_run() # 1. Load versioned data X_train, y_train = load_features("data/train.parquet") X_val, y_val = load_features("data/val.parquet") # 2. Log hyperparameters mlflow.log_params(params) # 3. Train the model model = xgb.XGBClassifier(**params) model.fit(X_train, y_train, eval_set=[(X_val, y_val)], early_stopping_rounds=10) # 4. Evaluate and log metrics preds = model.predict(X_val) acc = accuracy_score(y_val, preds) auc = roc_auc_score(y_val, preds) mlflow.log_metric("accuracy", acc) mlflow.log_metric("roc_auc", auc) # 5. Save model to registry mlflow.xgboost.log_model(model, "model") mlflow.end_run() return auc

💡 DevOps Tip — Spot Instances for Training: ML training jobs are perfect for Spot/Preemptible VMs — they're long-running batch jobs that can checkpoint progress and resume. Use AWS Spot or Azure Spot VMs to cut GPU costs by up to 90%. Just make sure your training code saves checkpoints every N minutes.
✅ Training Best Practices
  • Always split data: train / validation / test (never touch test until final eval)
  • Checkpoint training every N epochs — protect against spot instance interruption
  • Use early stopping — stop when val loss stops improving (avoids overfitting)
  • Log ALL experiments, even failed ones — failures teach you what not to try
  • Seed everything for reproducibility (random.seed, numpy.random.seed)
❌ Training Anti-Patterns
  • Training on ALL data — no validation set = no way to detect overfitting
  • Data leakage — test set accidentally influences training (inflated accuracy)
  • Not normalizing features for neural networks = slow/unstable training
  • Training without version control — "which dataset did we use again?"
  • Using accuracy alone for imbalanced datasets — always check precision/recall

Experiment Tracking
with MLflow

Experiment tracking is like git log for ML. Every training run is a commit — it records what parameters you used, what data you trained on, and what results you got. Without tracking, teams repeat experiments, can't compare models, and can't reproduce past results. MLflow is the industry-standard open-source tool.

MLflow Core Concepts + Commands

# Start MLflow server (local dev) mlflow server \ --host 0.0.0.0 \ --port 5000 \ --backend-store-uri postgresql://user:pass@db/mlflow \ --default-artifact-root s3://mlflow-artifacts/ # In your training code: import mlflow mlflow.set_tracking_uri("http://mlflow.internal:5000") mlflow.set_experiment("fraud-detection-v2") with mlflow.start_run(run_name="xgb-baseline") as run: mlflow.log_param("learning_rate", 0.01) mlflow.log_param("max_depth", 6) mlflow.log_param("n_estimators", 300) # ... training code ... mlflow.log_metric("accuracy", 0.954) mlflow.log_metric("roc_auc", 0.981) mlflow.log_metric("f1_score", 0.873) # Log confusion matrix plot mlflow.log_figure(fig, "confusion_matrix.png") # Log the model itself mlflow.sklearn.log_model(model, "model", registered_model_name="FraudDetector") → Run ID: a3f7c821 → Artifact URI: s3://mlflow-artifacts/a3f7c821

A logical grouping of runs. Like a project folder. "fraud-detection", "recommendation-v2"

  • UI is functional but not beautiful — enterprise teams prefer Weights & Biases

  • Model artifact — the serialized model file (.pkl, SavedModel)
  • MLmodel file — metadata (flavor, Python version, dependencies)

  • Code snapshot — git commit that produced this model
  • Tags & comments — approval notes, performance summary

Hyperparameter
Tuning

Hyperparameters are the "knobs" on a model — learning rate, tree depth, number of neurons. Training finds the best weights. Hyperparameter tuning finds the best knob settings. It's like finding the best recipe before you start cooking.

Grid Search (Brute Force)

Try every combination of every value. lr=[0.01,0.1] × depth=[3,6,9] = 6 runs. Simple but exponentially expensive. Good only for 2-3 hyperparameters.

⚠️ 5 params × 5 values each = 3,125 training runs

Random Search (Smarter)

Randomly sample from the hyperparameter space. Surprisingly 2-5x more efficient than grid search in practice. Best when you have a budget of N runs.

✓ Standard baseline — always try this first

Bayesian Optimization (Smartest)

Builds a model of the hyperparameter landscape. Uses past run results to predict which regions are promising. 10x fewer runs for the same quality.

✓ Best for expensive GPU training runs

Optuna — Bayesian Hyperparameter Search

import optuna import mlflow def objective(trial): # Optuna suggests hyperparameter values params = { "learning_rate": trial.suggest_float("lr", 1e-4, 0.3, log=True), "max_depth": trial.suggest_int("depth", 3, 10), "subsample": trial.suggest_float("sub", 0.5, 1.0), "n_estimators": trial.suggest_int("n_est", 100, 1000), } with mlflow.start_run(nested=True): mlflow.log_params(params) model = train_model(**params) auc = evaluate(model) mlflow.log_metric("auc", auc) return auc # Optuna maximizes this # Run 50 trials, using TPE (Bayesian) sampler study = optuna.create_study(direction="maximize") study.optimize(objective, n_trials=50, n_jobs=4) Best params: {'lr': 0.023, 'depth': 7, 'sub': 0.85, 'n_est': 650} Best AUC: 0.9847
⚡ Parallel Tuning on Kubernetes: Run each trial in a separate Kubernetes pod. Optuna has built-in support for distributed studies using a shared PostgreSQL database. 50 trials that take 10 min each = 500 minutes serial = 25 minutes on 20 pods.

Model Evaluation
Metrics That Matter

A model that's 99% accurate sounds amazing. But if 99% of your data is "normal" and 1% is fraud, a model that always says "not fraud" gets 99% accuracy and catches zero fraud cases. This is why understanding the right metrics is critical.

Deployment
Strategies

Just like deploying apps, deploying new ML models carries risk. A model that performed great offline can underperform in production for subtle reasons (different data distribution, edge cases). These strategies let you manage that risk.

🐦 Canary Deployment

Route a small percentage of traffic (e.g., 5%) to the new model. Monitor its performance vs the control group. If all is well, gradually increase to 100%.

  • 5% → 10% → 25% → 50% → 100%
  • Easy rollback: just route 0% to new model
  • Real user data validates the model
  • Requires traffic splitting (Istio, AWS ALB)
RecommendedLow risk
🔵🟢 Blue-Green Deployment

Run the old model (Blue) and new model (Green) in parallel. Instantly switch all traffic from Blue to Green at once. Rollback = switch back to Blue.

  • Zero-downtime switch
  • Full parallel environments (double cost)
  • Instant rollback capability
  • Same as App Service slot swaps
Zero downtime2x cost
👻 Shadow Mode

The new model receives all real traffic in parallel but its predictions are NOT shown to users. You compare new vs old model outputs in real-time, with zero risk to users.

  • Best pre-deployment validation
  • Detects edge cases real data has but test data didn't
  • No user impact whatsoever
  • Requires logging infrastructure for comparison
Zero riskBest practice
🎲 A/B Testing

Similar to canary, but explicitly for comparing two model variants as a statistical experiment. 50% of users go to model A, 50% to model B. Measure business outcomes, not just ML metrics.

  • Measures real business impact (clicks, revenue)
  • Requires statistical significance (run for days/weeks)
  • Must hold all other variables constant
  • Tools: Optimizely, LaunchDarkly, custom Istio
Business KPIsStatistical rigor
🏆 Recommended Production Pattern: Shadow Mode (1-3 days) → Canary 5% (24 hours) → Canary 25% (24 hours) → Canary 100%. This gives you confidence at every step with minimal user impact.

Data Drift
Detection

Data drift is when the real-world data your model sees in production starts looking different from the training data. Imagine training a fraud model on 2022 transactions — by 2024, payment methods, amounts, and merchant categories have all changed. The model silently degrades.

Data Drift

The statistical distribution of input features changes. Example: average transaction amount used to be $50, now it's $200 — but your model was trained when $50 was normal.

Feature distribution shift
Concept Drift

The relationship between features and the target label changes. Example: in 2020, using a VPN was suspicious. Now it's normal. Same features, different meaning for fraud.

Label relationship shifts
Label Drift

The distribution of the target label changes. Example: fraud rate was 0.1% in training, but in production it's now 2%. The model's threshold is calibrated for the wrong base rate.

Target distribution shifts

📊 Statistical Tests for Drift:
KS Test (Kolmogorov-Smirnov): Compares two distributions by their cumulative density functions. p-value < 0.05 means drift is likely.

Population Stability Index (PSI): Industry standard in banking. PSI < 0.1 = stable, PSI 0.1-0.2 = slight drift, PSI > 0.2 = significant drift, trigger retraining.
🎯 Practical Approach: Don't wait for model accuracy to drop (you need ground truth labels which arrive with a delay). Instead, monitor input feature distributions daily. Drift in inputs predicts accuracy drop before it happens, giving you time to retrain proactively.

Model Retraining
When and How

Retraining keeps your model current by incorporating new data. The question is: when do you retrain? There are three strategies — scheduled (simple), triggered by drift (smart), or triggered by business metrics (business-aligned). All three have a place.

📅 Schedule-Based

Retrain every Sunday at 2 AM. Simple. Predictable costs. Doesn't require monitoring infrastructure.

✓ Start here. Simple to implement.

✗ Wasteful when data is stable. May be too slow when it's not.

📊 Drift-Triggered

Retrain only when drift monitoring detects significant distribution shift. More efficient. Requires drift monitoring setup first.

✓ Best for data with unpredictable change patterns.

✗ Requires monitoring pipeline. False positives waste compute.

📉 Performance-Triggered

Retrain when model accuracy (or a proxy like click-through rate) drops below a threshold. Most business-aligned.

✓ Directly tied to business impact.

✗ Requires labeled ground truth — delayed by hours/days.

Automated Retraining Pipeline

# Triggered by Airflow DAG or GitHub Actions def retrain_pipeline(): # 1. Fetch latest data (last 90 days) new_data = fetch_training_data( start_date="now-90d", end_date="now") # 2. Validate new data quality validation_result = validate_data(new_data) if not validation_result.success: alert_and_abort("Retraining data failed validation") # 3. Train new model (same pipeline, new data) with mlflow.start_run(run_name="auto-retrain"): new_model, metrics = train_model(new_data) # 4. Compare vs current production model prod_metrics = get_production_model_metrics() if metrics["auc"] < prod_metrics["auc"] * 0.995: alert("New model underperforms. Not deploying.") return # 5. Auto-promote to staging if improved promote_model_to_staging(new_model) notify_team("New model candidate ready for review") # 6. 💡 Retraining Data Strategy:
Rolling window: Always train on last 90 days. Recent patterns dominate. Simple.

Expanding window: Add new data to all historical. Model sees everything. Can dilute recent patterns.

Weighted: Include all history but give recent data 2x weight. Best of both worlds. Complex.
⚠️ Catastrophic Forgetting

If you train only on recent data, the model may "forget" rare but important patterns (e.g., seasonal fraud spikes from 18 months ago). Always include enough historical data to cover seasonal cycles.

Kubeflow
Pipelines

Kubeflow Pipelines (KFP) is the most powerful open-source ML pipeline orchestrator. It runs on Kubernetes and lets you define ML pipelines as Python functions that are automatically containerized and executed as k8s pods. Every step is isolated, logged, and resumable.

Layman explanation: Think of Kubeflow Pipelines like GitHub Actions — but instead of CI steps, the steps are: "load data", "preprocess", "train model", "evaluate model", "deploy model". Each step runs in its own Docker container on Kubernetes. If step 3 fails, you can retry from step 3 without re-running steps 1 and 2.

Kubeflow Pipeline — Python DSL

import kfp from kfp import dsl from kfp.components import create_component_from_func # Each component runs in its own container @dsl.component(base_image="python:3.11-slim", packages_to_install=["pandas", "scikit-learn"]) def preprocess_data( input_path: str, output_path: dsl.Output[dsl.Dataset]): import pandas as pd df = pd.read_parquet(input_path) df.to_parquet(output_path.path) @dsl.component(base_image="python:3.11-slim", packages_to_install=["xgboost", "mlflow"]) def train_model( data: dsl.Input[dsl.Dataset], model: dsl.Output[dsl.Model], learning_rate: float = 0.01): import xgboost as xgb # ... training logic ... trained_model.save_model(model.path) # Compose pipeline @dsl.pipeline(name="fraud-training-pipeline") def fraud_pipeline(lr: float = 0.01): prep_task = preprocess_data(input_path="s3://data/raw") train_task = train_model( data=prep_task.outputs["output_path"], learning_rate=lr ) # Compile and submit client = kfp.Client(host="http://kfp.internal") client.create_run_from_pipeline_func(fraud_pipeline)
KFP Features
  • Component caching: Skip steps whose inputs haven't changed
  • Conditional steps: Only deploy if accuracy > threshold
  • Parallel steps: Run hyperparameter trials simultaneously
  • Artifact lineage: Track which data produced which model
  • Pipeline versioning: Every pipeline run has a reproducible graph
  • Recurring runs: Schedule pipeline on cron
  • Resource limits: Specify CPU/GPU/memory per step

Security
in MLOps

ML systems have unique security challenges beyond standard application security. Model weights can be stolen, training data can be poisoned, and adversarial inputs can trick models. As a DevOps engineer, you need to secure the entire pipeline — from data ingest to prediction endpoint.

🎯 Model Theft

Attackers make thousands of API calls to reverse-engineer your model's decision logic and replicate it. Protect against it with rate limiting, output obfuscation, and anomalous query detection.

High risk
☠️ Data Poisoning

Attacker injects malicious training examples to deliberately bias the model. E.g., injecting fraud samples labeled as "legitimate" to degrade your fraud detector.

Training attack
🎭 Adversarial Inputs

Inputs carefully crafted to fool the model. E.g., a stop sign with stickers that an autonomous vehicle classifies as a speed limit sign. Hard to fully prevent.

Inference attack
🛡️ MLOps Security Checklist
  • Use Managed Identities for all service-to-service auth — no hardcoded credentials
  • Store model artifacts in private buckets with IAM access control
  • Sign model artifacts (checksum/hash) and verify on load — detect tampering
  • Rate-limit prediction endpoints — prevent model extraction attacks
  • Validate and sanitize all input features at the API layer
  • Use Private Endpoints for all PaaS services (MLflow server, model registry)
  • Scan training data for anomalies before ingesting — detect poisoning
  • Enforce RBAC on who can promote models to production (approval gates)
  • Audit all training runs and model deployments for compliance
  • Encrypt model weights at rest and in transit (AES-256, TLS 1.3)
  • Run Defender for Containers on all model-serving pods
  • Implement output monitoring — flag anomalous prediction patterns
