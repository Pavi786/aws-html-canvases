🧑‍🏫 What is Auto Scaling? (Layman)Imagine a restaurant. On a quiet Tuesday, 2 chefs are enough. On Friday night, you need 10. Auto Scaling is like a manager who automatically calls in more chefs when it gets busy and sends them home when it's quiet — you never pay for idle chefs, and customers never wait too long.
Scaling Policies — Choose the Right One

Target Tracking (Use This First)

Tell ASG: "keep average CPU at 60%." It figures out how many instances to add or remove. Like a thermostat — you set the temperature, it controls the heat.

  • Best for: most web and API workloads
  • Add metric: ALBRequestCountPerTarget is more accurate than CPU for APIs
  • Set scale-in cooldown: 300s (5 min) to avoid yo-yo scaling
Scaling Policies

Predictive Scaling (Use with Target Tracking)

Uses machine learning to analyze past 2 weeks of traffic patterns and pre-scales BEFORE the spike hits. Like knowing every Friday at 12pm you get 5000 orders — so you staff up at 11:45am.

  • Pre-warms instances 5-10 minutes before predicted spike
  • Works best with weekly patterns (business hours, weekly cycles)
  • Enable in "ForecastAndScale" mode for full automation

🧑‍🏫 What is Nitro?

Traditional servers share hardware between the machine and your software — wasting resources. Nitro moves all the "hardware management" to dedicated chips, so 100% of CPU and RAM goes to YOUR workload. It's like having a dedicated support staff so the engineer can focus only on engineering. It also means much better security — your neighbor can't see your data.

Nitro Hypervisor

Micro-VM with Near Bare-Metal

  • Consumes <1% of CPU overhead (vs 10%+ for Xen)
  • Hardware-enforced isolation between VMs
  • Required for latest instance generations (m6i+, c6i+)
  • Enables ENA (Enhanced Networking) by default
Nitro Cards

Dedicated Offload Hardware

  • NVMe: dedicated card manages all EBS I/O
  • Networking: dedicated card manages all VPC network
  • Security: dedicated Nitro Security Chip — encrypted memory
  • Result: no noisy neighbor, predictable performance
Nitro Enclaves

Isolated Secure Compute

  • Isolated VM with NO persistent storage, NO interactive access, NO external networking
  • Only communicates via local vsock with parent EC2
  • Use case: processing PII, cryptographic operations, ML model IP protection
  • Cryptographic attestation proves what code is running
Cluster Placement Group

All in Same Rack

Instances are physically close — same rack in same AZ. Network latency between them is <1ms. Use when your app nodes talk to each other constantly (HPC, Kafka, distributed databases). Risk: if rack fails, all instances fail.

Spread Placement Group

Each on Different Hardware

Each instance is on its own physical rack. Maximum HA — one rack failure only takes out one instance. Use for critical small clusters (3-7 nodes max). Limit: 7 instances per AZ per group.

Partition Placement Group

Groups on Different Racks

Divide your fleet into partitions (e.g., 3 partitions × N instances). All instances in partition 1 are on rack-set-A, partition 2 on rack-set-B. Used for Hadoop, Cassandra — rack-aware replication.

✓ EC2 Do's
  • Enforce IMDSv2 via SCP — prevents SSRF attacks from stealing instance credentials
  • Use SSM Session Manager instead of SSH bastion hosts — no open port 22, full audit trail
  • Migrate gp2 → gp3 EBS volumes: same/better IOPS, 20% cheaper, independent IOPS provisioning
  • Tag every resource with: Environment, Team, Application, CostCenter — enforce with Config Rules
  • Use Launch Templates (not Launch Configurations) — supports versioning, mixed instances
  • Enable Detailed CloudWatch Monitoring (1-min intervals) for all production instances
  • Prefer Graviton (ARM) instances where possible — 20% better price/performance
✗ EC2 Don'ts
  • Never store secrets in EC2 User Data — visible in plaintext via metadata API and console
  • Never assign public IPs directly to production instances — use ALB + private subnets
  • Don't give EC2 instances overly permissive IAM roles — use least-privilege instance profiles
  • Never use T-series instances for sustained high-CPU production workloads — credit exhaustion causes throttling with zero warning
  • Don't run stateful applications on Spot without interruption handler and checkpoint/resume logic
  • Never skip EC2 Health Events in EventBridge — disk, network, and VM failures are announced in advance

🧑‍🏫 Cold Start Explained Simply

Imagine waking a sleeping employee vs. one who's already at their desk. Cold start is the time it takes to "wake up" a new Lambda environment — download your code, load it into memory, run setup code. This takes 100ms–1 second+. Subsequent calls use the "warm" environment and are instant. For user-facing APIs, cold starts feel laggy. The solutions: Provisioned Concurrency (always awake), SnapStart (Java snapshots), or smaller deployment packages.

Solution 1

Provisioned Concurrency

Pre-initialize N Lambda environments — they're always warm, never cold-start. You pay for idle time but get guaranteed sub-millisecond startup. Use Application Auto Scaling to scale PC up during business hours and down at night.

  • Cost: ~$0.000015/GB-sec for provisioned environments
  • Best for: user-facing APIs with latency SLAs
  • Combine with ASG: schedule based on traffic patterns
Solution 2 — Java Only

SnapStart

AWS takes a snapshot of your Java Lambda after initialization, then restores from that snapshot. Like hibernating a laptop vs rebooting — 10× faster. Free, just enable it.

  • Supported: Java 11, Java 17, Java 21
  • Reduces Java cold starts from 2-10s → under 1s
  • Requires: functions must be safe to restore from snapshot
Solution 3

Reduce Package Size

Smaller deployment packages = faster download during init. A 50MB Python package cold-starts much faster than a 500MB one. Lazy-load heavy imports inside handler logic rather than top of file.

  • Use Lambda Layers for shared libs — cached separately
  • Use container images for large deps (>250MB zipped)
  • Python: avoid importing heavy libs globally (boto3 loads fast, pandas does not)
💡 Lambda Memory = CPU (most people don't know this) Lambda doesn't let you set CPU directly. But CPU allocation is proportional to memory. 128MB = 1/13 of a vCPU. 1,769MB = exactly 1 full vCPU. 3,538MB = 2 vCPUs. For CPU-bound functions, doubling memory often halves execution time, making it the same or lower cost despite more memory.

🧑‍🏫 Concurrency Explained Simply

Concurrency = how many Lambda copies run simultaneously. If 100 people call your API at the same time, 100 Lambda instances run in parallel. Your AWS account has a shared pool of 1,000 concurrent Lambdas by default. Without Reserved Concurrency, one runaway function can eat ALL 1,000 slots, starving your other functions. Reserved Concurrency is like reserving parking spaces — guaranteed, but limited.

Reserved Concurrency

Guaranteed + Capped Allocation

  • Sets both a floor (guaranteed allocation) AND ceiling (max cap)
  • Setting RC = 0 disables the function (useful for emergency stop)
  • Always leave 100 unreserved at account level for burst capacity
  • Formula: required concurrency = (req/sec) × (avg duration in sec)
Provisioned Concurrency

Pre-warmed Environments

  • Always-ready environments — zero cold start latency
  • Must be combined with Reserved Concurrency
  • Only provision what you need — it costs money when idle
  • Use Application Auto Scaling to schedule up/down

Pattern 1 — Most Common

API Gateway → Lambda

HTTP request hits API Gateway, triggers Lambda, returns response. The classic serverless API. Use Lambda Function URLs for simpler cases (no API GW needed). Add Lambda Authorizer for JWT auth at edge.

Pattern 2

S3 Event → Lambda

File uploaded to S3 triggers Lambda. Use for: image resizing, CSV processing, virus scanning, thumbnail generation. Always use EventBridge instead of S3 native notifications for reliability and filtering.

Pattern 3

SQS → Lambda (Queue Worker)

Lambda polls SQS queue and processes messages in batches. Most reliable async pattern. Lambda automatically scales instances based on queue depth. Enable "Report Batch Item Failures" to only retry failed messages.

Pattern 4

DynamoDB Streams → Lambda

Every change to a DynamoDB table triggers Lambda with the old and new data. Use for: real-time analytics, cache invalidation, cross-region replication, audit logging. Maximum 2 triggers per shard.

Pattern 5

EventBridge Scheduler → Lambda

Like a cron job but serverless. Schedule Lambda to run every 5 minutes, at midnight, or on complex schedules. Much more reliable than self-calling Lambda. Supports timezone-aware scheduling.

Pattern 6

Lambda@Edge (CloudFront)

Run Lambda code at 450+ CloudFront edge locations — milliseconds from users worldwide. Use for: A/B testing, authentication at edge, request/response rewriting, geo-blocking. Max 128MB, 30s timeout.

Lambda Best Practice — Python with Powertools (Production-Ready) 
"""
Production Lambda: structured logging, tracing, metrics, error handling.
Use aws-lambda-powertools — it handles all the boilerplate.
pip install aws-lambda-powertools
"""
import os, json, boto3
from aws_lambda_powertools import Logger, Tracer, Metrics
from aws_lambda_powertools.metrics import MetricUnit
from aws_lambda_powertools.utilities.typing import LambdaContext
from aws_lambda_powertools.utilities.batch import (
    BatchProcessor, EventType, process_partial_response
)

# ── Module-level: runs once per container (not per invocation) ──
logger  = Logger()                                     # JSON structured logs
tracer  = Tracer()                                     # X-Ray auto-patch
metrics = Metrics(namespace="MyApp", service="OrderService")

dynamodb = boto3.resource('dynamodb')                  # reuse connection!
table    = dynamodb.Table(os.environ['ORDERS_TABLE'])  # resolved once
processor = BatchProcessor(event_type=EventType.SQS)   # SQS batch

# ── Secrets cache — avoid calling SM per invocation ──
_cache = {}
def get_secret(key):
    if key not in _cache:
        sm = boto3.client('secretsmanager')
        _cache[key] = json.loads(sm.get_secret_value(SecretId=key)['SecretString'])
    return _cache[key]

def process_message(record):
    body = json.loads(record.body)
    logger.info("Processing order", order_id=body['id'])
    table.put_item(Item=body)
    metrics.add_metric(name="OrdersProcessed", unit=MetricUnit.Count, value=1)

@tracer.capture_lambda_handler
@logger.inject_lambda_context(log_event=False, clear_state=True)
@metrics.log_metrics(capture_cold_start_metric=True)   # track cold starts!
def handler(event: dict, context: LambdaContext):
    # Always check remaining time for long-batch processing
    if context.get_remaining_time_in_millis() < 2000:
        logger.warning("Low time budget", remaining_ms=context.get_remaining_time_in_millis())

    # Process SQS batch — only retry failed messages (not whole batch)
    return process_partial_response(
        event=event, record_handler=process_message,
        processor=processor, context=context
    )
✓ Lambda Do's
  • Initialize SDK clients, DB connections, and secrets OUTSIDE the handler (module level) — they persist across warm invocations
  • Set timeout to 2× your measured P99 execution time — not the max 15 minutes
  • Use ARM (Graviton2) runtime — 20% cheaper, same performance
  • Always configure DLQ or SQS for async invocations — otherwise failed events silently disappear
  • Use AWS Lambda Powertools — structured logging, tracing, and batch processing in one library
  • Enable Report Batch Item Failures for SQS triggers — partial batch failure handling
✗ Lambda Don'ts
  • Never use Lambda for tasks over 15 minutes — use ECS Fargate or AWS Batch instead
  • Don't put Lambda inside a VPC unless absolutely needed — adds 100-400ms cold start overhead (use PrivateLink instead)
  • Never let Lambda call itself recursively without a stop condition — will run 1000 copies at once and burn through your budget in minutes
  • Don't hardcode AWS region or account ID — use environment variables or context
  • Never set Reserved Concurrency to exactly your account limit — leaves no room for other functions or burst handling
Page 03 of 23 — Compute: ECS & Fargate
ECS
Elastic Container Service
Run Docker containers at scale — with or without managing servers (Fargate)
🧑‍🏫 Layman Explanation

A Docker container is like a packed lunchbox — your app and everything it needs, all in one box. ECS is the kitchen manager that decides which fridge (server) each lunchbox goes into, ensures enough lunchboxes are ready during lunch rush, and replaces spoiled ones. Fargate is the option where AWS handles the fridges too — you just say "I need 10 lunchboxes" and they appear. You never touch a server.

ECS on EC2 — You Manage Servers

EC2 Launch Type

You run EC2 instances as the "cluster." ECS schedules containers on those instances. More control over instance types, storage, placement. Better for GPU workloads, extreme performance, or cost optimization with Spot.

  • Manage: EC2 instance patching, AMI updates, capacity
  • Advantage: use Spot EC2 → 70-90% cheaper than Fargate
  • Use Capacity Providers to mix Spot + On-Demand automatically
  • Better for workloads with specific instance requirements (NVMe, GPU)
ECS Fargate — Serverless Containers

Fargate Launch Type

No EC2 instances to manage. You define CPU and memory per task, AWS runs it on invisible infrastructure. Pay per-second for vCPU and GB used. Simpler ops, slightly higher cost than EC2 Spot.

  • No patching, no capacity planning, no AMI management
  • Fargate Spot: 70% cheaper — same interruption caveats as EC2 Spot
  • Each task gets its own network interface (ENI) — better isolation
  • Best for: microservices, APIs, batch jobs, small teams without DevOps

    name      = "api"

}

✓ ECS Do's
  • Enable ECS Exec (SSM-based) for interactive container debugging in production — no SSH, full audit
  • Use Deployment Circuit Breaker — auto-rollback when new task version fails health checks
  • Set both CPU and Memory reservations AND limits in task definitions — prevents noisy neighbor
  • Use Capacity Providers with managed scaling — ECS auto-adjusts EC2 fleet size for you
  • Pull secrets from Secrets Manager at task startup, not in Docker image build
✗ ECS Don'ts
  • Never bake secrets or environment-specific config into Docker images — use task definition environment/secrets
  • Don't set desired_count = 1 for any production service — zero-downtime deployments require minimum 2
  • Never ignore ECS Task health checks — failed tasks without health check = silent failures
  • Don't use bridge networking mode for Fargate — awsvpc is required and provides better isolation

EKS
Elastic Kubernetes Service
Managed Kubernetes — the industry standard for container orchestration at scale
🧑‍🏫 Layman Explanation

Kubernetes is like an air traffic control system for containers. Hundreds of planes (containers) taking off and landing, each going to different terminals (servers). Kubernetes tracks all of them, routes them correctly, restarts any that crash, and ensures no runway (server) is overloaded. EKS means AWS manages the control tower (Kubernetes control plane) — you manage the runways (worker nodes) or use Fargate for those too.

EKS Control Plane

Managed by AWS — $0.10/hr

  • AWS runs kube-apiserver, etcd, schedulers across 3 AZs
  • Automatically patched, upgraded, and backed up
  • Version upgrades: in-place, rolling — test in staging first
  • Control plane logs to CloudWatch: api, audit, authenticator, scheduler
Worker Nodes — 3 Options

Managed Node Groups

  • AWS manages EC2 lifecycle (launch, drain, terminate)
  • Rolling updates handle drain/cordon automatically
  • Spot support built-in via Karpenter or Managed Node Groups
  • Best default choice for most teams
Node Autoscaling

Karpenter (Recommended)

  • Replaces Cluster Autoscaler — 10× faster node provisioning
  • Directly calls EC2 APIs — no ASG overhead
  • Selects cheapest available instance type that fits workload
  • Consolidation: bin-packs pods and removes underutilized nodes

Route 53
AWS DNS — route users to the right servers with health checks and traffic policies
🧑‍🏫 Layman Explanation

DNS is the internet's phone book. When you type "google.com", your computer asks: "what's Google's IP address?" Route 53 is your phone book. But it's a smart phone book — if Google's New York office is down, it automatically gives callers the London office number. It can also route 10% of calls to a new experimental office for testing. Routing Policies

Simple

One record, one IP. For basic single-server setups. No health checks. Like putting one phone number in a phonebook. Use only for dev/test.

Routing Policies

Failover (Active-Passive)

Primary record used until health check fails, then Route 53 automatically switches to secondary record. Your DR site. Failover happens in 30-60 seconds. Use for: RDS read replica promotion, cross-region failover.

Routing Policies

Latency-Based

Route users to the AWS region that gives them lowest latency. User in Tokyo goes to ap-northeast-1. User in London goes to eu-west-1. No configuration needed — AWS measures latency automatically.

Routing Policies

Weighted

Send X% to record A, Y% to record B. Use for: canary deployments (send 5% to new version), A/B testing, gradual traffic shifting. Weight 0 = send no traffic (useful for removing a backend).

Routing Policies

Geolocation

Route users based on their country or continent. EU users go to EU infrastructure (GDPR compliance). US users stay in US. Fallback record for all other locations is mandatory.

Routing Policies

Geoproximity (Traffic Flow)

Like Geolocation but with "bias" — expand or shrink the geographic area that routes to each region. Shift traffic from US-East to US-West during an incident without changing locations.

DDB
DynamoDB
Serverless NoSQL database — single-millisecond performance at any scale
🧑‍🏫 Layman Explanation

A regular database (like a spreadsheet) needs you to define all your columns upfront. DynamoDB is like a flexible notebook where each row can have different fields. It's incredibly fast — reads and writes in under 1 millisecond even with billions of rows. AWS handles all the infrastructure, replication, backups, and scaling. The trade-off: you MUST know your access patterns upfront — the table design depends entirely on how you'll query data.

Data Modeling — The Golden Rule

Single Table Design

In SQL, you create many tables. In DynamoDB, put all your data in ONE table with clever keys. Think of it as filing everything in one giant drawer with smart labels. This enables efficient queries without expensive joins.

Example: Entity: PK=USER#user123, SK=PROFILE | Entity: PK=USER#user123, SK=ORDER#2024-01-15. Same table, different sort keys. One query gets all of a user's data.
Capacity Modes

On-Demand vs Provisioned

  • On-Demand: AWS auto-scales, pay per request. No capacity planning. 2.5× more expensive but zero ops. Best for unpredictable or low traffic.
  • Provisioned: You set Read/Write Capacity Units. Use Auto Scaling. Add Reserved Capacity for 80% savings on baseline. Best for predictable, sustained traffic.
  • Switch between modes once per 24 hours

✓ DynamoDB Do's
  • Design your data model around access patterns FIRST — draw out every query you need before designing table keys

✗ DynamoDB Don'ts

# Sliding window rate limiter — allow 100 requests per minute per user
def is_rate_limited(user_id):
    key = f"ratelimit:{user_id}"
    pipe = r.pipeline()
    now = int(time.time() * 1000)           # millisecond timestamp
    window = now - 60000                     # 60 seconds ago
    pipe.zremrangebyscore(key, 0, window)    # remove old entries
    pipe.zadd(key, {str(now): now})          # add current request
    pipe.zcard(key)                           # count requests in window
    pipe.expire(key, 60)                     # cleanup old keys
    results = pipe.execute()
    return results[2] > 100                  # True = rate limited

Simple Queue Service

🧑‍🏫 Layman Explanation

Imagine a ticket counter at a concert. Fans (messages) arrive faster than staff can process them. Without a queue, fans pile up chaotically — some give up. Messages delivered exactly once, in strict order. Limited to 3,000 messages/sec (with batching). Use for: financial transactions, order processing, anywhere duplicates cause real problems. 20% more expensive.

X-Ray
AWS X-Ray
Distributed tracing — follow a request through every service it touches
🧑‍🏫 Layman Explanation

User makes a request to your API. It goes through: API Gateway → Lambda → DynamoDB → an external payment API. Somewhere, 800ms is wasted. But where? X-Ray is like a GPS tracker attached to each request. You see: "API GW took 5ms, Lambda init took 200ms, DynamoDB took 3ms, payment API took 592ms." Now you know exactly where to optimize. Without X-Ray, you'd be guessing.

X-Ray Concepts

Traces, Segments, Subsegments

  • Trace: the complete journey of one request (unique trace ID)
  • Segment: one service's view (Lambda, API Gateway, ECS task)
  • Subsegment: operation within a service (DynamoDB call, HTTP request)
  • Trace ID propagated via HTTP header: X-Amzn-Trace-Id
  • Service Map: visual graph of all services and their connections
Sampling Rules

Don't Trace Everything

  • Default: 5% of requests sampled (to control cost)
  • Custom rules: 100% for error requests, 10% for health checks
  • Reservoir: fixed number of traces per second (ensure minimum coverage)
  • Always trace error responses regardless of sampling rate
  • Use ADOT (OpenTelemetry) for vendor-neutral tracing exportable to Datadog/Grafana
IAM
Identity & Access Management
Who can do what to which resources — the foundation of AWS security
🧑‍🏫 Layman Explanation

IAM is your company's badge and key card system. Every person (user), application (role), and service gets a badge. Each badge only opens specific doors (permissions). A janitor's badge opens cleaning closets, not the server room. A developer's badge opens staging but not production. If a badge is stolen, it has expiry dates and can be immediately revoked. No badge = no access, anywhere.

IAM Principals

Who Can Act in AWS

  • IAM Users: human users (avoid for prod — use IAM Identity Center SSO)
  • IAM Roles: assumed by services (EC2, Lambda, ECS) or humans temporarily
  • IAM Groups: collection of users with shared permissions
  • Service principals: AWS services acting on your behalf (CodeBuild, Lambda)
  • Federated identities: Google/AD users via SAML/OIDC
Policy Types

How Permissions Are Granted

  • Identity-based: attached to user/role (what they can do)
  • Resource-based: attached to resource (who can access it) — S3, SQS, KMS
  • SCPs (Service Control Policies): org-level guardrails — restrict what even admins can do
  • Permission Boundaries: maximum permissions a role can have — prevent privilege escalation
IAM Best Practices

Zero Trust Approach

  • Enable IAM Identity Center (SSO) — no long-lived IAM user credentials
  • Use OIDC for GitHub Actions — no access keys in CI/CD
  • IAM Access Analyzer — find unintended external access
  • Enable MFA for all humans — especially root account
  • Enable CloudTrail — every API call is logged, tamper-proof

Step Functions
Visual workflow orchestration — coordinate Lambda, ECS, and AWS services without managing state
🧑‍🏫 Layman Explanation

Imagine processing a loan application: verify identity → check credit score → calculate risk → get manager approval → send decision email. Each step depends on the previous. If one fails, you need to retry or go to a different path. Step Functions is like a LEGO flow chart that actually executes. You draw the steps visually, and AWS handles: running them in order, retrying failures automatically, waiting for human approval, and recording every step for audit.

Standard Workflows

Long-Running, Durable

  • Up to 1 YEAR execution duration
  • Exactly-once execution for each step
  • State persisted in Step Functions (not your code)
  • Full audit history of every state transition
  • Wait for human approval: pause execution for days waiting for callback
  • $0.025 per 1,000 state transitions
Express Workflows

High-Volume, Short-Duration

  • Up to 5 MINUTES execution
  • 100,000+ executions/second throughput
  • At-least-once (async) or exactly-once (sync) mode
  • Much cheaper: $1 per 1M state transitions
  • Best for: IoT event processing, real-time data processing, API backends

Cost Optimization
FinOps — spend smart, eliminate waste, and maximize value from every AWS dollar
🧑‍🏫 Layman Explanation

AWS makes it incredibly easy to spend money without realizing it. A forgotten test environment, data transfer fees you didn't know existed, over-sized instances "just to be safe" — these add up to thousands per month. FinOps is the practice of treating cloud spend like engineering — measure it, model it, optimize it, and make every engineer responsible for their cost footprint. The best teams can run the same workload for 60-80% less by applying these principles.

  • Reserved/Savings Plans — Biggest Lever (60-72% savings)Analyze 30 days of usage in Cost Explorer → get Savings Plans recommendations → purchase. Target 70-80% coverage of steady-state compute. Compute Savings Plans are most flexible (cover EC2 + Lambda + Fargate). Review quarterly.
  • NAT Gateway Data Transfer — Most Surprising Bill (often $1,000s/month)NAT Gateway charges $0.045/GB. Every S3 and DynamoDB API call that routes through NAT GW costs money. Add S3 and DynamoDB Gateway Endpoints (free) on day one. Use VPC Flow Logs to find other heavy NAT users.
  • Right-Size Instances — Compute Optimizer (free, ML-based)AWS Compute Optimizer analyzes 14 days of CloudWatch metrics and recommends the optimal instance type. Most environments have 30-40% of instances overprovisioned. CloudWatch Agent required for memory metrics — install on all EC2.
  • Spot Instances for Non-Critical Workloads (70-90% savings)Dev/test, batch jobs, ML training, CI/CD build agents — all excellent Spot candidates. Run CI/CD on Spot: save 80% on build compute. Use AWS Batch for ML training with Spot — automatic checkpointing on interruption.
  • S3 Intelligent-Tiering + Lifecycle (free management fee for IT)Enable IT on all S3 objects >128KB. It automatically moves objects between tiers based on access. Lifecycle rules: STANDARD → STANDARD_IA at 30 days → GLACIER at 90 days → DEEP_ARCHIVE at 365 days. The biggest savings: abort incomplete multipart uploads (lifecycle rule: 7 days).
  • Schedule Dev/Test Environments Off-Hours (save 65%)Dev envs don't need to run 24/7. Use Instance Scheduler or EventBridge to stop EC2 and RDS instances at 7pm, start at 8am weekdays. RDS instances cost $0 when stopped (for up to 7 days). Savings: (16hr/24hr) × weekend = 65% reduction.
  • EBS Volume Audit (gp2 → gp3 migration + delete orphans)gp3 is 20% cheaper than gp2 and you can provision IOPS/throughput independently. Delete unattached EBS volumes (often left after EC2 termination). Use AWS Config rule "ec2-volume-in-use-check" to find orphans. Also audit EBS snapshots — old ones accumulate silently.
  • Cost Anomaly Detection + Tagging + Budgets (prevent surprises)Enable Cost Anomaly Detection (free) — ML alerts you when any service spends more than normal. Enforce tags with SCPs. Budget alerts at 50%, 80%, 100% of monthly target. Weekly FinOps review with Engineering leads — cost ownership at the team level.
