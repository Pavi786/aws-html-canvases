What is an Ingress Controller?
All Platforms

An Ingress Controller is a specialized load balancer for Kubernetes that manages external access to services inside a cluster. It acts as the entry point for HTTP and HTTPS traffic, reading Ingress resources and configuring its underlying load balancer accordingly.

Unlike a Service of type LoadBalancer (which provisions one cloud load balancer per service), an Ingress Controller can route traffic to many services through a single IP and port, using host-based or path-based routing rules.

Internet │ ▼ ┌─────────────────────────────────────────────────────────┐ │ Ingress Controller │ │ (NGINX / Traefik / HAProxy / AWS ALB / AGIC) │ │ │ │ Rules: │ │ api.example.com/v1 ──────▶ Service: api-svc:80 │ │ api.example.com/v2 ──────▶ Service: api-v2-svc:80 │ │ app.example.com ──────▶ Service: frontend-svc:80 │ └─────────────────────────────────────────────────────────┘ │ │ │ ▼ ▼ ▼ Pod (api) Pod (api-v2) Pod (frontend)
ℹ
The Ingress resource (the YAML you write) and the Ingress Controller (the software running in the cluster) are two distinct things. Kubernetes does not ship with a default Ingress Controller — you must install one.

Why Ingress Controllers Exist

Cost Efficiency
One cloud load balancer instead of one per service. Critical at scale — without Ingress, 50 services = 50 LBs.
Smart Routing
Host-based, path-based, header-based, and weighted routing rules in a single declarative resource.
TLS Termination
Centralized SSL/TLS management. cert-manager automates Let's Encrypt certificate issuance and renewal.

How Ingress Actually Works
All Platforms

Understanding the control loop is critical for debugging. The Ingress Controller is a reconciliation loop that watches Ingress resources and configures its proxy.

┌──────────────────┐ │ kube-apiserver │ └────────┬─────────┘ │ Watch Ingress/Secret/Service ▼ ┌──────────────────┐ │ Ingress Controller│◀─── Runs as Pod(s) │ (Control Loop) │ in kube-system └────────┬─────────┘ or ingress-nginx ns │ Generates config ▼ ┌──────────────────┐ │ Proxy Process │ e.g. nginx.conf │ (NGINX / Envoy) │ haproxy.cfg └────────┬─────────┘ │ ┌──────────────┼──────────────┐ ▼ ▼ ▼ Service A Service B Service C (ClusterIP) (ClusterIP) (ClusterIP) │ │ │ Pods Pods Pods

Request Flow — Step by Step

  1. 1
    DNS Resolution
    Client resolves api.example.com → the IP of the cloud LoadBalancer (or Node IP on bare-metal). This is configured in your DNS provider pointing to the Ingress Controller's external IP.
  2. 2
    L4 Load Balancer → Node
    The cloud LB (AWS NLB/ALB or Azure LB) forwards the TCP connection to one of the cluster nodes, landing on the NodePort of the Ingress Controller Service.
  3. 3
    Ingress Controller Pod Receives Request
    kube-proxy routes the NodePort traffic to an Ingress Controller pod (NGINX, Traefik, etc.) where the HTTP request is fully parsed.
  4. 4
    Rule Matching
    The controller matches the request's Host header and path against rules in all Ingress resources. The most specific match wins.
  5. 5
    Upstream Proxy to Service
    The controller proxies the request to the matched backend Service. It reads the Endpoints object directly (bypassing kube-proxy) for efficient pod selection.

Kubernetes

The Ingress resource is the API object you create to define routing rules. Since Kubernetes 1.19, it is stable as networking.k8s.io/v1.

YAMLingress.yaml
apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: my-app-ingress namespace: production annotations: nginx.ingress.kubernetes.io/rewrite-target: / nginx.ingress.kubernetes.io/ssl-redirect: "true" nginx.ingress.kubernetes.io/use-regex: "true" spec: ingressClassName: nginx # Selects the controller tls: - hosts: - api.example.com - app.example.com secretName: tls-secret # kubernetes.io/tls Secret rules: - host: api.example.com http: paths: - path: /v1(/|$)(.*) pathType: ImplementationSpecific backend: service: name: api-v1-svc port: number: 80 - path: /v2(/|$)(.*) pathType: ImplementationSpecific backend: service: name: api-v2-svc port: number: 80 - host: app.example.com http: paths: - path: / pathType: Prefix backend: service: name: frontend-svc port: number: 3000

Ingress Controller Architecture Patterns
All Platforms

Different environments deploy Ingress Controllers differently. Understanding deployment topology prevents critical misconfiguration.

DaemonSet Pattern
Controller runs on every node. Traffic enters via each node's IP. Best for bare-metal (kubeadm) where you want maximum throughput without cloud LB. MetalLB or external DNS handles distribution.
Deployment Pattern
Controller runs as 2–3 replicas. Paired with a Service of type LoadBalancer. Standard for cloud environments (EKS, AKS). Cloud provider provisions an LB that targets the controller pods.
AWS ALB Pattern
AWS Load Balancer Controller provisions an Application Load Balancer per Ingress (or shared). The controller is just a Kubernetes operator — the actual proxy is in AWS infrastructure.
AGIC Pattern
Application Gateway Ingress Controller watches Ingress resources and configures Azure Application Gateway. The gateway runs outside the AKS cluster as a managed Azure resource.

kubeadm

Before installing an Ingress Controller on a kubeadm cluster, ensure your cluster meets these requirements. Bare-metal clusters need special handling since there's no cloud provider integration.

CNI Requirements

⚠
The Ingress Controller pods need network connectivity to backend pods. Ensure your CNI (Calico, Flannel, Cilium) is healthy. Flannel uses VXLAN overlay which works with NGINX Ingress. MetalLB — LoadBalancer for Bare Metal
kubeadm

On bare-metal kubeadm clusters, Services of type LoadBalancer stay in Pending state because there's no cloud provider. MetalLB provides a network load balancer implementation that assigns real IP addresses from a pool you define.

BASHinstall-metallb.sh
# Install MetalLB kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.3/config/manifests/metallb-native.yaml # Wait for MetalLB to be ready kubectl wait --namespace metallb-system \ --for=condition=ready pod \ --selector=app=metallb \ --timeout=90s
YAMLmetallb-config.yaml
# Layer 2 mode (ARP) — simplest, works on most networks apiVersion: metallb.io/v1beta1 kind: IPAddressPool metadata: name: first-pool namespace: metallb-system spec: addresses: - 192.168.1.200-192.168.1.250 # IPs on your LAN --- apiVersion: metallb.io/v1beta1 kind: L2Advertisement metadata: name: l2-advert namespace: metallb-system spec: ipAddressPools: - first-pool
ℹ
BGP mode is preferred in production data centers — it distributes traffic more evenly by announcing the VIP through BGP sessions with your router. Requires a BGP-capable router and more configuration (BGPPeer resources). L2 mode is simpler but fails over slower (ARP cache timeout ~10s).

NodePort Exposure Strategy
kubeadm

When MetalLB is not available or appropriate, NodePort is the fallback. An external load balancer (HAProxy, nginx on a VM, Keepalived) or cloud NLB can then forward port 80/443 to the NodePort range.

YAMLnginx-nodeport-svc.yaml
apiVersion: v1 kind: Service metadata: name: ingress-nginx-controller namespace: ingress-nginx spec: type: NodePort externalTrafficPolicy: Local # Preserves client IP selector: app.kubernetes.io/name: ingress-nginx ports: - name: http port: 80 nodePort: 30080 # Static NodePort protocol: TCP - name: https port: 443 nodePort: 30443 # Static NodePort protocol: TCP
NGINX/etc/nginx/nginx.conf (external VM)
# External NGINX acting as TCP LB to K8s NodePorts stream { upstream k8s_http { least_conn; server 10.0.0.10:30080; # node-1 server 10.0.0.11:30080; # node-2 server 10.0.0.12:30080; # node-3 } upstream k8s_https { least_conn; server 10.0.0.10:30443; server 10.0.0.11:30443; server 10.0.0.12:30443; } server { listen 80; proxy_pass k8s_http; proxy_protocol on; # Forward real IP } server { listen 443; proxy_pass k8s_https; proxy_protocol on; } }

Path-based & Host-based Routing Examples
kubeadm
YAMLpath-routing.yaml
# Path-based routing — single host, multiple backends spec: ingressClassName: nginx rules: - host: app.example.com http: paths: - path: /api pathType: Prefix backend: service: { name: api-svc, port: { number: 8080 } } - path: /static pathType: Prefix backend: service: { name: static-svc, port: { number: 80 } } - path: / pathType: Prefix backend: service: { name: frontend-svc, port: { number: 3000 } } --- # Host-based routing — multiple domains, separate backends spec: ingressClassName: nginx rules: - host: api.example.com http: paths: - path: / pathType: Prefix backend: service: { name: api-svc, port: { number: 80 } } - host: docs.example.com http: paths: - path: / pathType: Prefix backend: service: { name: docs-svc, port: { number: 80 } } - host: admin.example.com http: paths: - path: / pathType: Prefix backend: service: { name: admin-svc, port: { number: 8080 } }
✦
Path precedence: NGINX matches paths in order of specificity — longer paths take priority. /api/v2 beats /api. When two paths have the same length, the one defined first in the Ingress YAML wins.

ALB Ingress on EKS — Full Example
AWS EKS
YAMLalb-ingress.yaml
apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: app-ingress annotations: kubernetes.io/ingress.class: alb alb.ingress.kubernetes.io/scheme: internet-facing alb.ingress.kubernetes.io/target-type: ip alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-1:123:certificate/abc alb.ingress.kubernetes.io/listen-ports: '[{"HTTP": 80}, {"HTTPS":443}]' alb.ingress.kubernetes.io/ssl-redirect: '443' alb.ingress.kubernetes.io/load-balancer-name: my-app-alb alb.ingress.kubernetes.io/tags: Environment=prod,Team=platform alb.ingress.kubernetes.io/group.name: shared-alb # Share ALB alb.ingress.kubernetes.io/healthcheck-path: /health alb.ingress.kubernetes.io/healthcheck-interval-seconds: "30" alb.ingress.kubernetes.io/success-codes: "200-399" alb.ingress.kubernetes.io/wafv2-acl-arn: arn:aws:wafv2:... spec: ingressClassName: alb rules: - host: api.example.com http: paths: - path: / pathType: Prefix backend: service: name: api-svc port: { number: 8080 }
ℹ
target-type: ip vs instance: Use ip mode to route directly to pod IPs (requires VPC CNI). Use instance mode to route to node IPs via NodePort — needed for Fargate or when pods aren't directly addressable. ip mode is faster (one fewer hop) and preserves source IP.

Azure Application Gateway Ingress Controller
Azure AKS

AGIC (Application Gateway Ingress Controller) bridges Kubernetes Ingress resources with Azure Application Gateway. Unlike NGINX-in-cluster, the actual proxy runs as a managed Azure resource — offloading WAF, SSL offload, and autoscaling to Azure.

Advantages
No in-cluster proxy overhead. Native WAF (OWASP 3.2), Azure Monitor integration, autoscaling built-in. Certificates managed by Key Vault. Private Link support.
Limitations
Azure-only. Configuration propagation is async (~30s). Limited annotation support vs NGINX. No TCP/UDP ingress. Single AppGW per AGIC instance.
YAMLagic-ingress.yaml
apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: app-ingress annotations: kubernetes.io/ingress.class: azure/application-gateway appgw.ingress.kubernetes.io/ssl-redirect: "true" appgw.ingress.kubernetes.io/connection-draining: "true" appgw.ingress.kubernetes.io/connection-draining-timeout: "30" appgw.ingress.kubernetes.io/request-timeout: "60" appgw.ingress.kubernetes.io/backend-hostname: myapi.internal appgw.ingress.kubernetes.io/waf-policy-for-path: /subscriptions/.../wafpolicies/my-waf spec: tls: - hosts: [app.example.com] secretName: tls-secret rules: - host: app.example.com http: paths: - path: / pathType: Prefix backend: service: name: app-svc port: { number: 80 }

TLS Termination Patterns
All Platforms

TLS can be terminated at different layers. The choice affects security, performance, and certificate management complexity.

Edge Termination
TLS ends at the Ingress Controller. Traffic to backends is plain HTTP. Simplest, but unencrypted within cluster network. Default approach.
Re-encryption
Ingress terminates TLS, then establishes new TLS to backend. Backend needs a certificate. More complex but end-to-end encryption.
TLS Passthrough
Ingress passes TLS stream directly to backend. Backend handles TLS. No inspection possible. Required for SNI-based routing without termination.
BASHcreate-tls-secret.sh
# Create TLS Secret from existing certs kubectl create secret tls tls-secret \ --cert=tls.crt \ --key=tls.key \ --namespace=production # Verify secret structure kubectl get secret tls-secret -o yaml # Must have: tls.crt and tls.key keys # NGINX annotation for backend TLS (re-encryption) # nginx.ingress.kubernetes.io/backend-protocol: "HTTPS" # nginx.ingress.kubernetes.io/proxy-ssl-secret: "ns/backend-tls" # NGINX TLS passthrough (SNI routing) # nginx.ingress.kubernetes.io/ssl-passthrough: "true"

Multi-Tenant Ingress Architecture
All Platforms

Large organizations run multiple teams on shared clusters. Ingress isolation prevents teams from accidentally overriding each other's routing rules.

Shared Controller + Namespace Isolation
One controller, teams own their Ingress resources. Use RBAC to restrict Ingress creation to specific namespaces. Risk: one bad annotation can affect all routes. Use --watch-ingress-without-class=false.
Per-Team Controllers
Each team has a dedicated Ingress Controller with its own IngressClass. Total isolation. Higher resource overhead. Use different external IPs or ports per controller via different LoadBalancer Services.
YAMLrbac-ingress.yaml
# Restrict team-a to only manage Ingress in team-a namespace apiVersion: rbac.authorization.k8s.io/v1 kind: Role metadata: name: ingress-manager namespace: team-a rules: - apiGroups: [networking.k8s.io] resources: [ingresses] verbs: [get, list, watch, create, update, patch, delete] - apiGroups: [networking.k8s.io] resources: [ingressclasses] verbs: [get, list] # Read-only on IngressClass

Migration Strategies
All Platforms

kubeadm → EKS Migration

  1. 1
    Install AWS LBC on EKS
    Deploy the controller with IRSA. Create IngressClass alb. Keep existing NGINX with its own IngressClass.
  2. 2
    Duplicate Ingress Resources
    Create copies of Ingress manifests targeting ingressClassName: alb. Use different ALB-specific annotations.
  3. 3
    DNS Cutover with Low TTL
    Set DNS TTL to 60s 24h before cutover. Switch CNAME/A record to ALB DNS name. Both controllers running simultaneously.
  4. 4
    Remove NGINX
    After validating ALB traffic, delete NGINX Ingress resources and uninstall the controller.

NGINX → Traefik Migration (Zero Downtime)

ℹ
Deploy Traefik with a different IngressClass and separate LoadBalancer Service (different external IP). Migrate routes one by one by updating ingressClassName on each Ingress. Use weighted DNS to gradually shift traffic. Rollback is instant — just repoint DNS.
