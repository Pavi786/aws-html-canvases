Chapter 01 — Foundation

What is
SSL / TLS?

The security layer that protects every HTTPS website you visit
🍦 Layman Analogy
Imagine sending a secret letter. SSL/TLS is like sealing that letter in an unbreakable envelope, stamping it with your verified identity, and tamper-proofing the seal so you know nobody opened it en route.

The Simple Truth

SSL (Secure Sockets Layer) is the old name — it's actually deprecated and broken. TLS (Transport Layer Security) is what runs today. But the industry still says "SSL" out of habit. When your browser shows a padlock 🔒, TLS is doing the work.

🔒
Encryption
Scrambles your data so only the intended receiver can read it. Even if a hacker intercepts the traffic, they see gibberish — unreadable without the key.
✅
Authentication
Proves the server you're talking to is actually who it claims to be. Prevents "man in the middle" attacks where a fake server pretends to be your bank.
🔁
Integrity
Guarantees the data wasn't tampered with in transit. If even one bit changes, TLS detects it and drops the connection immediately.

Why It Matters Right Now

Without TLS, everything you send — passwords, credit cards, messages — travels as plain readable text across the internet. Any router or ISP between you and the server can read it. With TLS, even if intercepted, the data is useless without the decryption key.

HTTP (Plain text)

Data is encrypted end-to-end between browser and server

Data integrity is guaranteed — no silent tampering possible
Google ranks HTTPS sites higher in search results

❌ Without TLS

Susceptible to man-in-the-middle attacks

Chapter 01 — Foundation

The TLS
Handshake

What actually happens in those milliseconds before a secure connection begins
🤝 Layman Analogy
Imagine two spies meeting. First they verify their identity badges. Then they whisper a secret code to each other through a locked box. From that point on, everything they say uses that code — impossible for eavesdroppers to decode.

The 6-Step Secret Handshake

1
ClientHello — "Hey, I want to connect securely"
Your browser sends the server a list of TLS versions and encryption methods it supports. Think of it like saying: "I speak English, French, or Spanish — which do you prefer?"
2
ServerHello — "Great, let's use THIS method"
Server picks the strongest common encryption method. Sends back its chosen cipher suite. "Let's speak English with AES-256 encryption."
3
Certificate Sent — "Here's my ID"
Server sends its SSL certificate (containing public key + identity). Browser checks: Is this cert signed by a trusted CA? Is it expired? Does the domain match?
4
Key Exchange — The magic moment
Browser and server perform a mathematical dance (Diffie-Hellman or RSA) to agree on a shared secret key — without ever transmitting it directly. A hacker watching the conversation cannot derive this key.
5
Session Key Created — Symmetric from now on
Both sides independently compute the same session key. This symmetric key is much faster than asymmetric crypto and is used for all actual data.
6
Finished — Secure channel open!
Both sides send "Finished" messages encrypted with the session key. If both can decrypt each other's Finished message, the secure channel is established. Takes about 1-3 round trips.
# TLS 1.3 handshake (simplified view) Browser → Server : ClientHello [supported ciphers, random nonce] Server → Browser: ServerHello [chosen cipher] + Certificate + KeyShare Browser → Server : Finished [verify cert, send own KeyShare] # ✅ Connection is now fully encrypted in 1 round-trip! # TLS 1.3 is ~2x faster than TLS 1.2 (which needed 2 round trips)
💡 Key Insight
The brilliant part: the session key is never transmitted. Both sides independently calculate the same number using math. Even if someone recorded the entire handshake, they cannot recover the session key.

TLS Version
History

How the protocol evolved — and why old versions are dangerous
Version Year Status What Changed Should You Use?
SSL 1.0 1994 NEVER RELEASED First attempt by Netscape — too buggy to ship Never
SSL 2.0 1995 BROKEN First public SSL — POODLE & DROWN attacks Never
SSL 3.0 1996 DEPRECATED Better, but POODLE attack killed it in 2014 Never
TLS 1.0 1999 DEPRECATED Renamed from SSL. BEAST attack vulnerability Never
TLS 1.1 2006 DEPRECATED Fixed some TLS 1.0 issues. Deprecated 2021 Never
TLS 1.2 2008 ACCEPTABLE SHA-256, AEAD ciphers. Still widely used Minimum
TLS 1.3 2018 BEST Removed 200+ weak ciphers. 1-RTT handshake. Perfect forward secrecy mandatory. Always use

What Makes TLS 1.3 So Good?

⚡
Faster Connection
Only 1 round-trip needed for handshake (TLS 1.2 needed 2). For mobile users on high-latency networks, this is a significant improvement in page load times.
🛡️
Mandatory Forward Secrecy
Even if a server's private key leaks in the future, old recorded conversations cannot be decrypted. Each session has its own temporary key that is discarded.
🗑️
Removed Weak Algorithms
TLS 1.3 eliminated MD5, SHA-1, RC4, DES, 3DES, and RSA key exchange — all known to be weak or broken. Only the strongest algorithms remain.
🔮
0-RTT Resumption
If you visited a site before, TLS 1.3 can resume the session with zero extra round trips — data flows from the very first packet. Ultra-fast repeat visits.
⚠️ Action Item
Configure your server (Nginx/Apache/Cloudflare) to enforce minimum TLS 1.2 and prefer TLS 1.3. Reject all connections below TLS 1.2. This is a 5-minute config change with massive security gains.

Encryption
Deep Dive

Symmetric vs Asymmetric — the two encryption engines inside TLS
🔑 Layman Analogy
Asymmetric = A special padlock with two keys. You give everyone a copy of your padlock (public key). Only YOUR private key opens it. Anyone can lock a message for you — only you can open it.

Symmetric = One shared key — like a house key both roommates have. Faster, but you need to first securely share that key — which is what asymmetric encryption solves!
🗝️
Asymmetric Encryption (RSA / ECC)
Two mathematically linked keys: Public Key (shared with everyone) and Private Key (kept secret on server).

Used during: Certificate signing, key exchange in TLS handshake.

Slow Secure key distribution

RSA-2048 or ECC P-256 are most common today.
⚡
Symmetric Encryption (AES)
One shared key used for both encryption and decryption. Extremely fast — used for ALL actual data transfer after handshake.

AES-256-GCM is the gold standard. GCM mode provides both encryption AND integrity checking simultaneously.

Very fast Bulk data

How TLS Combines Both

Asymmetric (RSA/ECC)
→
Securely exchange session key
Symmetric (AES-256)
→
Encrypt all actual data
HMAC / AEAD
→
Verify data integrity

Key Sizes — What's Secure?

AlgorithmKey SizeSecurity LevelUse In TLS
RSA2048-bitMinimumCertificate signing
RSA4096-bitStrongCertificate signing (slower)
ECC (P-256)256-bitEquivalent to RSA-3072Modern certs & key exchange
AES128-bitStrongSession data encryption
AES256-bitVery StrongSession data encryption

💡 Why ECC > RSA for Modern Use
ECC (Elliptic Curve Cryptography) at 256 bits provides the same security as RSA at 3072 bits — but is much smaller and faster. This is why modern TLS prefers ECDH key exchange and ECDSA certificates.

Chapter 02 — Certificates

What is a
Certificate?

An SSL certificate is NOT encryption — it's an identity document
🪪 Layman Analogy
A certificate is like a passport. It contains your name (domain), your public key (what you look like), who issued it (country/CA), when it expires, and official stamps of verification. The passport itself doesn't protect you — it just proves who you are.

The Big Misconception

Most people think the SSL certificate IS the security. Wrong. The certificate is just an identity card. It contains your domain name and public key, signed by a trusted authority. TLS uses the certificate during the handshake to verify identity, then the actual encryption happens separately using session keys.

✅
What a Cert DOES contain
🌐 Domain name(s)
🔑 Public key
🏛️ Issuer (CA name)
📅 Valid from date
📅 Valid until date
✍️ CA's digital signature
🔢 Serial number
📋 Key usage restrictions
❌
What a Cert DOES NOT contain
❌ Private key
❌ Encryption logic
❌ Session keys
❌ User data
❌ Payment info
❌ Your source code
❌ Server config
🔐
Private Key (kept separate!)
The private key lives ONLY on your server, never in the certificate. It's used to prove you own the cert and to decrypt data encrypted with your public key. NEVER share it — ever.

Chapter 02 — Certificates

Inside a
.crt File

Decode exactly what you're looking at when you open a certificate

What a Certificate Looks Like

-----BEGIN CERTIFICATE----- MIIFazCCA1OgAwIBAgIRAIIQz7DSQONZRGPgu2OCiwAwDQYJKoZI... ...Base64 encoded data... -----END CERTIFICATE----- # After decoding with: openssl x509 -in cert.pem -text -noout Subject: CN=example.com, O=Example Corp, C=US ↑ Who this cert belongs to Issuer: CN=Let's Encrypt Authority X3, O=Let's Encrypt ↑ Who signed/issued this cert Not Before: Jan 1 00:00:00 2024 GMT Not After : Apr 1 00:00:00 2024 GMT ↑ Valid 90-day window Subject Alternative Names: DNS:example.com, DNS:www.example.com ↑ All domains this cert is valid for Public Key Algorithm: id-ecPublicKey (P-256) ↑ The encryption algorithm used Signature Algorithm: sha256WithRSAEncryption ↑ How the CA signed this cert

The Critical Fields Explained

📋 Common Name (CN) / SAN
The domain(s) this certificate is valid for. Modern certs use Subject Alternative Names (SAN) which can list multiple domains. CN is now legacy — SANs are what browsers actually check.
✍️ CA Signature
The most critical part. The CA's digital signature proves the CA vouches for this cert. Your browser verifies this signature against the CA's public key in its trust store. If it validates, the cert is trusted.
📅 Validity Window
Certificates expire. Google pushes for 90-day certs (more secure, forces automation). Let's Encrypt issues 90-day certs. GoDaddy and commercial CAs typically offer 1-2 year certs.
🔑 Public Key
The certificate's payload. This public key is shared with everyone. Data encrypted with this key can only be decrypted by the matching private key sitting on your server.
⚠️ 2024 Update — 90-day Max Certs Coming
Apple (Safari) and Google (Chrome) have announced they will only trust certificates valid for 90 days or less by 2025. This forces automation (certbot, ACME protocol). Plan for automated renewal — not manual.

Chapter 02 — Certificates

Certificate
Authority (CA)

The trusted middlemen who vouch for the entire internet
🏛️ Layman Analogy
A CA is like a notary public or passport office. They verify your identity and stamp/sign your documents. Because governments trust the passport office, embassies trust passports. Because browsers trust CAs, browsers trust certificates.

The Trust Chain (Most Important Concept)

🌳 Root CA
Hardcoded in browsers/OS
← Trusted by browsers directly
↓
🌿 Intermediate CA
Signed by Root CA
← Root CA signs this. Not in browsers by default.
↓
🍃 Your Domain Cert
Signed by Intermediate CA
← What your server presents

Why Intermediate CAs Exist

Root CA private keys are kept in air-gapped hardware security modules (HSMs) in vaults. They're too precious to use daily. So Root CAs sign Intermediate CA certs, and those CAs do the daily work of signing domain certificates. If an intermediate gets compromised, it's revoked — the Root stays safe.

Full Chain
Certificate

The most common SSL misconfiguration — and how to fix it
🔴 The Problem Without Full Chain
You install your certificate. Works in Chrome on your laptop. But iOS Safari shows "Not Trusted". Android throws errors. Some API clients fail. This is almost always a missing intermediate certificate — the most common SSL mistake.
🍱 Layman Analogy
Your cert is like a letter of recommendation. But the person reading it doesn't know your recommender. So your recommender needs to include THEIR letter of recommendation from someone famous. The full chain = your cert + everyone's recommendation up to someone the world already trusts.

What fullchain.pem Contains

# fullchain.pem = cert.pem + chain.pem concatenated ---Block 1: YOUR domain certificate--- -----BEGIN CERTIFICATE----- MIIFazCCA1OgAwIBAgIRAIIQ... (your domain cert) -----END CERTIFICATE----- ---Block 2: Intermediate CA certificate--- -----BEGIN CERTIFICATE----- MIIEkjCCA3qgAwIBAgIQCgFB... (intermediate cert) -----END CERTIFICATE----- ---Block 3: Another Intermediate (if exists)--- -----BEGIN CERTIFICATE----- XKD9z7q2p... (second intermediate, if needed) -----END CERTIFICATE----- # NOTE: Root CA is NOT included (browsers have it built-in) # Nginx config: ssl_certificate /etc/ssl/fullchain.pem; ← USE THIS (not just cert.pem!) ssl_certificate_key /etc/ssl/privkey.pem;
❌
Only cert.pem (Wrong)
Chrome (desktop, which caches intermediates): Works ✓
Firefox: Might work ✓
iOS Safari: FAILS ✗
Android (stock): FAILS ✗
Curl / API clients: FAILS ✗
Java HttpClient: FAILS ✗
✅
fullchain.pem (Correct)
Chrome: Works ✓
Firefox: Works ✓
iOS Safari: Works ✓
Android: Works ✓
Curl / API clients: Works ✓
Java HttpClient: Works ✓

Chapter 03 — Domains & DNS

Domain Types
Explained

Root domains, subdomains, wildcards, SAN — mastered once and for all
🌐
Root Domain (Apex Domain)
example.com  mysite.in

The base domain without any prefix. Also called "naked domain" or "apex domain". DNS-wise, it cannot have a CNAME record (only A/AAAA). Some DNS providers (Cloudflare, Route53) offer CNAME flattening for the apex.
🔗
Subdomain
www.example.com  api.example.com

Any label before the root domain. www is technically a subdomain (though treated specially). Each subdomain can point to different servers — api. to your API server, cdn. to your CDN, etc.
✱
Wildcard Domain
*.example.com

The asterisk matches exactly ONE level of subdomain.
✓ Covers: api.example.com, app.example.com
✗ Does NOT cover: example.com (root)
✗ Does NOT cover: a.b.example.com

Needs both *.example.com AND example.com for full coverage.
📋
SAN — Multi-Domain
example.com example.in myapp.net

Subject Alternative Names. One certificate that lists multiple completely different domains. Required when you have different TLDs (.com, .in, .net) or completely unrelated domains that need one cert.

DNS Record Types That Matter for SSL

RecordPurposeSSL Relevance
A Record Domain → IPv4 address Primary — points domain to your server
AAAA Record Domain → IPv6 address IPv6 support
CNAME Record Domain → another domain Used for CDN, Cloudflare, subdomains
TXT Record Text data DNS validation for SSL issuance! CA adds TXT record to verify domain ownership
CAA Record Which CAs can issue certs Security feature — restricts which CAs can issue for your domain
🛡️ Pro Security Tip — CAA Records
Add a DNS CAA record: example.com CAA 0 issue "letsencrypt.org"
This tells the internet: "Only Let's Encrypt can issue certs for my domain." Even if a hacker controls a different CA, they cannot fraudulently issue a cert for your domain.

Wildcard
Certificates

The one cert to rule all subdomains — and its surprising limitations
🌂 Layman Analogy
A wildcard cert is like a hotel master keycard. It opens any room on the floor — 101, 102, 103, 199. But it does NOT open the lobby (root domain) or rooms on other floors (deep subdomains like sub.sub.example.com).

What *.example.com Covers

✅
Wildcard DOES cover
www.example.com
api.example.com
app.example.com
mail.example.com
dev.example.com
staging.example.com
cdn.example.com
Any single-level subdomain
❌
Wildcard DOES NOT cover
example.com (root/apex!)
a.b.example.com
sub.api.example.com
*.example.in (different TLD)
example.net
example.org
Multi-level subdomains
⚠️ Critical: Add Root Domain Explicitly
When getting a wildcard cert, always add the root domain too. A proper wildcard cert covers: *.example.com AND example.com in the SAN field. Without the root domain explicitly listed, https://example.com will show a cert error.

Wildcard Cert Validation Challenge

Wildcard certs CANNOT use HTTP file validation. They can only be validated via DNS TXT record. This is why you need DNS access when getting a wildcard cert from Let's Encrypt or any CA.

# DNS challenge for *.example.com (Let's Encrypt / certbot) certbot certonly --manual --preferred-challenges dns \ -d example.com -d *.example.com # Certbot asks you to add a TXT record: Please add DNS TXT record: _acme-challenge.example.com → "randomToken123abc..." # After adding the record, validation passes and cert is issued # Result: fullchain.pem covers BOTH example.com AND *.example.com
✅ Wildcard Pros
One cert for unlimited subdomains — no managing dozens of certs
Add new subdomains anytime without new cert
Cost effective for commercial CAs
Easier management and renewal
❌ Wildcard Cons
One key compromised = all subdomains compromised
Cannot use HTTP validation — DNS access required
Let's Encrypt wildcard renewal harder to automate
Doesn't cover root domain by default

SAN / Multi-Domain
Certificates

One certificate, many completely different domains
🎫 Layman Analogy
A SAN cert is like a multi-entry visa that lists every country you're allowed to visit. One document, explicitly listing: India ✓, USA ✓, UK ✓. A wildcard visa would cover all cities in one country — SAN covers different countries entirely.

When You Need a SAN Cert

🌍
Multiple TLDs
example.com AND example.in AND example.net — completely different domain registrations that need one cert. Neither wildcard nor regular cert covers multiple TLDs.
🏢
Multiple Brands
A company running brand-a.com AND brand-b.com AND internal-tool.com — all on the same server. One cert covers them all without managing three separate certs.
🔗
Mixed Coverage
Combine wildcards and specific domains: *.example.com, example.com, *.example.in, example.in — all in one SAN cert. Maximum coverage with one cert.
# Example SAN cert (what the X.509 Subject Alternative Names field contains) X509v3 Subject Alternative Names: DNS:example.com # Root domain DNS:*.example.com # All subdomains of .com DNS:example.in # Root domain .in DNS:*.example.in # All subdomains of .in DNS:example.net # Third TLD DNS:checkout.external-payment.com # Completely different domain # One cert file. One private key. All the above domains are trusted.

example.com + example.in SAN cert Wildcard cannot cross TLD boundaries
Single blog/app DV cert Free from Let's Encrypt

.in vs .com
Reality Check

Why example.in and example.com are completely separate universes
🚨 The Dangerous Assumption
"I have SSL on example.com — so example.in is also covered, right?"

WRONG. Completely, dangerously wrong. example.in and example.com are as different as apple.com and mango.com. Different registrations, different DNS zones, different SSL certificates, different ownership validation.
example.in
Registered with Indian (.in) registrar
Separate DNS zone
Separate SSL cert required
Managed independently
Different TXT records for validation

Cannot share SSL with .com
≠
example.com
Registered with any ICANN registrar
Completely separate DNS zone
Own SSL certificate
Independently managed
Different validation required

Separate entity from .in

Correct Options for .in + .com

A
Option A: Separate Certs
Get individual SSL certs for each domain.
DV cert for example.com
DV cert for example.in

Easiest. Free with Let's Encrypt. Works everywhere.
B
Option B: SAN Cert
One commercial cert with both domains in SAN:
example.com, *.example.com, example.in, *.example.in

More expensive. Easier to manage. One renewal.
C
Option C: Cloudflare
Add both domains as separate zones in Cloudflare.
Universal SSL activates automatically for each.

Best for most teams. Free. Auto-renews. Zero config.
🔄 Best Practice: Redirect .in → .com
If .in is just for Indian traffic to find you, redirect it to .com via 301. Configure in Cloudflare Rules → Redirect Rules. Both domains still need valid SSL for the redirect to work securely (HTTPS → HTTPS redirect).

Chapter 04 — GoDaddy

GoDaddy SSL
Flow

Step-by-step: from purchase to installation
1
Generate a CSR (Certificate Signing Request)
On your server, generate a private key and a CSR. The CSR contains your domain info and public key. The private key NEVER leaves your server. openssl req -new -newkey rsa:2048 -nodes -keyout private.key -out domain.csr
2
Submit CSR to GoDaddy
Paste the CSR text into GoDaddy's SSL management portal. They extract your domain and public key from the CSR to create your certificate.
3
Domain Validation
GoDaddy verifies you own the domain via one of three methods: (a) Add a DNS TXT record, (b) Upload an HTML file to your web root, (c) Receive verification email to admin@yourdomain.com
4
Download Certificates
After validation, download: certificate.crt (your domain cert) + gd_bundle-g2-g1.crt (the intermediate chain). You'll need BOTH files.
5
Install on Server
Configure Nginx/Apache with your cert, chain file, and private key. Test with nginx -t, then reload. Verify at SSL Labs (ssllabs.com).
6
Manual Renewal (The Pain)
Set a calendar reminder 30 days before expiry. Repeat steps 1-5 manually every year. Miss this → your site shows a scary security warning to all visitors.
# Nginx config with GoDaddy cert server { listen 443 ssl; server_name example.com www.example.com; ssl_certificate /etc/ssl/certificate.crt; ← WRONG: only domain cert ssl_certificate /etc/ssl/fullchain.crt; ← RIGHT: domain + chain ssl_certificate_key /etc/ssl/private.key; ssl_protocols TLSv1.2 TLSv1.3; ssl_ciphers ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-AES128-GCM-SHA256; }

What a CDN Actually Does

📦
Caches Static Content
Copies your images, CSS, JS, fonts, and video to edge locations worldwide. First request comes from origin. All subsequent requests: served from nearby cache. Origin sees a fraction of traffic.
⚡
Reduces Latency
Physics is the enemy of speed — data cannot travel faster than light. Putting cached content 10ms away instead of 200ms away means pages load 20x faster for that part. Real difference for global users.
💪
Absorbs Traffic Spikes
Reddit hug of death? Product Hunt launch? CDN handles 100,000 simultaneous requests without sweating. Your origin server serves only cache misses — typically <5% of total traffic.

CDN Request Flow

User in Mumbai requests: https://example.com/logo.png ─── First request (Cache MISS) ─── User → CF Mumbai POP → Cache MISS → Origin Server (US) Origin → CF Mumbai POP → User ~200ms CF Mumbai stores logo.png in cache 💾 ─── All subsequent requests (Cache HIT) ─── User2 → CF Mumbai POP → Cache HIT → served from Mumbai ~8ms User3 → CF Mumbai POP → Cache HIT → served from Mumbai ~8ms User4 → CF Mumbai POP → Cache HIT → served from Mumbai ~8ms Origin server is NOT hit for requests 2, 3, 4... # Result: 96% reduction in origin load, 25x faster for Mumbai users

What CDN Caches vs What It Doesn't

✅
CDN DOES cache (static)
Images (jpg, png, gif, webp, svg), CSS files, JavaScript files, Web fonts (.woff2, .ttf), Videos, PDF files, Zip/archive files. Anything with Cache-Control: public max-age headers.
❌
CDN DOES NOT cache (dynamic)
HTML pages with personalized content, API responses with unique data, shopping carts, user dashboards, POST/PUT/DELETE requests, content with no-store/no-cache headers, authenticated content.

Chapter 07 — Security

HSTS
Explained

The header that makes "downgrade attacks" impossible
🔒 Layman Analogy
Normally, if you type "example.com" (without https://), your browser first tries HTTP, then gets redirected to HTTPS. For a fraction of a second, you're on HTTP — vulnerable to attack. HSTS tells your browser: "Never even TRY HTTP for this domain. Go straight to HTTPS. No exceptions."

The Problem HSTS Solves

!
Without HSTS: The Downgrade Attack Window
User types "mybank.com". Browser sends HTTP request first. Attacker on same WiFi intercepts the HTTP request, redirects to fake-mybank.com. User never sees HTTPS. Credentials stolen.
✓
With HSTS: Zero Window for Attack
Browser remembers from last visit: "mybank.com ALWAYS uses HTTPS". User types "mybank.com". Browser directly sends HTTPS — never touches HTTP. No attack window exists.
# HSTS Header breakdown Strict-Transport-Security: max-age=31536000; includeSubDomains; preload # max-age=31536000 → 1 year (in seconds). Browser won't try HTTP for 1yr. # includeSubDomains → HSTS applies to ALL subdomains too # preload → Opt into browser's hardcoded HSTS list # HSTS Preload List: browsers come with this list BUILT-IN # Even on FIRST visit, before you've ever seen the header, # browser goes straight to HTTPS. Submit at: hstspreload.org
⚠️ HSTS Gotcha — Don't Enable Prematurely
Once HSTS is enabled with a long max-age, if you ever need to go back to HTTP (e.g., broken cert during migration), users who received the HSTS header CANNOT access your site over HTTP for the max-age duration. There's no override. Test thoroughly first. Start with a short max-age (300 seconds) before going to 1 year.
✅
HSTS Enables
Eliminates SSL stripping attacks, HTTP downgrade attacks, eliminates first-visit vulnerability, improves trust score, required for HSTS preload list inclusion, minor performance gain (no redirect hop).
⚠️
HSTS Risks
Once set with preload, reverting to HTTP is extremely painful. Affects all subdomains if includeSubDomains is set. Misconfigured cert + HSTS = site completely inaccessible. No exceptions for the max-age duration.
