PANIC MODE OFF. The data is NOT gone — it's invisible. MySQL recorded everything in its binlog. Follow this guide in order and you'll get it back.
🛑 STEP 1 — Scale down app pods (stop all writes)
Like turning off the water tap before mopping a flood. Stop your app from writing new data while you recover the old data.
SHELLDO FIRSTK8S
▼
# Stop all app deployments — no new writes to DB
kubectl scale deployment app-deployment --replicas=0 -n production

# If multiple deployments exist
kubectl scale deployment api-server worker-service --replicas=0 -n production

# Confirm everything stopped
kubectl get pods -n production
# Expected: No resources found.

# Optionally lock MySQL to read-only
kubectl exec -it mysql-0 -n mysql-pitr -- \
  mysql -u root -p'YourPassword' -e "SET GLOBAL read_only = ON;"
Why first
Prevent new writes mixing into recovery
Skip risk
New writes after DELETE = chaos, can't untangle
Time
~5 seconds
💾 STEP 2 — Flush binary logs RIGHT NOW
Like pressing Ctrl+S before the power dies. Closes the current binlog cleanly so it can be copied safely without corruption.

Safe to run

Check Binlog Status — Verify Your Safety Net
Confirm binlogs exist and are readable before attempting recovery
5 cmds
🟢 Is binlog ON? — The most important check
Like checking if the DVR was plugged in before the match. If log_bin = OFF, there's no recording and PITR is not possible.
SQLDIAGNOSTIC
▼
-- Check if binary logging is enabled
SHOW VARIABLES LIKE 'log_bin';
-- ✔ GOOD:
-- +---------------+-------+
-- | Variable_name | Value |
-- | log_bin       | ON    |
-- +---------------+-------+
-- ✘ BAD: log_bin = OFF → no PITR, only full backup restore

-- Check binlog format (ROW is best)
SHOW VARIABLES LIKE 'binlog_format';
-- Should show: ROW  (captures actual data changed, not just SQL)

-- Check binlog file path
SHOW VARIABLES LIKE 'log_bin_basename';
-- Example: /var/lib/mysql/mysql-bin

-- Check retention period
SHOW VARIABLES LIKE 'expire_logs_days';
-- Should be 7 or higher
log_bin = ON
PITR possible ✔
log_bin = OFF
Can only restore full backup, no time travel
Best format
ROW — captures exact data row changes

Like looking at your DVR recordings list. Shows every tape (file) you have and how big it is. You need files covering the period from backup → disaster.

Read Binlogs — Decode the Recording
Translate binary logs into human-readable SQL events with timestamps
5 cmds
💡
Binlog files are binary (not text). mysqlbinlog is the decoder tool — like a subtitle reader for your DVR footage.
👁️ Basic read — see all events with timestamps
Like playing back your DVR with subtitles on. You see every INSERT, UPDATE, DELETE with the exact time it happened.
SHELL
▼
# Copy binlog from pod first
kubectl cp mysql-pitr/mysql-0:/var/lib/mysql/mysql-bin.000003 ./mysql-bin.000003

# Read in human-readable format
mysqlbinlog \
  --base64-output=DECODE-ROWS \
  --verbose \
  mysql-bin.000003

# Pipe to less for easy scrolling (q to quit)
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003 | less

# Sample output you'll see:
# # at 4891
# #241201 11:00:23 server id 1  end_log_pos 4960
# ### DELETE FROM `mydb`.`orders`
# ### WHERE
# ###   @1=1001 (id=1001)
# ###   @2='john@email.com'
📅 Read binlog filtered by time window only
Like jumping your DVR to a specific time range — 10:50 to 11:10 — and only watching that part. Much faster than reading the whole file.
SHELLSAFE READ
▼
# Read events only between 10:50 and 11:10
mysqlbinlog \
  --base64-output=DECODE-ROWS \
  --verbose \
  --start-datetime="2024-12-01 10:50:00" \
  --stop-datetime="2024-12-01 11:10:00" \
  mysql-bin.000003

# Search for just the DELETE events in that window
mysqlbinlog \
  --base64-output=DECODE-ROWS --verbose \
  --start-datetime="2024-12-01 10:55:00" \
  --stop-datetime="2024-12-01 11:05:00" \
  mysql-bin.000003 | grep -B5 -A10 "DELETE"
🔢 Read event summary — positions + timestamps only
Like getting a table of contents of the recording — just the chapter markers, not the full content. Useful to quickly scan thousands of events.
SHELLFAST SCAN
▼
# Show just event headers: position numbers and timestamps
mysqlbinlog mysql-bin.000003 | grep -E "^# at |#[0-9]{6} [0-9]{2}:"

# Output:
# # at 154
# #241201  9:15:33
# # at 892
# #241201 10:30:11
# # at 4891     ← position of the DELETE
# #241201 11:00:23  ← timestamp of the DELETE

# Get event type summary (INSERT/UPDATE/DELETE counts)
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003 \
  | grep "^### " | awk '{print $2}' | sort | uniq -c | sort -rn

# Output:
#  49874 INSERT (normal inserts)
#      1 DELETE  ← there it is — the bad one

Find The Exact Bad Event + Position
Pinpoint the exact timestamp AND position number of the DELETE
4 cmds
🎯 Find exact position of the DELETE event
Like finding the exact frame number in CCTV footage where the crash happened. You'll get a position number (like 4891) — this is MORE precise than a timestamp for recovery.
SHELLKEY STEP
▼
# Method 1: grep DELETE and show 10 lines before it (to get position)
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003 \
  | grep -B10 "DELETE FROM.*orders"

# Output:
# # at 4891           ← START POSITION of DELETE  ★ NOTE THIS
# #241201 11:00:23    ← TIMESTAMP of DELETE
# server id 1  end_log_pos 4960   ← END POSITION of DELETE  ★ NOTE THIS
# ### DELETE FROM `mydb`.`orders`
# ### WHERE
# ###   @1=1001

# Method 2: Find all events with types — cleaner view
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003 \
  | awk '/^# at /{pos=$3} /^#[0-9]/{ts=$2" "$3} /^### /{print ts,"POS:"pos,$0}' \
  | grep -i delete

# ★ WRITE THESE DOWN:
# START of DELETE: position 4891  → you want to STOP BEFORE this
# END of DELETE:   position 4960  → you want to START AFTER this
Stop position
4890 (start-1)
Skip position
4961 (end+1)
Position vs time
Position is exact — no 1-second ambiguity
📌 Check backup file for starting binlog position
Your mysqldump file has a bookmark inside it showing exactly which binlog position the backup ended at. This is where you START replaying events from.

# Without that flag, you must estimate the start time instead

Like setting up a blank VCR and inserting the 2 AM tape. You create a fresh temporary MySQL, load the backup, and you now have a clean starting state.

Replay Binlogs — The Time Machine
Apply all changes from 2 AM to 10:59:59 — skipping the 11 AM DELETE
6 cmds
⭐ THE BIG ONE — Replay binlogs, stop at 10:59:59 (timestamp)
This is the core recovery command. Like playing your DVR from 2 AM but pressing STOP at exactly 10:59:59 — the 11:00:23 DELETE never gets played. All 50,000 orders come back.
SHELL⭐ THE KEY CMD
▼
# ── TIMESTAMP-BASED RECOVERY ───────────────────────────────────────
# Play all binlogs from 2 AM, HARD STOP at 10:59:59
# The 11:00:23 DELETE is never replayed!

mysqlbinlog \
  --start-datetime="2024-12-01 02:00:00" \
  --stop-datetime="2024-12-01 10:59:59" \
  mysql-bin.000001 \
  mysql-bin.000002 \
  mysql-bin.000003 \
  | mysql -u root -p'RecoverPass123' -h 127.0.0.1

# ── SAME CMD — INSIDE KUBERNETES ──────────────────────────────────
kubectl exec -i mysql-recover -n mysql-pitr -- bash -c "
  mysqlbinlog \
    --start-datetime='2024-12-01 02:00:00' \
    --stop-datetime='2024-12-01 10:59:59' \
    /var/lib/mysql/mysql-bin.000001 \
    /var/lib/mysql/mysql-bin.000002 \
    /var/lib/mysql/mysql-bin.000003 \
    | mysql -u root -pRecoverPass123
"

# ✔ RESULT:
# DB state = 10:59:59 AM
# All 50,000 rows in orders: BACK ✔
# The 11:00:23 DELETE: NEVER HAPPENED ✔
--start-datetime
When your backup was taken (2 AM)
--stop-datetime
1 second BEFORE the DELETE
Multiple files
List all binlog files — it reads them in sequence
| mysql
Events piped directly into MySQL to execute
🔢 PRECISE — Stop at exact binlog position (more accurate than timestamp)
Like using a frame number instead of a timestamp. Timestamps round to the second; positions are exact to the byte. Use this when you've found the DELETE position number.
SHELLMORE PRECISE
▼
# You found: DELETE starts at position 4891 in mysql-bin.000003
# Step 1: Apply older files fully (000001 and 000002)
mysqlbinlog \
  --start-position=154 \
  mysql-bin.000001 mysql-bin.000002 \
  | mysql -u root -p'RecoverPass123'

# Step 2: Apply 000003 but STOP right before DELETE at 4891
mysqlbinlog \
  --start-position=4 \
  --stop-position=4890 \
  mysql-bin.000003 \
  | mysql -u root -p'RecoverPass123'

# ── WHAT THE NUMBERS MEAN ─────────────────────────────────────────
# --start-position=154   → from CHANGE MASTER TO in backup file
# --stop-position=4890   → 4891 (DELETE starts) minus 1 = stop before it

# ✔ EXACT recovery — no rounding, no ambiguity
Start pos (154)
From --master-data=2 in backup
Stop pos (4890)
1 byte before DELETE's start position
Why better
Timestamps can include extra events in same second
🔄 Save binlog replay to a SQL file first (inspect before applying)
Like printing out the DVR transcript to read before acting on it. You convert binlogs to a .sql file first, review it, then apply it. Safer than piping directly.
SHELLSAFER APPROACH
▼
# Convert binlogs to a SQL file you can review
mysqlbinlog \
  --start-datetime="2024-12-01 02:00:00" \
  --stop-datetime="2024-12-01 10:59:59" \
  mysql-bin.000001 mysql-bin.000002 mysql-bin.000003 \
  > replay.sql

# Review it — check for any surprises before applying
wc -l replay.sql                   # how many lines
grep -c "DELETE" replay.sql         # should be 0 if you stopped before it
grep -c "INSERT" replay.sql         # should be many thousands
tail -20 replay.sql                 # check last events look right

# Once satisfied, apply the SQL file
mysql -u root -p'RecoverPass123' < replay.sql

# ✔ Safer than piping directly — you can inspect first

Surgical Recovery — Skip Only The Bad Event
Advanced: keep data before AND after the DELETE, skip only the DELETE itself
3 cmds
💡
Use this when: New orders came in at 11:30 AM that you still want. Instead of losing everything after 11 AM, you surgically remove just the DELETE event and keep the rest.
🔬 Two-part replay — skip ONLY the DELETE, keep before + after
Like cutting one scene from a film reel and splicing it back together. Part 1 plays up to the DELETE. Part 2 jumps past it and continues. The bad scene never plays.
SHELLSURGICALADVANCED
▼
# DELETE event: starts at position 4891, ends at position 4960
# ── PART 1: Everything BEFORE the DELETE ──────────────────────────
mysqlbinlog \
  --start-position=4 \
  --stop-position=4890 \       # STOP 1 byte before DELETE
  mysql-bin.000003 \
  | mysql -u root -p'RecoverPass123'

# ✔ DB now at 10:59:59 — all orders exist

# ── PART 2: Everything AFTER the DELETE ──────────────────────────
mysqlbinlog \
  --start-position=4961 \      # START 1 byte after DELETE ends
  mysql-bin.000003 \             # rest of this file
  mysql-bin.000004 \             # and newer files
  | mysql -u root -p'RecoverPass123'

# ✔ SURGICAL RESULT:
# Orders from before 11 AM:      ✔ ALL EXIST
# The 11:00:23 DELETE:            ✔ SKIPPED ENTIRELY
# New orders from after 11 AM:   ✔ ALSO EXIST
# Zero data loss beyond the one bad event!
Part 1 ends
4890 (one before DELETE start 4891)
Part 2 starts
4961 (one after DELETE end 4960)
Effect
DELETE surgically removed from history

Backup Commands — Run These BEFORE Disaster Strikes
These create the safety net that makes PITR possible
5 cmds
📸 Full mysqldump with all PITR flags — the correct backup command
Like taking a photo + writing down which frame of the video tape you're on. The --master-data=2 flag is the critical addition that makes PITR work.
SHELLDAILY BACKUP
▼
# THE correct full backup for PITR support
mysqldump \
  -u root -p'YourPassword' \
  --all-databases \
  --single-transaction \       # no table locks (safe for InnoDB)
  --master-data=2 \            # ← CRITICAL: records binlog position
  --flush-logs \               # ← starts fresh binlog after backup
  --events \
  --routines \
  --triggers \
  > /backup/full_$(date +%Y%m%d_%H%M%S).sql

# Single database backup
mysqldump -u root -p --single-transaction --master-data=2 --flush-logs \
  mydb > /backup/mydb_$(date +%Y%m%d).sql

# Compressed backup (saves ~70% disk space)
mysqldump -u root -p --all-databases --single-transaction \
  --master-data=2 --flush-logs \
  | gzip > /backup/full_$(date +%Y%m%d_%H%M%S).sql.gz

# Restore compressed backup
gunzip -c /backup/full_20241201_020000.sql.gz | mysql -u root -p
--master-data=2
Records binlog position — REQUIRED for PITR
--flush-logs
Clean binlog cut point after backup
Without these
PITR becomes difficult or impossible
🔄 Ship binlogs to S3 — production-grade offsite safety
Like uploading your DVR recordings to the cloud every hour. If the whole server explodes, you still have your binlogs somewhere safe.

# ── CRONTAB: run every hour ──────────────────────────────────────
# 0 * * * * /usr/local/bin/ship-binlogs.sh

# ── RESTORE FROM S3 ──────────────────────────────────────────────

aws s3 cp s3://your-bucket/backups/full_20241201_020000.sql ./

✅ Verify recovered data — 5 checks to run before going live
Like proofreading a document before sending it to your boss. Count rows, check timestamps, spot-check specific records. Only go live after all 5 pass.
SQLDO BEFORE SWAP
▼
-- CHECK 1: Row count matches pre-disaster number
SELECT COUNT(*) AS total FROM orders;
-- Expected: 50000 (your pre-disaster count)

-- CHECK 2: Latest record is BEFORE 11:00:23
SELECT MAX(created_at) AS latest FROM orders;
-- Expected: 2024-12-01 10:59:58 (or earlier — NOT 11:00+)

-- CHECK 3: Spot check known records
SELECT * FROM orders WHERE id IN (1001, 49999, 50000);
-- Should return these rows (they existed before disaster)

-- CHECK 4: No records from after the disaster (if timestamp recovery)
SELECT COUNT(*) FROM orders WHERE created_at > '2024-12-01 11:00:00';
-- Expected: 0

-- CHECK 5: Table health check
CHECK TABLE orders;
-- Expected: OK (no corruption)

-- BONUS: Compare with a known reference count
SELECT TABLE_NAME, TABLE_ROWS FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'mydb';
Green light
Count correct + latest before 11 AM
Red flag
Wrong count or post-11AM timestamps
🔁 Final swap — dump recovered DB into production
Like printing a certified copy and officially handing it in. You dump the verified recovery, import into production, then restart everything.
SHELLFINAL STEPK8S
▼
# 1. Dump the verified recovered database
kubectl exec mysql-recover -n mysql-pitr -- \
  mysqldump -u root -p'RecoverPass123' \
  --all-databases --single-transaction \
  > ./recovered_final.sql

# 2. Lock production to read-only before importing
kubectl exec mysql-0 -n mysql-pitr -- \
  mysql -u root -p'YourPassword' -e "SET GLOBAL read_only = ON;"

# 3. Copy recovered dump into production pod
kubectl cp recovered_final.sql mysql-pitr/mysql-0:/tmp/recovered_final.sql

# 4. Import into production
kubectl exec -i mysql-0 -n mysql-pitr -- \
  mysql -u root -p'YourPassword' < /tmp/recovered_final.sql

# 5. Re-enable writes
kubectl exec mysql-0 -n mysql-pitr -- \
  mysql -u root -p'YourPassword' -e "SET GLOBAL read_only = OFF;"

# 6. Scale app back up
kubectl scale deployment app-deploy --replicas=3 -n production
kubectl rollout status deployment/app-deploy -n production

# ✔ PRODUCTION IS LIVE WITH RECOVERED DATA!
# ✔ Crisis resolved. Go drink water. You earned it. 🍵

# 7. Cleanup recovery pod
kubectl delete pod mysql-recover -n mysql-pitr
Order matters
read_only ON → import → read_only OFF → scale up
Downtime window
~5-15 min for the final swap
After recovery
Write incident report + add binlog monitoring
