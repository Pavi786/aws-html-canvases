🔥 Firewall — iptables / nftables / ufw
🔥iptables — The Classic Firewall
iptables is the traditional Linux packet filter. Works with chains (INPUT, OUTPUT, FORWARD) and rules processed top-to-bottom. Every packet is checked against rules until a match or default policy applies.
# View all rules with line numbers
iptables -L -n -v --line-numbers

# Block an IP permanently
iptables -A INPUT -s 192.168.1.100 -j DROP

# Allow SSH only from specific IP
iptables -A INPUT -s 10.0.0.0/8 -p tcp --dport 22 -j ACCEPT

# Rate limit to prevent brute force (max 3/min)
iptables -A INPUT -p tcp --dport 22 -m state --state NEW -m recent --set
iptables -A INPUT -p tcp --dport 22 -m state --state NEW -m recent --update --seconds 60 --hitcount 4 -j DROP

# Save rules (Ubuntu/Debian)
iptables-save > /etc/iptables/rules.v4

# Flush ALL rules (DANGER!)
iptables -F # ← Removes ALL firewall rules!
⚠️ Always set a default DROP policy AFTER adding your ACCEPT rules. Never set DROP first or you'll lock yourself out!
Works on all old/new kernels
Huge documentation
Precise packet control
Stateful inspection
Syntax complex & verbose
Rules not persistent by default
IPv4/IPv6 separate tools
Being replaced by nftables
Always backup rules before changes: iptables-save > backup.rules
Test rules before making default DROP policy
Never run iptables -F on a live server without a recovery plan
Never allow port 0 or wildcard opens on public interfaces
Production SafeDevOps Essential
🛡️UFW — Uncomplicated Firewall (Ubuntu Friendly)
UFW is a frontend for iptables that makes firewall management human-readable. Perfect for servers where you want simple allow/deny without complex rule syntax. Behind scenes it still uses iptables.
# Enable UFW
ufw enable

# Default deny everything incoming
ufw default deny incoming
ufw default allow outgoing

# Allow specific services
ufw allow ssh # port 22
ufw allow 80/tcp # HTTP
ufw allow 443/tcp # HTTPS
ufw allow from 10.0.0.0/8 to any port 5432 # Postgres from LAN

# Rate limit SSH (6 attempts in 30 sec = block)
ufw limit ssh/tcp

# Check status verbose
ufw status verbose
ufw status numbered # see rule numbers

# Delete rule by number
ufw delete 3
💡 Use `ufw app list` to see available pre-defined app profiles (Nginx, Apache, OpenSSH etc.)
Run ufw allow ssh BEFORE enabling ufw to avoid lockout
Use `ufw limit` on SSH instead of just allow
Don't use UFW and another firewall manager simultaneously

🔒SSH Hardening — Pro-Level Security
SSH is the most attacked surface on any Linux server. Proper hardening eliminates brute-force attacks, unauthorized access, and man-in-the-middle risks. Every DevOps engineer MUST know this.
# /etc/ssh/sshd_config — KEY SETTINGS
Port 2222 # Change from default 22
PermitRootLogin no # NEVER allow root SSH
PasswordAuthentication no # Keys only!
PubkeyAuthentication yes
MaxAuthTries 3 # 3 attempts max
LoginGraceTime 20 # 20 sec to login
AllowUsers ubuntu deploy # Whitelist users
ClientAliveInterval 300 # 5 min timeout
ClientAliveCountMax 2
X11Forwarding no
Banner /etc/issue.net # Legal warning banner

# Generate ED25519 key (stronger than RSA)
ssh-keygen -t ed25519 -C "devops@company.com"

# Test config before restart!
sshd -t # Config test — always do this!
systemctl restart sshd
🚨 ALWAYS test sshd -t before restarting SSH. A bad config = permanent lockout if no console access!
Eliminates password attacks
ED25519 is quantum-resistant
WhitelistUsers = zero leakage
Lost private key = no access
Port change = update firewalls
Team key management needed
Use ED25519 keys, not RSA-2048
Always have out-of-band access (console/VNC) before hardening
Never commit private keys to Git repos EVER
Never allow PermitRootLogin yes on any production server
🚫fail2ban — Automatic IP Banning
fail2ban monitors log files for patterns (failed logins, port scans etc.) and automatically bans offending IPs using iptables/nftables. Essential for any internet-facing server.
# Install
apt install fail2ban

# /etc/fail2ban/jail.local — Custom config
[DEFAULT]
bantime = 3600 # Ban for 1 hour
findtime = 600 # Within 10 minutes
maxretry = 3 # 3 failures = ban
ignoreip = 127.0.0.1/8 10.0.0.0/8 # Never ban these

[sshd]
enabled = true
port = 2222 # Your custom SSH port
logpath = /var/log/auth.log

# Check status
fail2ban-client status
fail2ban-client status sshd

# Unban an IP
fail2ban-client set sshd unbanip 203.0.113.10

# See banned IPs
fail2ban-client get sshd banlist
✅ Pro tip: Set bantime = -1 for permanent bans on repeat offenders. Use recidive jail for this!
Always add your IP to ignoreip to avoid self-lockout
Monitor /var/log/fail2ban.log regularly
Don't set maxretry = 1 — causes legitimate user lockouts

🔑 File Permissions & ACLs
chmod — Change Permissions
Controls who can read, write, execute files. Uses numeric (octal) or symbolic notation. Core to Linux security model.
# Octal notation: r=4, w=2, x=1
chmod 755 script.sh # rwxr-xr-x
chmod 644 config.conf # rw-r--r--
chmod 600 id_rsa # rw------- (private key!)
chmod 000 secret.txt # No access

# Symbolic notation
chmod u+x script.sh # Add execute for user
chmod go-w file.txt # Remove write from group+other
chmod a+r readme.md # Add read for all

# Recursive
chmod -R 755 /var/www/html
find /var/www -type f -exec chmod 644 {} \;
find /var/www -type d -exec chmod 755 {} \;
⚠️ 777 = everyone can write! NEVER use on servers. Max 755 for dirs, 644 for files.
chown + ACLs — Advanced Ownership
chown changes file ownership. ACLs (setfacl) extend Unix permissions to allow per-user/per-group fine-grained access beyond the owner/group/other model.
# Change owner and group
chown www-data:www-data /var/www/html
chown -R deploy:deploy /opt/app

# ACL — Give user read without changing owner
setfacl -m u:alice:r /etc/config

# Give group write access via ACL
setfacl -m g:developers:rwx /opt/project

# Set default ACL (applies to new files)
setfacl -d -m g:developers:rwx /opt/project

# View ACLs
getfacl /opt/project

# Remove ACL
setfacl -x u:alice /etc/config

OpenSSL — Encryption & Certificates
OpenSSL handles TLS/SSL, encrypting files, generating keys, signing certificates. Every server admin needs these commands.
# Generate self-signed cert
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
-keyout server.key -out server.crt

# Check certificate expiry
openssl x509 -in cert.pem -noout -dates

# Verify remote cert
openssl s_client -connect example.com:443

# Encrypt a file (AES-256)
openssl enc -aes-256-cbc -in secret.txt -out secret.enc

# Decrypt
openssl enc -d -aes-256-cbc -in secret.enc -out secret.txt

# Check cert expiry (one-liner for monitoring)
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -enddate

📡ip — Modern Network Configuration (Replaces ifconfig)
The `ip` command is the modern replacement for ifconfig, route, and arp. Controls interfaces, routing tables, ARP cache, namespaces. Part of iproute2 package.
# Show all interfaces
ip addr show # or: ip a
ip link show # just link state

# Add IP to interface
ip addr add 192.168.1.100/24 dev eth0

# Bring interface up/down
ip link set eth0 up
ip link set eth0 down

# Routing table
ip route show
ip route add 10.0.0.0/8 via 192.168.1.1
ip route del 10.0.0.0/8
ip route add default via 192.168.1.1 # default GW

# ARP cache
ip neigh show
ip neigh flush all # flush ARP cache

# Network namespaces (containers/VMs)
ip netns list
ip netns add myns
ip netns exec myns bash
Unified tool (replaces 3+ old tools)
Supports namespaces
JSON output: ip -j addr
Available everywhere
Verbose compared to ifconfig
Changes not persistent (use netplan/systemd-networkd)
⚠️ Changes made with `ip` are NOT persistent. Use /etc/netplan/*.yaml or /etc/network/interfaces for permanent config.
🔍ss / netstat — Socket Statistics
ss (socket statistics) is the modern replacement for netstat. Shows open ports, established connections, listening services. Critical for security audits and debugging.
# All listening ports (TCP+UDP)
ss -tulnp
# t=TCP u=UDP l=listening n=numeric p=process

# All established connections
ss -tnp state established

# Filter by port
ss -tnp dport :80
ss -tnp sport :443

# Show connections to specific IP
ss dst 203.0.113.10

# Count connections per state
ss -s

# Which process is using port 8080?
ss -tulnp | grep :8080

# Watch for TIME_WAIT buildup (DDoS indicator)
ss -tn state time-wait | wc -l

# Show Unix sockets
ss -x
Use ss -tulnp as first step in any security audit
Monitor TIME_WAIT count as DDoS early warning
Don't ignore LISTEN ports you don't recognize — investigate immediately
🕵️tcpdump — Packet Capture (Wireshark for CLI)
tcpdump captures and analyzes network packets at the lowest level. Essential for debugging network issues, analyzing protocols, detecting attacks, and understanding exactly what traffic passes through your server.
# Capture on interface eth0
tcpdump -i eth0

# Capture HTTP traffic only
tcpdump -i eth0 -n port 80

# Capture and save to file
tcpdump -i eth0 -w capture.pcap

# Filter by source IP
tcpdump -i eth0 src 203.0.113.10

# Show HTTP GET requests
tcpdump -i eth0 -A port 80 | grep "GET "

# Full verbose with hex dump
tcpdump -i eth0 -XX -v port 443

# Complex filter: TCP SYN only (port scans!)
tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'

# DNS queries
tcpdump -i eth0 -n port 53
💡 Use -w to save pcap, then open in Wireshark for GUI analysis. Always get approval before capturing traffic in production.

🗺️DNS Tools — dig, nslookup, host
DNS troubleshooting is 80% of "why can't I connect" issues. These tools query DNS servers directly, trace resolution paths, and verify DNS propagation.
# dig — Most powerful DNS tool
dig google.com # A record
dig google.com MX # Mail records
dig google.com NS # Name servers
dig google.com TXT # TXT records (SPF/DKIM)
dig +short google.com # Just the IP

# Query specific DNS server
dig @8.8.8.8 google.com
dig @1.1.1.1 google.com # Cloudflare DNS

# Trace full DNS resolution path
dig +trace google.com

# Reverse DNS lookup
dig -x 8.8.8.8
host 8.8.8.8

# Check DNS propagation
dig @8.8.8.8 mysite.com && dig @1.1.1.1 mysite.com

# DNSSEC validation
dig +dnssec google.com

📊Disk Usage — df, du, ncdu
Monitor disk space before it fills up. Full disks crash databases, stop logs, cause data loss. These commands show you where space is used.
# Disk filesystem usage (human readable)
df -h
df -hT # Include filesystem type

# Show inode usage (can fill up too!)
df -i # Critical: full inodes = no new files

# Directory sizes
du -sh /var/log/* # Size of each log
du -sh /* # Root level sizes

# Find top 10 largest files
du -ah / 2>/dev/null | sort -rh | head -10

# ncdu — Interactive disk usage (install it!)
ncdu /var # Navigate with arrow keys

# Find large files (>100MB)
find / -size +100M -type f -exec ls -lh {} \; 2>/dev/null
🚨 When / partition hits 95%: databases corrupt, SSH may fail, cron stops. Set alerts at 80%!
Set up disk monitoring alerts at 80% threshold
Check df -i (inode usage) regularly — often overlooked
Don't wait for 100% to investigate. 95% is emergency territory.
🏗️LVM — Logical Volume Manager
LVM adds a virtualization layer over physical disks. Allows dynamic resizing of volumes, snapshots, and spanning across multiple physical disks. ESSENTIAL for production servers.
# LVM Hierarchy: PV → VG → LV
# Physical Volume → Volume Group → Logical Volume

# Create PV from disk/partition
pvcreate /dev/sdb
pvdisplay # show PVs
pvs # brief summary

# Create Volume Group
vgcreate data_vg /dev/sdb
vgs # show VGs

# Create Logical Volume (50GB)
lvcreate -L 50G -n data_lv data_vg

# Format and mount
mkfs.ext4 /dev/data_vg/data_lv
mount /dev/data_vg/data_lv /data

# EXTEND volume (online, no downtime!)
lvextend -L +20G /dev/data_vg/data_lv
resize2fs /dev/data_vg/data_lv # ext4
xfs_growfs /data # xfs

# Create snapshot (for backup/testing)
lvcreate -s -n snap_backup -L 10G /dev/data_vg/data_lv

# Add new disk to existing VG
pvcreate /dev/sdc
vgextend data_vg /dev/sdc
Online resize (no downtime)
Snapshots for backup
Span multiple disks
Thin provisioning
Complexity overhead
Recovery harder than raw disk
Snapshot performance impact
⚡fdisk / parted — Disk Partitioning
Partition management for physical and virtual disks. fdisk for MBR disks (max 2TB), parted/gdisk for GPT (supports >2TB). Required when adding new storage.
# List all disks and partitions
lsblk -f # Tree view with FS info
fdisk -l # Detailed partition tables
blkid # UUIDs and FS types

# Interactive partition editor
fdisk /dev/sdb # n=new, d=delete, p=print, w=write

# parted — GPT support (>2TB)
parted /dev/sdb
(parted) mklabel gpt
(parted) mkpart primary ext4 0% 100%
(parted) quit

# Format partitions
mkfs.ext4 /dev/sdb1 # ext4
mkfs.xfs /dev/sdb1 # XFS (better for large files)
mkfs.btrfs /dev/sdb1 # btrfs (snapshots built-in)
mkswap /dev/sdb1 # swap partition
🚨 fdisk/parted operations on wrong device = DATA LOSS. Triple-check device names with lsblk before ANY write operations!
🔗Mounting & /etc/fstab
Mounting makes filesystems accessible. /etc/fstab makes mounts persistent across reboots. A misconfigured fstab can prevent server from booting — handle with care.
# Manual mount
mount /dev/sdb1 /mnt/data
mount -t ext4 /dev/sdb1 /mnt/data
mount -o ro /dev/sdb1 /mnt/data # Read-only

# Mount NFS share
mount -t nfs server.local:/exports /mnt/nfs

# /etc/fstab entry (format: device mountpoint fstype options dump pass)
UUID=abc123 /data ext4 defaults,noatime 0 2
# Always use UUID not /dev/sdX (device names change!)

# Get UUID
blkid /dev/sdb1

# Test fstab SAFELY (before reboot!)
mount -a # Mount all from fstab — test it!

# Unmount
umount /mnt/data
umount -l /mnt/data # Lazy unmount (when busy)
fuser -m /mnt/data # See who's using mount
Always use UUID in fstab, never /dev/sdX
Add "nofail" option for non-critical mounts to prevent boot failure
Never edit fstab without testing with mount -a first
💽RAID — Redundant Array of Independent Disks
RAID provides redundancy and/or performance using multiple disks. Software RAID with mdadm is reliable and free. Understanding RAID levels prevents data loss scenarios.
# RAID Levels Summary:
# RAID 0: Stripe (speed, NO redundancy)
# RAID 1: Mirror (redundancy, 50% usable)
# RAID 5: Stripe+Parity (min 3 disks, 1 can fail)
# RAID 6: Dual parity (min 4 disks, 2 can fail)
# RAID 10: Mirror+Stripe (best performance+redundancy)

# Create RAID 1 (mirror)
mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/sdb /dev/sdc

# Check RAID status
cat /proc/mdstat
mdadm --detail /dev/md0

# Add spare disk
mdadm /dev/md0 --add /dev/sdd

# Simulate disk failure
mdadm /dev/md0 --fail /dev/sdb
mdadm /dev/md0 --remove /dev/sdb
mdadm /dev/md0 --add /dev/sde # Replace with new disk
RAID ≠ BackupHA Storage
🏃Disk I/O Performance — iostat, iotop, fio
Diagnose disk bottlenecks. Slow disks kill application performance. These tools identify if disk I/O is your bottleneck and which processes are causing it.
# iostat — Disk I/O statistics
iostat -x 1 # Extended stats every 1 sec
iostat -xz 2 10 # 10 samples, 2 sec interval
# Look for: await>10ms, %util>80%, await spike = problem

# iotop — per-process I/O (like top for disk)
iotop -o # Show only active I/O
iotop -a # Accumulated totals

# fio — Benchmark disk performance
fio --name=randwrite --ioengine=libaio \
--iodepth=1 --rw=randwrite --bs=4k \
--direct=1 --size=1G --numjobs=1 \
--runtime=60 --group_reporting

# Quick disk speed test
dd if=/dev/zero of=/tmp/test bs=1G count=1 oflag=dsync
dd if=/tmp/test of=/dev/null bs=1G count=1

📈top / htop — Process Monitor
Real-time process monitoring. top is always available, htop is the superior interactive version. Shows CPU, memory, load average, and per-process stats.
# top — Built-in process monitor
top
top -u www-data # Filter by user
top -p 1234,5678 # Watch specific PIDs

# top keyboard shortcuts:
# M = sort by memory
# P = sort by CPU
# k = kill process
# 1 = per-CPU view
# H = show threads

# htop — Enhanced interactive monitor
htop
htop -u deploy # Filter user
htop -p PID # Watch specific process

# Understanding Load Average: (1min 5min 15min)
# Load < CPU count = healthy
# Load = CPU count = 100% utilized
# Load > CPU count = overloaded!

uptime # Quick load average check
💡 htop tip: F4=filter, F5=tree view, F6=sort, Space=tag process for bulk kill. Install it: apt install htop
Check load average trend (1/5/15 min) to see if problem is getting worse
Don't panic at high %CPU single-core — check if it's sustained over 15 min
💾Memory Monitoring — free, vmstat, /proc/meminfo
Linux memory management is different from Windows — Linux uses all RAM for caching. Understanding available vs free memory prevents false alarms and catches real issues.
# free — Memory overview
free -h # Human readable
free -h -s 2 # Refresh every 2s
# KEY: Look at "available" column, NOT "free"!
# "free" = unused | "available" = what apps can use

# vmstat — Virtual Memory Statistics
vmstat 1 # Every 1 second
vmstat -s # Summary stats
# si/so columns = swap in/out. Non-zero = memory pressure!

# Detailed memory info
cat /proc/meminfo

# Find memory-hungry processes
ps aux --sort=-%mem | head -10

# Clear page cache (dev/test only, NOT production!)
echo 3 > /proc/sys/vm/drop_caches # NEVER on production!

# Check swap usage
swapon -s
cat /proc/swaps
⚠️ If vmstat shows si/so (swap in/out) consistently > 0, you need more RAM or you have a memory leak!
📉sar — System Activity Reporter (Historical Data)
sar (from sysstat package) records historical system performance data. Unlike top/htop which only show NOW, sar shows what happened 2 hours ago when the server slowed down. INVALUABLE for post-incident analysis.
# Install sysstat
apt install sysstat
systemctl enable sysstat && systemctl start sysstat

# CPU usage history
sar -u # Today's CPU data
sar -u -f /var/log/sysstat/sa20 # Specific day

# Memory history
sar -r # RAM usage over time

# Disk I/O history
sar -d -p # Disk activity

# Network history
sar -n DEV # Network interface stats
sar -n TCP,ETCP # TCP errors

# Load average history
sar -q # Load/queue history

# Real-time (like iostat)
sar -u 1 10 # CPU: 1s interval, 10 times
Post-IncidentMust Install
Install sysstat on EVERY server from day one
Use sar during post-mortems to reconstruct what happened
🔬strace / lsof — Deep Process Inspection
strace shows every system call a process makes. lsof shows every open file/socket. Together they reveal exactly what a misbehaving process is doing — essential for debugging hung processes.
# strace — Trace system calls
strace ls # Trace command
strace -p 1234 # Attach to running process
strace -p 1234 -e trace=network # Only network calls
strace -p 1234 -e trace=file # Only file calls
strace -c python app.py # Summarize syscall counts

# lsof — List open files
lsof -p 1234 # All open files by PID
lsof -i # All open network connections
lsof -i :8080 # Who's using port 8080
lsof -i TCP # All TCP connections
lsof /var/log/nginx # Who has this file open
lsof -u www-data # All files by user

# Find deleted files still held open (consuming disk!)
lsof | grep deleted
✅ "lsof | grep deleted" finds files deleted but still held by a process — common cause of "disk full" when df shows space used
⚙️perf — Linux Performance Profiling
perf is the Linux profiling Swiss Army knife. Identifies CPU hotspots, cache misses, branch mispredictions. Used by kernel developers and performance engineers for deep analysis.
# Record CPU profile of command

# View flamegraph-style report
perf report

# Attach to running process

# System-wide stats (60 seconds)

# watch — Repeat command, show output

📟dmesg & System Journals
dmesg shows kernel ring buffer — hardware events, driver errors, OOM kills, disk errors. journalctl queries systemd journal for all service logs. First tools to check after any system problem.
# dmesg — Kernel messages
dmesg # All kernel messages
dmesg -T # Human-readable timestamps
dmesg -T --level=err,warn # Only errors/warnings
dmesg | tail -50 # Last 50 messages
dmesg | grep -i 'oom\|kill' # OOM killer events
dmesg | grep -i 'error\|fail' # Hardware errors

# journalctl — systemd journal
journalctl -xe # Recent errors, jump to end
journalctl -u nginx # Single service logs
journalctl -f # Follow (like tail -f)
journalctl --since "1 hour ago"

Redis is the most popular caching layer. Stores data in RAM for microsecond access. Supports strings, hashes, lists, sets, sorted sets, streams. Used for sessions, queues, rate limiting, pub/sub, leaderboards.

⚙️Nginx Caching — Proxy Cache
Nginx can cache backend responses, serving repeat requests without hitting your app. Simpler than Varnish but very effective for API caching and static content.
# nginx.conf — Cache zone setup
proxy_cache_path /var/cache/nginx
levels=1:2
keys_zone=my_cache:10m
max_size=10g
inactive=60m
use_temp_path=off;

# In server block:
location /api/ {
proxy_pass http://backend;
proxy_cache my_cache;
proxy_cache_valid 200 10m; # Cache 200 for 10 min
proxy_cache_valid 404 1m;
proxy_cache_use_stale error timeout;
add_header X-Cache-Status $upstream_cache_status;
}

# Check cache status in response headers
curl -I https://example.com/api/users
# X-Cache-Status: HIT / MISS / BYPASS / EXPIRED

# Purge cache (requires ngx_cache_purge module)
curl -X PURGE https://example.com/api/users
Add X-Cache-Status header to debug cache hits/misses
Use proxy_cache_use_stale to serve stale on backend failure
Never cache responses containing user-specific data without Vary headers

⚡kill, signals, nice — Process Control
Signals communicate with processes. SIGTERM asks nicely, SIGKILL forces termination, SIGHUP reloads config. Nice values control CPU priority (-20=highest, 19=lowest).
# Kill signals
kill 1234 # SIGTERM (15) — graceful
kill -9 1234 # SIGKILL — force kill
kill -HUP 1234 # Reload config
kill -STOP 1234 # Pause process
kill -CONT 1234 # Resume paused

# Kill by name
pkill nginx # Kill by name
pkill -9 -u baduser # Kill all user's processes
killall nginx # Kill all matching

# Priority (nice value)
nice -n 10 ./cpu_job.sh # Start with low priority
renice -n 5 -p 1234 # Change running process
renice -n 19 -u backupuser # Low priority for user

# Limit resources with ulimit
ulimit -n 65536 # Max open files
ulimit -a # Show all limits
Always try SIGTERM first, wait 30s, then SIGKILL if needed
Never use kill -9 on databases — it skips cleanup and causes corruption

🔐sudo — Privilege Escalation Done Right
sudo allows controlled privilege escalation. The /etc/sudoers file (edited with visudo) defines exactly who can run what as whom — the gold standard for server access control.
# /etc/sudoers — Edit with: visudo (validates syntax!)

# Allow user to run all as root
alice ALL=(ALL:ALL) ALL

# Allow without password (for automation)
deploy ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx

# Allow specific commands only
developer ALL=(ALL) /usr/bin/journalctl, /usr/bin/tail

# Alias for cleaner rules
Cmnd_Alias DOCKER = /usr/bin/docker *
devteam ALL=(ALL) NOPASSWD: DOCKER

# Check sudo access
sudo -l # List my sudo permissions
sudo -l -U alice # Check another user

# Run as different user
sudo -u www-data ls /var/www
sudo -i # Root shell (with root env)
sudo -s # Root shell (current env)
Always use visudo to edit sudoers — it validates before saving
Prefer specific commands over ALL in sudo rules
Never add NOPASSWD ALL — always restrict to specific commands

♻️logrotate — Log Rotation
logrotate automatically rotates, compresses, and deletes old logs. Without it, /var/log fills up and crashes your server. Every production server must have this configured.
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
daily # Rotate daily
rotate 14 # Keep 14 days
compress # Gzip old logs
delaycompress # Don't compress latest
missingok # OK if log missing
notifempty # Don't rotate if empty
sharedscripts
postrotate
systemctl reload nginx # Re-open log file
endscript
}

# Test your config
logrotate --debug /etc/logrotate.d/myapp

# Force rotation
logrotate --force /etc/logrotate.d/myapp

# View rotation status
cat /var/lib/logrotate/status
Always include postrotate to signal app to reopen log files
Set up logrotate for every custom application log
Don't keep logs forever — storage fills up. 14-30 days is typical.

📝Bash Scripting — Pro Patterns
Professional bash scripts with error handling, logging, argument parsing. The difference between a script that breaks silently and one that alerts you when something goes wrong.
#!/bin/bash
# Pro bash script template
set -euo pipefail # Exit on error, undefined vars, pipe failures
IFS=$'\n\t' # Safer word splitting

# Logging function
log() { echo "[$(date +'%Y-%m-%d %H:%M:%S')] $*" | tee -a "$LOGFILE"; }
error() { log "ERROR: $*" >&2; exit 1; }

# Check dependencies
command -v docker >/dev/null || error "docker not found"

# Argument parsing
ENVIRONMENT="${1:-production}"
[[ "$ENVIRONMENT" =~ ^(staging|production)$ ]] || error "Invalid env"

# Trap for cleanup on exit
cleanup() { log "Cleaning up..."; rm -f /tmp/deploy.lock; }
trap cleanup EXIT

# Lock file (prevent concurrent runs)
LOCKFILE=/tmp/deploy.lock
( flock -n 200 || error "Another deploy running!" ) 200>$LOCKFILE

# Health check function
health_check() {
local url="$1" retries=5
for i in $(seq 1 $retries); do
curl -sf "$url" && return 0
sleep 5
done
return 1
}
Always use set -euo pipefail at the top of every script
Use trap for cleanup to handle unexpected exits
Never write scripts without error handling — silent failures cause data loss

✅DevOps Do's & Don'ts — Golden Rules
Hard-won lessons from production incidents. These rules prevent outages, data loss, and 3am emergency calls.
Test in staging BEFORE production. Always.
Take a snapshot/backup before destructive operations
Use `--dry-run` flags when available before real execution
Use configuration management (Ansible, Terraform) — no manual snowflakes
Monitor everything: CPU, memory, disk, network, application errors
Set up alerting BEFORE you need it, not after the incident
Keep runbooks updated with step-by-step procedures
Use tmux on remote servers — SSH drops kill unprotected sessions
Rotate and monitor TLS certificates (use Let's Encrypt + auto-renew)
Principle of least privilege: minimum permissions always
Never run `rm -rf` without echo dry-run first
Never store secrets in environment variables in plain text
Never ignore "disk 80% full" warnings — act at 80%, not 99%
Never restart a database without knowing recovery plan
Never use root for daily operations — use sudo
Never commit credentials, private keys, or passwords to git
Never deploy on Fridays unless you enjoy weekend on-call
Never skip the backups "just this once"
