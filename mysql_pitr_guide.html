What is PITR? (Layman Explanation 🎬)

🎬 Think of it like a DVR / Video Recorder for your Database

Imagine your database is a movie being recorded 24/7. MySQL constantly writes a binlog (binary log) — it's like a frame-by-frame recording of every change ever made.

Every INSERT, UPDATE, and DELETE is recorded in sequence with a timestamp. A full backup (mysqldump) is like a snapshot photo of the movie at a certain time. Together → you can rewind to any point in time.

📸
Full Backup
Snapshot at 2 AM daily
🎞️
Binlog
Frame-by-frame recording of all changes
⏪
PITR
Restore snapshot + replay binlog up to exact timestamp
🧨

Someone deleted all orders at 11:00 AM
🎯
Goal
Recover DB state at 10:59:59 AM
✅
Result
All data before deletion is back, deletion is gone

🚨 The 11 AM Disaster Scenario

💥 What Happened?

It's 11:00:23 AM. A dev runs DELETE FROM orders; — without a WHERE clause. Your entire orders table — 50,000 rows, 3 months of data — gone in 0.3 seconds. Last full backup was taken at 2:00 AM that morning.

Your mission: Restore to exactly 10:59:59 AM — just 1 second before the DELETE.

⚙️ Prerequisites — Enable Binlog

💡
Binlog must be enabled BEFORE disaster happens. You cannot recover without it. Think of it as your flight recorder — it must be running before the crash.
📄 /etc/mysql/mysql.conf.d/mysqld.cnf — MySQL Config CONFIG 
# ── BINLOG MUST-HAVE SETTINGS ────────────────────
[mysqld]
server-id               = 1
log_bin                 = /var/lib/mysql/mysql-bin   # binlog path
binlog_format           = ROW                        # ROW = exact data captured
expire_logs_days        = 7                          # keep 7 days of logs
max_binlog_size         = 100M
sync_binlog             = 1                          # flush every commit (safest)
innodb_flush_log_at_trx_commit = 1                  # durability guaranteed
🔍 Verify binlog is ON SQL 
-- Run inside MySQL to verify
SHOW VARIABLES LIKE 'log_bin';
-- Should show: log_bin = ON

SHOW BINARY LOGS;
-- Lists all binlog files with their sizes

SHOW MASTER STATUS\G
-- Shows current binlog file and position

### 3. CONFIGMAP — MySQL config with binlog enabled
### ════════════════════════════════════════════════════════
apiVersion: v1
kind: ConfigMap
metadata:
  name: mysql-config
  namespace: mysql-pitr
data:
  my.cnf: |
    [mysqld]
    server-id               = 1
    log_bin                 = /var/lib/mysql/mysql-bin
    binlog_format           = ROW
    expire_logs_days        = 7
    max_binlog_size         = 100M
    sync_binlog             = 1
    innodb_flush_log_at_trx_commit = 1
    default_authentication_plugin = mysql_native_password
---
### ════════════════════════════════════════════════════════
### 4. PERSISTENTVOLUMECLAIM — Data + Binlog storage
### ════════════════════════════════════════════════════════
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-data-pvc
  namespace: mysql-pitr
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 50Gi
  storageClassName: standard  # adjust to your cluster
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-backup-pvc
  namespace: mysql-pitr
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 20Gi
  storageClassName: standard
---
### ════════════════════════════════════════════════════════
### 5. STATEFULSET — MySQL with binlog PVC mounts
### ════════════════════════════════════════════════════════
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: mysql-pitr
spec:
  serviceName: mysql
  replicas: 1
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: MYSQL_ROOT_PASSWORD
        ports:
        - containerPort: 3306
        volumeMounts:
        - name: mysql-data
          mountPath: /var/lib/mysql   # binlogs live here too
        - name: mysql-backup
          mountPath: /backup
        - name: mysql-config-vol
          mountPath: /etc/mysql/conf.d
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "2Gi"
            cpu: "2000m"
        livenessProbe:
          exec:
            command: ["mysqladmin", "ping", "-h", "localhost"]
          initialDelaySeconds: 30
          periodSeconds: 10
      volumes:
      - name: mysql-data
        persistentVolumeClaim:
          claimName: mysql-data-pvc
      - name: mysql-backup
        persistentVolumeClaim:
          claimName: mysql-backup-pvc
      - name: mysql-config-vol
        configMap:
          name: mysql-config
---
### ════════════════════════════════════════════════════════
### 6. SERVICE — ClusterIP for internal access
### ════════════════════════════════════════════════════════
apiVersion: v1
kind: Service
metadata:
  name: mysql
  namespace: mysql-pitr
spec:
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306
  clusterIP: None  # headless — StatefulSet best practice
---
### ════════════════════════════════════════════════════════
### 7. CRONJOB — Nightly full backup at 2 AM
### ════════════════════════════════════════════════════════
apiVersion: batch/v1
kind: CronJob
metadata:
  name: mysql-backup
  namespace: mysql-pitr
spec:
  schedule: "0 2 * * *"   # every night at 2 AM
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: mysql:8.0
            env:
            - name: MYSQL_PWD
              valueFrom:
                secretKeyRef:
                  name: mysql-secret
                  key: MYSQL_ROOT_PASSWORD
            command:
            - /bin/sh
            - -c
            - |
              DATE=$(date +%Y%m%d_%H%M%S)
              mysqldump -h mysql.mysql-pitr.svc.cluster.local \
                -u root --all-databases \
                --single-transaction --master-data=2 \
                --flush-logs --events --routines \
                > /backup/full_${DATE}.sql
              echo "Backup done: /backup/full_${DATE}.sql"
            volumeMounts:
            - name: backup-vol
              mountPath: /backup
          volumes:
          - name: backup-vol
            persistentVolumeClaim:
              claimName: mysql-backup-pvc

🔥 Full Recovery Flow — Step by Step

🚨
STOP! First thing — flush binlogs NOW to capture everything up to this moment, and STOP writes to the database before doing anything else.
1

🚨 Stop the bleeding

Immediately stop writes. Scale down app pods to prevent further changes.

kubectl scale deploy app-deploy --replicas=0 -n production
2

💾 Flush current binlogs

Force MySQL to close the current binlog file so we can copy it safely.

mysql -u root -p -e "FLUSH LOGS;"
3

📋 Find backup + binlogs

Identify the last full backup and list all binlog files created after it.

ls -lth /backup/*.sql | head -5
4

⏰ Find exact timestamp

Use mysqlbinlog to find the exact time/position just before the DELETE.

mysqlbinlog --read-from-remote-server ...
5

♻️ Restore full backup

Load the last mysqldump backup into a restored MySQL instance.

mysql -u root -p < full_20241201_020000.sql
6

⏪ Replay binlogs to 10:59:59

Apply binlogs from backup time up to one second BEFORE the disaster.

mysqlbinlog ... --stop-datetime="2024-12-01 10:59:59"
06

⌨️ The Exact Commands — Copy & Run

STEP 1 — Exec into MySQL pod + flush logs SHELL 
# Get into the MySQL pod
kubectl exec -it mysql-0 -n mysql-pitr -- bash

# Inside pod: flush binlogs (creates a fresh binlog file)
mysql -u root -p'StrongP@ssw0rd!' -e "FLUSH BINARY LOGS;"

# List all binlog files
ls -lth /var/lib/mysql/mysql-bin.*
STEP 2 — Read binlogs to find the DELETE event (with human-readable time) SHELL 
# See ALL events with timestamps — find the DELETE
mysqlbinlog \
  --base64-output=DECODE-ROWS \
  --verbose \
  /var/lib/mysql/mysql-bin.000003 \
  | grep -A 5 "DELETE"

# Output will look like this:
# # at 4891
# #241201 11:00:23 server id 1  end_log_pos 4960
# DELETE FROM `orders`
# WHERE
#   @1=1001 ...

# The timestamp: 2024-12-01 11:00:23 ← THIS IS YOUR DISASTER TIME
# You want to recover to: 2024-12-01 10:59:59 ← 1 second before
STEP 3 — Restore full backup (from 2 AM snapshot) SHELL 
# Copy backup from backup pod to your local or restore pod
kubectl cp mysql-pitr/mysql-0:/backup/full_20241201_020000.sql ./full_backup.sql

# Create a RESTORE pod (do NOT overwrite production yet!)
kubectl run mysql-restore --image=mysql:8.0 --restart=Never \
  --env="MYSQL_ROOT_PASSWORD=StrongP@ssw0rd!" \
  --command -- sleep 3600

# Restore the dump into the restore pod
kubectl cp full_backup.sql mysql-pitr/mysql-restore:/tmp/full_backup.sql

kubectl exec -it mysql-restore -n mysql-pitr -- \
  mysql -u root -p'StrongP@ssw0rd!' < /tmp/full_backup.sql

✔ Full backup restored — DB is now at 2:00 AM state
STEP 4 — ⭐ THE KEY COMMAND: Apply binlogs UP TO 10:59:59 (stop before DELETE) CRITICAL 
# Copy binlog files from MySQL pod
kubectl cp mysql-pitr/mysql-0:/var/lib/mysql/mysql-bin.000001 ./
kubectl cp mysql-pitr/mysql-0:/var/lib/mysql/mysql-bin.000002 ./
kubectl cp mysql-pitr/mysql-0:/var/lib/mysql/mysql-bin.000003 ./

# ─── MAGIC COMMAND: replay binlogs, STOP at 10:59:59 ───
mysqlbinlog \
  --start-datetime="2024-12-01 02:00:00" \   # from backup time
  --stop-datetime="2024-12-01 10:59:59" \    # STOP 1 sec before DELETE
  mysql-bin.000001 mysql-bin.000002 mysql-bin.000003 \
  | mysql -u root -p'StrongP@ssw0rd!' -h 127.0.0.1

# Alternative: stop at exact binlog POSITION instead of time
mysqlbinlog \
  --start-position=154 \       # position from --master-data=2 in backup
  --stop-position=4890 \       # position just BEFORE the DELETE event
  mysql-bin.000003 \
  | mysql -u root -p'StrongP@ssw0rd!' -h 127.0.0.1

✔ All changes from 2 AM to 10:59:59 replayed
✔ The 11:00:23 DELETE was NEVER applied
✔ All 50,000 orders are BACK!
STEP 5 — Verify data + swap production SQL 
-- Verify the recovered data looks correct
SELECT COUNT(*) FROM orders;
-- Should return 50000 (or whatever your count was at 10:59 AM)

SELECT * FROM orders ORDER BY created_at DESC LIMIT 5;
-- Verify the latest records look right — none after 10:59:59

SELECT MAX(created_at) FROM orders;
-- Should show a time before 11:00:23
STEP 6 — Point production to recovered instance SHELL 
# Option A: Dump recovered instance and reimport into production
mysqldump -u root -p'StrongP@ssw0rd!' \
  --all-databases --single-transaction \
  > recovered_final.sql

mysql -u root -p'StrongP@ssw0rd!' \
  -h mysql.mysql-pitr.svc.cluster.local < recovered_final.sql

# Option B: Use kubectl rollout (if you used a separate StatefulSet)
kubectl rollout restart statefulset/mysql -n mysql-pitr

# Scale app back up
kubectl scale deploy app-deploy --replicas=3 -n production

✔ PRODUCTION RESTORED. Data is back. Crisis over.

📋 DevOps PITR Cheatsheet

Quick Reference — All Key Commands CHEATSHEET 
# ── DAILY BACKUP (cron: 0 2 * * *) ────────────────────────────────
mysqldump -u root -p \
  --all-databases \
  --single-transaction \    # no table locks (InnoDB)
  --master-data=2 \         # records binlog position in dump
  --flush-logs \            # start a new binlog file after dump
  --events --routines \
  > /backup/full_$(date +%Y%m%d_%H%M%S).sql

# ── CHECK BINLOG FILES ─────────────────────────────────────────────
mysql -e "SHOW BINARY LOGS;"
mysql -e "SHOW MASTER STATUS\G"

# ── READ BINLOG WITH TIMESTAMPS ───────────────────────────────────
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003

# ── FILTER BINLOG BY TIME RANGE ───────────────────────────────────
mysqlbinlog \
  --start-datetime="2024-12-01 02:00:00" \
  --stop-datetime="2024-12-01 10:59:59" \
  mysql-bin.0000* | mysql -u root -p

# ── FILTER BINLOG BY POSITION (MORE PRECISE) ──────────────────────
mysqlbinlog \
  --start-position=154 \
  --stop-position=4890 \
  mysql-bin.000003 | mysql -u root -p

# ── SKIP SPECIFIC EVENT (SKIP JUST THE DELETE) ────────────────────
mysqlbinlog \
  --start-datetime="2024-12-01 02:00:00" \
  --stop-position=4890 \      # stop just before DELETE
  mysql-bin.0000* | mysql -u root -p

mysqlbinlog \
  --start-position=4961 \    # resume AFTER the DELETE
  mysql-bin.000003 | mysql -u root -p   # apply everything after

# ── APPLY TO KUBERNETES MYSQL POD ─────────────────────────────────
kubectl exec -i mysql-0 -n mysql-pitr -- \
  mysql -u root -p'StrongP@ssw0rd!' < recovery.sql

# ── COPY BINLOGS OUT OF POD ───────────────────────────────────────
kubectl cp mysql-pitr/mysql-0:/var/lib/mysql/mysql-bin.000003 ./mysql-bin.000003

🎯 Advanced: Skip Only The Bad Event (Keep Data After 11 AM)

⚠️
What if you had good transactions AFTER the DELETE? (e.g., new orders came in at 11:30 AM). Use position-based recovery to skip only the DELETE and keep everything else.
Skip only the DELETE event — keep data before AND after it SURGICAL RECOVERY 
# Step 1: Find exact position of DELETE event
mysqlbinlog --base64-output=DECODE-ROWS --verbose mysql-bin.000003 \
  | grep -B3 -A10 "DELETE FROM.*orders"

# Output shows:
# at 4891    ← start of DELETE
# ...
# end_log_pos 4960    ← end of DELETE

# Step 2: Apply BEFORE the DELETE
mysqlbinlog \
  --start-position=154 \
  --stop-position=4890 \   # 1 byte BEFORE DELETE starts
  mysql-bin.000003 | mysql -u root -p

# Step 3: Apply AFTER the DELETE (skip it!)
mysqlbinlog \
  --start-position=4961 \  # 1 byte AFTER DELETE ends
  mysql-bin.000003 mysql-bin.000004 | mysql -u root -p

✔ The DELETE is surgically removed from history
✔ Everything before AND after it is preserved!

🛡️ Production Checklist

✓

🕐 Binlog Retention

Keep at least 7 days of binlogs. Store on a separate PVC or S3 bucket, NOT the same disk as data.

✓

📸 Backup Frequency

Full backup nightly. Test restores weekly — a backup never tested is not a backup.

✓

🔒 Read-Only Replica

Run a MySQL replica. Disasters rarely hit both primary and replica simultaneously.

✓

⏱️ RTO/RPO Targets

Know your numbers. RPO = max data loss (aim for <1min). RTO = max downtime (aim for <30min).

✓

🚨 Monitoring

Alert on missing binlogs, backup job failures, and disk space. Use Prometheus + Alertmanager.

✓

📝 Runbook

Document your exact recovery commands. During a crisis, you CANNOT think — you execute from runbook.
