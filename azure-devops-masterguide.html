CHAPTER 01 // CORE SERVICES

Compute — Run Your Applications

Where your actual code lives and breathes in the cloud

Think of Compute as the "hardware" layer of the cloud. On-premises, you'd rack physical servers. In Azure, you just pick a compute service, tell it how powerful you want it, and Azure handles everything underneath. The key DevOps question is: which compute service fits my workload?
💻
Azure Virtual Machines
IaaS — Infrastructure as a Service
IAAS
🗣 Layman Explanation It's like renting a full laptop/server in Microsoft's datacenter. You get the hardware, you install the OS yourself, configure everything yourself. Maximum control — maximum responsibility.
Imagine renting an empty apartment. Azure gives you the walls, electricity, and plumbing. You decide furniture, paint, and locks — everything inside is yours to manage.
An Azure VM is a virtualized compute instance running on Azure's hypervisor (Hyper-V). You choose the VM size (e.g., Standard_D2s_v3 = 2 vCPUs, 8GB RAM), the OS image (Windows/Linux), storage disks, networking, and availability options. VMs live inside a Virtual Network, get a private IP (and optional public IP), and can be placed in Availability Zones for redundancy. You SSH or RDP into them just like a real machine.
Availability Zones Managed Disks Custom Images OS Patching Manual Scaling
✅ PROS
  • Full OS-level control
  • Run any software/legacy app
  • Lift-and-shift migrations
  • Custom networking configs
  • Persistent storage
❌ CONS
  • You manage OS patching
  • Slow to provision vs containers
  • Idle cost even when not in use
  • Harder to scale rapidly
  • Heavy operational overhead
Always use Managed Disks, not unmanaged. Enable Azure Update Manager for automatic OS patching. Use Azure Bastion for SSH — never expose port 22 to the internet.
📊
VM Scale Sets (VMSS)
Auto-scale fleet of identical VMs
AUTO-SCALE
🗣 Layman Explanation Imagine a pizza shop. When the lunch rush hits, you clone your best chef 10 times. When it's quiet at 3pm, you send 8 of them home. VMSS does exactly that — automatically spawns or removes identical VMs based on load.
It's like a photocopier for your server. One template, unlimited identical copies, automatically managed.
VMSS manages a group of load-balanced VMs that can scale from 0 to thousands. You define a VM image/config once, and VMSS maintains that uniformity across all instances. Autoscale rules can trigger based on CPU %, memory, custom metrics, or schedules. VMSS integrates with Azure Load Balancer and Application Gateway. "Uniform" mode gives uniform VMs; "Flexible" mode allows mixed VM configs. Rolling, blue-green, or canary upgrade modes let you update apps without downtime.
Autoscale Load Balanced Rolling Upgrades Stateless Preferred
✅ PROS
  • Auto-scales with demand
  • Handles massive traffic spikes
  • Rolling updates with zero downtime
  • Cost-efficient (scale to zero)
❌ CONS
  • Still requires OS management
  • Stateful apps are tricky
  • Scaling takes 2-5 minutes (not instant)
  • Heavier than containers
Set scale-in cooldown periods to avoid flapping. Use custom scripts in the VM image for bootstrapping. Prefer AKS for containerized apps — VMSS is ideal for legacy apps that can't containerize.
⎈
Azure Kubernetes Service (AKS)
Managed Kubernetes orchestration
CONTAINERS
🗣 Layman Explanation Kubernetes is like an airline operations center. You have thousands of flights (containers), runways (servers), and crew (resources). AKS is like hiring a professional airline manager — you just say "I want 10 flights to NYC daily" and it handles gates, crew schedules, rerouting, everything.
Think of containers as shipping boxes. Kubernetes is the cargo ship sorting system. AKS is Azure running that cargo ship for you — you just pack the boxes.
AKS is Azure's managed Kubernetes service. Azure manages the control plane (API server, etcd, scheduler) for free. You only pay for the worker nodes. You deploy containerized apps via YAML manifests (Deployments, Services, Ingress). AKS integrates with ACR (pull images), Azure Monitor (logs/metrics), Key Vault (secrets via CSI driver), Entra ID (RBAC), Azure CNI networking, and Application Gateway as Ingress. Node pools let you mix VM sizes. KEDA enables event-driven autoscaling. Virtual nodes (ACI burst) handle traffic spikes without pre-provisioning nodes.
Horizontal Pod Autoscaler KEDA Azure CNI Workload Identity Ingress AGIC
✅ PROS
  • Industry standard orchestration
  • Excellent auto-scaling
  • Rich ecosystem (Helm, Flux, ArgoCD)
  • Multi-tenancy with namespaces
  • Azure manages control plane free
  • Blue/green and canary native
❌ CONS
  • Steep Kubernetes learning curve
  • Complex networking concepts
  • Node pools still cost money idle
  • Overkill for simple apps
Use Workload Identity (not service principals) for pod-level Azure access. Enable cluster autoscaler on node pools. Use namespaces to separate environments. Apply Pod Disruption Budgets for HA deployments.
📦
Azure Container Apps
Serverless container platform (built on Kubernetes)
SERVERLESS K8S
🗣 Layman Explanation AKS but without having to know Kubernetes. You just say "here's my Docker container, run 3 copies, auto-scale on HTTP requests." Azure does all the Kubernetes plumbing invisibly. It's the sweet spot between Azure Functions (too limited) and AKS (too complex).
Like AKS with training wheels — all the power of containers, none of the cluster management headaches.
Container Apps runs on Kubernetes + KEDA + Dapr under the hood, but abstracts all of that. You define your container, scaling rules (HTTP requests, CPU, message queue depth), ingress (internal/external), environment variables, and secrets. It scales to zero automatically. Dapr sidecar support gives you pub/sub, state management, service invocation out of the box. Revisions let you do canary/A-B deployments. Traffic splitting sends X% to revision A, Y% to revision B. Ideal for microservices, APIs, background workers.
✅ PROS
  • No Kubernetes knowledge needed
  • Scale to zero (cost efficient)
  • Built-in Dapr integration
  • Traffic splitting for canary
  • Event-driven scaling (KEDA)
❌ CONS
  • Less control than raw AKS
  • No custom Kubernetes operators
  • Limited GPU/specialty node support
  • Cold start latency when scaled to 0
Use Container Apps for microservices where you don't want full K8s overhead. Use it with Service Bus or Event Grid for event-driven workloads. Perfect for APIs + background workers combo.
⚡
Azure Functions
Serverless event-driven compute
SERVERLESS
🗣 Layman Explanation Imagine a vending machine. You press a button (trigger), it does its one job (dispenses snack), charges you per use, then goes idle. Azure Functions is the same — event happens, function runs, you pay for execution time only. No server to manage ever.
Functions are freelancers — you call them when needed, they work, you pay per job. No salary when idle.
Azure Functions supports multiple trigger types: HTTP (REST API), Timer (cron), Queue, Blob, Event Hub, Service Bus, CosmosDB change feed, etc. Plans matter: Consumption Plan (true serverless, pay-per-execution, 5min timeout max), Premium Plan (no cold start, VNet integration, longer timeout), Dedicated Plan (always-on, runs on App Service). Durable Functions extend this with stateful workflows — orchestrator + activity functions, fan-out/fan-in patterns, and human approval steps.
✅ PROS
  • Zero infrastructure management
  • Pay per execution (very cheap)
  • Event-driven by nature
  • Rich trigger/binding ecosystem
  • Auto-scales infinitely
❌ CONS
  • Cold start latency (Consumption)
  • 5-minute execution limit (Consumption)
  • Stateless by default
  • Debugging is harder
  • Vendor lock-in risk
Use Premium Plan for production APIs to avoid cold starts. Store secrets in Key Vault and reference via app settings. Use Application Insights auto-instrumentation — it's built-in.
🌍
Azure App Service
Managed PaaS for web apps & APIs
PAAS
🗣 Layman Explanation Like Heroku or Railway.app. You give Azure your code (or Docker image), it handles the server, OS, scaling, SSL certificates, and deployment slots. You just focus on your app. No server configuration ever.
A furnished apartment vs empty apartment (VM). App Service = fully furnished. You move in with just your bags (code).
App Service runs on App Service Plans (defines compute: F1 Free → P3v3 Premium). Supports .NET, Java, Node.js, Python, PHP, Ruby natively plus Docker containers. Deployment Slots are game-changing: you deploy to "staging" slot, test it, then swap to "production" — zero-downtime. Slot swap also swaps environment variables. Auto-scaling is rules-based. Built-in SSL, custom domains, auth (Entra ID, Google, GitHub), WebSocket support, and VNet integration on Standard+.
✅ PROS
  • Dead simple deployment
  • Deployment slots for zero-downtime
  • Built-in auth, SSL, scaling
  • Supports containers + code
  • Integrated CI/CD with Azure DevOps
❌ CONS
  • Less control than VMs/containers
  • Can get expensive at scale
  • Windows plans have quirks
  • Not ideal for microservices
Always use deployment slots (Blue/Green). Keep app settings in Key Vault references — never hardcode secrets. Enable Always On to prevent cold starts on B1+.
🧊
Azure Container Instances (ACI)
Run containers without any cluster
EPHEMERAL
🗣 Layman Explanation Need to run a container for 10 minutes to process a file, then throw it away? ACI is your on-demand container runner. No cluster, no setup. Just: "run this Docker image NOW." Pay by the second.
ACI is the fastest way to run a Docker container in Azure. Spins up in seconds. No node management. You define CPU, RAM, image, environment variables, and volumes. Ideal for: one-off batch jobs, CI pipeline steps, short-lived API tasks, testing images, bursting from AKS via virtual nodes. Container groups let you run sidecars alongside your main container. Supports GPU instances too.
✅ PROS
  • Fastest container startup in Azure
  • Pay per second, no idle cost
  • No cluster to manage
  • Great for batch/CI workloads
❌ CONS
  • No orchestration/auto-healing
  • Not for persistent long-running apps
  • Limited networking features
  • No built-in load balancing
Use ACI in Azure DevOps pipelines as ephemeral build agents. Use it to burst AKS workloads via virtual nodes during traffic spikes — cheaper than pre-provisioning nodes.

CHAPTER 02 // MOST CRITICAL

Networking — The Backbone

If compute is the muscles, networking is the nervous system

No DevOps without networking. Every resource you deploy in Azure lives inside a network. You control who can talk to what, how traffic flows in and out, and how to keep attackers out. A bad network design = security breaches and outages. A good design = zero-trust, resilient, and fast.
🏘
Virtual Network (VNet)
Your private cloud network space
FOUNDATION
🗣 Layman Explanation A VNet is like buying a plot of land in Azure's city. You define your property boundaries (IP address range like 10.0.0.0/16), divide it into sections (subnets), and control who can enter your property and who can leave.
Your office building. Floors = subnets. Security guard at door = NSG. Address = IP range. VNet peering = connecting two office buildings with a private bridge.
A VNet is an isolated Layer-3 network in Azure. You define a CIDR range (e.g., 10.0.0.0/16 = 65,536 addresses). Within it, you create subnets (e.g., 10.0.1.0/24 = 256 addresses). Resources (VMs, AKS, App Service) get deployed into subnets. VNets are region-scoped. To connect VNets: VNet Peering (same or cross-region), VPN Gateway (over internet encrypted), or ExpressRoute (dedicated circuit). VNet peering traffic stays on Microsoft backbone — no public internet.
✅ PROS
  • Complete network isolation
  • Free to create (pay for data egress)
  • Full control over IP addressing
  • Works with all Azure services
❌ CONS
  • Plan CIDR carefully — can't resize easily
  • Overlapping IPs break peering
  • Region-scoped (one VNet per region)
Plan your IP space carefully before deploying anything. Use /16 for VNets, /24 for subnets. Never overlap CIDR ranges across VNets you'll ever peer. Document your IP map in Confluence from day 1.
🛡
Network Security Groups (NSG)
Traffic firewall rules for subnets & NICs
FIREWALL L4
🗣 Layman Explanation NSG is a bouncer at the club. It has a list: "Port 443 from anywhere — IN. Port 22 from only office IPs — IN. Everything else — OUT." Every packet of traffic hitting your subnet goes through this bouncer first.
Airport customs. Each rule is a customs officer instruction: "Passengers from country X with visa Y — let through on gate 80." No rule match = deny by default.
NSGs contain inbound and outbound rules. Each rule has: priority (100-4096, lower = higher priority), source/destination (IP, CIDR, service tag, or ASG), port, protocol (TCP/UDP/ICMP), and action (Allow/Deny). Service Tags simplify rules — "AzureLoadBalancer" means Azure's health probe IPs. "Internet" means all public IPs. Application Security Groups (ASG) let you group VMs by role (WebServers, DBServers) and write rules against those groups. NSGs apply at subnet-level AND NIC-level — both are evaluated.
✅ PROS
  • Free, built-in micro-segmentation
  • Service tags simplify management
  • Stateful (return traffic auto-allowed)
  • Apply at subnet or NIC level
❌ CONS
  • L4 only (no L7/app-layer filtering)
  • Can't do URL-based filtering
  • Complex rules get hard to audit
  • No WAF capabilities
Default deny all, then open only what's needed. Use service tags instead of IP lists — they auto-update. Apply NSGs to subnets, not individual NICs (easier to manage). Use NSG Flow Logs + Traffic Analytics to audit.
🗺
User Defined Routes (UDR)
Custom traffic routing tables
ROUTING
🗣 Layman Explanation Normally Azure decides how traffic gets from A to B automatically. UDR lets you override that. "Hey Azure, when someone in my app subnet wants to reach the internet, force ALL that traffic through my Azure Firewall first for inspection."
UDRs (Route Tables) override Azure's default system routes. You create a route table, add routes (prefix + next hop), and associate it with a subnet. Next hop types: Virtual Appliance (e.g., Azure Firewall's IP), VNet Gateway, VNet (local), Internet, or None (black hole). The classic pattern: Associate a UDR on all subnets that sends 0.0.0.0/0 (all internet traffic) to Azure Firewall's private IP — this forces all outbound internet through the firewall for inspection and logging.
✅ PROS
  • Force traffic through security appliances
  • Hub-spoke routing control
  • Override default Azure routing
❌ CONS
  • Misconfiguration causes blackholes
  • Easy to lock yourself out
  • Routing debugging is complex
Always route all egress through Azure Firewall in production. Disable BGP route propagation on subnets to prevent VPN routes from overriding your UDRs unexpectedly.
⚖️
Azure Load Balancer
L4 TCP/UDP traffic distribution
L4 LB
🗣 Layman Explanation Ten cashiers at a supermarket. The manager directs customers evenly: "You go to cashier 1, you to cashier 2..." Azure Load Balancer distributes network connections evenly across your VMs. If a cashier calls in sick (VM fails), the manager automatically stops sending customers there.
Azure Load Balancer operates at Layer 4 (TCP/UDP). It doesn't understand HTTP — it just distributes raw connections. SKUs: Basic (free, limited features) and Standard (production-ready, zone-redundant, SLA-backed). Standard LB supports Availability Zones for HA. Health probes (TCP/HTTP) check backend VM health every few seconds — unhealthy VMs are removed from rotation. Inbound NAT rules for individual VM SSH access. Outbound rules for SNAT (source NAT for outbound internet).
✅ PROS
  • Extremely low latency (no SSL termination)
  • Free for Standard (pay for rules)
  • Zone-redundant for HA
  • Health probe auto-removes failed VMs
❌ CONS
  • No HTTP awareness (use App GW for that)
  • No WAF, no URL routing
  • Limited logging vs Application Gateway
Always use Standard SKU. Set health probe to HTTP endpoint, not just TCP — TCP doesn't tell you if your app is healthy, only if the port is open. Use session persistence only if truly needed.
🚪
Application Gateway + WAF
L7 HTTP/HTTPS load balancer with firewall
L7 + WAF
🗣 Layman Explanation Azure Load Balancer is a dumb traffic splitter. Application Gateway is a smart one. It understands HTTP. "Route /api requests to the API VMs. Route /static to blob storage. Block requests that look like SQL injection attacks." It also handles your SSL certificate — your backends speak plain HTTP internally.
Load Balancer = traffic cop waving cars through. Application Gateway = airport gate agent who reads your boarding pass (URL), assigns you the right gate (backend), and checks you're not on the no-fly list (WAF).
App Gateway (v2) is a regional L7 load balancer. Key features: URL-based routing (path-based rules), host-based routing (multiple domains), SSL termination (and end-to-end SSL), session affinity (cookie-based), connection draining, auto-scaling, and WAF_v2 for OWASP rule sets. In AKS, the AGIC (App GW Ingress Controller) manages App Gateway routing via Kubernetes Ingress resources. WAF policies can be in Detection (log only) or Prevention (block) mode.
✅ PROS
  • URL/host-based routing
  • SSL termination — backends simpler
  • Built-in WAF (OWASP 3.2)
  • Works as AKS Ingress
  • Auto-scaling v2
❌ CONS
  • Expensive (~$250+/month minimum)
  • Slow to provision (5-10 mins)
  • Regional only (use Front Door for global)
  • Complex configuration
Put App Gateway in its own dedicated subnet (/24 or larger — it needs space). Use WAF in Prevention mode for production. Offload SSL here — backends use HTTP internally for simplicity.
🌍
Azure Front Door
Global CDN + L7 LB + WAF at edge
GLOBAL CDN
🗣 Layman Explanation App Gateway is regional (one city). Front Door is global (every city on Earth). It puts a presence at 200+ edge locations worldwide. A user in India hits your app — Front Door routes them to the nearest Azure region. If that region goes down, it automatically fails over to another region.
Azure Front Door (Standard/Premium) is a global entry point running on Microsoft's backbone. It provides: anycast routing (user connects to nearest PoP), caching (CDN at edge), WAF globally, health monitoring across origins, instant failover, and URL rewrite/redirect. Origin groups define backends (multiple regions). Priority + weight control traffic distribution. Custom domains with managed SSL certs. Premium SKU adds Private Link origins (backend stays private, Front Door reaches it via private link).
✅ PROS
  • Global L7 load balancing
  • CDN caching reduces latency worldwide
  • Multi-region failover (automatic)
  • WAF at the edge (closest to attacker)
❌ CONS
  • More expensive than App Gateway
  • Global propagation can take minutes
  • Complex for simple single-region apps
Use Front Door when you have multi-region deployments or global users. Combine with App Gateway behind it: Front Door (global edge/WAF) → App Gateway (regional L7 routing) → AKS/VMs.
🔒
Private Endpoints
Bring Azure PaaS into your VNet privately
ZERO-TRUST
🗣 Layman Explanation By default, Azure Storage, SQL, Key Vault etc. have public endpoints — any machine on the internet can try to reach them. Private Endpoints create a private doorway from your VNet directly into that service, and you can then lock the public door shut. Your VM talks to storage privately, never touching the public internet.
Instead of your employees going through the public lobby (internet) to reach the HR office (Azure SQL), you build a private hallway (private endpoint) directly from your floor to HR. Nobody outside can use that hallway.
A Private Endpoint creates a Network Interface Card (NIC) inside your subnet with a private IP. It maps to a specific Azure PaaS resource (storage account, SQL server, Key Vault, ACR, etc.). DNS is crucial: you need Azure Private DNS Zones to override public DNS resolution — so "mystorageaccount.blob.core.windows.net" resolves to the private IP inside your VNet. After creating a private endpoint, disable public network access on the PaaS resource — now only VNet-connected resources can reach it.
✅ PROS
  • PaaS services become fully private
  • Traffic never leaves Microsoft backbone
  • Eliminates public attack surface
  • Works across peered VNets
❌ CONS
  • DNS setup is tricky (Azure Private DNS Zones)
  • Cost per endpoint (~$7-10/month)
  • Debugging DNS issues is hard
For every PaaS resource in production: create a private endpoint + disable public access. Use Azure Private DNS Zones linked to your VNet. This is a zero-trust requirement, not optional.
📖
Azure DNS
Public & private DNS hosting
DNS
🗣 Layman Explanation DNS is the phone book of the internet. You type "myapp.com" and DNS translates that to an IP like 20.40.50.60. Azure DNS hosts that phone book. Private DNS Zones host a private internal phone book only your VNet can read.
Azure DNS hosts public DNS zones (your domain's A, CNAME, MX records) with 100% SLA, anycast routing for low-latency resolution, and DNSSEC support. Private DNS Zones provide name resolution within VNets — critical for private endpoints. You can auto-register VM hostnames. Azure DNS integrates with Traffic Manager for geo-routing and Front Door for CNAME delegation. Azure DNS is not a domain registrar — buy the domain elsewhere, then delegate name servers to Azure DNS.
✅ PROS
  • Extremely low latency (anycast global)
  • 100% availability SLA
  • Private zones for internal resolution
  • Azure RBAC for DNS management
❌ CONS
  • Not a registrar (buy domain elsewhere)
  • Private zones need VNet links
Create private DNS zones for every Azure service you use with private endpoints (e.g., privatelink.blob.core.windows.net). Link them to your VNet. Without this, private endpoints won't work.

CHAPTER 03 // DATA LAYER

Storage — Where Data Lives

Blobs, disks, files, and lakes — each has its purpose

Storage is where everything gets persisted. Logs, backups, container images, VM disks, application data — all needs a home. Azure's storage services are among the cheapest and most reliable in the cloud. As a DevOps engineer, you need to know which storage type fits which use case and how to optimize cost using tiering.
🪣
Azure Blob Storage
Object store for unstructured data
OBJECT STORE
🗣 Layman Explanation Blob Storage is a giant file cabinet in the cloud. Videos, images, log files, backups, Terraform state files, ML datasets — anything that's just a file goes here. It's like Google Drive but for machines. Infinitely scalable, incredibly cheap.
An Amazon warehouse with unlimited shelves. Each shelf = container. Each item on it = blob. You can store a million items or a single 100TB file. Amazon (Azure) manages the warehouse building.
Blob Storage is Azure's primary object store. Organized as: Storage Account → Containers → Blobs. Three blob types: Block Blobs (standard files, logs, images), Append Blobs (log streaming — append-only), Page Blobs (VHD disks for VMs). Three tiers: Hot (frequent access, higher storage cost), Cool (infrequent access, cheaper storage, penalty on access), Archive (rarely accessed, dirt cheap storage, hours to rehydrate). Lifecycle policies automatically move blobs between tiers based on age. Public access can be disabled completely. Supports NFS 3.0 for Hadoop workloads.
Hot / Cool / Archive Lifecycle Policies SAS Tokens Immutable Storage
✅ PROS
  • Cheapest storage in Azure
  • Infinitely scalable (exabytes)
  • 99.999999999% (11 9s) durability
  • Lifecycle policies for cost control
  • Supports static website hosting
❌ CONS
  • Not a filesystem (no directory structure)
  • Archive tier = hours to access
  • Egress costs add up at scale
  • No random-write access
Store Terraform state in Blob with state locking via Azure Table Storage. Use lifecycle policies to auto-archive logs older than 30 days. Enable soft-delete + versioning for blob recovery. Use private endpoints for production.
💽
Azure Disk Storage
Block storage for VM operating & data disks
BLOCK STORAGE
🗣 Layman Explanation When a VM boots up, it needs a hard drive. Azure Disk Storage is that hard drive in the cloud. You pick the size and speed (spinning disk vs SSD vs NVMe SSD). The OS boots from the OS disk; you attach extra data disks for your database files.
Azure Managed Disks are SSD/HDD volumes attached to VMs. Disk tiers: Ultra Disk (highest IOPS, lowest latency — for databases), Premium SSD v2 (configurable IOPS, sub-ms latency), Premium SSD (production workloads), Standard SSD (dev/test), Standard HDD (backups, archival). Managed = Azure handles replication and physical management. Disk snapshots for point-in-time backup. Disk encryption at rest via platform-managed or customer-managed keys in Key Vault. Shared disks let multiple VMs mount the same disk (clustering scenarios).
✅ PROS
  • High IOPS for database workloads
  • Encryption at rest (automatic)
  • Snapshots for backup
  • Online resize without restart
❌ CONS
  • Tied to one VM (mostly)
  • Ultra Disk is expensive
  • Can't share like blob storage
Always use Managed Disks (never unmanaged). Use Premium SSD for production VMs. Enable Azure Backup for VM disk snapshots. For database VMs, use Ultra Disk or Premium SSD v2 — never Standard HDD.
📂
Azure Files
Managed file share (SMB/NFS protocol)
FILE SHARE
🗣 Layman Explanation Like a shared network drive (like Z: drive in an office). Multiple VMs or containers mount the same folder and all read/write to it. In AKS, your pods can share files this way. Think of it as a corporate shared drive but in the cloud.
Azure Files provides fully managed SMB 3.x and NFS 4.1 file shares in the cloud. Mount them on Windows (drive letter mapping) or Linux (mount command). Multiple VMs can mount simultaneously with read/write. Azure File Sync syncs on-premises file servers to Azure Files — great for migrations. In AKS, Azure Files is used as Persistent Volume (PV) for ReadWriteMany workloads where multiple pods need the same data. Premium Azure Files uses SSD for low latency.
✅ PROS
  • Multiple concurrent mounts (RWX)
  • SMB + NFS protocol support
  • Azure File Sync for hybrid
  • Works in AKS as PV
❌ CONS
  • More expensive than Blob
  • NFS requires Premium tier
  • Latency higher than local disk
Use Azure Files in AKS for shared config/data volumes that need ReadWriteMany. Use Azure File Sync to gradually migrate on-prem file servers to cloud. Use NFS shares for Linux workloads.
🏞
Azure Data Lake Storage Gen2
Hierarchical blob storage for big data analytics
BIG DATA

CHAPTER 05 // EVENT-DRIVEN ARCHITECTURE

Messaging & Eventing

Decoupling services so they don't crash together

Direct API calls between services create tight coupling. If Service B is down, Service A fails too. Messaging decouples them: A drops a message in a queue and moves on. B picks it up when ready. This is the foundation of resilient, event-driven architecture.
🚌
Azure Service Bus
Enterprise message broker — queues & topics
ENTERPRISE MQ
🗣 Layman Explanation Like a post office with guaranteed delivery. You (sender) drop a package in the mailbox (queue). The post office holds it safely. The recipient picks it up when ready. If the recipient is sick for a week, the package waits. Nobody loses anything.
A restaurant order system. Waiter takes order (producer), puts ticket on the kitchen rail (queue). Chef (consumer) picks tickets when ready. Kitchen going slow doesn't make customers at the table disappear.
Service Bus has two modes: Queues (one sender, one receiver — point-to-point) and Topics with Subscriptions (one publisher, many subscribers — pub/sub). Messages have: TTL (time-to-live), delivery count, and properties. Dead Letter Queue (DLQ): when a message fails processing X times, it moves to the DLQ for investigation — never lost. Sessions support ordered message processing (FIFO per session ID). Duplicate detection prevents processing same message twice. Lock mechanism: consumer claims a message for N seconds, must complete/abandon before timeout. Standard tier vs Premium (isolated, predictable latency, VNet support, large messages up to 100MB).
Dead Letter Queue Topics + Subscriptions Message Sessions At-least-once delivery
✅ PROS
  • Guaranteed delivery (at-least-once)
  • Dead Letter Queue for failures
  • Ordered processing with sessions
  • Duplicate detection
  • Pub/sub with Topics
❌ CONS
  • Not for high-volume streaming (use Event Hub)
  • Premium tier is expensive
  • 80GB max storage per namespace
Always monitor DLQ — messages there need investigation. Set message TTL appropriately. Use Topics for fan-out patterns (one event, multiple independent consumers). Use Premium for production with VNet integration.
📡
Azure Event Grid
Reactive event routing service
EVENT ROUTING
🗣 Layman Explanation Event Grid is like a notification system. "When someone uploads a photo to blob storage, tell my Azure Function." It's the nervous system that says: "this happened" → "notify these things." It's push-based — events are pushed to subscribers immediately.
Event Grid routes events from sources (Azure services: Blob, Resource Groups, Service Bus, custom apps) to event handlers (Azure Functions, Logic Apps, Event Hub, Webhooks, Service Bus). System topics are built-in (blob events, resource events). Custom topics for your own events. Event subscriptions filter events by type, subject prefix, or advanced filters. CloudEvents schema support for standards compliance. Near-real-time delivery (sub-second). At-least-once delivery with dead-lettering. Not for high-volume streaming — for reactive event-driven workflows.
✅ PROS
  • Push-based — no polling needed
  • Near-instant event delivery
  • Native integration with 20+ Azure services
  • Very cheap (pay per event)
❌ CONS
  • Not for ordered processing
  • Not for streaming large volumes
  • Events not replayed after TTL
Use Event Grid to trigger automation: blob uploaded → process, resource deployed → tag it, VM deallocated → alert. Chain with Logic Apps for no-code automation workflows.
🌊
Azure Event Hub
Real-time data streaming platform (Kafka-compatible)
STREAMING
🗣 Layman Explanation If Service Bus is a post office, Event Hub is a firehose. Millions of events per second — IoT sensor data, application telemetry, clickstream data — all streaming in. Think Apache Kafka but managed by Azure. Multiple consumers can read the same stream independently, each at their own pace.
Event Hub is a partitioned (up to 32 partitions) event log. Producers write events; consumers read from partitions at their own offset (position). Events retained for 1-7 days (Standard) or up to 90 days (Premium). Consumer groups allow multiple independent consumers. Kafka protocol compatibility: point your existing Kafka apps at Event Hub without code changes. Event Hub Capture auto-writes all events to Blob/ADLS for permanent storage. Throughput Units (Standard) or Processing Units (Premium) control capacity. Scalable to millions of events/second.
✅ PROS
  • Millions of events/second
  • Kafka wire protocol compatible
  • Multiple independent consumers
  • Event capture to ADLS
  • Time-based replay
❌ CONS
  • No dead letter queue
  • Events expire after retention period
  • No guaranteed ordering across partitions
  • Complex consumer offset management
Use Capture to persist all events to ADLS — replaying from scratch otherwise is impossible. Monitor consumer lag per partition. Use dedicated partition keys for ordered processing per entity (e.g., deviceId).

Security & Identity

Security is not a feature — it's the foundation

A single misconfigured IAM policy or exposed secret = data breach. Security in Azure is built around identity (who are you?), access (what can you do?), and protection (how do we block bad actors?). The DevOps security philosophy: shift security left, automate compliance, never trust implicitly.
🪪
Microsoft Entra ID (formerly AAD)
Azure's identity & access management platform
IAM
🗣 Layman Explanation Entra ID is Azure's bouncer database. Every human (developer, admin) and every machine (VM, app, service) must have an identity here. When you try to do something in Azure, Entra ID checks: "Who are you? Is your ID valid? Are you allowed to do this?" Like an Active Directory for everything in the cloud.
Microsoft Entra ID is an IDaaS (Identity as a Service). Key concepts: Users (humans), Groups (collections of users), Service Principals (machine identities for apps), Managed Identities (special service principals tied to Azure resources — no credential management needed), App Registrations (OAuth/OIDC apps), Enterprise Apps. Supports: OAuth 2.0, OIDC, SAML. Multi-tenant architecture lets you manage external users. Conditional Access policies add context-aware MFA: "if user is outside corporate network OR logging in from new device, require MFA." Privileged Identity Management (PIM) for just-in-time access.
✅ PROS
  • Single identity for all Azure resources
  • MFA + Conditional Access
  • Managed Identities (no passwords!)
  • SCIM provisioning from HR systems
  • SSO for thousands of apps
❌ CONS
  • Complex permissions model
  • P2 license required for PIM ($$$)
  • Guest user management can get messy
Always use Managed Identities instead of service principals with passwords. Enable MFA for all users — no exceptions for admins. Use PIM for privileged roles — no standing admin access ever.

Azure RBAC
Role-Based Access Control for Azure resources
LEAST PRIVILEGE
🗣 Layman Explanation RBAC answers: what can you DO in Azure? "Alice is a Contributor on the Dev resource group" = she can create/edit/delete resources there, but can't assign permissions. "Bob is Reader everywhere" = he can see everything, change nothing. Least privilege: give only the access someone needs for their job — nothing more.
RBAC uses: Principal (who — user/group/service principal/managed identity), Role Definition (what — list of allowed actions like Microsoft.Compute/virtualMachines/write), Scope (where — management group → subscription → resource group → individual resource). Built-in roles: Owner (everything including RBAC), Contributor (everything except RBAC), Reader (read only), plus 100+ service-specific roles (AKS Admin, Key Vault Secrets Officer, Storage Blob Data Contributor). Custom roles let you define exact permissions. Deny assignments block even Owners. Role assignments are inherited downward in scope hierarchy.
✅ PROS
  • Granular per-resource permissions
  • Inherited scope hierarchy
  • 100+ built-in roles
  • Custom roles for precise control
❌ CONS
  • Complex to audit at scale
  • Role proliferation is common
  • Maximum 2000 assignments per subscription
Never use Owner role in production — use Contributor. Assign roles to Groups not individuals (easier to manage). Use PIM for time-bound elevated access. Audit role assignments monthly with Azure Access Reviews.
🤖
Managed Identities
Password-free machine identities
ZERO SECRETS
🗣 Layman Explanation Your AKS pod needs to read from Key Vault. Old way: create a username/password, store it as secret, hope nobody leaks it. New way: give the pod a Managed Identity — Azure auto-generates a certificate, rotates it every day, and your pod authenticates automatically with zero secrets in your code.
Managed Identities come in two flavors: System-Assigned (tied to one Azure resource — deleted when resource deleted, 1:1) and User-Assigned (standalone identity shared across multiple resources, lifecycle independent). The resource uses the identity to get an access token from Entra ID via the Instance Metadata Service endpoint. That token is used to authenticate to Azure services (Key Vault, Blob, SQL, ACR, etc.). Works with: VMs, VMSS, AKS (Workload Identity), App Service, Functions, Container Apps, Logic Apps. For AKS pods: Workload Identity uses OIDC federation to give individual pods distinct identities.
✅ PROS
  • Zero credentials to manage or rotate
  • Auto-rotated by Azure
  • Works with RBAC like normal identities
  • Free (no additional cost)
❌ CONS
  • Only for Azure resources (not on-prem apps)
  • AKS Workload Identity is complex to configure
Make this your default: every Azure resource authenticating to another Azure resource should use Managed Identity. If you find yourself creating a service principal with a password for Azure-to-Azure auth, stop — use Managed Identity instead.
🗝
Azure Key Vault
Centralized secrets, keys & certificates management
SECRETS MGMT
🗣 Layman Explanation Never store passwords, API keys, or connection strings in your code or environment variables. Put them all in Key Vault (a secure digital vault). Your app has a Managed Identity and permission to read from Key Vault. Key Vault delivers the secret at runtime. Nobody ever sees it in plain text.
Key Vault stores three object types: Secrets (username/password, connection strings, API keys — text values), Keys (RSA/EC cryptographic keys for encryption — never leaves the vault, operations done in HSM), Certificates (SSL/TLS certs with auto-renewal from DigiCert/Let's Encrypt). Two tiers: Standard (software-protected) and Premium (HSM-protected keys). Access policies (legacy) or RBAC (modern) control who can read/write secrets. Access model: GET secret = read a secret value, SET secret = create/update. Soft-delete protects against accidental deletion (90-day recovery). Audit log of every access. Secrets versioned — you can roll back.
✅ PROS
  • Centralizes all secrets management
  • Managed Identity authentication (no passwords)
  • Secret versioning and rotation
  • Full audit log of access
  • Certificate auto-renewal
❌ CONS
  • Adds latency (SDK call per secret)
  • Rate limits can be hit at scale
  • HSM Premium is expensive
Use Key Vault references in App Service — secrets auto-sync. In AKS, use the CSI Secrets Store driver to mount secrets as files or env vars. Enable Private Endpoint for Key Vault in production. Rotate secrets on a schedule using Azure Automation or Event Grid.

Azure Policy
Compliance guardrails for your Azure environment
COMPLIANCE
🗣 Layman Explanation Azure Policy is a set of rules that FORCE compliance. "All storage accounts MUST use HTTPS only." "All VMs MUST be in approved regions." "All resources MUST have these tags." If someone tries to create a non-compliant resource, Azure Policy blocks it. Existing non-compliant resources are flagged and auto-remediated.
Azure Policy works on three levels: Audit (log non-compliant resources), Deny (block non-compliant resource creation), DeployIfNotExists/Modify (auto-remediate by adding/changing properties). Policy Definitions → Initiatives (collections) → Assignments (applied at scope). Built-in initiatives: Azure Security Benchmark, CIS Controls, PCI DSS, HIPAA. Compliance dashboard shows overall compliance percentage. Remediation tasks run auto-fix for existing resources. Policy exemptions for resources that legitimately need to break rules. Integrate with Azure DevOps pipelines: run policy compliance checks before deploying.
✅ PROS
  • Enforce standards at infrastructure level
  • Auto-remediation (no manual fix)
  • Compliance reporting built-in
  • Works across all subscriptions
❌ CONS
  • Overly strict policies block legitimate work
  • Remediation tasks can take hours
  • Complex policy authoring
Assign policies at Management Group level for consistent enforcement. Start with Audit mode before switching to Deny — avoid blocking legitimate deployments. Use Initiatives for grouped compliance standards. Define all policies as code (Bicep/Terraform) and version control them.
🏰
Azure Bastion
Secure VM access without public IP or VPN
SECURE ACCESS
🗣 Layman Explanation Your VM has no public IP. No one from the internet can even see it. But you (the admin) need to SSH in. Azure Bastion creates a secure tunnel from your browser through the Azure Portal directly to the VM — without exposing any ports to the internet. No VPN client needed.
Azure Bastion is deployed in your VNet (in its own AzureBastionSubnet /26 or larger). It provides browser-based RDP/SSH to VMs in the same VNet or peered VNets — over HTTPS (port 443). Your VMs need NO public IP and NO NSG rule for port 22 or 3389. Bastion authenticates you via Entra ID. Session audit log shows who connected to which VM when. Standard tier adds IP-based connect (connect to VMs in peered VNets by IP). Developer/Shareable Link tiers available for specific use cases.
✅ PROS
  • No port 22/3389 exposure
  • No public IP needed on VMs
  • Browser-based (no client software)
  • Session audit logging
❌ CONS
  • $140-200+/month minimum
  • One Bastion per VNet (use peering)
  • Some features require Standard tier
Deploy one Bastion in the hub VNet (hub-spoke model) — it can access all spoke VNets via peering. This is much cheaper than one per VNet. Remove ALL NSG rules for port 22/3389 from VM subnets — if anyone questions it, it's intentional.

Low-code workflow automation
LOW-CODE

Azure Automation + Runbooks
PowerShell/Python automation for Azure ops
OPS AUTOMATION
🗣 Layman Explanation Runbooks are scripts that run automatically on a schedule or trigger. "Every Friday at 5pm, shut down all dev VMs to save cost." "When Defender alerts fire, auto-quarantine the affected VM." You write the script once (PowerShell or Python), schedule it, and never think about it again.
Azure Automation is a hybrid automation platform. Key features: Runbooks (PowerShell/Python scripts stored and versioned in Azure), Job Schedules (cron-like triggers), DSC (Desired State Configuration for VM config management), Update Management (patch VMs across Azure + on-prem), Change Tracking (detect config drift), Inventory (list software installed on VMs). Hybrid Runbook Workers extend automation to on-premises machines. System-assigned Managed Identity for Azure access. Start/stop VM schedules are the classic use case. Automation can call ARM/Bicep/Terraform.
✅ PROS
  • Scheduled/triggered ops automation

  • Built-in Azure integration
  • Free tier (500 minutes/month)
❌ CONS
  • PowerShell heavy (less modern)
  • Limited compared to full CI/CD pipelines
  • Debugging runbooks is painful
Use Automation for: start/stop VMs on schedule, rotate secrets in Key Vault, apply patches, clean up old snapshots. These save significant cost and toil. Store runbooks in Git, import to Automation via pipeline.

Reserved Instances + Savings Plans
Pre-commit to save up to 72%
COST SAVINGS
🗣 Layman Explanation Pay-as-you-go: rent a hotel room at full price any night. Reserved Instance: book the hotel for 1-3 years at checkout — 40-72% discount. If you know a VM will run 24/7 for a year, reserve it. You pay upfront or monthly — huge savings vs hourly billing.
Reserved Instances: commit to a specific VM SKU (e.g., Standard_D4s_v3) in a specific region for 1 or 3 years. Discount: 40% (1-year) or 72% (3-year) vs pay-as-you-go. Apply to VMs, AKS nodes, SQL databases, Cosmos DB, App Service, Redis, etc. Savings Plans: more flexible — commit to a $/hour spend level regardless of VM SKU/region. Covers compute across any VM, AKS, Functions, App Service. Azure Advisor recommends reservations based on your usage history. Unused reservations can be exchanged or (for 1-year) refunded.
Up to 72% off 1 or 3 year terms Use for stable workloads
✅ PROS

  • Applies automatically to matching resources
❌ CONS
  • Upfront or committed spend
  • Wasted if workload is decommissioned
  • 1-3 year lock-in
Check Azure Advisor for reservation recommendations — it shows your top spending VMs and projected savings. Reserve production VMs after 30 days of stable operation. Use Spot VMs for dev/test (up to 90% cheaper, but can be evicted).

// Azure DevOps Engineer Mental Model — Quick Fire Q&A
Q: User wants to upload a video file. Where do you store it? A: Azure Blob Storage (Hot tier). Use SAS URL for time-limited access. Q: App needs DB password. How do you provide it securely? A: Store in Key Vault. App uses Managed Identity to read it at runtime. No env vars. Q: AKS pods need to write to Azure Storage. How? A: Assign User-Assigned Managed Identity to pods via Workload Identity. Give it Storage Blob Data Contributor role. Q: How do you deploy to AKS with zero downtime? A: Kubernetes Rolling Update strategy (default). Or use Argo Rollouts for Canary/Blue-Green. Q: New developer joined. How do you give Azure access? A: Add them to an Entra ID Group. A: Azure Policy — Deny policy blocking specific VM SKUs or regions. Q: Production database went down. How do you recover? A: Auto-Failover Groups handle it automatically (30-60 second failover). Connection string is unchanged. Q: How do you handle 10x traffic spike suddenly? A: AKS HPA (Horizontal Pod Autoscaler) scales pods. Cluster Autoscaler adds nodes. Or KEDA for event-driven scale. Q: How do you monitor if your app is down for users globally? A: Application Insights Availability Tests — ping from 5 global regions every minute. Q: Your Terraform ran and created wrong resource. How to fix? A: Fix the .tf file, run terraform plan to verify, then terraform apply. State tracks the delta. Q: How do you expose SSH to one VM securely? A: Azure Bastion. No public IP on VM. A: Application Insights → Failures → Drill into exception traces → Find which dependency failed. Q: What's the difference between Service Bus and Event Hub? A: Service Bus = guaranteed delivery, ordering, DLQ (enterprise messaging). Event Hub = high-volume streaming, Kafka-compatible, replay by time (telemetry/logs). Q: What is zero-trust in Azure context? A: Verify every identity (Entra ID + MFA), least-privilege access (RBAC), assume breach (private endpoints, encryption, audit logs).
