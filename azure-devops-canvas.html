🖥️ Compute Services

These are the engines that actually run your application code. Think of compute as the "workers" — you tell them what to do, and they do it.

🧠
Big Picture: When someone visits your website, something has to run your code and send back a response. That "something" is a compute service. Azure gives you 7 different types — each suited for different needs, scales, and budgets.
💻
Azure Virtual Machines
Your own computer in the cloud

A Virtual Machine (VM) is literally a computer running inside Microsoft's data centre that you rent. You get a full OS (Windows or Linux), install whatever you want, and have complete control. It's like renting an office where you furnish it yourself.

🏠 Real-World Analogy
Renting an empty apartment. You get the walls and electricity — you bring your own furniture, fridge, and décor. Full control, but full responsibility too.
✅ Pros
  • Full control of OS & software
  • Lift-and-shift legacy apps
  • Any workload type
  • Custom software installs
❌ Cons
  • You manage OS patching
  • No auto-scaling by default
  • Higher management overhead
  • Costs even when idle
⚡ When to Use
Legacy apps Custom software Dev/Test envs SQL Server self-managed
📈
VM Scale Sets (VMSS)
Auto-multiplying VMs

Imagine you have 1 VM serving your website. On Black Friday, traffic spikes 10x. VMSS automatically creates 10 identical VMs to handle the load, then deletes them when traffic drops. You define the rules — Azure does the work.

🏠 Real-World Analogy
A restaurant that automatically opens more serving counters when a queue forms — and closes them when it's quiet. Same menu, same staff training, just more of them.
✅ Pros
  • Auto-scales in/out based on rules
  • Load balanced automatically
  • Pay only for what you use
  • Uniform VM configuration
❌ Cons
  • Scale-out takes 2-5 minutes
  • Stateless apps only (ideally)
  • Complex autoscale rule tuning
  • Still need OS management
⚡ When to Use
Web servers Batch processing Variable traffic
☸️
Azure Kubernetes Service (AKS)
The crown jewel of container orchestration

Kubernetes (K8s) is the world's most popular way to run containerised apps at scale. AKS is Microsoft's managed version — they handle the complex Kubernetes control plane, you just deploy your containers. K8s automatically restarts crashed containers, scales them, and routes traffic between them.

🏠 Real-World Analogy
A logistics company (Kubernetes) that manages a fleet of delivery workers (containers). If one worker gets sick, the company instantly hires a replacement. If deliveries spike, they bring in more workers. The manager (control plane) handles all this — you just say "I need 10 deliveries per hour."
🔵 Pods
Smallest unit in K8s. One or more containers packaged together. Like a "lunch box" — container is the food, pod is the box.
🟢 Nodes
The actual VMs that run your pods. AKS manages these VMs for you. Think of nodes as the tables in a restaurant where pods (dishes) are served.
🟡 Services
A stable network endpoint (IP+port) that routes traffic to your pods. Pods can come and go — the service address stays the same.
🔴 Ingress
The front door for external traffic into your cluster. Routes based on URL paths, handles SSL termination. Essential for AKS DevOps work.
✅ Pros
  • Auto-healing (restarts failed containers)
  • Horizontal pod autoscaling
  • Rolling deployments with zero downtime
  • Microservices-ready architecture
  • Rich ecosystem (Helm, Istio, etc.)
  • Azure manages control plane (free!)
❌ Cons
  • Steep learning curve
  • Complex networking (CNI, ingress)
  • Overkill for simple apps
  • YAML configuration heavy
  • Debugging can be tricky
  • Node pool patching still your job
⚡ When to Use
Microservices High-scale apps Multi-container apps DevOps pipelines ML workloads
⚡
Azure Functions
Run code without managing servers

Write a small piece of code (a "function"), upload it, and Azure runs it whenever triggered — by an HTTP request, a timer, a queue message, or a file upload. You pay only for the milliseconds it runs. Perfect for event-driven tasks.

🏠 Real-World Analogy
A freelancer who only works when called. The moment a job comes in, they start. When done, they disappear. You pay per job, not per hour of availability.
✅ Pros
  • Zero server management
  • Pay-per-execution (very cheap)
  • Scales to zero = no idle cost
  • 100+ triggers supported
❌ Cons
  • Cold start latency (first call slow)
  • Max 10 min execution (Consumption)
  • Hard to debug locally
  • Stateless by default
⚡ When to Use
Webhooks Scheduled jobs Event processing API backends
🌐
Azure App Service
Managed platform for web apps

App Service is a fully managed platform for hosting web applications. Give it your code (Python, Node, .NET, Java, PHP) or a container — Azure handles the server, OS, runtime, load balancing, and SSL certificates automatically. Perfect middle-ground between VMs and serverless.

🏠 Real-World Analogy
A fully-furnished serviced apartment. You bring your clothes (your app code), the building provides everything else — furniture, cleaning, security, utilities.
✅ Pros
  • Zero OS management
  • Built-in autoscaling
  • Custom domains + free SSL
  • Deployment slots (staging)
  • GitHub/DevOps integration
❌ Cons
  • Less control than VM
  • Premium tier gets expensive
  • Cold starts on Free/Shared tiers
  • Some OS-level things blocked

🌐 Networking

The veins of your cloud infrastructure. Without networking, nothing talks to anything. This is the most critical area for DevOps — and the most commonly misunderstood.

⚠️
Why Networking Matters Most: You can have the best app in the world, but if the networking is wrong — it won't be accessible, it won't be secure, and it won't scale. Network design is the skeleton of your cloud architecture.
🌐
Virtual Network (VNet)
Your private cloud neighbourhood

A VNet is your own private, isolated network inside Azure. Everything you deploy lives inside a VNet. You define the IP address ranges, create subnets, and control who can talk to whom. By default, nothing from the internet can access resources in your VNet.

🏠 Real-World Analogy
A gated residential community with its own internal roads and buildings. The community has an address range (10.0.0.0/16). Each neighbourhood within it (subnets) has its own street range. Only residents and approved visitors get in.
✅ Pros
  • Full network isolation
  • Custom IP address spaces
  • Free to create
  • Peering with other VNets
❌ Cons
  • IP range can't be changed after creation
  • Peered VNets can't have overlapping IPs
  • Max 1000 VNets per subscription
🛡️
Network Security Groups (NSG)
Firewall rules for your network

An NSG is a list of allow/deny rules for network traffic. You attach it to a subnet or NIC and it filters traffic going in and out. Each rule specifies: source IP, destination IP, port, protocol, and allow/deny. Rules are evaluated by priority (lower number = higher priority).

🏠 Real-World Analogy
A bouncer at a club with a rulebook: "Allow VIP guests (port 443) from anywhere. Block everyone else. Allow staff (SSH port 22) only from the office IP." Rules are checked in order — first match wins.
✅ Pros
  • Free — no extra cost
  • Stateful (return traffic auto-allowed)
  • Attach to subnet or NIC
  • Default deny inbound from internet
❌ Cons
  • No application-layer inspection
  • Can get complex with many rules
  • No logging without enabling flow logs
⚖️
Azure Load Balancer
Splits traffic across multiple VMs

When you have multiple VMs running the same app, you need something to divide incoming requests between them. The Load Balancer does this at Layer 4 (TCP/UDP level) — it sees IP addresses and ports, not HTTP content. It also does health probes — if a VM goes down, it stops sending traffic there.

🏠 Real-World Analogy
A bank with 5 tellers. A queue manager directs each customer to the next available teller. If a teller calls in sick (health probe fails), customers are redirected to the remaining 4. Everyone gets served, no one waits too long.
✅ Pros
  • Ultra-low latency (Layer 4)
  • Supports millions of flows
  • Internal and external modes
  • HA Ports for all traffic
❌ Cons
  • No SSL offloading
  • No URL-based routing
  • No WAF capability
  • Standard tier has costs
🚪
Application Gateway (WAF)
Smart Layer-7 HTTP/S load balancer

Unlike a Load Balancer that works at IP level, Application Gateway understands HTTP/S. It can route based on URL paths (/api goes to API servers, /images goes to image servers), handle SSL certificates, and optionally include a Web Application Firewall (WAF) to block SQL injection and XSS attacks.

🏠 Real-World Analogy
A hotel concierge who reads your request and directs you specifically: "You want the restaurant? 3rd floor. Spa? Basement. Conference rooms? 5th floor." Plus a security guard (WAF) who stops suspicious people at the door.
✅ Pros
  • URL-based routing
  • SSL termination (saves backend work)
  • WAF protection included
  • Autoscaling support
  • Cookie-based session affinity
❌ Cons
  • Expensive (starts ~$100/month)
  • Single region only
  • Deployment takes 5-10 min
  • Complex configuration
🔒
Private Endpoints
Bring PaaS services inside your VNet

Azure PaaS services (SQL, Storage, Service Bus) are public by default — anyone can reach them over the internet (with credentials). Private Endpoints give them a private IP inside your VNet, so traffic never leaves Microsoft's network. Zero-trust security principle in action.

🏠 Real-World Analogy
Instead of visiting a public bank branch (internet), the bank opens a private door inside your office building. You never have to step outside — and neither does your money data.
✅ Pros
  • Eliminates public internet exposure
  • Works with most Azure PaaS services
  • Satisfies compliance requirements
  • Network traffic stays private
❌ Cons
  • DNS configuration complexity
  • Additional cost per endpoint
  • Harder to debug connectivity
🌍
Azure Front Door
Global load balancer + CDN + WAF

Azure Front Door is Application Gateway's global sibling. It sits at Microsoft's edge network (200+ Points of Presence worldwide), routing users to the nearest/fastest backend. It combines global load balancing, CDN caching, SSL offloading, and WAF — all in one service.

🏠 Real-World Analogy
A global airline hub system. If you're in India, you fly from Mumbai. If you're in the US, you fly from New York. Smart routing finds the nearest airport (edge node) to minimise your journey time.
✅ Pros
  • Global presence = low latency worldwide
  • Built-in CDN capabilities
  • Automatic failover across regions
  • WAF + DDoS protection
❌ Cons
  • More expensive than App Gateway
  • Complex to configure initially
  • Caching can cause stale content issues

💾 Storage

Where your data lives when it's not being processed. Choosing the right storage type massively impacts cost, performance, and compliance.

☁️
Blob Storage
Object storage for any file

Blob (Binary Large Object) storage is Azure's cheapest, most scalable storage. Store any file — images, videos, backups, logs, CSV files. Files are stored as "blobs" inside "containers" (like folders). Globally replicated, extremely durable (11 nines: 99.999999999%).

🏠 Analogy
A massive, cheap warehouse where you throw in any boxes (files). You can retrieve any box by its name. The warehouse has tiers — premium shelving (Hot) for frequently accessed items, deep storage (Archive) for things you rarely need.
✅ Pros
  • Extremely cheap (Archive: $0.002/GB)
  • Unlimited scale
  • Lifecycle policies to auto-tier
  • CDN integration
❌ Cons
  • Not a filesystem (no directories)
  • Access fees on retrieval (Archive)
  • Not suitable for databases
💿
Azure Disk Storage
Block storage for VMs

Managed disks are like physical hard drives for your VMs. When you create a VM and it needs an OS drive or data drive, it uses managed disks. Unlike Blob, disks are only attached to one VM at a time and provide low-latency block-level storage.

🏠 Analogy
A hard drive plugged into your computer. Fast, local, block-level access. SSD types: Ultra (fastest, most expensive), Premium SSD, Standard SSD, Standard HDD (cheapest).
✅ Pros
  • Low latency for VMs
  • Snapshots for backup
  • Encryption by default
❌ Cons
  • More expensive than Blob
  • Usually 1 VM at a time
  • Not accessible via HTTP
📁
Azure Files
Shared network file system

Azure Files provides a fully managed SMB/NFS file share in the cloud. Multiple VMs (or even on-premises machines) can mount the same file share simultaneously. Great for shared configuration files, apps that need a shared filesystem, or migrating on-prem file servers.

🏠 Analogy
A shared Google Drive folder mounted as a network drive on every employee's computer (Windows Z: drive). Everyone can read/write the same files simultaneously.
✅ Pros
  • Mount on multiple VMs simultaneously
  • Works with SMB & NFS
  • On-prem connectivity via VPN
❌ Cons
  • More expensive than Blob
  • Latency higher than disk
  • Not for high IOPS apps
📊 Blob Storage Access Tiers — Cost vs Speed
🔥 Hot
Highest storage cost. Lowest access cost. Use for frequently accessed data (daily reads).
❄️ Cool
Lower storage cost, higher access cost. Use for monthly or quarterly access. Min 30-day storage.
🧊 Cold
Even cheaper storage. For data accessed every 90 days. Min 90-day storage. (Newer tier)
🗄️ Archive
Cheapest (~$0.002/GB). But retrieval takes hours and costs money. Use for compliance backups, legal records. Min 180-day storage.

🗄️ Databases

Where structured data lives. Azure offers both traditional SQL and modern NoSQL solutions — all fully managed so you don't run database servers yourself.

🗄️
Azure SQL Database
Fully managed SQL Server in the cloud

A fully managed Microsoft SQL Server database. No patches, no backups (automatic), no HA setup — Azure does all that. You just create tables, write queries, connect your app. Supports all standard SQL features. Scales by changing tiers (DTUs or vCores).

🏠 Analogy
A fully managed filing cabinet where Azure keeps the cabinet organised, backed up, and oiled. You just open drawers and file papers. No maintenance headache.
✅ Pros
  • Auto-backup (35-day retention)
  • Built-in HA (99.99% SLA)
  • Auto-tuning for performance
  • Serverless tier = pause when idle
❌ Cons
  • No SQL Agent (use Managed Instance)
  • Limited OS-level access
  • Cross-database queries restricted
🌍
Cosmos DB
Globally distributed NoSQL database

Cosmos DB is Microsoft's flagship NoSQL database with one superpower: it can replicate your data to multiple Azure regions simultaneously and serve reads/writes from the nearest region. Think of a global social media app — users in India read from India, users in USA read from USA. Sub-10ms latency globally.

🏠 Analogy
A bookstore with branches in every major city worldwide. Each branch has the same inventory. When you walk in, you're served from your local branch — no delays, no shipping time.
✅ Pros
  • Single-digit millisecond latency globally
  • Multiple APIs (SQL, MongoDB, Cassandra, Gremlin)
  • Tunable consistency levels
  • Auto-scales throughput
❌ Cons
  • Very expensive at scale
  • No joins (NoSQL limitation)
  • RU (Request Units) pricing confusing
  • Complex data modeling
🐘
Azure DB for PostgreSQL
Managed open-source PostgreSQL

If you love PostgreSQL (the world's most advanced open-source SQL database), Azure manages it for you. High availability, automatic backups, scaling — all built in. Supports all PostgreSQL extensions. Perfect for teams using Django, Rails, or any PostgreSQL-based stack.

✅ Pros
  • 100% PostgreSQL compatible
  • Open source — no licensing
  • Extensions supported (PostGIS, etc.)
  • Flexible server = stop/start
❌ Cons
  • Less Azure-native integration than SQL DB
  • Some advanced features lag behind self-hosted
⚡
Azure Cache for Redis
In-memory data store for speed

Redis is an in-memory key-value store that's incredibly fast (microsecond latency). Use it as a cache — store frequently accessed database results in Redis so your app reads from lightning-fast memory instead of slow disk databases. Also used for session storage, pub/sub messaging, and leaderboards.

🏠 Analogy
Your desk vs a filing cabinet. Instead of going to the filing cabinet (database) for every document, you keep the most-used documents on your desk (Redis). Instantly accessible — no walking required.
✅ Pros
  • Sub-millisecond reads/writes
  • Reduces DB load dramatically
  • Many data structures (lists, sets, hashes)
  • Pub/Sub messaging built-in
❌ Cons
  • Data lost on restart (unless persistent)
  • Memory = expensive at scale
  • Cache invalidation is hard to get right

📩 Messaging & Eventing

How services talk to each other asynchronously. Instead of service A calling service B directly (tight coupling), messaging services act as buffers — decoupling producers from consumers.

💡
Why Async Messaging? Imagine an e-commerce site where placing an order triggers: sending an email, updating inventory, notifying the warehouse, and logging analytics. If you call all 5 services synchronously, one failure breaks the whole flow. With messaging, you just publish "order placed" to a queue — each service picks it up independently. Resilient, scalable, decoupled.
🚌
Azure Service Bus
Enterprise message broker

Service Bus is the most feature-rich messaging service. It supports queues (point-to-point: one sender, one receiver) and topics (pub/sub: one sender, many subscribers). Messages are guaranteed to be delivered, can be ordered (sessions), and supports Dead Letter Queues (DLQ) for failed messages.

🏠 Analogy
A professional postal service with tracking. Mail (message) is guaranteed to reach the recipient. If delivery fails, it goes to a "returned mail" room (DLQ). Certified mail = sessions (ordered delivery).
✅ Pros
  • At-least-once delivery guarantee
  • FIFO with Sessions
  • Dead Letter Queue built-in
  • Duplicate detection
  • Transactions supported
❌ Cons
  • Max message size 256KB (Standard)
  • More expensive than Queue Storage
  • Not for massive throughput (use Event Hub)
⚡ Use When
Order processingMicroservices commsWorkflow triggers
⚡
Azure Event Hub
High-throughput event streaming

Event Hub is built for big data streaming. Think millions of events per second from IoT devices, click streams, or log aggregation. It's like Apache Kafka — events are stored for days, multiple consumer groups can read the same stream independently, from any offset (point in time).

🏠 Analogy
A river of data. Events flow in continuously. Multiple systems can "fish" from the river simultaneously — each at their own pace, their own spot in the river. The data flows for days before being flushed out.
✅ Pros
  • Millions of events/second
  • Kafka-compatible API
  • Replay events (consumer groups)
  • Capture to Blob Storage
❌ Cons
  • No delivery guarantee to individual consumers
  • Complex consumer offset management
  • Not for RPC/request-reply patterns
⚡ Use When
IoT telemetryLog streamingClickstreamAnalytics pipelines
🎯
Azure Event Grid
Event routing for Azure-native events

Event Grid routes events from Azure resources to handlers. When a blob is uploaded, a resource is created, or a custom event fires — Event Grid notifies subscribers. It's push-based (fires at subscribers) vs Event Hub (pull-based). Near real-time, serverless event routing.

🏠 Analogy
A notification system. When something happens (a package arrives = blob uploaded), it immediately texts everyone who subscribed to that alert. You don't check — it pushes to you.
✅ Pros
  • Deep Azure service integration
  • Near real-time delivery (< 1 sec)
  • Pay per event (very cheap)
  • Filter events by type/data
❌ Cons
  • No replay / no stream
  • Best for low-throughput events
  • Retry logic has limits
📋
Azure Queue Storage
Simple, cheap queuing

The simplest Azure queue. Store up to 500TB of messages. Apps poll the queue for new messages. No fancy features like Service Bus — just basic first-in-first-out queuing. When all you need is simple decoupling without enterprise features, this is the cheapest option.

✅ Pros
  • Extremely cheap
  • Simple REST API
  • Up to 500TB of messages
  • Good for simple decoupling
❌ Cons
  • No topics/subscriptions
  • No sessions / ordering guarantee
  • Max message size: 64KB
  • No DLQ (must implement yourself)

🚀 CI/CD & Infrastructure as Code

The beating heart of DevOps. CI/CD automates building, testing, and deploying your app. IaC means your infrastructure itself is code — versioned, repeatable, auditable.

🔥
This is the core DevOps skill. Manual deployments = errors, inconsistency, and fear. Automated pipelines = repeatable, fast, and confident releases. Teams that master CI/CD ship 200x more frequently with 24x faster recovery from failures (DORA metrics).

Azure DevOps Pipelines
Microsoft's enterprise CI/CD platform

Azure DevOps is a complete platform: Repos (Git hosting), Pipelines (CI/CD), Boards (Agile tracking), Test Plans, and Artifacts. Pipelines are defined in YAML and can build, test, and deploy anything across any cloud or on-premises environment. AZ-400 is almost entirely about Azure DevOps mastery.

🏠 Analogy
A factory assembly line defined as a recipe card. Every time new ingredients (code) arrive, the same recipe (pipeline) is followed automatically. Quality checks (tests) at each station. Bad batches (test failures) stop the line immediately.
# azure-pipelines.yml — Multi-stage pipeline example trigger: branches: include: [main, release/*] stages: - stage: Build jobs: - job: BuildAndTest pool: vmImage: 'ubuntu-latest' steps: - task: Docker@2 inputs: command: buildAndPush containerRegistry: 'myACRConnection' repository: 'myapp' tags: '$(Build.BuildId)' - stage: Deploy_Staging dependsOn: Build jobs: - deployment: DeployToAKS environment: 'staging' strategy: runOnce: deploy: steps: - task: KubernetesManifest@0 inputs: action: deploy manifests: '$(Pipeline.Workspace)/manifests/*.yaml' - stage: Deploy_Production dependsOn: Deploy_Staging condition: succeeded() jobs: - deployment: DeployToProd environment: 'production' # Requires approval gate
✅ Pros
  • YAML-as-code pipelines (version controlled)
  • Multi-stage with approval gates
  • 1,500+ marketplace extensions
  • Self-hosted agents (run on your VMs)
  • Deep Azure integration
  • Free for open source
❌ Cons
  • Complex YAML syntax to learn
  • Classic vs YAML pipelines confusion
  • Cost for private repos with many parallel jobs
  • UI can be overwhelming
🐙
GitHub Actions
GitHub-native CI/CD with Azure integration

GitHub Actions is GitHub's built-in CI/CD. Since Microsoft owns GitHub and Azure, the integration is seamless — OIDC authentication (no stored secrets!), Azure deployment actions, and tight GitHub ecosystem integration. Many teams prefer GitHub Actions for its simplicity and massive community of pre-built workflows.

🏠 Analogy
If Azure DevOps is a professional factory setup, GitHub Actions is a smart home system — set up automations that trigger when things happen. "When the front door opens (code pushed), turn on lights (run tests) and lock the back door (block merge if failed)."
✅ Pros
  • Free for public repos (unlimited)
  • OIDC auth = zero stored credentials
  • Massive marketplace (50,000+ actions)
  • Simpler YAML than Azure DevOps
❌ Cons
  • Less enterprise governance features
  • No built-in Boards / Artifacts
  • GitHub = required (not Azure DevOps repos)
📦
Azure Container Registry (ACR)
Private Docker image repository

When you build Docker container images, they need to be stored somewhere before deployment. ACR is your private, Azure-native Docker registry. Images are stored in Azure, geo-replicated, and pull authentication works natively with AKS and other Azure services via Managed Identity.

🏠 Analogy
Docker Hub is a public library. ACR is your company's private library — only your team can access it, it's hosted in your Azure region for speed, and it integrates automatically with your Azure workloads.
✅ Pros
  • Native AKS integration (no credentials)
  • Geo-replication for multi-region
  • Image scanning (Defender)
  • Tasks: build images in ACR itself
❌ Cons
  • Cost for storage and transfers
  • Premium tier needed for geo-replication
🏗️
Infrastructure as Code — Bicep vs Terraform
Your cloud infrastructure defined as code

Deployment Strategies
How you release new versions safely

Deploying new code to production is risky. Modern deployment strategies minimise risk by gradually rolling out changes and providing easy rollback paths.

🔵🟢 Blue/Green Deployment
Run two identical environments. Blue = current production. Green = new version. Test green thoroughly, then switch traffic instantly. One click rollback — switch back to blue. Zero downtime.
🐦 Canary Deployment
Release new version to 5% of users first. Monitor for errors. If stable, gradually increase to 25%, 50%, 100%. Limits blast radius of bad releases. Like coal miners using canary birds to detect gas.
🔄 Rolling Deployment
Update servers one by one (or in batches). Old and new versions run simultaneously during rollout. Slower than blue/green but requires less infrastructure.
🔑
Secrets in Pipelines
Never hardcode credentials. Never.

Pipelines need credentials (DB passwords, API keys). NEVER put these in YAML files. Use Azure Key Vault linked to pipeline variables, or use OIDC (Workload Identity Federation) so your pipeline authenticates with Azure using a temporary token — no stored secrets at all.

🏠 Analogy
Instead of giving every contractor a copy of your house key (stored secret), you install a smart lock that generates temporary access codes (OIDC tokens). The code expires after one use — no key to lose or steal.
✅ Best Practices
  • Use OIDC/Workload Identity Federation
  • Pull secrets from Key Vault at runtime
  • Rotate secrets on schedule
  • Never log secret values
❌ Anti-Patterns
  • Secrets in YAML files
  • Secrets in environment variables (visible in logs)
  • Long-lived Service Principal passwords

📊 Monitoring & Observability

You can't manage what you can't measure. Monitoring tells you when things break. Observability tells you why they broke. The difference between reactive firefighting and proactive engineering.

📊
Azure Monitor — The Observability Platform
Collects everything from everywhere

Azure Monitor is the umbrella service that collects metrics (numbers over time: CPU%, request rate), logs (text records of events), and traces (request journeys across services). All other monitoring services (Log Analytics, App Insights, Alerts) feed into or are powered by Azure Monitor.

🏠 Real-World Analogy
Think of Azure Monitor as a hospital's monitoring system. It connects to every machine (metrics), records every doctor's note (logs), and tracks each patient's journey through departments (traces). Nurses (alerts) get paged when anything looks wrong.
📈 Metrics
Numbers sampled at regular intervals. CPU%, memory usage, HTTP request rate, disk IOPS. Stored for 93 days. Used for autoscaling rules and dashboards.
📝 Logs
Structured or unstructured text records of events. "User logged in at 14:23", "Error: null reference at line 42". Stored in Log Analytics for querying with KQL.
🔍 Traces
End-to-end request tracking. User clicks button → API call → DB query → response. Application Insights shows the full chain with timing, enabling bottleneck identification.
🔍
Log Analytics Workspace
Query logs with KQL (Kusto Query Language)

Log Analytics is where all your logs end up. You search and analyse them using KQL — a SQL-like query language. "Show me all errors from the last 24 hours, grouped by error type, for the production API." Powerful for debugging, security investigations, and building dashboards.

// KQL: Find slow HTTP requests in last 1 hour AppRequests | where TimeGenerated > ago(1h) | where DurationMs > 2000 | summarize count() by ResultCode, Url | order by count_ desc // KQL: Alert query — Error rate > 5% AppExceptions | where TimeGenerated > ago(5m) | summarize ErrorCount = count() | where ErrorCount > 100
✅ Pros
  • Powerful KQL queries
  • Central log repository for all Azure services
  • Retention up to 2 years
  • Powers Sentinel (SIEM)
❌ Cons
  • Cost = per GB ingested (can get expensive)
  • KQL has learning curve
  • Queries can be slow on large datasets
🔬
Application Insights
APM: See inside your application

Application Insights is APM (Application Performance Monitoring). You add a small SDK to your app code, and instantly get: request/response times, failure rates, dependency tracking (how long DB calls take), user flow analysis, distributed tracing, and real-user monitoring. Essential for production apps.

🏠 Analogy
Attaching a tiny body camera and health monitor to your app. Every action it takes is recorded — which DB it queried, how long it waited, what errors occurred. You watch the footage later to find problems, or get alerted in real-time when something goes wrong.
✅ Pros
  • Zero-config for many Azure services
  • Live Metrics stream (real-time)
  • Distributed tracing (end-to-end)
  • Smart detection (anomaly alerts)
  • User/session analytics
❌ Cons
  • SDK overhead (slight CPU/memory)
  • Data ingestion costs
  • Sampling needed at high volume
🚨
Alerts & Action Groups
Get notified before users complain

Define alert rules on metrics or log queries. When a condition is met (CPU > 80% for 5 minutes, error rate > 1%), an Action Group fires — sending emails, SMS, calling a webhook (PagerDuty, Slack), or triggering an Azure Function for auto-remediation. Good alerts = peaceful nights on-call.

✅ Alert Best Practices
  • Alert on symptoms, not causes (high error rate, not high CPU)
  • Set appropriate thresholds (not too sensitive)
  • Use dynamic thresholds (ML-based)
  • Define runbooks for each alert
❌ Common Mistakes
  • Alert fatigue (too many alerts)
  • Alerting on low-value metrics
  • No runbook linked to alert
  • Not testing alert channels

🔐 Security & Identity

Security is not optional. In the cloud, a misconfigured permission or leaked secret can cost millions. Zero-trust means "never trust, always verify" — every access must be authenticated, authorised, and logged.

🔴
The #1 Cloud Security Risk: Misconfiguration. Accidentally making a storage account public, giving a service account Owner permissions, or storing a connection string in code. Security in Azure is a shared responsibility — Microsoft secures the platform, you secure what's on it.
👤
Microsoft Entra ID (formerly Azure AD)
The identity backbone of Azure

Entra ID is Azure's cloud identity service. Every Azure subscription has an Entra ID tenant. Users, groups, and apps authenticate through Entra ID. It handles Single Sign-On (SSO), Multi-Factor Authentication (MFA), Conditional Access, and application registration. Think of it as the company's HR system for digital identity — it decides who gets access to what.

🏠 Real-World Analogy
A corporate headquarters badge system. Your badge (identity) gets you through the front door. Different departments (resources) have different badge readers (permissions). The security desk (Entra ID) issues badges, revokes them, and tracks every door swipe (audit logs).
🔐 SSO
Sign in once, access everything (Azure, Office 365, Salesforce, Slack). No re-entering passwords. Federated with thousands of SaaS apps.
📱 MFA
Even if password is stolen, attacker can't login without the second factor (phone app, SMS code). Must-have for all admin accounts.
🚦 Conditional Access
Smart access policies: "Allow login only from managed devices, only from approved countries, require MFA when outside corporate network."
✅ Pros
  • Central identity for all Microsoft services
  • Conditional Access policies
  • Seamless SSO for 3000+ SaaS apps
  • Built-in audit logs for all sign-ins
  • B2B/B2C identity federation
❌ Cons
  • Complex role assignments
  • Premium P1/P2 needed for advanced features
  • Not a traditional on-prem AD (LDAP)
  • Can be confusing with multiple tenants
🏷️
RBAC (Role-Based Access Control)
Who can do what, where

RBAC defines permissions in Azure. Instead of individual permission lists, you assign roles. Built-in roles: Owner (full control), Contributor (create/manage, no permissions), Reader (view only). You assign a role to a security principal (user/group/service) at a scope (subscription/resource group/specific resource).

🏠 Analogy
Job roles in a company. A "Manager" can approve expenses up to $10,000. An "Employee" can only submit expenses. An "Auditor" can only read records. The job title (role) determines what you can do — not individual permission assignments.
Who (Principal)
User, Group, Service Principal, Managed Identity
What (Role)
Owner, Contributor, Reader, or custom roles
Where (Scope)
Management Group → Subscription → Resource Group → Resource
⚠️
Least Privilege Principle: Always grant the minimum permission needed. Give developers "Contributor" on dev resource groups, not "Owner" on the entire subscription.
🤖
Managed Identities
Apps authenticate to Azure without passwords

When your app (running on an AKS pod or App Service) needs to access Azure Key Vault, SQL Database, or Storage — instead of using a username/password, it uses a Managed Identity. Azure automatically manages the credentials — you never see them, never rotate them, and they can never be stolen.

🏠 Analogy
An employee's company-issued badge that automatically opens the doors they're authorised to enter. No one memorises a key code — the badge handles everything. If the employee leaves, you just deactivate the badge. No keys to change, no codes to share.
✅ Pros
  • Zero credential management
  • No secrets stored in code or config
  • Automatic rotation by Azure
  • Works with 95% of Azure services
  • System-assigned or User-assigned
❌ Cons
  • Only works within Azure
  • Some services don't support MI
  • Debugging auth failures can be tricky
🔑
Azure Key Vault
The safe for all your secrets, keys & certificates

Key Vault securely stores three types of sensitive items: Secrets (passwords, API keys, connection strings), Keys (cryptographic keys for encryption/decryption operations), and Certificates (SSL/TLS certificates with auto-renewal). Access is controlled via RBAC, every read/write is audited, and values are encrypted at rest with HSMs.

🏠 Analogy
A bank vault for your secrets. You don't carry your valuables (secrets) around. Authorised staff (Managed Identities) can visit the vault when needed. Every vault visit is logged with timestamp and identity. The vault manager (Key Vault) handles locks — you just store and retrieve.
✅ Pros
  • HSM-backed (tamper-resistant hardware)
  • Complete audit trail of all access
  • Auto-rotation for secrets and certificates
  • Soft-delete + purge protection
  • Integrates with all Azure services
❌ Cons
  • Throttle limits (can be hit at scale)
  • Adds latency if not cached
  • One Key Vault per region (performance)
📜
Azure Policy
Enforce standards across your Azure environment

Azure Policy lets you define rules that Azure enforces automatically. "All storage accounts must have HTTPS only." "All VMs must be tagged with a cost centre." "No public IP addresses in production." Policies can audit (report violations), deny (block non-compliant deployments), or auto-remediate (fix existing issues).

🏠 Analogy
Building code enforcement. A city has rules: buildings must have fire exits, minimum ceiling height, etc. Azure Policy is the building inspector who checks your cloud "buildings" and refuses to approve construction that violates codes.
✅ Pros
  • Prevent misconfiguration at deploy time
  • Compliance reporting built-in
  • Policy Initiatives = bundle many policies
  • Auto-remediation tasks
  • Inherits through Management Groups
❌ Cons
  • Can block legitimate deployments if too strict
  • Complex to write custom policies
  • Evaluation delay (up to 30 min)
🏰
Azure Bastion
Safe SSH/RDP without public IPs

To access a VM remotely (SSH for Linux, RDP for Windows), you traditionally open port 22/3389 to the internet — a massive security risk. Azure Bastion provides browser-based SSH/RDP through the Azure Portal, over HTTPS (port 443). Your VMs have NO public IP, no exposed ports. DevOps engineers access them securely through Bastion.

✅ Pros
  • No public IP on VMs needed
  • No VPN required for admin access
  • Browser-based — works anywhere
  • Integrated with Entra ID auth
❌ Cons
  • Adds ~$140/month cost per VNet
  • Single bastion per VNet
  • File transfers not supported (standard)

⚙️ Orchestration & Automation

Automate repetitive operational tasks so humans focus on higher-value work. From simple VM patching scripts to complex multi-step business workflows.

🔀
Azure Logic Apps
Visual workflow automation

Logic Apps automate workflows with a drag-and-drop designer. Connect 400+ connectors — when an email arrives → extract data → write to SQL → post to Slack. No code needed. Think of it as Zapier or Power Automate for Azure. Perfect for non-developer workflow automation.

✅ Pros
  • 400+ connectors (Salesforce, SAP, etc.)
  • No code required
  • Built-in retry and error handling
  • Serverless — pay per execution
❌ Cons
  • Complex logic = messy diagrams
  • Debugging can be challenging
  • Not for high-performance processing
⚡
Azure Automation + Runbooks
Automate operational tasks with scripts

Azure Automation runs PowerShell or Python scripts (Runbooks) on a schedule or triggered by events. Classic use cases: patch VMs every Sunday night, clean up unused resources, scale resources based on business hours. Runbooks run in Azure's infrastructure — no servers needed.

✅ Pros
  • Schedule or event-trigger scripts
  • Update Management (patch VMs)
  • Hybrid Worker (run on on-prem too)
  • Integrated with Azure Monitor alerts
❌ Cons
  • PowerShell/Python knowledge required
  • Cold start on sandbox runbooks
  • Being superseded by Azure Functions
🎯
Durable Functions
Stateful workflows as code

Regular Azure Functions are stateless (no memory between calls). Durable Functions add state, enabling long-running workflows. "Process 1000 orders in parallel, wait for all to complete, then send a summary email." All coordinated in Python/C# without managing queues or state storage yourself.

✅ Pros
  • Fan-out/fan-in patterns
  • Human approval workflows
  • Retry built-in
  • State persisted automatically
❌ Cons
  • Complex mental model
  • Local debugging difficult
  • Costs from Storage account usage

💰 FinOps & Cost Management

Cloud costs can spiral fast. A DevOps engineer who can optimise cloud spend is worth their weight in gold. FinOps = applying financial accountability to cloud spending.

💰
Azure Cost Management
Understand where every dollar goes

Azure Cost Management provides cost analysis dashboards, shows spending by service/resource group/tag, enables budget alerts, and forecasts future spend. You can break costs down by team (using tags), identify wasteful resources, and track trends over time. Free to use.

✅ Key Features
  • Cost breakdown by any dimension
  • Budget alerts (email when threshold hit)
  • Forecast next 30/60/90 days
  • Export to Storage for custom analysis
❌ Limitations
  • Data up to 8-24 hours delayed
  • Not real-time billing
  • Multi-cloud needs Cloudyn (deprecated)
🎯
Cost Optimisation Strategies
Save 40-72% on Azure spend

There are specific Azure features designed to dramatically cut costs for predictable workloads.

📌 Reserved Instances (RI)
Commit to 1 or 3 years upfront, get 40-72% discount vs pay-as-you-go. Best for VMs and databases that run 24/7. ROI in months for stable workloads.
💾 Savings Plans
Like RIs but flexible — commit to spend $X/hour on compute. Applies to Functions, AKS, App Service too. More flexible than RIs.
⚡ Spot VMs
Use Azure's unused capacity at up to 90% discount. But Azure can evict your VM with 30 seconds notice. Perfect for batch jobs, CI/CD agents, ML training.
🔵 Azure Advisor
Free AI-powered recommendations: "This VM has been at 3% CPU for 30 days — consider downsizing." Identifies idle resources, underused reserved instances, and security gaps.

🏗️ Architecture Patterns

PRO DevOps engineers don't just know services — they design complete architectures. Here are the patterns you must understand for both the exams and real work.

🌐
Zero-Trust Network Model Never trust any traffic by default — even inside your VNet. Use NSGs to restrict east-west traffic. Use Private Endpoints for PaaS. Require MFA for all access. Authenticate every service call with Managed Identity.
🏗️
Hub-and-Spoke Network Topology One central Hub VNet contains shared services (Firewall, Bastion, VPN Gateway). Multiple Spoke VNets (one per workload/team) peer to the Hub. Centralises security and reduces complexity. Standard enterprise pattern.
♻️
HA + Disaster Recovery HA = redundancy within a region (availability zones). DR = backup to a different region. RTO (Recovery Time Objective) = max downtime. RPO (Recovery Point Objective) = max data loss. Azure SQL geo-replication achieves RTO/RPO in seconds.
🔄
GitOps for Infrastructure All infrastructure changes go through Git PRs. Pipelines automatically apply Terraform/Bicep changes on merge. No manual portal changes. Drift detection compares actual state vs Git state. Full auditability.
📊
Observability-First Design Build monitoring in from day one — not as an afterthought. Define SLOs (99.9% uptime = max 8.7 hours downtime/year). Create dashboards per service. Alert on SLO burn rate, not individual metrics.
🔒
Secrets Rotation Strategy Use Key Vault with auto-rotation policies for certificates. Use Managed Identity where possible (no secrets). When secrets are needed, set 90-day rotation, alert on near-expiry. Store version history in Key Vault.

Core Azure management skills
Identity (20-25%)
Entra ID: users, groups, RBAC, Conditional Access, PIM. Know the difference between Authentication and Authorisation.

VNet, NSG rules, peering, Load Balancer vs App Gateway, DNS, VPN types (route-based vs policy-based).

Blob tiers, SAS tokens, storage replication types (LRS/ZRS/GRS/GZRS), Azure Files, lifecycle policies.
Compute (20-25%)

Monitor & Backup (10-15%)
Azure Monitor, Log Analytics KQL, Azure Backup vaults, Recovery Services vault.
